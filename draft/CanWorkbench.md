# CanWorkbench — bounded, approved task assistance

Employees need a private workspace for a named piece of AI-assisted work: prioritize selected tasks or prepare their follow-up. The model should use current authorized facts, suggest an exact change and explain it. It must not gain an employee's privileges, discover arbitrary tools or claim that a suggestion was executed.

A session selects one workplace, one purpose, a short goal and one to ten existing readable tasks. Every planning step rereads that selected scope through the canonical `workbench.context` read operation. There is no private directory, automatic full-team scan or external browsing in this initial workflow. The fact projection includes task identity/version, title, description, due date, priority and completion state; it excludes unrelated comments and personal HR data. The source-owned Input contract supplies the fixed planning instructions as a normalized default, frozen into each step. Retrieved facts and returned model text are data, never executable instructions.

Each session permits at most eight model requests, each with at most 32,768 input tokens and 2,000 output tokens, within one hour. Context projection bounds each title to 2,000 characters and description to 8,000; oversized source content or a tokenized request over the ceiling fails instead of being silently truncated. Failed, skipped and uncertain requests consume their step. A single unresolved proposal must be approved or rejected before another is requested. A failed/unknown delivery may be followed by an explicit new request with a fresh reservation, while its prior receipt remains distinct. These are bounded requests/tokens, not a monetary budget or a claim of actual usage. A stopped/expired session cannot dispatch or approve more work.

## Suggestions and approval

The model may return an answer or exactly one complete invocation of the existing `todo.Task.update` or `todo.complete`. The new shared `invocation(...)` type derives tool input schemas directly from those owner declarations. It carries all normalized arguments and frozen record versions. The adapter validates its result against the originating authorized request reference set, rejects other targets/records/users/files, and cannot upgrade versions or authorize execution. Here the only supplied user reference is the worker, and there are no file inputs: the model cannot invent another assignee or attachment. No JavaScript, SQL, shell command, copied mutation DTO or hand-maintained string dispatch switch is accepted.

A typed field preview displays the owning operation and complete effective arguments, including omitted versus null updates and expected versions. The initiating employee explicitly approves that immutable proposal through `workbench.approve`; browser and MCP use the same canonical operation. Approval checks the worker, current active employment/membership/workplace eligibility, session lifetime/current step, and a fresh viewer-authorized context read. Every selected task and workplace version must still match the frozen context. The current real caller then invokes the owner operation, which independently rechecks its own authority, expected versions, locks and invariants. An incomplete or currently undisclosable full preview cannot be approved through an alternate MCP path.

This named task workflow keeps every selected task at its original workplace. Even if generic Task.update permits changing location, such a proposed change rolls back here. Other permitted fields retain their owner's actual rules. Completion uses the real exported `todo.complete`, including its not-already-done condition and current worker attribution. Proposal admission never implies permission or successful completion.

The task effect and approval evidence commit in one owner transaction. If either fails, neither is recorded. A stale/failed approval retains its original arguments; rejection followed by a new planning step refreshes the context instead of silently rebasing. A second new approval of an applied step fails. Normal operation replay retains its canonical replay semantics. Stop preserves earlier committed task effects; it is not compensation.

## Persistence, access and recovery

Run identity, purpose, selected scope, owner and deadline are locked. Each step freezes its context/input, keeps its own typed delivery association and locks its proposal when received. Applied attribution and state are locked. Trusted model callbacks only store a current eligible proposal; they never call a task mutation or impersonate the worker. Late results after stop, replacement, expiry or work eligibility loss cannot create new actionable progress.

Status and approval attribution remain available to the owner, while full copied context/proposal reads require current workplace eligibility and every selected task still in that workplace and unarchived. This stricter workflow scope prevents a moved task from leaving old copied context readable here. Canonical source Task reads also govern refreshed context. Losing work access denies both new context reads and approval. An owner who remains a member can still stop their session without recovering data access.

The server-rendered `/workbench` page carries breadcrumbs and refreshes authorized state every two seconds and reconnects by reading persisted runs/steps. Session purposes and step states render as badges and delivery as status; every collection has an explicit empty state and pagination, and the start form places typed radio/textarea/select controls. Refresh never repeats a planning request or approval. Safe status and stop controls remain renderable after scope loss; private context/proposal columns use their current field grants, without a presentation guard that must first read withheld scope fields. Receipts expose unresolved/error state without a second transport-status model. Stop blocks future application and delayed dispatch; it does not promise provider cancellation or a refund for already dispatched work. A user can reject an obsolete suggestion, reopen the ordinary task UI, or start a separate bounded session after reviewing prior outcomes. There is no automatic background actor delegation.

## Composition and draft limits

Workbench depends on Task's canonical exported type/CRUD and `complete`, the employee access helpers and workplace type. The coordinator adds only the export modifier to `todo.complete`, preserving its body and guards. The declared app-owned planner capability provides a typed final proposal; the deployment binding pins its model adapter. It is not an implemented provider. The full invocation type and its exact provenance/display/call contract are recorded in [the design note](../design/complex-apps/workbench.md#full-invocation-contract) and adopted into the shared draft separately.

Inline tables and connected sequences specify opening limits, callback-only proposal creation, actual approved update/completion, duplicate approval denial, an intervening real task edit, actual Employee deactivation, stop-before-approval, and stopping after an actual task move has denied context/continuation/approval. Seeded proposals are snapshots, not evidence that a model ran or a person approved. Malformed invocation/receipt setup must fail setup rather than satisfy an expected business error. Source and desired JavaScript remain unimplemented language/runtime artifacts; syntax and structural correspondence checks are not proof of provider, UI, MCP, authorization-fence or BDD execution.
