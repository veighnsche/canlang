# CanInbox — departmental email with reviewed authority

This is a complete application design draft, with its actual [Can source](CanInbox.can) and corresponding [desired JavaScript](CanInbox.mjs). It is not a deployed email client or implemented classifier. The accepted draft language/provider contracts and research are in [the Inbox design](../design/complex-apps/inbox.md); shared semantics remain owned by DESIGN/GRAMMAR.

## Purpose and scope

A company receives email in connected departmental mailboxes, evaluates whether a reply/action is requested, predicts the responsible department and scores urgency against ordered criteria. Staff read the full retained evidence, correct the judgment, authorize any transfer to another private queue, and approve an exact reply. Model confidence alone never grants another department access or sends mail.

The app owns mailbox configuration, queues/grants, immutable normalized incoming messages, assessment history, reviewed routing decisions, reply drafts, approval attempts and resolution history. Shared adapters own MIME parsing, provider authentication, finalized attachment handling, decision-model normalization, durable transport and authoritative provider reconciliation. It does not duplicate chunks, provider retry workers or vendor SDKs in application code. It does not implement a help-desk ticket, customer identity verification, attachment OCR, AI-written replies, forwarding, CC/BCC or automatic cross-app disclosure. A future CanDesk handoff requires an explicit source operation and current destination authorization.

## Identity, grants and configuration

Use shared team authentication and owner-managed package roles. `inbox_admin` configures queues/mailboxes and can handle every queue; `mail_staff` alone grants no message access. A current active per-queue `Grant` supplies read access and separate transfer/reply permissions. Granting those permissions requires an active eligible account. Revoking a grant or role changes subsequent access without rewriting historic authorship.

Queue names and fixed department kinds are visible to inbox staff; private messages and all descendants require access to their current queue. Staff receive only mailbox name, enabled/classification switches and permitted destinations when they participate in its intake or a permitted queue, or can still read one of its retained messages. Removing a destination from future configuration therefore does not hide the limited mailbox context of already-held work. Exact provider mailbox keys and daily usage remain administrative. Model summaries, attachment downloads, histories, polling, UI pickers and MCP results obey those same current grants. Knowing an opaque message identity does not bypass a mutation guard.

Each exact deployment mailbox key maps to one configured `Mailbox`, its private intake and 1–20 explicitly permitted destination queues including intake. The normalized incoming event must match that key and authenticated deployment/team. Thread identifiers are advisory, and sender/reply-to values are unverified message evidence rather than company-account identities. Mailbox keys, original message source/envelope and queue department identities are immutable. Disabling a mailbox or queue preserves existing readable work; it prevents new evaluations/sends under the authored guards. Staff can review, correct, resolve and reconcile existing work while a provider is unavailable. No nullable-provider syntax or accidental business package inclusion is required.

## Intake and bounded files

Receive once per `(mailbox,source)`. An exact duplicate is a no-op and consumes no classification budget. Changed content with the same source is rejected; the adapter must preserve stable normalized evidence and finalization identity across redelivery. Unknown/unconfigured mailboxes are visible ingress failures, not silently assigned to a convenient queue.

Retain subject, normalized sender/reply target, plain-text body, received time, optional thread, original attachment count and explicit body/attachment completeness. Shared MIME parsing must not execute HTML, follow remote resource URLs or treat embedded model instructions as commands. The body is at most 30,000 Unicode scalars, subject at most 300. Truncated/withheld content is visibly incomplete. Inbound attachments are finalized immutable files: at most eight, each at most 5 MiB, PDF/PNG/JPEG/plain text only; total retained attachment payload is therefore at most 40 MiB per message. Unsupported, excess or unavailable attachments are withheld with truthful counts/completeness. Provider URLs are never files. Staff can inspect retained files through authorized standard downloads; classifier input explicitly excludes their content.

Reply attachments obey the same eight-file/type/size boundary; review evidence is limited to four. Ownership or a currently readable attachment relationship is checked for every file at actual mutation admission. Invalid/foreign/unfinished files cannot be made acceptable by a label, fixture, model output or copied URL. A provider's smaller aggregate transport cap fails visibly, never drops selected attachments.

## One typed judgment, retained uncertainty

`Triage` authors exactly three questions once: `reply` is NOUL, `route` has purchasing/support/sales/general choices, and `urgency` has ordered routine/today/immediate criteria. The residual `general` case covers ambiguity, unrelated content and multiple departments. The declaration generates its evaluation interface, literal choice/level types, complete result schema and immutable `JudgmentSpec`. Queue kinds and staff-reviewed urgency reuse those generated types. There is no separately authored result schema or lookup/conversion from arbitrary model text.

Each evaluation freezes a minimized state containing subject, body, body completeness and original attachment count, plus the complete source-language specification. It excludes addresses and attachment text. Model inputs are untrusted evidence; they cannot change question IDs, criteria, authorization, outbound recipient or operations. The result retains actual model identity, specification revision, input/output usage, NOUL probability, every choice probability and provider confidence, and every ordered score level/probability with the fractional expected score. A score of 1 can represent a 50/0/50 distribution across levels 0/1/2; it is not evidence that level 1 was selected.

Can's pinned adapter profile validates complete question/option/level sets, bounds, exact source legends, finite exact decimals, distribution sums/score expectations within 0.000001, and a valid maximal choice including ties. Invalid/partial results are failed deliveries with safe diagnostics, not empty successful assessments. Provider confidence is retained rather than portrayed as calibrated certainty. Model selection belongs to the deployment; wording edits preserve old frozen specifications and results. Choice/schema/order changes require ordinary migration/outstanding-work review.

Automatic classification is off by default. Enabling it applies a mailbox UTC-day request budget (default 100, configurable 1–1,000) and at most three evaluations per message. A committed intent consumes a slot even if skipped, failed or uncertain; it is not silently refunded. Intake persists when disabled or exhausted. Explicit reevaluation requires current queue access, enabled classification, an open message, an active queue, budget, no current pending assessment, and affirmative authorization of an additional potentially billable evaluation. An unknown prior result is not presented as a free same-intent retry. Shared storage serialization/commit fencing prevents concurrent callers exceeding the declared counters.

Completion matches the associated delivery and causal specification, updates only that assessment, and never changes the current queue, staff review or current assessment pointer. Earlier results remain reviewable even if staff already transferred the message or requested another assessment. A successful assessment cannot subsequently be rewritten by late failure. Classification failure/unavailability does not prevent manual review or human reply preparation.

## Reviewed assignment and correction

Only the current source queue's transfer authority can assign an open message to an active destination permitted by its mailbox. Staff explicitly choose destination, whether action/reply is needed and an ordered urgency level, and give a nonblank reason with optional bounded evidence. Store an immutable `Review` with reviewer/time and the assessment available at review. Setting the current queue and review is atomic. No predicted department, probability or global threshold substitutes for this decision.

The destination's existing grant holders gain access to the message and its retained history; previous queue holders lose access unless independently authorized. A correction is another attributable review under the now-current queue's permissions. Earlier reviews/model evidence remain intact. Queue transfer may change the visibility of existing drafts/attempts too; the transfer is the explicit disclosure authorization. The original approver is rechecked at dispatch, so queued mail can be skipped after authority loss. Already dispatched work can finish and retain its true result.

## Replies and recovery

An authorized current queue member drafts a nonblank reply to the single retained normalized reply target. A missing reply target blocks drafting rather than guessing an address. Drafting and editing do not send. The screen shows exact recipient, subject, body and attachments; submission records the approving person/time and freezes the full `MailReply` with one stable logical source. Drafts may be discarded. Submitted content cannot be edited or silently replaced.

Each authorized send is an `Attempt`, with its delivery, reconciliation receipt, outcome and safe evidence. Recheck current message/queue/mailbox/approver at dispatch. Atomic outbox intent and operation replay follow shared runtime rules. A per-reply maximum of three attempts and three reconciliation requests per attempt bounds user-triggered recovery; there is no hidden app retry loop. The same frozen source/payload is used on a proven unsent resubmission.

| Observed fact | App state and permitted action |
| --- | --- |
| Queued intent | Queued; await the current receipt. |
| Provider accepts exact request with stable reference | Accepted; show evidence, without claiming recipient delivery/read. |
| Authoritative proof of no send and no later send from the original request | Confirmed not sent; current authorized staff may explicitly resubmit frozen content within the bound. |
| Failed transport, invalid returned schema, timeout, missing evidence or provider uncertainty | Unknown; reconcile the original source, never infer non-send. |
| Dispatch guard skips an undispatched request | Confirmed not sent for that attempt; permission must pass again before resubmission. |
| Failed/unknown/skipped reconciliation | Remain unknown; reconciliation never sends mail. |
| Old callback after accepted/proven not sent, or unrelated receipt | Preserve the established attempt fact; do not replace current work. |

Reconciliation remains available while mailbox sending is disabled. It needs current reply permission, current unknown attempt, no pending check and remaining check budget. An unavailable provider or exhausted reconciliation budget leaves visible unresolved work for an administrator/operator; the app has no button that invents delivery proof. A provider that cannot establish authoritative non-send must continue to report unknown. New separately reviewed replies are new business intents, not a repair that changes the meaning of an uncertain earlier reply.

Close/reopen is explicit and reasoned, recorded as an immutable `Disposition` by someone with current transfer or reply authority. Closing rejects editable drafts and any current queued/unknown attempt. Staff can close a reviewed message needing no reply, or a proven unsent case they decide not to send, with their explanation. Reopening preserves the full history. Domain records have no user delete path or automatic retention expiry in this draft; an organization-specific disposal policy would need a declared lifecycle change and unresolved-work/reference handling, rather than accidental deletion of evidence.

## UI and bilingual authoring

The standard `/inbox` shared shell provides authorized queue/state filters and preferences, subject search and a split message view. It shows incoming text/files and incomplete-content flags, retained question specifications, complete probability tables and fractional score, staff review history, allowed transfer destinations, exact editable/frozen replies, approval/reconciliation evidence and resolutions. Every page carries breadcrumbs and every collection an explicit empty state and pagination; workflow states render as badges, classification delivery as status, and disclosure sections use collapses with a classification notice. Bare typed forms keep their generated remainder with placed checkbox/textarea/select/radio controls while array and user inputs stay generated. Mutation controls retain current permission checks; every operation rechecks on invocation. Five-second polling reads projections only and never re-evaluates or sends. The administrative page configures queues, active grants, mailboxes and budgets. Labels, descriptions, state names and explanatory UI text have inline English/Dutch variants; model instructions stay pinned to the source language independently of display locale.

## Inline behavior witnesses and verification limits

Source/desired-JS examples cover exact duplicate intake without repeated spend; changed evidence rejection; exhausted/disabled intake; authorized classification; manual transfer and correction; missing reply target; file attachment authority; explicit approval; late classification preserving current staff assignment; unknown/failed/accepted/proven-unsent/skipped sends; terminal fact preservation; correlated reconciliation without another send; bounded resubmission; and rejection of closing unresolved work. The transfer sequence uses one shared isolated state and real per-call actors, proving the intended prior-queue rejection after transfer rather than merely describing two unrelated snapshots.

Fixtures are isolated typed snapshots, including protected provider receipts; they are not evidence a live model/provider was called. The late-result and recovery tables do not simulate distributed concurrency, fabricated provider certainty or wire-schema rejection. Canonical adapter/transport tests must cover result validation, file finalization, provider idempotency, concurrency fences and crash recovery. No permanent mock provider or app-local test runtime is introduced.

The desired JavaScript is syntax-checked. The current parser cannot parse the accepted new `judgment` declaration, typed delivery associations, page polling or shared-state sequence form; an explicitly limited ordinary-syntax projection is checked separately. No semantic checker, BDD runner, UI renderer, stdlib adapter or deployed email flow was executed. Exact check commands, projection exclusions and source/target evidence are retained in [verification](../design/jev/complex-inbox-20261004/verification.md).
