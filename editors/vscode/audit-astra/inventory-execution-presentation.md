# Independent execution, presentation and maintenance inventory

This report audits the frozen snapshot at `editors/vscode/audit-astra/snapshot`, not the unrelated `/can-lang` repository. Evidence locations below are relative to that snapshot unless explicitly labeled audit output. I read its AGENTS.md, normative GRAMMAR.md, the relevant DESIGN sections and current-status/refinement sections of DECISIONS.md. I inventoried all 44 `.can` sources (7,489 physical source lines) by their execution, example and presentation constructs, then inspected the actual TextMate patterns. I did not read the implementer's GRAMMAR-AUDIT.md or check-highlighting.cjs conclusions, change implementation files, install/reload an extension or operate IDE UI.

The corrected user requirement is **one shared standout color for Given, When and Then**. Separate lexical scopes are compatible with that requirement when the theme maps all three to the same color. Authored identifiers spelled Given/When/Then must retain their identifier roles. The frozen grammar provides distinct section scopes at `editors/vscode/syntaxes/can.tmLanguage.json:56`, `:60`, `:64`; root's `sections-and-identifiers` tokenizer probe confirms section markers and same-spelled field/parameter/scenario names have distinct roles. Color resolution belongs to root's separate inspection.

I also ran ten fresh narrow TextMate probes against both the frozen grammar and root's captured `latest-extension` grammar. Requests and exact token scopes are saved in `execution-presentation-probes.json`, `execution-presentation-probe-results.json` and `execution-presentation-latest-results.json` under the audit directory. These are syntax-role excerpts, not assertions that their undeclared surrounding names or runtime contracts have been semantically validated. `execution-presentation-tokenize.cjs` uses the installed Cursor TextMate/Oniguruma libraries without extension activation. Latest findings are labeled below; they do not replace frozen file:line evidence. Root's `changed-during-audit.json` records that DESIGN, DECISIONS, CanRent, shared Locations and extension files changed while this audit was running.

## Concrete findings

All priorities are highlighting priorities, not production business-security assessments. E1–E7 reproduce in both the frozen grammar and the captured latest grammar; latest improves other reference/parameter scopes but leaves these cases.

**E1 — P2: a block structural-value return is colored as a stored model declaration.** `return {value=1}` produces `return <entity.name.type.can>` in fresh `block-struct-return`, line 3. GRAMMAR:329 allows any expression, and :203–208 allow structural values. The earlier stored-model regex at `can.tmLanguage.json:328` fires from a name followed by `{` before the effect regex at :430. This is a production-shape mistake: a known execution statement is not a model even though both involve braces. Current corpus uses named typed returns instead (CanStats:58–64), so its source alone misses the case.

**E2 — P2: loop bindings named contextual words break classification, including a false model/ownership declaration.** Fresh `loop-contextual-binding`, line 3 is `for in in values limit=1`. The actual roles are `for` loop introducer, first `in` authored binding, second `in` loop syntax. Frozen and latest return `for <entity.name.type.can>`, first `in <keyword.control.ownership.can>`, second `in <entity.name.type.can>`. The model regex :328 is ahead of loop :393 and accepts a prefix without requiring the model's schema. GRAMMAR:70 requires full production shape, :72 permits contextual authored names, and :331 specifies the fixed loop `in`. Also fresh `contextual-domain-header`, line 4, `for return in values limit=1` leaves the genuine second `in` as a variable because of the spelling blacklist at :606/:838.

**E3 — P2: a contextual member or query alias suppresses a genuine operator/clause that follows it.** Fresh `member-before-operators` gives `value.return and true`: `return` correctly remains a member but `and` incorrectly becomes `variable.other.readwrite.can`; `value.where or false` similarly loses `or`. `value.select as item select item` loses query `as` and binding `item`. Fresh `query-contextual-alias` has `values as where where where.active`; the alias name is correctly a binding, but the next actual `where` clause is plain variable. Fresh `contextual-domain-header` gives `list list as item columns=name`, and loses `as`/binding. The hardcoded predecessor-word blacklists at :581/:606/:610/:621 and :813/:838/:842/:853 do not track whether those spellings were members, primaries or aliases. GRAMMAR:72 and :238–244 explicitly permit these contextual names and distinguish complete left operands from syntax.

**E4 — P2: delimiter-joined physical lines lose query clause roles.** Fresh `multiline-clause-after-domain`, lines 2–5, with `(Item` on the prior line, leaves `as`, its alias, `where` and `select` as general variables; `order` is only a property key. Root's independent `query-newlines` confirms this. GRAMMAR:35 joins balanced delimiters and :229–240 permits the same query production; each clause should keep its role across physical lines. The existing query patterns require a completed expression's final character on the same line and retain no query state.

**E5 — P2: examples do not establish an expression/table context; fixed CRUD action words become variables, and input identifiers become UI keywords.** `examples create/update/delete` in fresh `examples-crud-actions` gives each fixed action `variable.other.readwrite.can`. The valid header `title -> result.title` gives its input selector `keyword.control.can`, wrongly applying the UI `title` matcher. GRAMMAR:348 names the three actions; :350–358 requires header/rows to be expression lists, not UI/effect statements. Current corpus includes real fixed `create` (CanInvoice:139) and `update` (TeamTasks:14, CanCRM:43, CanApprove:31), so this action-role gap is already observable. A future scenario input named `delete`, `action`, `history`, etc. has the same header problem. The generic statement matcher :415 remains active in examples; there is no example-table region to constrain it. Root's tokens confirm existing observation-side queries should remain queries, while selector primaries such as `as` retain test-only identifier meaning.

**E6 — P2: known UI selector slots misclassify contextual field names as literals/operators.** Root's independent `identifier-after-keyword`, line 6, `table Thing columns=not,true,false,null`, yields `not <keyword.operator.word.can>` and the other three `<constant.language.literal.can>`. These are selector paths under GRAMMAR:381–383 and must identify fields (authored field names accept contextual words under :72). The corresponding `row.not,row.true,row.false,row.null` line is correctly member-scoped, proving the issue is missing selector context, not a need to reserve those names. Blanket `not` and literal patterns are at :625–630/:857–862. The same concern applies to selector lists inside preference ordering; they are explicitly symbolic schema selectors (DESIGN:621), not expression arrays. Adding a global keyword rule for `columns/order/default/cases` would not solve it.

**E7 — P3: maintenance target roles are incomplete or flattened.** Fresh `maintenance-targets` and root's independent `maintenance` show `rename before.Task.title to Task.name` coloring all of `Task.name` as `entity.name.type.can`; `name` is a field target, not part of a type identity. `backfill Task` colors Task as generic variable despite its syntactic model-target slot. `drop before.Task.legacy` and `invalidate before.tick` reuse ordinary field access and do not reflect the predecessor model/field/handler target categories. Evidence: :120–134 special rename capture; generic :415 backfill/drop/invalidate; GRAMMAR:409–413,423. This family needs absent-source probes, not invented installed snapshots or real migrations.

**E8 — P3: query ordering has no query-specific lexical role; effect binding `as` is given a query-specific scope.** Frozen `can.tmLanguage.json:595`/`:827` colors every `NAME=` property key, so real query `order=...` is not distinguishable from UI `order=` or an object key. Real effect `create/call/send … as NAME` uses :610/:842 and receives `keyword.control.query.can`. Current examples include query order CanAffiliate:71, UI order CanTable:68, effect binding CanAffiliate:60–61 and CanApprove:45. GRAMMAR:242 explicitly makes query and UI ordering different syntactic slots, while :321/:324/:326 make effect binding different from :232 query alias. These remain recognizable as generic keys/control, so this is a scope-precision gap rather than total loss of highlighting. Reusing a general `as` control scope can be reasonable; calling every occurrence a query is inaccurate.

## Probe validity and absent-family recommendations

The saved fresh probes intentionally omit unrelated declarations so each role defect stays small. Their source spellings are permitted by the relevant grammar productions; missing named types, actual read grants, authority, installed predecessor IDs and return shape compatibility require surrounding declarations and semantic checking. In particular, the `all()/any()` probe is a syntactic control used to show that a closing call delimiter restores operator matching; those empty calls are not claimed to satisfy builtin signatures. The contextual-domain-header excerpt has free-standing UI/loop lines for token isolation and must be placed in their proper enclosing suites for a parse check.

Prioritize standalone grammar-valid sources covering: a contract-valued block `return {value=1}`; models/parameters/fields named `in`, `where`, `return`, `not`, `true`, `false`, `null`; a loop binding named `in`; query aliases named `where`; contextual field selectors; a parenthesized query split across physical lines; CRUD `examples delete`; example input headers named UI words; leading/body guard `message=`; scalar routes; page `data/group/nav`; each legal semicolon leaf family; and every migration directive plus both inline and block backfill forms. Include positive control cases where member names stay members and primary names stay references. Use finite syntax probes, not copied business fixtures or a new verification framework.

For scalar routes, root's `routes-all-type-shapes` exercises enum/action/union/array/nullable type *syntax*, not proof those representations are supported scalar-route types. For maintenance, use a clearly illustrative predecessor string only in syntax tests; DESIGN:786 requires real compiler-issued evidence for actual deployment. No authored migrations should be fabricated for the 44 apps: DECISIONS:42 says they have no installed history.

## Specification/source and semantic boundaries

- The current frozen corpus contains newer extensions: CanDo:123 preference ordering, CanDo:134 refresh/poll and CanCRM:144–148 / CanCustomer:206,213 CSV import/review. GRAMMAR:400,447,449 explicitly records that the syntax prototype has not implemented these extensions. This is a known source-versus-prototype gap, not an alternate spelling or a TextMate grammar rejection. Any older “all 44 parse” claim predating these source edits cannot establish current parser compatibility.
- DESIGN:611 has a Markdown paragraph beginning `#A page`; it describes page polling, not a `.can` declaration. GRAMMAR:400 still mentions “link labels” despite Then accepting only pages and authored nav/link trees being removed (:435; DESIGN:579). That phrase is stale editorial wording; there is no normative `link` production to add to the highlighter.
- I found no demonstrated new `.can` grammar violation in the execution/presentation inventory itself. This is not a complete parse/type/business proof: no parser, BDD runner, compiler or runtime was run here. Explicit documented unsupported syntax-prototype extensions remain as above.
- Contextual call spellings and operation-looking identifiers require real resolution. Syntax alone cannot prove a bare primary names a model, enum case, role, callable action, imported operation or builtin. Likewise poll/refresh authorization, route uniqueness, form auto-binding, row/parent scope, preference restrictions, typed filters, hidden-field safety, default-timezone behavior and label fallback are checker/runtime contracts. Highlighting should reflect fixed source slots without claiming those checks occurred.
- Snapshot migrations, exact predecessor identity, mapper purity/initialization, old locks, historical references, staged activation, queued work disposition and multi-owner installation remain unimplemented. Their absence from live `.can` corpus is expected and must not be conflated with lexical support.
