## Presentation components versus language syntax

**F10 is a semantic highlighting-category distinction, not a proposed language redesign.** The grammar uses contextual introducers for both language structure and UI composition. The user explicitly wants the UI composition roles to look like components/tags, independently of declaration/control keywords. The existing full-file token evidence already proves the shared `keyword.control.can` classification, so no new UI inspection or broad test run was necessary.

The component family inside valid Then/page bodies includes grouping (`card`, `details`, `tabs`, `tab`), collections (`list`, `table`, `board`, `calendar`), forms (`form`), content (`title`, `text`, `content`, `metrics`, `copy`), and operation/history controls (`edit`, `delete`, `action`, `actions`, `history`). A dedicated component scope such as `entity.name.tag.component.can` is a **suggested unimplemented scope contract in this audit**, not an existing API. Page declarations should keep an explicit page/declaration role; section markers retain their separate white/bold scope.

The correction must preserve these distinctions:

| Source context | Required role |
| --- | --- |
| `text row.title` in a presentation body | Content component |
| `caption:text` | Primitive type, with `caption` a field |
| `delete` in presentation | UI operation control |
| `delete record` inside an execution body | Mutation effect |
| `action approve` / `actions approve,reopen` in presentation | Operation component/control; operands retain operation-reference roles |
| `target:action(approve)` | Action type constructor and allowed operation reference |
| Resolved `action(...)` expression call | Builtin/call role, not a UI component |
| `row.text`, `record.delete`, `form:text`, selector `columns=text` | Member/field/selector roles, not component keywords |
| `require members` inside a page or execution body | Actual guard/control keyword, never a component |
| `Given`, `When`, `Then` at valid section boundaries | Section markers, not components |

The implementation should use the enclosing syntax region, not a global word-list recolor. In particular, `#statements` currently lacks enough context to distinguish the legitimate UI `delete` from an execution effect or an example-table identifier. Merely renaming the shared keyword scope would move those existing mistakes into the component category. The user has not specified a new component color in this clarification; this audit does not choose or claim one.

## What 0.1.2 has already corrected

Do not re-report the following frozen 0.1.1 failures as current:

- Derived fields such as `Day.year` are now properties; pure functions remain function declarations.
- Signature parameters now have parameter/variable scopes instead of field-property scopes.
- Typed structural constructors such as `WorkView {…}` now get type scopes.
- Plain `call/send` targets and singular `form/action` references now get function scopes.
- App/package/migration identities no longer all get type scopes; role declarations use predicate scopes.

The new behavior was independently observed with identical probes and actual full-file state. Some remaining inconsistencies are expected syntax-only limits: a model used as a query domain, an imported alias, a bare role predicate, or `Task.` in an operation path cannot universally be assigned a resolved symbol kind without a symbol table. Known syntactic slots should be consistent; ambiguous names should use a documented conservative fallback. An editor-only highlighter should not pretend it has checked grants, bindings, type identity or callable authority.

## Focused description/string follow-up

The late description-color report was initially incomplete. The user subsequently confirmed the exact screenshot symptom: `@{` is string-colored inside `#` prose but white after a source string. This matches the independently reproduced F9 boundary observation below. Three additional focused cases used the captured 0.1.2 grammar and final muted-gray settings with each editor's own TextMate engine. See `description-probe.cjs`, `description-results.json` and the readable `description-results.txt`.

**F9 — P3, resolved by 0.1.3: identical localization punctuation inherited different colors from its containing construct in 0.1.2.** In `# A title. @{nl="Een titel."}`, the `@{` marker and final `}` inherit `string.unquoted.description.can`; they are purple **#E394DC** in configured Cursor, orange **#CE9178** in Antigravity. After a source string such as `label="A title"@{nl="Een titel"}`, those same marker/closer roles fall back to normal foreground (**#F0F0F0** / **#CCCCCC**). The locale key and translation string colors themselves stay consistent. This explains a concrete start-in-description versus after-string color difference without requiring a string scanner leak.

The tested quoted strings, JSON escapes, raw quoted prose, escaped raw `\@{`, quoted language keys, explicit null variants, and multiline descriptions all return to the expected declaration/attribute/field scopes afterward. `order=1`, a following schema field, the next declaration and section marker do not remain string-colored in these probes. No general string-termination failure was reproduced. `#= captions.title` also uses default foreground for its static message-reference scope, unlike inline prose; it is a different grammar role, though its intended palette may deserve an explicit decision.

The original correction advice was to use a context-independent marker/closer scope and explicit targeted palette mapping, or bound the raw-prose string scope before its descriptor suffix. The verified 0.1.3 update follows the explicit-scope/mapping approach. Preserve translation strings and locale keys as their respective roles. Do not recolor whole lines or alter description attachment/JSON/ICU semantics. The user-confirmed marker symptom is accounted for by this observation; no broader string-termination problem is established.

## Language/source consistency and current boundaries

The baseline had seven two-argument `dates(...)` calls inconsistent with DESIGN's mandatory `limit:int`. The live recheck found all seven corrected; this was a semantic source issue, not an unrecognized grammar token. Live DESIGN subsequently adds `flatten` using ordinary call syntax. Further business-source changes during the audit are preserved by the final drift manifest, not claimed to be behavior-verified here.

One narrower specification ambiguity remains in the baseline and inspected live wording: DESIGN says contract fields follow model field rules and that secret fields require server initialization, while `Heartbeat.token:secret` is an input contract field without `server=`. This may be an intended stored-field-only restriction. The report records the ambiguity for specification clarification; it does not recommend changing the app, rejecting the token, or inventing a rule.

Newer documented preference ordering maps, page polling/refresh, CSV form import/review, declared-role subject calls, inline localization and label objects were included even where the syntax-parser prototype is documented as incomplete. Header/object token coloring is not evidence that those closed shapes, required attributes or permission contracts have been validated. Layout validity, duplicate fields/attributes, name resolution, builtin signatures, ICU validation, grants, operation examples and migration execution remain outside this syntax-only audit.
