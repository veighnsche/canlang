# Values, Interfaces and Contracts: additional Rust benefit audit

Planning-only source review at `08dc8c3928f53c7a06984136ac52ff944360075c` (18 October 2026). No product edits, build, test, Git mutation, benchmark, JEV call, activation or implementation release. Native preparation remains held. Optional ideas below add no active task IDs and change no original acceptance or queue.

The assigned inventory is complete: **291 tracked paths**: Values 142, Interfaces 121, Contracts 28. Coverage gives a responsibility and explicit inspection depth for every path: 128 production/source entries, 137 test/fixture entries, 26 generated/config entries. This is a package responsibility audit, not a claim that every statement in all tests/generated corpora received an exhaustive correctness review. Large and mixed production files received focused body/control-flow inspection alongside declaration/import/caller review; test declarations and fixture sections were inventoried, with behavior bodies inspected where needed. Multi-megabyte generated corpora and Wasm internals were inventoried rather than reread as handwritten algorithms.

## Main result

No additional whole-package port is justified here. The strongest actual Rust-shaped workloads in these packages—exact numbers/UTC temporal operations and whole owned-input validation—already belong to A and V. Finishing their existing consumer/asset/profile outcomes is more defensible than opening a second arithmetic, codec, parser-provenance or validator programme. Remaining interesting new ideas are conditional consolidation/portability investigations, not proven speedups.

### Contracts disposition

**Retain the entire package as the shared declaration/constant owner.** It contains compiler artifact and diagnostic vocabulary; deployment/assets/upgrade contracts; Identity, Files, State storage/receipts/opaque File/migration metadata; Work/fanout/receipt diagnostics; provider/Judgment/media declarations; Values/Wire; reference and UI/presentation contracts; optional Node Chromium ports. TypeScript erases most content. Translating declarations to Rust alone removes no runtime work and would add an ABI/code-generation authority problem.

The README's “type-only/no runtime behavior” shorthand is not literally exhaustive. Actual runtime pieces include `presentation.ts:collectionFilterName/collectionCursorName/styleUseAttributes/styleHostAttributes/assertGeneratedViewInstanceProps/assertGeneratedViewRender`, `wire.ts:DELIVERY_RESULT_LEAVES/deliveryResultLeaves`, `deployment-assets.ts:installedModuleTypeFor/assetByteLength/isTextOnlyInventory`, shared provider descriptors and Work observable tables. They are small data/accessor/assertion helpers attached to their defining contracts, and several use JS function checks, encodeURIComponent, TextEncoder or string/HTML assembly. They do not justify a Rust runtime dependency. Existing A/V/W/P/C04 must derive compatible Rust facts from these owners rather than move application identity/composition into independent Rust tables.

## Ranked genuinely new possibilities (optional, no dispatch)

**1. Bounded ICU syntax/usage consolidation: strongest maintainability hypothesis inside the assigned scope, presently decision work only.**

Exact next decision: **should compiler validation and public runtime pattern parsing share a common syntax core while preserving separately declared profiles, or should their divergent profiles remain intentionally separate?** Do not begin by picking a Rust library or promising full ICU parity.

Evidence: Values `icu.ts:IcuParser`, `parseMessageFormat`, `validateMessagePattern`, `collectUsages/checkUsageCompatible` versus existing Rust compiler `analysis/examples.rs:icu_error` and `analysis/types.rs` placeholder scanners. This is a real duplicated grammar responsibility; the exact-values plan explicitly excludes ICU so it is not an unimplemented A checkbox. However, Values accepts literal `#` outside plural ( explicitly asserts this), whereas compiler `icu_error` rejects it. Public parse returns frozen AST and exact bigint selectors, while compiler emits diagnostic text. Other grammar/profile differences must be identified before choosing shared policy.

- Defining owner: Values for public parser/AST/errors; Compiler for authored source acceptance/diagnostics; UI owns its existing consumer profile. Root must agree any shared grammar ownership with those owners.
- Concrete prerequisite output: one finite shared-versus-profile-specific grammar/usage/error table covering existing consumers, including the literal-`#` divergence, quoting, depth, rich tags, exact selectors and placeholder type/name order. No generic new AST carrier/arena is assumed.
- Proposed outcome: remove one proven duplicate bounded syntax mechanism or supply a demonstrated native consumer while keeping observable public/runtime and compiler acceptance unchanged at their declared profiles.
- Finite acceptance if later released: original public parse/validation callers plus compiler diagnostics agree on shared cases; known profile cases retain intentional differences; freezing, bigint selectors, UTF16/lone-surrogate and error ordering survive the actual delivered adapter; TS and Rust complete-call/copy/startup/resource costs are compared against TS parser reuse or preparse/caching. Keep Intl rendering/locale/tzdb out.
- Uncertainty: no runtime bottleneck or net maintenance reduction is measured. A JS preparse/cache or explicit profile documentation could be the smaller complete change. A compiler-only Rust consolidation might solve duplicate compiler scanners without porting any packages runtime.

**2. Whole pinned media graph canonicalization/substitution: optional consolidation/resource hypothesis, only with an actual native consumer or measurement.** Supplemental source review below supplies the concrete contract. Node already uses native SHA; merely porting hash is not this outcome. A whole graph call avoids repeated fine-grained crossings, but returning the complete graph still requires JS reconstruction and host-owned admission. No active candidate is recommended ahead of existing exact/validation delivery.

**3. Files immutable-byte content+digest kernel: optional throughput hypothesis.** One bytes call could potentially fuse scanning/digest passes for large text/bytes, but tiny binary signature matching alone is not worth a port. Compare the same full sync workflow against noble and a native host alternative; do not assume Rust beats native TextDecoder or that async WebCrypto is behaviorally interchangeable.

Other ideas considered and declined now: arbitrary structural equality/grouping, tiny UUID/ref/version checks, Markdown anchor hashing, standalone text case/trim/join, canonical JSON helper ports, auth/policy projection, CSV escape alone, all Contracts declarations and a replacement Intl/tzdb stack. They lack a demonstrated whole native consumer/net benefit or would change current host semantics. Existing V already covers owned schema/type/codec/profile opportunities; existing P already covers native artifact preparation.

## Supplemental source challenge: Files and Services joins

These focused extra paths are outside the 291-path coverage denominator. This is original source analysis, not another review layer or new task queue.

- **Files `upload/index.ts:detectContentType/checkContent/sha256Hex` and actual `completeUploadContent`, finalize/retention call sites.** SHA-256 currently uses synchronous `@noble/hashes/sha2.js`; it is not already WebCrypto. PDF/PNG/JPEG inspect short prefixes; text does a NUL byte scan then native fatal UTF8 TextDecoder and rejects empty text. `checkContent` detects content before evaluating allowed types/size and records caller claimed type without trusting it. Completion, immutable re-read, finalize and retention consume these sync helpers while retaining their own policy/authority/physical-byte checks. Replacing SHA with `crypto.subtle.digest` changes evaluation/await points and return types of sync storage flows; changing detection to a full file parser would add requirements. A finite future bytes kernel would return only detected type/size and exact `sha256:` digest from one immutable snapshot; host wrappers must retain current failure classes/order, lost-reply and policy/refusal behavior, and cleanup/commit order. Prerequisite: a released exact byte ownership/call-site profile and full-call evidence that scans/copying matter. Owner: Files; cryptography remains a maintained pinned implementation, not handwritten Rust SHA.

- **Services `media/mapping.ts`, `media/comfyui.ts` constructor and submit joins.** `sha256Hex` already uses native `node:crypto.createHash`. Real maintained work is `copyGraphData` own-data admission, recursively sorted-key `stableStringify`, graph digest comparison, typed destination/output checks, substitution, clone/freeze and error projection. `copyGraphData` inspects property descriptors without invoking accessor values or `toJSON`, rejects executable/nonfinite/sparse/cyclic inputs and preserves shared acyclic data. It explicitly is not a Proxy/intrinsic sandbox. Mapping and input objects still have original JS property reads/error order; do not serialize them eagerly to declare them safe. `substituteAndValidate` verifies the unsubstituted graph digest before mapping outputs and input scalar checks; duplicate destinations and missing/incompatible slots preserve exact `MappingValidationError`. Actual calls come from installation checks and `ComfyUIAdapter` submit. A later whole graph native candidate needs same canonical UTF16 key order/number JSON bytes, source graph digest, unchanged nonmapped edges, error priority and public frozen graph shape. Prerequisite: a complete admitted native graph profile or demonstrated full-call resource cost; compare preparation/caching in TS fairly. No new digest carrier, hashing owner or provider transport rewrite is justified.

- **Services `judgments/specification.ts` and mixed `judgments/systemone.ts`.** Keep two contracts distinct. Legacy `buildFrozenJudgmentRequest/readJudgmentBatchResult/mapJudgmentResponse` uses JSON stringify/parse, structuredClone, Number distributions and tolerance. Static authored `exactJson/wireDecimal/staticResult/staticRequest` preserves original numeric lexemes using `JSON.parse` reviver `context.source`, then public Values Decimal/int64, bigint-unit tolerance, exact answer/option/legend consistency and source order. `freezeJudgmentSource` owns source normalization/revision, borrows Values nominal validation and uses synchronous noble SHA. Rust conversion must not silently “improve” or unify legacy numbers/observable object coercion with static exact semantics. A distinct **portability** proposal can be stronger than a speed claim: raw response text→canonical static Judgment result could support an actual required host lacking numeric-source JSON parsing. First decision: which currently unsupported host must consume this exact authored workflow, and whether a small JS raw-token parser or Rust is the cheapest complete solution? Defining owner: Services response normalizer, Values exact primitives, runtime host delivery. Prerequisite: released named host/caller requirement, exact raw JSON numeric/string/duplicate-last-wins policy and retained current corpus. Finite later acceptance: real installed provider response enters that host with same question order, Number-free exact decimals/int64, legend/winner/tolerance/errors/null results and delivery identity; transport, current authority, tokenizer and remote model remain owning host responsibilities. A pure native normalizer cannot qualify the provider or the deployment tokenizer. No speed or supported-host claim is made here.

No extra builds/tests are appropriate for this planning-only source note. Root can use its existing JSON/reference/diff checks once when consolidating documentation. The canonical execution view and native/default/publication holds remain unchanged.
