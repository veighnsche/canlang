## Recommendation

There is no source-grounded reason to port all of State or Work. The highest-confidence useful next work is already in `W02–W08`: share the matching TS mechanisms and finish concrete consumers of the registered Rust decision families. It is additional adoption work, not a new Rust opportunity. The selected recovery whole call is already finished at its accepted scope.

Beyond that programme, retain two **conditional proposals**: (1) a whole-batch State order operation at an existing producer seam, if prepared TS and conversion-inclusive measurement justify it; (2) shared structural migration-plan validation with the compiler, if a genuinely shared contract avoids duplicated policy. Neither has a current measured benefit or release. Record a retain-TS outcome as successful evaluation when reuse or total cost does not justify the change.

## New proposal 1: already-selected State batch ordering

**Benefit sought:** one reusable exact order implementation for the State engine and generated-source query consumer, or a material complete-call improvement for already materialized batches. Source identifies the computation but does not establish either benefit yet. Scope does not include storage scanning, projection, permission decisions, source predicates, page transforms or mutation authority.

**First boundary:** `packages/state/src/query/engine.ts:orderSourceReadRecords` (line 728) already copies its input array, validates order/array declarations, decodes field-major then row-major including singleton results, sorts, and returns the same record objects in a frozen array. `packages/cloudflare/src/runtime/invoke.ts` around 5830–5860 calls it after original source `where` execution and lazy protected field reads, before the original limit/checkpoint. The engine's internal `decodeTypedOrder`/`compareRowsForOrder` around 642–727 run after original row visibility/projection/data predicate/source predicate order. For a smallest first pilot, keep the original host key decoding and error projection, transport only the resulting total-comparison key leaves, null/missing tags and UTF16 IDs, return permutation indices, and let the host retain original row/view identities. Keep money or other potentially throwing comparator profiles in TS unless the original comparator-demand/first-failure behavior is proved; an arbitrary different sorting algorithm is not equivalent on those profiles. Do not send unrelated full row payloads to Rust.

**Owner:** State query producer; Values owns exact int/decimal/money/date/instant codecs/comparison. Cloudflare owns the existing source consumer. **Concrete prerequisites:** current checked model/order declaration and actual already-selected rows at this exact seam; relevant released Values operation contracts if reused. No other owner's entire plan is a prerequisite. New Rust implementation would require its own explicit release; current held int/ASCII source adoption is not implicitly released.

**Finite acceptance:** both existing owning call sites return the same identities/order and first public fault for the selected inert profile; preserve field-major decode order, eager decoding even a singleton, null/missing order, booleans as numbers, UTF16 strings/ID tiebreak, exact beyond-safe-integer int/decimal/temporal order ; mixed money currency comparator faults remain an explicit retained-TS profile until separately proved at the original comparison point. Source failures and lazy reads must occur at their old positions; callback/object-rich profiles remain TS. Existing page post-transform and final Identity/revision revalidation remain unchanged. Run only affected producer and actual source-consumer vectors after a future release, plus conversion-inclusive ordinary TS/prepared TS/Wasm measurements and delivered binary/lifetime checks for this profile.

**Why prepared TS first:** `decodeTypedOrder` already predecodes each key once. Pages cap materialized candidates at 1000; raw adapter scans can be larger but are not CPU work this order boundary removes. Precomputed key vectors or prepared compare plans in TS may obtain the useful simplification without UTF16/typed-key marshalling and an additional binary. Sorting very small sets does not justify one FFI call per comparison. There is no basis here to claim Rust is faster, safer or lower memory.

**Original IDs:** the owning query/authority behavior is `challenge:T32`, with imported containment behavior remaining `challenge:T29` where consumed; exact primitive semantics overlap existing A/V ownership. This proposal is not already a W family or an accepted Rust task. Do not invent a canonical ID or broaden T32 acceptance to require Rust. Root should decide whether to record it as a separately proposed evaluation.

**Critical separation:** `policy/grants.ts:evalPredicateForRow` is two-valued post-projection matching (`not` negates a false null/type mismatch); `storage/memory.ts:evalPredicate` is SQLite-style three-valued logic, including NULL-aware `eq`/`ne` and `BETWEEN`. `storage/sqlite-codecs.ts:compilePredicate` emits corresponding SQL bindings. Unifying these as a universal evaluator would alter behavior. Current source AST `where` functions and per-row exceptions are host demand, not closed data facts. The broader authorized query batch remains deferred unless its exact demand boundary is independently established.

## New proposal 2: structural migration-plan reuse with compiler

**Benefit sought:** remove duplicated structural migration disposition rules between compiler Rust and State, not accelerate rare storage migration IO. `state/src/migration/transition.ts:validateTransition` is explicitly pure and creates old-model/old-field mappings, target/source uniqueness, backfill/staging flags, new-model and invalidation lists. Compiler `analysis/migrate_check.rs` checks duplicate model/field consumption and rename targets; `codegen/ir.rs` and `codegen/artifact.rs` emit related directives. They have overlapping rules, not an already demonstrated identical contract.

**Owner:** State migration semantics with compiler producer cooperation. **Prerequisite output:** a finite structural input/output contract that distinguishes compiled declaration checking from runtime installed predecessor/snapshot and checked model-table agreement. Retain owning TS intake and ordered `StateError` projection. First compare reuse with simpler shared fixtures/TS normalization; avoid exporting the whole mutation ModelTable or adding a general schema engine.

**Finite first scope if selected:** only pure `validateTransition` mapping/disposition checks on inert compiler-produced schema summaries, with exact predecessor/no-op, owner rename/drop, explicit model rename, field collision/source coverage/backfill/new-model and deterministic first-error/output ordering. No mapper execution or retained-work/callback/hash/activation/publish/flip in Rust. Preserve current unsupported composite-unique migration refusal in `internal/unique-value.ts:assertMigrationUniqueSupported`; a port does not invent its missing source-group census. Compare the actual emitter/State consumer, not two fixtures calling the same new helper. Accept reuse only when one rule owner genuinely replaces duplicated rules; otherwise retain TS is the recommended result.

**Original IDs:** no existing W port covers structural State schema migration. Keep existing migration owner/consumer criteria unchanged; record this only as a proposal pending root cross-plan mapping. No independent ID or new prerequisite for ordinary migrations is introduced.

## Retain TS and avoid duplicate ports

- **Raw replay canonicalization and digest:** `invocation/replay.ts:stableStringify` observes `toJSON`, sorted Object.keys, symbols, dynamic array length and element getters in one original pass. Admission-only `hashAdmittedInputs` bounds that same pass; `hashInputs` retains its broader public profile. `admit` reads revision, hashes raw inputs, consults existing receipt, applies retained-only authority/replay, then age, authority, normalization and references. Hashing normalized inputs or prewalking getters would change identity/order. WebCrypto owns SHA256. Ordinary rich-object serialization should remain TS; a closed-data canonical encoder requires a separately proved producer and existing Values/transport overlap analysis. File/metadata/source comparisons widely consume this serializer from Cloudflare; it is not an isolated cleanup leaf.
- **Equality and unique encoding:** `mutation/pipeline.ts:refValuesEqual` compares reference IDs while ignoring other fields; `fieldDataEqual` uses Object.is, array length, ordinary object prototypes, key reads and remembered alias pairs. `internal/unique-value.ts` derives scalar/user/ref-enum keys, conditional predicate eligibility and actual containment parent namespaces, and shares those rules with migration validation/activation. These are different equality domains. Existing Values decode owns canonical reference/numeric rules. Per-field FFI would likely add cost and copying; no current consumer needs a new generic Rust equality/record encoder.
- **SQL/record encoding:** D1 and DO already share `sqlite-codecs.ts` for record/receipt/history/outbox/schedule/migration conversion and SQL predicate/order construction. DO has local planned statements; D1 binds statements to the real API. Both serialize data/history/receipt/defaults before execution and preserve release-before-claim and insert-before-ack ordering. Replacing JSON.stringify with a new encoding risks persisted bytes, errors, absent-versus-null and JS number spelling. Moving SQL text construction alone leaves DB IO in JS and adds marshalling; prefer ordinary shared TS statement-planning cleanup if a demonstrated duplication warrants it.
- **Bounded parsing:** `sqlite-codecs.ts:checkCohortJson` scans raw stored JSON before JSON.parse, and SQL CASE gates withhold oversized payloads before driver materialization. Cohort, history and retained outbox have distinct count/text/byte/depth/envelope error profiles; memory validates before copying. A Rust scanner cannot repair a bound checked only after driver allocation. Shared protected parser work overlaps existing Values transport/preallocation scope; no second parser or blanket resource profile is recommended here.
- **File census/retirement:** `storage/file-retirement.ts:census` traverses complete bounded rows, checked installed/migrating declaration profiles, actual framework validators and opaque original-lifetime resolution. It retains duplicate array positions and archived references and closes publication/removal barriers under one real store fence. It is not merely set subtraction. Keep host declarations/provenance and atomic retirement TS unless a later specific closed occurrence-set operation has measured reuse.
- **Hosts and transactions:** D1 uses its atomic batch/fence insert and version checks; DO plans before a synchronous SQLite transaction and maps version/revision/constraint errors; memory validates/copied state before publishing. State ports are reader-only or single-shot, and caller retries remain caller-owned except the explicit canonical invoke admission loop. A Rust scheduler or storage engine is a new architecture, not a required prerequisite for pure kernels.
- **Receipt/progress observation:** keep request/grant/content/fence callback demand, original payload identity, original/current secret exclusions and current logical lifetime checks. `observation/observation.ts` explicitly consults only requested granted result/error leaves and content only when needed. Current nominal result contexts and source-produced observations cannot be replaced by arbitrary frozen JSON.
