## Old payloads, reviewed publication and failures

`loadPreviousPlan` treats an absent sidecar as first deploy, rejects unreadable/malformed JSON and minimally requires `{wrangler,schedules}`. Its consumers then project concrete nested config fields; malformed nested historical shapes can throw instead of being silently normalized. Previous plans support review/diff, not predecessor-schema authority or restoration snapshots. Legacy plans without a bundle retain `./dist/worker/entry.js`; a real bundle replaces that main. Only the specific missing Worker-main condition triggers the host's loud legacy fallback; arbitrary link/asset/module failures refuse. Native previous-plan resumes preserve absent-null versus present-invalid input classification and load at the requested native stage, rather than eagerly manufacturing a fallback DTO.

The shared confirmed publisher checks compiler release match **before** writing. It preflights both sidecars before publishing bundle files; sidecars stage in a fresh private directory with retained reviewed metadata and then publish in order. Preview publication is forbidden in the adapter. Destination relative paths reject absolute/NUL/backslash/traversal forms and existing symlink chains. These checks serve a cooperative account-owned output tree; no adversarial same-UID filesystem sandbox is established. Writers remain `mkdir+write`, so multi-file publication is deliberately sequential rather than a transaction.

If a bundle/sidecar write fails, earlier outputs may remain; no Wrangler apply follows that failure. `PublicationError` reports files that returned successfully plus pending entries. A failing underlying write may have partially affected its own target, so “not in written” is not evidence that every byte stayed untouched. Local-command interruption attaches partial-output context and preserves the operative interruption instead of converting it into a clean publication or automatically undoing earlier files. Cleanup removes the private staging root on ordinary return/throw; abrupt process/power failure has no separate fsync/recovery protocol here.

`runWranglerDeploy` requires explicit `yes`, uses argv without a shell, supplies cwd, suppresses Wrangler metrics and bounds the default spawn to three minutes (or remaining command lifetime). A nonzero numeric exit returns `applied:false` with captured output. Missing binary, timeout, signal or other unconfirmed spawn failure throws with an instruction to inspect the remote deployment before retry. `publishDeployAndApply` retains published local files and reports `applied`, status/detail/manual command; it does not retry or roll back the remote operation. Its terminal `ok:true` records completion of the local report even when `applied:false`; consumers must read the explicit applied/verdict fields rather than treating `ok` as proof the remote app is serving. After an attempted apply, an interruption remains remote-outcome-unconfirmed, even when no success envelope reaches the caller.

**DELIVERY-F01 — consumed staged bytes lack the promised identity check.** `PublicationSession::stage` records length/hash. `verifyReviewed` compares retained reviewed buffers to those records, but does not reread/hash the staged file. `publish` later reads that file and passes its bytes to the writer without checking recorded length/hash. Thus the exported helper sequence `stage → alter staged file → verifyReviewed → publish` can publish different bytes while the comments promise disk-drift refusal. This is a bounded helper-contract defect, not an executed exploit. The actual host currently uses a synchronous private stage/verify/publish sequence; no public deployment injection or asynchronous gap has been established.

## Native preparation and installed selectors

The native route is an explicitly selected transformation producer, not a second deployment authority. `runNativeDeploy` serves genuine activation/bundle/module frontend facts on the requested stage, memoizes the same verdict, and retains actual bundle bytes for publication. `finishNativeDeploy` admits the prepared outputs, checks final native module digest against the real host bundle before any write, then calls the **same** confirmed publisher. A semantic refusal inside the native session throws to the owner so the child is settled before the CLI maps its failure; it does not fall through to TS after a begun native job fails.

`executable.ts` resolves an explicit environment path as an absolute cwd path before verify/spawn, then packaged host triple, then a development candidate. Packaged host mapping claims Linux x64/glibc and macOS arm64; mapped Windows spelling alone is not release support. `verifyNativeLaunch` checks the adjacent executable manifest for host triple/executable/bytes/hash, binds the manifest's real path to the selected path, checks the imported owning release and performs a fresh readiness handshake/abort/exit probe before the real job. This guard applies to the selected resolution; an environment override is not permission to execute arbitrary unmanifested bytes. Readiness is not an operation's semantic success.

The session owner launches a piped process with native argv, owns stdin errors, and after terminal success or failure performs bounded settlement before returning/emitting failure. POSIX group signalling reaches retained same-group descendants; escalation and timer cleanup are explicit. This is bounded cleanup of the launched group/direct process, not universal containment of descendants that escape the group. A terminal prepared frame's authority and later process exit status remain distinct; native protocol assertions cannot qualify a provider deploy or installed migration. Source/backend ownership and installed selectors are now mapped; P-R05/L-REVIEW-DEV retain their different generation/owner lifecycle duties.
