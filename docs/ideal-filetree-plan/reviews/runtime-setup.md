## Requirements and owner boundary

The protected-setup contract requires one application-local first owner; the first user/team/active owner membership and consumed setup admission commit together. Matching credentials and admission recover the original completion without password reset or privilege recreation; another admission or conflicting credentials refuse. Raw token/password bytes must not enter durable claims or completion receipts. A local completion file is a publication of that Identity outcome, not its transactional authority. The documented recovery window deliberately ends at token expiry, including when Identity committed and the local receipt was lost.

This explicit setup contract is narrower than general State operation replay. Do not import State's operation-ID retention/age policy or invent expiry bypass from analogy. The runtime-only stopped administrator is trusted infrastructure; its direct `/bootstrap` command intentionally supports matching owner recovery without browser setup metadata. That is not a public setup replay route.

Identity owns complete owner/credential/membership verification and the D1 transaction. Platform owns private files, HTTPS Origin admission, actual application context, retained storage, private transport, child lifetime and local receipt publication. Source has these separate authorities already; collecting them into one generic claim helper would conceal rather than remove the D1/filesystem commit boundary.

## Admission and durable state trace

1. `startSodaSetup` reads an absolute token path with `O_NOFOLLOW`, checks the opened descriptor is an account-owned regular file with exactly mode `0600`, bounds it to 64 KiB, and admits exactly `operation`, `token`, `expires_at`. Operation syntax/length, token length and integer expiry are checked. This is length validation of operator-provisioned entropy, not a random-token generator. The documented operator still owns issuing a strong random token.
2. The receipt parent must resolve under `/home`, be an account-owned private directory and not itself a symlink. The canonical configured application origin must be an exact HTTPS origin. The host derives the serialized context from actual app, artifact digest, mixed bundle digest and storage fingerprint; the HTTP body cannot supply it.
3. Provisioning obtains the exclusive retained writer before starting the private admin Worker. Public setup exposes exactly `GET /setup` and `POST /setup/claim`; ordinary application/auth/MCP routes are absent. The form clears the fragment from history, sends credentials without cookies, uses nonce CSP and no-referrer/no-store responses, and retains credentials only in its live form/request.
4. The claim requires exact `Origin` and `content-type: application/json`, a bounded object with only operation/token/email/password/timezone keys, matching operation, equal-length constant-time token comparison and unexpired admission. Host-derived operation/token hash/context/expiry are sent to the private `/setup` path. The private gateway replaces caller-supplied dispatch headers with its own secret and original URL; `workerd-config.ts` exposes only its secret-gated loopback entry socket, not the admin service. Other local HTTP clients still need that secret. This is a same-account/private-host boundary, not isolation from a hostile process with equivalent filesystem/process authority.
5. `soda-admin.ts` bounds its body and delegates to `bootstrapD1SetupOwner`; it does not mint an owner independently. The public setup request cannot select `/member` or `/bootstrap`. Errors from this private administrator and public setup are generic rather than SQL/password/token disclosures.
6. `bootstrapD1SetupOwner` validates admission bounds/expiry, then `bootstrapOwner` normalizes email, checks password policy and timezone, refuses a port without genuine `batch` before schema writes, and ensures Identity DDL. `IDENTITY_TABLES` is derived from static table DDL, including both bootstrap and setup claims. Any populated owning table prevents a new unclaimed database from being adopted. Schema initialization itself is sequential/idempotent and can partly finish on failure; it is not the atomic owner transaction.
7. New IDs/password hash are produced before the batch. The singleton owner claim is inserted only when every owning table is empty. User, team and active owner membership inserts select only the newly generated claimed user ID. The consumed setup operation/token hash/context/completion time is a fifth statement under the same condition and genuine batch. A competitor cannot insert its own account behind another winner's singleton. The singleton `CHECK(slot=1)`/unique constraints make competing claims fail rather than duplicate.
8. The saved owner is read through a join of bootstrap claim, verified user, team and the exact active owner membership. A raw email lookup is insufficient. Recovery checks normalized email, timezone and password against the original stored hash; it returns original user/team IDs and never writes a reset. Setup recovery additionally requires original operation, token hash and serialized context. Consequently body binding is semantic: equivalent normalized email, matching password and timezone (including omitted default `UTC`) are accepted, not a hash of exact raw JSON bytes. Foreign app/artifact/bundle/storage context refuses even if credentials match.

## Uncertain acknowledgement and local publication

`bootstrapOwner` catches a thrown batch acknowledgement, then independently reads the complete owner and setup claims and verifies credentials. A committed batch with lost transport acknowledgement can therefore recover. A batch that rolls back leaves no complete claim and reports a retryable transaction failure; an unclaimed populated/incomplete database refuses instead of being repaired optimistically. A read failure propagates; it is not converted into a successful outcome. The matching prior-claim path also verifies setup metadata before credential recovery.

The D1 adapter's `queries` bounds request bytes, statement count and admitted parameter values. `transactionSync` executes the complete query list; statement failure escapes that callback and rolls back the list. It collects BLOB/null/rows/columns and change metadata for the built-in client, then awaits durable storage `sync()` and obtains a commit bookmark before returning success. It does not automatically replay a transport failure. A failure in `sync`, bookmark production or response delivery can occur **after** the SQL transaction; the caught provider error cannot honestly mean that nothing committed. Identity's matching-claim recovery is therefore necessary even for local D1. Generic State/Work consumers still need their own retained-operation semantics; this packet does not assert the adapter makes every non-idempotent caller safe to retry.

After confirmed Identity recovery, the host validates team/completion-time shape and constructs a credential-free receipt. `saveReceipt` exclusively creates a random mode-`0600` sibling, writes and fsyncs it, hardlinks without replacing an existing destination, requires an existing private receipt to serialize identically, fsyncs the parent directory, and removes its temporary name. Success is sent only after this sequence. Concurrent matching submissions can converge on the same bytes; a foreign receipt is never overwritten.

The consequences at each boundary are distinct:

| Failure point | Actual state and supported retry |
| --- | --- |
| Before Identity batch or failed transactional statement | No new owner transaction; same valid admission/credentials may retry |
| Batch committed, acknowledgement lost | Read complete matching claims/credentials; retain original outcome and completion time |
| Identity committed, temporary write/link/parent fsync fails | Client gets a failure although Identity is consumed; matching unexpired retry regenerates the same outcome and tries publication again |
| Hardlink already exists with matching bytes | Treat as the same completion and sync the directory; do not replace it |
| Existing destination has different bytes/unsafe metadata | Refuse publication; preserve owner and destination; no new owner or automatic file takeover |
| Expiry passes after Identity commit but before successful retry | Host and Identity admission refuse; documented automatic recovery window has ended. No new setup token can silently adopt the old claim |
| Temporary write/file sync fails before the link cleanup block | Identity remains committed; a private random temporary file may remain because that early failure precedes the unlink `finally`. This is residue, not authority or a published receipt |

`expiresAt` is rechecked immediately before building the setup statement after password hashing, with `completed_at` captured at that point. It is not a database-clock predicate evaluated at physical commit. A request admitted before expiry can finish publication after expiry, while a later retry refuses. This is consistent with the documented retry-before-expiry rule; a stronger commit-deadline guarantee is neither implemented nor established as required. Keep any future policy change explicit rather than treating this as credential-recovery authority.

## Writer custody and retirement

`acquireWriter` admits an existing absolute private account-owned retained directory under `/home`. It opens `.writer-lock` with `O_NOFOLLOW|O_NONBLOCK`, validates the actual regular owned mode-`0600` descriptor, and gives that same descriptor to `flock`. The acquisition helper exits without `LOCK_UN`; Node retains the open-file description. The actual workerd child inherits it as FD4 while the control pipe is FD3. The native guard requires distinct valid descriptors and an absolute workerd executable, arms Linux parent-death SIGKILL **before** comparing the expected parent, clears `FD_CLOEXEC` on both descriptors and `exec`s workerd. It does not reopen a pathname to obtain a different inode or release a shared lock prematurely.

Disposal closes HTTP admission and waits for active server closure, then workerd retirement, then closes the Node lock descriptor. `soda-workerd.ts` sets stopped before SIGTERM, awaits child close, escalates after ten seconds and reports forced/nonzero termination as failure. Stage deletion follows actual close. Unexpected child death resolves `failed`; setup/runtime stop their listeners, mark failure and dispose/release. The outer CLI supervisor requests awaited cleanup via IPC, treats forced termination as failure, and the gateway also disposes on supervisor disconnect. Abrupt gateway death kills its direct workerd via the guard. An independent new writer remains excluded while the old workerd retains FD4, even if the Node reference has disappeared.

These are actual inode/open-description guarantees for the checked file. They do not promise recovery against a malicious same-UID operator unlinking/replacing the lock pathname or racing checked parent directories. The source neither unlinks the lock during ordinary retirement nor claims to sandbox equivalent host authority. `storage.json`/form-key reading and nested retained-directory confinement are wider retained-storage hardening questions, not evidence of a remotely admitted setup bypass in this packet.

## Allocation, alternatives and remaining gates

Retain TypeScript for Fetch, D1 bindings, password APIs, JSON and Node private filesystem/server integration. Keep account semantics in Identity, the admin Worker as a transport adapter, and receipt publication in the host. Moving bootstrap into a generic platform claim store would duplicate Identity's transactional owner/credential facts; moving Node filesystem receipt logic into Identity would couple its Worker-safe API to a local target. Neither alternative removes the cross-store boundary.

Retain the narrow Rust Linux exec guard because arming parent death before `exec` with exact inherited descriptors requires native process operations. A shell-only trap cannot guarantee cleanup after unexpected gateway death. A full Rust rewrite of the Node/Worker adapter would add protocol and credential/Fetch integration boundaries without an established requirement. A daemon/supervisor that owns a separate lock lifecycle would add a durable custodian; the current inherited open-description/parent-death mechanism already expresses the selected direct-child contract. No new process or language owner is justified here.

The build producer stages the real bundled admin Worker and guard into Cloudflare `dist/host`. Runtime packing copies them beside the bundled runtime CLI and workerd/Node, excludes named development input graphs, retains the D1-derived notice/licenses, and inventories actual copied bytes/modes. Inventory generation is not a runtime loader's authentication of arbitrary installed bytes, nor proof that every platform tool/library is in an appliance image: the launcher still uses shell/readlink and acquisition uses shell/flock. The selected target remains Linux x86_64. P-R06 owns exact archive/image/install/upgrade interruption and release-selector checks; no broader installed-delivery qualification or new pinning scheme is selected by this review.

RT-SETUP-REVIEW/P-R04 may close their **source tracing** after independent challenge of this record. Keep SETUP-F01 as a concrete future integration repair and SETUP-F02 as narrowly scoped verification work; neither requires reopening unrelated account/browser/provider/migration reviews. Wider Identity authority/removal workflows and activation/migration ownership remain their own packets. Root is the sole writer of shared findings, tasks, owner/tree and completion matrices.
