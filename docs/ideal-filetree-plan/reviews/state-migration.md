## Requirements and completion scope

The contract requires an exact installed owner predecessor, separate target and body identities, immutable applied artifacts, explicit one-to-one dispositions, same physical authority/containment, frozen predecessor input, bounded resumable staging and complete desired-state validation. It independently requires original locks and protected values, archived/creation metadata, row versions, references, uniqueness, expiry and real File custody to survive their applicable transitions. Deployment must close admissions, writers, cleanup and dispatch across preparation/partial activation; a final local flip is not an atomic D1-plus-DO release. Old work requires actual release contracts and complete inventory, including retained releases. Preparation failure leaves the predecessor selected; once publication has moved rows recovery is forward-only with access closed.

## Persisted state and actual failure/retry chain

[Contracts](../../../packages/contracts/src/state.ts) define `InstalledSnapshot`, `MigrationTransition`, `MigrationProgress`, `StagedRow`, `MigrationDrop`, `MigrationOutcome`, `MigrationFailure` and storage inputs. [Storage schema](../../../packages/state/src/storage/schema.ts) stores:

- `migration_staging`: migration/model/id key, target version/data/parent/converted and optional creation/archive metadata. Source metadata supplies creation identity through a rename; `mergePublishedColumns` in `storage/sqlite-codecs.ts` chooses staged/live/history fallback values and conversion history supplies updated attribution.
- `migration_progress`: migration ID, phase, source staging cursor, target publication cursor and updated revision. It does **not** retain predecessor/target/body digests or a complete immutable plan. `migration_failures` adds leg, prior phase, both cursors, error/time/revision; outcomes retain migration/intent/handler contract.
- `snapshots`: owner/snapshot/digest/installed revision/time. Live records, history, unique claims and outbox status change in their own fenced publish/flip transaction. The flip writes its actual revision rather than the caller's placeholder.

The reviewed adapter closures are memory `stageMigrationRows` through `readMigrationFailure`, D1 `1004–1300` plus `publishRecordStatements`, `publishDropStatements`, `publishClaimStatements`, `flipSnapshotStatement`/`flipAuxStatements`, and DO `planStage`, `planPublish*`, `planFlip`, failure/discard planners and their `1178–1410` execution sites. D1 builds one `db.batch` with a unique next-revision `fence_log` insert; DO runs the matching SQL through synchronous `transact`; memory prepares copied records/claims before installing state. The fence serializes each commit. It does not freeze the earlier validation scans or serialize different migration IDs for an entire deployment.

A mapper failure occurs before the staging chunk write; previous committed chunks/cursor survive. A storage fence conflict translates to `StateError` busy. Deterministic validation/constraint `StateError` preserves current phase; automatic resume therefore retries from that committed cursor. Unexpected failures through `resumeMigration`/`activate` attempt a fenced durable `failed` record with the **current** committed progress. Failure-record write failure is attached as cause where possible and the original error rethrows. Direct `stageNextChunk`/`validateStaged` callers do not acquire that orchestration automatically.

A successful publish chunk writes rows, histories, drops, claim releases-before-claims, progress and guarded File state together. If a later chunk fails, earlier live publication remains and the predecessor pointer can still be selected: access must stay fenced. Retry rereads the publication cursor; true drop enumeration resumes from remaining live rows, not a separate drop cursor. `retryFailedMigration` restores the saved prior phase/cursors with an empty fenced staging write and routes again; it cannot repair invalid data or a missing compatible contract. `abortMigration` discards only shadow rows/progress at staging/staged or staging-leg failure, retaining failure audit. Publishing, active and activation-leg failed states refuse abort. The final flip atomically selects/removes the local snapshot pointer, removes the renamed predecessor pointer, skips **pending** invalidated intents, writes outcomes and marks active. A committed-but-unacknowledged flip is recovered by reading active progress; no destructive backward row rewrite exists.

Because progress is keyed only by migration ID, the orchestration must bind that ID to the original predecessor, target, body and executable release across retries. A newly supplied validated plan is not compared to a persisted body/target record by these modules. This is a missing deployed binding contract, not evidence that a real host currently accepts an altered plan.

## Concrete source finding and bounded gaps

**RT-MIG-01 — valid final unique-key exchanges depend on publication chunk size.** DESIGN §11.2 requires complete target uniqueness and resumable bounded application; it does not prohibit a pure backfill exchanging two existing unique values. `validate.ts:315–371,1025–1053` accepts a staged same-model target where rows A/B exchange unique values x/y: the final values are distinct. With `chunkSize=1`, `activate.ts:483–485,676–700` publishes A first, releases only A's old x claim and claims y, while B's original y claim remains. `storage/memory.ts:972–987`, D1 `publishClaimStatements:626–651`, and DO `planPublishClaims` enforce the existing claim and fail atomically. Same-size retry repeats the same cursor and conflict. Increasing the chunk to include both happens to release both claims first; that is not a general bound-safe algorithm for arbitrary cycles. This is source-derived, not a reproduced result. The `activate.ts:33–39` header already records a cross-chunk swap/chain limitation; this finding supplies the same-model source chain and task ownership rather than claiming a newly discovered deployed exploit. No corruption or unauthorized provider action is alleged. Compiler-produced mapper/protocol admission remains unqualified.

Correction owner remains State migration/claim publication, coordinated with all three adapters. Establish a complete collision-safe claim transition with persisted bounded progress/authority before selecting an algorithm; do not weaken final uniqueness or assume larger chunks solve arbitrary dependencies. Existing per-chunk atomicity is useful and must remain. This gates correctness/port readiness even though source review is complete.

Other established limits are **not** promoted to an end-to-end exploit:

- `InterimLock` (`mutation/models.ts:379`) contains only name/predicate. `validate.ts:439–505` proves originally true predicates remain true after mapping, and refuses dropped predicate inputs. It does not compare every protected field value or prove desired lock coverage. `checkDesiredLocks` merely evaluates predicates. The compiler checker `analysis/migrate_check.rs` explicitly leaves old-schema checking to runtime and its owner model view has names/fields, not old lock coverage. The complete lock/snapshot producer is missing from the inspected deployed path; predicate truth alone must not be credited as the stronger DESIGN lock contract. Publication also stamps updated metadata after validation, whose synthesized view uses live timestamps; predicates/invariants on updated metadata need an exact supported contract.
- Optional `isExpiredRow`, missing reference scope descriptors and callback mapper execution are marked interim in code. No source evidence here closes the required expiry/physical scope/purity producer joins; the narrowed native target refuses migrations. Complete installed support is gated, not assumed safe because an optional callback was omitted.
- `freshInstallSnapshot` is validation-only; protected `installFileReferenceInventory` is a real atomic pointer+inventory producer used by native startup. The old generic comment that no fresh pointer producer exists is therefore too broad. That real path does not close generic migration immutable-plan/progress binding.
- Composite unique migration explicitly refuses via `assertMigrationUniqueSupported`; do not port or advertise it as supported based on ordinary tuple mutation support.
