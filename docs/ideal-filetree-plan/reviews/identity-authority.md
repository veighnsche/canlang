## Contract before implementation

[REQUIREMENTS](../../specification/REQUIREMENTS.md):202,223 requires MCP connections to resolve a real app user and authorized team, recovery and sign-out, verified email where email ownership matters, and removal ending team access while preserving history. [DESIGN](../../specification/DESIGN.md):406–410 distinguishes public/authenticated/member/owner/declared-role authority, protects the last owner, limits invitation grants, and says completed removal prevents new admissions while already-admitted work may finish; D1 fencing also detects intervening membership changes. DESIGN:1136–1142 makes team tools canonical business operations, leaves login/recovery/consent as runtime interfaces, binds MCP consent to one team (or app-only for a non-team app), and rejects argument-supplied identity/roles/team grants. DESIGN:894 requires context changes to recheck access and clear previous private presentation data. REQUIREMENTS:225,252 explicitly prohibits assuming transactions across D1/DO/R2/providers.

These contracts do not establish retroactive cancellation of all work after session logout, or a transaction spanning Identity and State. Local lifetimes, token sizes, cookie mechanism, public OAuth client restriction and consume-before-mint failure policy are authored implementation contracts. Their source comments are evidence of that mechanism, not independent language requirements. In particular `authentication/revocation.ts` describes credential checking as commit-time, whereas its actual interface callers label and implement **pre-invoker admission**. The actual checkpoint must be reported accurately.

## Ownership and strongest supported alternative

Retain Identity as the defining asynchronous TypeScript owner of account/session/grant/team lifecycle and bounded SQL commands; Interfaces owns browser/MCP transport, origin/CSRF admission and safe errors; State owns business admission/fence/replay/query authority; Cloudflare owns physical bindings and original-removal-to-State staging. Retain exact authentication/session/team leaves named above, `identity/src/{ports,testing}.ts` and `storage/d1.ts`; no extra identity database, role service, bearer DTO authority or new process is selected. Atomic commands remain beside their authoritative Identity schema. SQL is an essential defining part of their guarantees, not incidental glue to relocate into a generic orchestrator.

The strongest already-supported alternative is Rust/Wasm for pure token/codecs/comparison or complete lifecycle logic behind the existing JS host, using the repository's real Rust/Wasm toolchain. The pure pieces are small and already delegate cryptography, encoding and cookies to WebCrypto/native host, `@scure/base` and `cookie`; a port gains no demonstrated workflow correctness or storage atomicity. Full lifecycle port still requires async D1 batches, mail, WebCrypto/random/clock, browser cookie/origin handling and JS error/ordering equivalence through a new ABI. Conditional Node/workerd comparison modules already preserve the native host seam and fail closed when workerd lacks it. Retaining TS/SQL is the lower-complexity technical recommendation on present evidence, not proof of performance superiority or an unrestricted language policy. The decisive improvement is a truthful atomic storage command where required, independently of language.

## Account, invitation and installed delivery follow-up

Root completed substantive reads of `accounts/passwords.ts`, `accounts/registration.ts`, `teams/{invitations,roles,selection}.ts`, token codecs, and the real D1 invitation-acceptance command. This is additional source inspection, not an execution or a security recommendation about current password parameters. Password policy/encoding constants are implementation-authored: policy counts JS string units; hashing creates a random salt, derives via WebCrypto and stores a versioned encoding. Verification admits bounded positive iteration counts and exact salt/key sizes, returns false for malformed encoding or derivation failure, and lets native comparison faults propagate. Base64url byte decoding preserves historical ignored tail bits; bearer lookups hash the exact presented string instead of normalizing it. Unknown-user login pays the dummy derivation and returns the same ordinary credential failure; no full timing-equivalence claim follows.

Registration normalizes/validates email, checks duplicate account, hashes, then separately persists the unverified account/proof and sends addressed mail. Failed mail does not roll back the account; verification's user update and proof consumption are separate writes. Those are real failure boundaries, not atomic registration/recovery commands. Existing recovery's stronger transactional command remains as previously reviewed; do not transfer that guarantee to every account helper.

`inviteMember` verifies team/current owner, validates a qualified role or owner, prevents an already-active member, stores the exact grant ceiling and expiry, then sends mail separately. A mail failure can leave a durable invitation. This layer validates role spelling; source-declared role existence must come from the canonical operation's owning registry, which is part of the missing delivery join below. An invitation ID is not a bearer acceptance secret: acceptance demands the current verified addressed account. It checks live proof state, rejects active membership and refuses a store without the atomic command.

D1 `acceptInvitationWithMembership` rechecks unused/unrevoked/unexpired invitation and verified address in the actual batch. It inserts or reactivates the unique team/user membership using the stored owner/roles ceiling, conditionally consumes through the immediately prior winner's `changes()`, reads the winning membership, then demands consistent definitive acknowledgements. It preserves prior membership creation identity on reactivation. No active-member role extension, caller-authored ceiling or second successful proof consumption is inferred. A committed-but-lost acknowledgement is not reconstructed as a successful retry by this API; later acceptance sees the proof spent. These transaction/acknowledgement duties need real D1 qualification, not the memory revocation fixture. Source search of the current TS test subjects found no direct invitation acceptance call; that search is not proof that arbitrary external consumers do not exist.

Role assignment verifies current owner and active target. Owner demotion also relies on D1's conditional last-owner guard. Qualified roles remain stored assignments, not implicit owner privileges; add/remove currently writes the whole role array, so this trace does not solve previously known concurrent role-array lost updates or atomic issuer-currentness across separate reads/writes. Selection verifies live session/team/membership before storing a hint. Future admission resolves current membership again; a saved selected team is never a grant. The helper does not itself clear browser DOM or provide a filesystem/session-wide transaction.

### Current disclosure and browser boundary
