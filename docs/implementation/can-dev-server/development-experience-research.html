The plan now includes an explicit lifecycle, check and preview state-machine design, including transition guards, duplicate-start protection and cleanup recovery. The user-designated lifecycle chat owns implementation; this refinement remains planning-only. The earlier roadmap here is research context, not another execution queue.

A compact, readable live status area in the ordinary terminal, with a durable activity history above it. At every moment the author can tell what Can is doing, which preview is actually available, whether it includes the latest source, and what action makes sense next.

This is a design proposal. The selectable screens below are illustrative snapshots, not a running dev server. Times, ports and diagnostic examples are invented to make the interface reviewable; they are not benchmarks or promised timing. This refinement changes only this research artifact. The recommended surface

Use normal terminal scrollback with a short live block after the activity transcript. Keep the shell's history, selection, copy/paste and familiar exit behavior. A full-screen TUI would offer more log navigation, but brings more interaction and accessibility machinery than the current need justifies. An append-only presentation is equally supported for simple terminals, recordings, screen readers and anyone who prefers a stable transcript.

Phases, timing and readable feedback during long waits

The terminal should use a small author-facing vocabulary: Connecting, Capturing inputs, Checking source, Building preview, Preparing local state, Validating preview, Publishing, and Releasing previous preview. Owners emit only the phases they actually perform; an existing preview reuse path can skip most of them. “Details” can show lower-level names and completed phase durations without placing every internal step in the default view.

Distinguish elapsed time since the request from time in the current phase and time spent queued. The default busy line shows the current phase duration; one adjacent summary shows the whole operation duration. Completed durations freeze in the transcript. Owner monotonic timings support authoritative phase durations; a presenter can show its own waiting for response timer before acknowledgement. It must not turn that local timer into invented compiler time. After reconnect, show duration only if the owner can supply it; otherwise say unavailable.

A long-running phase remains the named phase: Building preview · 12.4 s in phase. If no new status arrives, say no newer status received; an old heartbeat alone does not prove the process is stalled. Phase changes and serious errors deserve durable events, but timer ticks do not. No ETA, performance blame or “almost done” without evidence. The terminal should stay responsive to status and stop while the owner works; the current synchronous bundler wait makes that an implementation concern for event delivery, not permission to fabricate progress.

Diagnostics, failures and recovery

Present an error as a small incident: what failed, where, what still works, what to do next. The first relevant diagnostic gets its severity/code, a copyable path:line:column, the captured source line and focused range, followed by any compiler-supplied correction. Do not invent suggestions. Multiple errors get a truthful total and details action; if the compiler/service omitted diagnostics, state that explicitly rather than implying the visible list is complete.

Render excerpts from the captured revision that produced the diagnostic. If the author has since edited the file, label it from the previous check; source has changed; do not silently splice old offsets into new file contents. A diagnostic opened after its retained evidence was evicted says details no longer retained; run check again. Existing source-reference and failure-detail commands remain the defining retrieval routes.

On correction, preserve old diagnostic text in scrollback and append a concise successful outcome. The live status then reports the new state. A page-opening action cannot dismiss source errors. Source failure, runtime preparation failure, access expiry, missing tools, unsupported profile, schema mismatch, connection loss and cleanup failure need their own next steps. Schema errors explicitly preserve data; no “fix” shortcut performs a reset. Runtime refusal evidence remains a structured business outcome where appropriate, rather than every expected denial becoming a frightening server error.

Stopping, interruption and ownership

The view header says either started here or attached. For a session started by this foreground invocation, Ctrl+C immediately acknowledges Stopping Tasks, asks its verified owner to stop and reports actual release progress. For an attached view, Ctrl+C says Detached; Tasks remains running. The footer always advertises the applicable action; explicit stop is available when the author intends to stop an attached session.

While stopping, disable new checks and opens, keep status available and distinguish releasing runtime, pending cleanup and loss of contact. A second Ctrl+C should exit this terminal view only, with the first acknowledgement already explaining Ctrl+C again detaches; shutdown may continue. It is not a hidden force-kill of workerd or another owner. If the view exits before release is verified, print the verified session reference and exact recovery command. Do not say Stopped. Existing lifecycle ownership handles cancellation, waits and retry; the presenter must not invent those semantics.

If cleanup fails, keep the visible state Shutdown incomplete, preserve the cause, and offer retry of the same owner's stop only when its lifecycle contract supports it. The unmerged cleanup work provides that retryable behavior and must remain labeled unmerged until integrated. On current main, do not advertise a retry as guaranteed. Success means the owner has confirmed the release its contract promises; endpoint disappearance alone must not be translated into a stronger claim about every child process.

What the terminal design needs from the existing owners

This is a bounded interface definition, not another implementation plan. Control CLI/client owns presentation, command input and stream selection. Session daemon/core/service owns authoritative operation state, revision relationships and retained outcomes. Compiler, bundle and preview owners report their actual phase boundaries and failures. Preview bridge provides non-secret origin separately from explicit access issuance. Lifecycle owner determines actual stop/retry/release semantics.

The small missing contract is: active operation identity and phase; queued/start/phase elapsed values; confirmed changed inputs versus capture uncertainty; a bounded last-operation result including preview error/cleanup health; safe preview origin; and verified terminal attachment/ownership. Reconnection needs that snapshot before applying subsequent events, so delayed events cannot overwrite a newer outcome. Use the existing revisioned diagnostics and retained failure data; no general observability platform or browser acknowledgement protocol is required for this terminal refinement.

Without those additions, the immediately honest experience can still say Starting control session or Check requested · waiting for result, display the completed outcome well, and expose useful commands. It cannot pretend to know that compilation, bundling or runtime startup is happening. Likewise, the current status cannot by itself recover a missed preview-build error after reconnect. These are genuine source/API gaps, not copywriting issues.

Earlier research: a responsive development loop for Can

Make saving update the existing protected preview automatically. Keep the session and browser origin stable, reuse work whose inputs have not changed, and give the author truthful feedback throughout. Add CSS replacement and bounded server-rendered page updates before attempting general state-preserving component replacement.

Roughly two seconds for a small edit is an aspiration. This research neither establishes that timing nor treats an automatic fifteen-second rebuild as the intended finished experience. Workflow automation and actual computation reduction should proceed together.

Scope: existing checkout read-only; official documentation and source research; three independent research perspectives and three JEV consultations. No builds, server launches, installations, benchmarks, worktrees, code changes, commits, merges, messages to existing project agents, or automations. This document lives outside the repository. Recommended architecture

Save / latest generation→Check affected inputs
reuse valid outputs→Prepare + validate→Atomic promotion
stable protected origin→CSS swap / page update
or reload

One session owns the loop. Extend the existing owner rather than introducing another orchestration layer. Debounce save bursts, keep one active preparation and one latest pending generation, and discard obsolete results. Cancel only owned cancellable work; preparation that cannot safely cancel finishes and is discarded/cleaned. Do not enqueue a complete rebuild for every keypress; serialize state-changing provisioning and activation where the existing storage contract requires it.

The browser origin outlives a build. Move protected bridge lifetime to the session and atomically select a ready backend. Initial bootstrap stays explicit and private; replacement does not mint a fresh access capability merely to repaint. Preserve application Identity, CSRF and origin checks on each request. Pin each in-flight request to one generation, bound the drain of retired requests, and never replay an uncertain mutation automatically. Resources must be revision-addressed or otherwise held consistently so an old document cannot silently fetch incompatible new assets.

Start with a small update channel. An authenticated, same-origin SSE stream is a plausible first choice for one-way ready/error/restart notifications; an ordinary POST can acknowledge application. WebSocket is equally viable if bidirectional needs justify it. Reconnection obtains the latest serving revision instead of replaying every old update. Expired access and stopped sessions remain explicit. The existing bridge buffers Worker responses, so this is a deliberate gateway-owned streaming route, not an assumption that forwarding SSE already works. Keep the dev client out of release bundles.

Cache artifacts, not permission outcomes. Key reusable work by its consumed source/dependency graph, compiler/catalog/tool identity, relevant flags/configuration, producer and generated-input identities, and target assumptions. Cache membership and resolution too: additions, deletions, symlink changes and missing imports can matter. Reuse after establishing that the relevant inputs are current. A watcher is a hint, not proof. Immutable producer snapshots or an existing cooperative ownership mechanism can reduce repeated hashing; mutable contributor files cannot be trusted just because no event arrived. Failed/superseded results never become the current successful generation. Even when semantic output is reusable, source provenance, spans and consumed-source evidence must describe the new source generation; reusing code is not reusing an obsolete freshness claim.

Begin at the narrowest reuse boundary. The current portable bundle rebuilds common MCP/HTTP producer chains that do not intrinsically depend on a sentence. Cache those exact outputs first when their verified input keys match. Retain a verified compiler/catalog staging snapshot per identity if safe. Share repeated capture work only across boundaries that guarantee the same coherent input generation. Keep the full source check initially; add declaration-level incremental checking only if its measured contribution warrants it. No new framework dependency or general compiler rewrite is justified by the aggregate timing alone.

UI updates use checked ownership. Can already has compiler-owned stylesheet identities and checked asset digests. It also has a main-region morph that preserves compatible edited controls, manages generated-mount cleanup and removes actions after denied reads. These are reuse candidates, not existing development HMR. Ordinary morphing deliberately retains some form nonce/token/CSRF/version state; a code-generation change cannot blindly reuse that assumption. Use a fresh authorized render and validate binding compatibility; transfer harmless draft values only where the owner permits. A quoted string can be an executable input, message dependency or identifier, so textual diffs alone cannot certify presentation-only change. bundle.ts:1855–1953; bootstrap.ts:406–524; operations.ts:445–459.

Today generated styles are combined into the canonical CSS resource, and the browser resource digest is staged into the Worker artifact. The first CSS-only browser swap can follow an ordinary validated build and preserve the DOM; it does not automatically eliminate backend rebuild work. Avoiding that work needs a separately owned, coherent resource-publication boundary if the measured benefit warrants it.

Failure and recovery behavior

  • Invalid source or failed build: retain the last accepted preview, label its stale revision, display the new diagnostic and retry on the next save. Startup with no accepted preview shows an unavailable/error state, never a false Ready.
  • Source changes mid-build: discard the superseded candidate, clean owned resources and process the newest pending generation. Do not apply an old browser event after a newer generation.
  • Browser/runtime error after publication: display the failing revision and a recovery route. Retaining or restoring the prior code is possible only where storage/configuration remains compatible; no claim of automatic database rollback.
  • Unsaved input or an in-flight mutation: do not force reload through draft protection or retry a mutation with uncertain completion. Prefer compatible update; otherwise visibly defer refresh or let the author explicitly reload. Automatic updates resume after the blocking interaction settles.
  • Authority changes: the serving generation remains the last accepted code while new source is pending. Every request still checks live Identity, grants and data under that generation; no cached permission judgment crosses a revision. After promotion, refreshed controls receive current bindings. Invalid policy edits do not silently become effective.
  • Schema mismatch: preserve data and state the existing refusal/recovery option. Explicit data reset is a user choice, not a reload optimization.
  • Cleanup failure: show which release failed; retain the cleanup handle and prevent further runtime growth. The unmerged lifecycle change already introduces this behavior and shutdown_error; consume that contract rather than recreating it.
  • Expired preview access or disconnected browser: say access renewal/reconnection is required. Do not log access secrets or claim the page updated. Keep watch ownership clear when Ctrl+C stops an owned session versus detaches from an existing one.
