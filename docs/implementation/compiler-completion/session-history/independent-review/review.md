## Alternatives and limits

The accepted immediate all-live replacement is consistent with the current borrowed synchronous callback boundary and absence of a public Server DB lease. A storage reclamation API could reduce copying unaffected text but broadens immutable ID/owner compatibility work. Budgeted history could reduce rebuild frequency but introduces an unprovided threshold and retains historical bytes until that threshold. Source-level review supports the narrow implementation closure; it does not establish that immediate rebuilding is fastest for larger live sets. Copying/hashing scales with all live text, and rebuilding transiently retains old/new storage plus the appended changed text.

The three JEV replies materially disagree, favor broader alternatives with low confidence, and contain no rationale. Reviewed the preserved uncertainty and source/workload tradeoff investigation. The root's choice accepts proportional all-live copying for the declared boundary. No consensus or numerical superiority is inferred, and no additional design decision was made by this review.

This review does not repeat a complete suite or establish RSS, latency, long-running host performance, GUI behavior, cross-file semantics, generalized reclamation, or completed overall integration. Other root work may rebuild original target paths; every new control above uses the preserved archives. Remaining integration/shared decision bookkeeping is root-owned.
