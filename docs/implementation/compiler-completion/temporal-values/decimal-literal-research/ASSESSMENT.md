# Existing-owner qualification for the Decimal literal E6008 seam

Read-only finite research, 2026-10-08. **An existing public exact constructor is available:** `parseDecimal(text:string):Decimal`, exported from `@canlang/values` and re-exported as the same function by `@canlang/stdlib`. No backend or API invention is needed to construct current authored dotted decimal literal values. This qualifies an existing capability; it does not authorize or implement compiler lowering.

## Public controls and input pins

`public-module.mjs` imports `parseDecimal` and `negateDecimal` directly from the genuine installed `@canlang/stdlib` export, without a fake runtime or altered generated module. It is a research module, explicitly not compiler output. `probe.mjs`, raw `run.stdout`, `outcomes.json` and `pins.json` retain twelve constructor vectors, exact codec results, five schema-default/null/update vectors, nullable wire control and the exported binding-carrier roundtrip. All selected source/dist/catalog/spec input hashes were stable before/after execution; resolved export roots and Node24.21.0 are saved separately. No compiler executable, build, suite, Git, JEV, network, production or decision write was used.

- `1.50` constructs frozen owner Decimal `{coef:150n,scale:2}`; leading-zero spelling `0001.50` has the same coefficient/scale. `0.00` and `-0.00` retain scale2; Decimal has no negative-zero coefficient distinction. `-1.50` and actual exported `negateDecimal(parseDecimal('1.50'))` both preserve scale2/coefficient-150n.
- A full38-digit integral constructor input retains its exact coefficient at scale0. A38-significant-digit/18-fractional-digit dotted input and minimum nonzero scale18 input remain exact. Scale19 and39 significant digits fail `out-of-range`; exponent and plus forms fail `invalid-construction`.
- Public `@canlang/values/bindings/carriers` exposes `tag`/`reconstruct`; `1.50` roundtrips as `{t:'decimal',coef:'150',scale:2}` and native owner Decimal150n/scale2. This uses the actual public subpath and constructor, not a synthetic bridge.
- Public schema normalization with wire-default `'1.50'` gives exact Decimal150n/scale2 on create omission. An explicit replacement `'9.00'` stays900n/scale2. An omitted nullable field becomes null; an explicit nullable null suppresses its `'2.00'` default; nonnullable null rejects. Update omission returns each canonical `UPDATE_OMITTED` sentinel (checked through public `isUpdateOmitted`), not defaults. JSON omits those symbols in raw display; the saved booleans establish their identity.

These schema controls qualify the owner's existing wire/schema preconditions. They do not prove an emitted native metadata default is accepted by every creation engine, or that compiler-generated Decimal default code currently executes.

## Exact source and consumer closure

Lexer `syntax/lexer.rs::lex_number` recognizes decimal only as unsigned ASCII digit runs with a dot followed by digits. The sign is unary syntax, not inside the Decimal token. Exponents, separators and decimal unit suffixes are not admitted literal syntax. `analysis/types.rs::type_literal` checks decimal38/18 and reports E3001; the range count matches the owner's coefficient significant-digit check, including leading zeros. `codegen/ir.rs::decode_literal` stores dotted spelling unchanged in `IrExpr::Decimal(String)`. This is sufficient input for the existing string-only checked constructor, with no Number conversion. Unary minus already uses the exported `negateDecimal` lowering when the scalar family is Decimal.

`codegen/js.rs::lower_expr` currently refuses `IrExpr::Decimal` with E6008, stating that no §13 lowering/catalog constructor exists. `Emitter::stdlib` is the deterministic import assembly used by expression helpers: emitted helpers need not themselves be authored catalog builtins (current arithmetic/temporal helpers demonstrate that distinction). `import_lines` imports accumulated names from `@canlang/stdlib`. A future narrow Decimal literal branch can therefore use the verified public helper contract, but must be explicitly selected and tested; the current refusal is not disproved by export existence.

Owner closure: `values/src/decimal.ts::parseDecimal` uses BigInt coefficient parsing plus retained fractional length, checked by `Decimal`; `values/src/index.ts` re-exports that module, package self-export resolves to `dist/src/index.js`; `stdlib/src/index.ts` explicitly re-exports `parseDecimal` and `Decimal` from that public root. Source/dist and manifests are separately pinned. `parseDecimal` is absent from actual `values/dist/catalog.json` and source catalog. Thus adding a lowerer import does not require exposing an authored `parseDecimal(...)` Can builtin, and no authored signature is inferred. `decimalFromInteger` is exported by values but **not** the current stdlib façade; `parseDecimal` already handles integral text if a separately scoped contextual-literal repair needs it.

Bindings are another layer: current `bindings/backend.ts` TS smoke table covers Decimal add/negate, not parse; `bindings/carriers.ts` reconstructs the coefficient/scale tag through the public Decimal constructor. `parseDecimal` itself is direct TS exact construction and does not dispatch through a selected wasm/backend. This finite export/carrier evidence does not prove all primitive transport, wasm plans, exact-values bridge retirement or generated caller surfaces.

## Literal, wire, defaults and remaining boundaries

`codegen/js.rs::literal_json` preserves authored dotted spelling as a wire string (including `1.50`), and `js_field_default` retains that separately typed artifact descriptor. By contrast executable `lower_default(IrDefault::Literal)` invokes `lower_expr`: current runtime/default lowering therefore still hits E6008. Nested literal arrays/objects also reach expression lowering; argument defaults and message bindings have their own consumers. A future change must qualify those actual consumers rather than borrowing descriptor-fixture success.

Owner wire `decodeDecimal` calls `parseDecimal`, retaining supplied scale. Wire **encode** uses normalized `decimalToString`: constructor1.50 emits wire`1.5` and decodes as15n/scale1; zero emits`0`. This intentional wire normalization is distinct from source-literal/carrier scale preservation and artifact default spelling. Replacing source construction with encode/decode roundtrip would lose authored scale. Null and omission live in surrounding schema/codec/runtime paths; a Decimal constructor should not consume absent or null operands or default-fill updates.

A second, distinct seam remains: expected Decimal contexts admit integral literal spellings up to38 digits (`type_literal` R16/T11), but `decode_literal` still represents those tokens as `IrExpr::Int(i128)` and `lower_expr(Int)` emits bigint. That can retain mathematical magnitude yet differ from the desired native Decimal carrier/scale0. Simply filling the `IrExpr::Decimal` branch does not establish complete contextual-integral literal behavior. The largest admitted38-digit magnitude fits positive i128; this observation is not a license to cast Decimal values to integers. Keep the future narrow leaf's scope explicit.
