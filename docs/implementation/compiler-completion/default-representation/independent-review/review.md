## Contract and caller assessment

`lib.rs` exports `codegen`, which exports `js`; the enum constructor, `literal_json`, `js_field_default`, `to_json`, and `Serialize` are public. The private six-variant `WireLiteral` builds exact domain strings and ordered object pairs before `literal_json` encodes them. The public String payload additionally admits any syntactically valid JSON supplied by a caller. `JsFieldDefault::serialize` validates that payload as borrowed `RawValue`, preserving its interior token representation through the JSON serializers rather than replacing it with a map or floating-point value. Invalid syntax returns a Serde serialization error. The infallible `to_json` wrapper calls `descriptor_json(...).expect(...)`, so that wrapper panics on such an invalid payload; the error qualification must name the serialization route.

The reviewed closure includes both operation projection calls, model projection, derived/server/parent default variants, optional default omission, live `operations_json` in `canApp`, and typed artifact operations/models borrowing. It also includes `machine_for`: that path constructs a descriptor literal and decodes its JSON String for the machine's initial state. This extra String parse is not a second `RawValue` site, but remains part of any future representation replacement budget. Native schema/default expression lowering and derive-function undefined-only default evaluation separately consume the typed expression through `lower_expr`; they do not prove retirement of the artifact carrier.

No same-contract retirement was identified. Promoting the private literal tree to the sole payload breaks public String construction and does not admit the full caller-supplied JSON representation. A raw-number/ordered-pairs extension still changes payload type and invalid-input timing. Generic `serde_json::Value`, even with order preservation, does not retain repeated object members and raw numeric spelling. A second typed variant or internal borrowed serialization path could avoid encode/parse work for selected compiler-owned values, but keeping String compatibility leaves the original storage/revalidation mechanism and adds code or another representation; that is not the stated retirement. No performance benefit or net deletion is established for those alternatives. Retention is justified by these contract consequences, not convenience or an assumption that external users are absent.

A future alternative should first release a narrow owning public representation/migration gate covering constructors, exhaustive matching, helpers, admission/error behavior, raw JSON representation, and machine initial extraction. Then qualify compiler-owned and caller-constructed inputs separately and count the whole replacement/compatibility closure. This review proposes no implementation or waiver.
