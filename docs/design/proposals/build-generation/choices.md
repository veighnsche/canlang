# Accepted build-generation choices

Status: human-required outcomes and unaffected choices remain accepted, 13 October 2026. Codex selects and freezes D1/D4/D6 v1 in [implementation-contract.md](implementation-contract.md) under the human's explicit Muse implementation authorization; this does not claim the human personally selected every syntax/API spelling or that the engine is implemented/qualified. Named/inline model/field traits remain distinct from named standalone custom Given keywords with genuinely novel implicit semantics; anonymous keyword prompts and prompts on applications are excluded. Ordinary When remains authored Can. Full retry regenerates every current prompt in the active app/build closure, including preferred styles; selective refinement and saved work remain supported. MCP-only submissions, enforced generator no-write access, cooperative leases, static prompts and row-bound views remain governing constraints. Earlier bounded-Given/do-prompt/selected-retry advice remains history. The launch consultation separately advises the selected contract, with weak/split keyword-surface advice and no implementation qualification. [Requirements](../../../specification/BUILD_GENERATION_REQUIREMENTS.md) own outcomes and [implementation-plan.md](implementation-plan.md) is the single execution view.

## Source forms

The following illustrates the frozen v1 source contract, not current compilable Can. Named/inline traits remain distinct from standalone custom keywords. Ordinary When remains authored Can. Earlier handwritten draft sources retain old rehearsal syntax and are not rewritten or qualified by this record.

```can
Given
 trait completable $"Add done:bool=false with Open/Done labels. Use the existing authorized update path."
 Todo {title:text trim min=1 max=200} completable
 Note {body:text} trait $"Add pinned:bool=false."
 keyword canonical_identity(target:model, field:field(target,text)) $"Use NFKC-normalized, ASCII-lowercased keys without changing stored spelling or permissions."
 Account {handle:text}
 canonical_identity target=Account field=Account.handle

When
 scenario complete(task:Todo) by=members
  do set task {done=true}

Then
 style TaskSurface $"Readable task surfaces, subtle borders, generous hit targets and visible keyboard focus."
 view TaskTile(row:Todo) $"Arrange admitted title/status and declared edit/archive controls." $TaskSurface
  edit fields=title,done
  delete
 page / title="Todos" $"A calm workspace that stacks on phones."
  card "Add a task" $"A compact entry area."
   form Todo.create fields=title
    input title
  list Todo as task $TaskSurface
   show TaskTile {row=row} $TaskSurface
```

The `$` adjacent to a JSON string marks a static generation prompt in every generation slot, with no interpolation, translation suffix or general runtime expression meaning. Ordinary strings such as `title="Todos"` and `card "Add a task"` remain values/descriptions. The marker never invokes paid generation during ordinary build/check/bundle; explicit selected generation invokes the configured CLI. `policy`, `unique`, `invariant` and `lock` are examples of existing statement-level declarations carrying implicit behavior, not built-in expressions to replace with prompts. Given supports named trait prompts for reusable attached model/field behavior, inline trait prompts for one-off attached model/field behavior, and distinct named custom-keyword prompts defining new standalone Given declarations with their own targets, arguments and implicit semantics. Anonymous inline keyword definition/application prompts are excluded. Custom-keyword acceptance requires novel behavior unavailable in current Can; composing/relabeling existing Can or supplying trait contribution/reuse alone is insufficient. The explicit keyword signature and standalone named arguments follow the frozen contract; declaration references expose metadata and checked constants, without runtime Given bindings. Ordinary When bodies stay authored Can; `$"prompt"` is invalid as a `do` body and does not establish a generation target.

Named traits and named custom keywords are definition-owned generation units; compatible applications reuse checked saved implementation without another model call. An attached inline trait owns a separate one-off model/field unit; no anonymous inline keyword prompt establishes a unit. Changing a shared definition reports affected applications, just as changing a shared view reports its uses. Model/field traits retain checked contributions applied in source order: model traits can add fields and supported model invariants/hooks; field traits add compatible constraints/defaults to their field, without sibling fields. Reject incompatible targets, duplicate contributions and contradictory defaults; traits cannot grant authorization or invent operations from a prompt. Their effects retain canonical operation/hook ownership. Named custom keywords instead define new standalone Given declarations with their own targets, arguments and implicit semantics; they are not merely named property traits. D1/D4 v1 select explicit signatures and checked owner-versioned producer bindings; future required kinds/producers receive concrete owner implementations and checks. Reject target/type/authority mismatches and conflicting contributions as applicable. New behavior, dependencies, effects or permissions must be compiler-visible and subject to normal owner admission; none may bypass canonical storage, permission, transaction or replay enforcement.

A prompted view's `edit`, `delete` and other supported canonical form/action declarations establish the bindings the renderer can arrange. They are not slots or arbitrary executable children. The compiler provides admitted row data, checked controls and existing presentation helpers. Browser code may enhance those controls and use canonical submission helpers. It must preserve field identity, version/CSRF data, validation feedback and focus behavior. Ordinary view children and instances use `$Name` or `$"prompt"` attachments on rendered components. A prompted view binds its renderer root/part hooks through the optional second style suffix on its own header, never through a `style` child.

The top-level owning Then `style TaskSurface $"..."` defines reusable CSS without an ordinary presentation body. Its two `$TaskSurface` attachments apply that CSS with separate compiler-owned instance roots/hooks; the inline entry-area style owns one independent one-off unit. A named definition is the sole logical generation association for that CSS, without prescribing a runner job per definition: uses share its saved CSS with zero AI per use and no copied generated output. Resolve names in the owning package/app Then namespace; initially admit no exports, cross-package imports, parameters or style inheritance. Duplicate/unknown/cyclic references and incompatible ownership or part contracts diagnose. Styles cannot change data or authority. A new compatible use consumes existing CSS without regeneration; incompatible hook/template contracts diagnose. Generation consumes actual checked use contracts, and refinement also consumes current saved CSS through the shared pipeline.

## Configuration

```toml
version = 1

[generation]
runner = "codex"
model = "YOUR_SUPPORTED_MODEL_ID"
max_attempts = 1
timeout_seconds = 600

# Optional complete runner/model pair, selectable with agent=fast.
[generation.profiles.fast]
runner = "opencode"
model = "PROVIDER/MODEL_ID"
```

Model strings are placeholders, not promised model availability. The shared runner/model pair is required for generation, never for an ordinary saved build. Profile pairs are complete; optional limits use shared finite limits when omitted. Native options belong to the chosen recipe and adapter, with no cross-runner inheritance. One bounded runner execution and 600 seconds per command are defaults; a CLI job may make multiple model/tool calls; larger finite settings are explicit. Limits bound each requested execution, rather than preventing later explicitly requested retry commands. Automatic repetition of known-failed work within finite bounds is distinct from manual full retry; unknown completion never triggers automatic repetition. Limits apply to each requested execution in the frozen compatible-recipe job grouping.

`frontend` is the reserved Then default: a configured profile of that name overrides the shared recipe; otherwise it resolves to shared. Given uses shared; ordinary When has no generator recipe. An explicit run profile overrides an owning declaration's optional `agent`, then the category default applies. Unknown explicit profiles diagnose. Children with their own generation units resolve their own defaults, rather than inheriting a parent's tool choice silently.

Choose `--settings FILE` instead of the root file when supplied, then apply explicit run overrides. Overriding the runner also requires an explicit compatible model. Report each effective field's origin. CLI authentication stays native and outside committed files. Optional native controls must be documented/enforced by the selected adapter. Recipe changes affect future attempts only.

## Identity and saved code

`can.generated/<unit-id>/` contains only the current unit's required files: `unit.json`, `server.js`, `browser.js`, `style.css`, compiler-readable `contributions.can` and owned assets as applicable. The compiler derives interfaces/imports/assets from checked declarations and current implementation; no second authored manifest is required. `unit.json` holds the opaque ID, source association, kind/target, `abi_version=1`, the minimal checked contribution/export contract and truthful original generation provenance. Original output fingerprints and current bytes are distinct facts.

Match a unique declaration using its owner, kind, optional label and normalized structural context, ignoring formatting/comments. A prompt-only change may retain an ID when the non-prompt anchor is unchanged and unique. Do not infer identity from a sole unmatched old/new pair, nearest offset or prompt similarity. A changed body/owner with insufficient evidence requires explicit `bind`: supply the inspected source location and source revision plus an existing ID, or request a new ID. Copies get new IDs. These IDs associate source and saved files internally; retry callers need not author or select them. Names are needed for trait/custom-keyword/style/component reuse, not retry UX. Named traits and custom keywords own definition units, compatible applications share them, and attached inline traits own one-off units; anonymous inline keyword prompts have no generation identity. Conflicts leave the saved group intact and make builds identify the association requiring reconciliation.

Ordinary direct edits to current JS/CSS are immediately build inputs. `adopt` is needed only when reconciling source/interface drift, not for every compatible byte edit. Candidates and execution records live under ignored `.can/gen/attempts/<unit-id>/<attempt-id>/`. Build-time agents submit structured CSS, JavaScript and other admitted generated content through the custom MCP session using opaque allowed targets, not arbitrary caller paths. The host validates target ownership, output roles and content and owns canonical isolated placement and metadata/provenance. Submission never overwrites current saved files; existing validation, leases, fences and conditional promotion govern acceptance. Historical source-controlled revisions and the one previous group retained at promotion provide explicit rollback targets; generation does not commit to Git automatically.

## JavaScript interface

Emit a versioned interface for each unit using checked source/contracts. The currently described `run(inputs, effects)`, pure synchronous `defaultValue(inputs)`/`check(inputs)`, and `render({row, bindings, ui})` with optional browser `mount(root, presentation)` returning cleanup cover illustrative keyword execution/callback and component choices. They are not a closed export-role list for new Given keywords. The selected descriptor exposes target, exact inputs/results, owner-versioned lifecycle/producer binding, reads/dependencies, effects/authority and bounds; it does not require lowering all behavior into existing built-ins. Admit only declared, checked integration. A renderer cannot mutate application state. No module runs merely to discover its schema or permission.

Compiler wrappers validate inputs/results with existing Can exact-value codecs. Native record handles retain admitted model/row/version associations; an arbitrary JS object cannot impersonate a mutation target. Effects are declared, admitted compiler-bound methods. They delegate to projected reads over the staged overlay, canonical writes and admitted deferred effects. Extend compiler/runtime integration as required by new keyword semantics while retaining those owners and enforcement. Contract mismatches diagnose; a new effect, permission or service capability is not granted by its appearance in JS. The existing method set is not an accepted ceiling.

Authors await effect calls in order. Permit at most one active call; overlapping calls or returning with a pending call fail the invocation. Validate/capture arguments before the call's await, reject calls after closure and retain any canonical failure even if JS catches its rejection. Later reads see earlier staged writes. Validate/project the final result before the existing single fenced commit. Failure/conflict commits nothing; canonical replay does not rerun generated code. This discipline does not prove every property of arbitrary JS control flow.

Server exports target the selected workerd configuration; browser exports receive admitted presentation data and checked action descriptors. Allow checked compiler producer imports and unit-local modules/assets. Privileged imports, raw storage/commit access and undeclared network effects violate the application contract. The initial feature accepts trusted project code, as ordinary application source does; import checks and target tests are not hostile-code isolation. Pure callback/render contracts prohibit side effects, but finite checking is not a proof of arbitrary JS purity.

Use existing actual-target examples for relevant success, refusal, failure/conflict and replay outcomes. CSS-only changes require CSS/render checks, not unrelated workerd invocations. Maps point to current saved JS, with the owning `.can` location alongside it.

## CSS boundary

Attach unit ownership and root/part hooks to existing rendered elements. Every selector-matching element belongs to its nearest style unit. Nested child roots additionally expose a parent host hook; a parent rule may style that host's placement, size and inherited inputs, but may not traverse into its descendants. Custom view instances and named style applications keep separate compiler-owned DOM roots/identity/hooks while sharing their definition's saved styling. Hook/template compatibility is checked at every use; no output is copied per use.

Parse saved scope-relative CSS, including supported nesting, and insert ownership guards on each element-matching selector compound. Support ordinary local selectors/pseudo-classes, parts, media/supports/container conditions and namespaced local keyframes. Reject global selectors/escapes, initially unsupported relational selectors, `@import` and `@font-face`. Use existing theme/system fonts. Namespace authored unit-local custom properties; shared theme variables are readable but not redefinable by a local style. CSS asset URLs must resolve to owned unit files; reject remote URLs and path traversal.

Scope enforcement applies equally to generated and directly edited CSS. Ordinary inheritance stays: parent typography/color, theme inputs and layout can change a child's appearance. Report those dependencies without claiming pixel isolation. Inspection walks checked trait/custom-keyword/view/style uses, returning the selected definition and all source sites and owners; validation can cover affected consumers. Targeted refinement may update that definition, while manual retry includes every generation prompt in the active app/build closure. Refining a selected named style changes its checked uses after acceptance while unrelated unit bytes remain unchanged; it does not regenerate those consumers. New compatible uses require no AI, and incompatible ownership/part/template contracts diagnose.

## Agent protocol and lifecycle

The private generation tooling host owns the custom MCP server/session lifecycle; no new package or persistent daemon is required. It supplies checked source/contracts, operation-appropriate captured context and opaque allowed output targets. Build-time coding agents must submit content through this server and cannot create or write source, current implementation or candidate files themselves. The runner enforces this restriction, disabling generic write tools and shell write access as applicable; prompt instruction alone is insufficient. Unsupported MCP transport or enforcement diagnoses before launch. Selected tools are `generation_context` and batched `generation_submit` of `{target,role,content}`; UTF-8 text and checked encoded binary assets use session-bound handles. Concrete transport remains adapter-specific. Multiple outputs may be submitted in one job; an MCP submission is not one AI call or prompt and does not force a provider job boundary. D6 selects whole-Then context per compatible frontend recipe and one complete acceptance set.

```json
{
  "version": 1,
  "request_id": "r42",
  "operation": "refine",
  "unit_id": "u17",
  "instruction_file": "change.txt",
  "accept": true
}
```

Required operations are `doctor`, `status`, `inspect`, `bind`, `generate`, `refine`, `retry`, supported `resume`, `diff`, optional `preview`, `validate`, `adopt`, `accept`, `cancel`, `reset`, `rollback`, `edit.begin`, `edit.end` and interrupted-lease recovery. `generate` requires `prepare` or `fresh`; retry uses normal active-app selection without per-prompt IDs/names. Other scoped controls retain unit/attempt selectors, explicit source revision for bind, and exactly one instruction carrier. Given preparation precedes dependent frontend consumers. Jobs group by compatible effective complete recipe, with each frontend job receiving whole-Then context and all intents/use contracts. All required retry outputs form one candidate set; incomplete/failed/conflicting sets retain current files. A CLI job may make many model/tool calls; scoped refinement remains supported.

The final result contains version/request/operation/selected IDs, state, paths, effective recipe, phase/validation summaries, structured errors and bounded next actions. Optional JSONL progress ends with the same final envelope. Exit codes: 0 requested outcome succeeded; 2 invalid request/config/selection; 3 conflict/held lease; 4 validation failure; 5 runner failure; 6 unknown completion. `accepted` and merely `candidate` are different states; requested acceptance cannot report success after candidate creation alone. A repeated request ID with the same input returns or recovers the existing operation; different input under that ID conflicts. It never launches duplicate provider work merely because the caller resends.

`refine` captures current edited files plus current intent/contracts and the new instruction. `fresh` captures the current group for conflict/rollback protection but supplies source intent instead of current code as the design baseline. `retry` freshly captures current source intent/contracts/recipes and regenerates all prompts in the active app/build dependency closure, including successful or preferred styles. It does not keep a preferred style unchanged or repeat only a selected failed capture. Unrelated apps in a draft repository are excluded; ambiguous active-app selection diagnoses normally. Existing current code and manual edits remain saved until explicit or agent acceptance. Reset/cancel do not delete working code. Unknown completion requires supported recovery or an explicit new attempt acknowledging possible duplicate work/cost. Reset/cancel/new acceptance fence superseded attempts before releasing coordination. Late outputs remain inspectable and never promote themselves.

## Promotion, direct edits and recovery

**Accepted BGEN 10 scope:** concurrent replacement protection covers agents/tools participating in the write-lease protocol. Direct editing remains supported. Arbitrary writers ignoring that protocol can race a comparison and replacement; neither the existing helper nor a journal can guarantee preservation of every such write. Observed conflicts refuse promotion. The human explicitly adopted this boundary, now incorporated in BGEN 10.

`edit.begin` returns a token and exact unit/source paths; end-user authoring agents then edit those files normally and release with `edit.end`. The lease is coordination, not an AI call, candidate approval or permission prompt. Capture/adopt/accept coordinate the relevant source paths and selected unit in a canonical lock order. A build takes read leases, refuses pending promotion journals, snapshots the required current inputs and compiles that snapshot. Long-running generation holds no write lease; unrelated units remain usable. This direct `.can` and saved JS/CSS edit workflow remains allowed for end-user agents. It does not grant the build-time generator direct file-write access; its output route is MCP submission to the host.

Acceptance obtains all relevant leases, compares the complete captured source/contract/target/current-byte/fence closure and confirms complete validation. Stage one run journal with all old/replacement groups; full retry accepts its required outputs together. Then replace files atomically per file, gating readers until commit. Incomplete/failed/conflicting sets change no current output. Retain one prior accepted set including direct edits. Scoped refinement uses the same mechanism at its affected scope. Qualify supported durable file/rename operations; unsupported guarantees diagnose.

Recovery under the same leases restores the whole old set for an uncommitted journal or finishes the whole new set for a committed journal. Unexpected bytes refuse destructive recovery and preserve both saved groups for reconciliation. Repeated recovery is idempotent; builds never consume an unresolved mixed group. A rollback is an explicitly selected compatible replacement using this same protocol.

Leases do not expire or get stolen automatically. A crashed writer requires explicit lease recovery after its process is confirmed stopped; unknown provider/writer activity stays unknown. The outcome guarantee is consistent consumption, retained current work on detected conflicts and finite explicit recovery under the cooperative protocol. Full hostile-code containment, uncooperative-writer CAS, arbitrary component APIs and global CSS generation are outside this initial scope.

Human-required outcomes remain governing constraints, and future target/producer integrations remain extensible through their owners. No engine/API/target qualification is claimed here.
