# Source migration coverage

Migration date: October 3, 2026. The inputs are the 39 app requirements plus WORKSPACE_OPERATOR, PORTFOLIO, ADMIN_SURFACES, root REQUIREMENTS and DESIGN. The business requirement documents remain the target; this report does not relax their completion criteria.

## Changes made

All 39 companion app sources were rewritten, including CanCustomer, CanReception, CanMail and CanReport. Focused names are preserved. Each now declares its own identity/description and `uses` membership in its actual business source. Seven portfolio compositions are declared alongside related business apps instead of in wrapper files. CanRent/CanMember retain their specified internal package splits. Shared locations, employees and suppliers have one source definition; customer/company identity belongs to CanCustomer.

The later composition migration removed all 47 app/context wrappers, their directory, and the authored build manifest. It omitted standard runtime/database/auth/team/theme setup and updated both reference examples. Business package bodies, operations, pages, fixtures and inline expectations were preserved at that stage. The assistant-created OperatorCore shell was removed, without replacing it with another scaffold. Retaining identical explicit file policies was a further repetition violation, corrected by the subsequent token audit.

The token audit inspected all 44 `.can` sources. R2/default upload policy is now implicit: 38 identical file declarations and 37 empty contexts are removed, leaving two contexts with actual queue/analytics resources. It also removed five explicit archive defaults, five identical create/update field lists and 53 unconditional lock predicates. Omitted lock conditions now mean true. These normalizations retain the former effective policy/allowlists/locks; business guards, permissions, operation identities and all inline expectations remain unchanged. Grouped imports from [the audit](../DECISIONS.md#token-repetition-audit) are now adopted; the other larger grammar reductions remain proposals.

The drafts replace inferred inputs, overloaded user/trusted handlers, implicit record binding and prose effects with typed parameters, query aliases, canonical CRUD, explicit guards/copies/locks, declared contracts and finite effects. Trusted handlers use `on`; business tools use `by`. Pages use the bounded daisyUI primitives with automatic HTMX responses. Source descriptions use `#`.

Payment, allowance, staff reservation, stock posting, document generation and credential requests retain source identity and pending/failed/unknown states rather than treating a delivery receipt as fulfillment. Commercial booking terms are copied from the catalog, not supplied by the buyer. Customer roles, employee location grants, published commercial catalogs and moderation responsibilities are separated.

There are now 52 inline example tables across all 39 app sources. They include success, invalid-state, permission, month-end/leap restoration, cross-year calendar coverage, delayed-event cutoff, source freshness, attachment preservation/renewal and selected capacity/budget cases. CanExpense and CanContract use the specified finalized-file fixtures for positive attachment examples. Example tables are authored expectations, not executed tests or complete acceptance coverage.

Deployment bindings on package imports are requirements for installed implementations. A name such as `deployment.billing` does not generate or discover a service. Ingress/egress mappings, authentication, signature checks, replay handling and result correlation must be implemented and reviewed. The typed invoice and staff-scheduling ingress handlers provide concrete owner-side boundaries; room/membership and several other integrations still need equivalent owner-side coverage. A driver must not invent missing business operations.

Focused and composed app declarations are alternative assemblies. Composition deduplicates shared canonical local packages; separate deployments cannot treat imported canonical models as immediately consistent remote data or bypass permissions by sharing a filename. Role assignment and scoped directory-read grants also need deployment configuration; importing Customer does not give every sales or finance user customer-management authority.

The new schema-evolution contract does not retroactively establish an upgrade from any earlier draft. CanMember's frozen calendar values require actual historical anchors, zone and interval; a mutable current plan is insufficient. CanLeave's stored-year removal requires its predecessor definition and review of any preserved historical meaning. CanCatch's raw-payload record split cannot be expressed by this one-old-row/one-target-row subset; it needs a separately defined extension or installation with no predecessor data. Unknown baselines, record splits/merges, team/parent/physical-authority transfers and unsupported pending-work conversions block upgrades. The hypothetical migration in DESIGN illustrates syntax only; all 44 source files remain unchanged in this schema-evolution round.

### Package-owned interfaces

The user requested the import/export change be applied to the sources. Interfaces now live in their owning packages. `export` prefixes the existing declaration, avoiding separate name lists; `use` resolves it in the consumer. Local operation calls keep their existing atomic/authorization rules. `use invoice {BillingV1 as Billing} from=deployment.billing` binds an exported service interface with the existing asynchronous send/event semantics. Business contracts moved into invoice, reservations, membership, scheduling, stock, work queues, reports, reception, support, proposals, affiliate settlement, heartbeat and error packages. The overloaded SourceV1 was split into work, report and sales interfaces. The common Outcome shape is represented once by the standard `std.OperationOutcome` type.

The compiler derives executable local dependencies and schema-only external dependencies from composition/import declarations; no authored source inventory is needed. A bound import uses the owner's exported schema without adding that owner's database records, UI or background handlers to the consumer. Imports grant visibility, while existing permissions and source restrictions govern invocation. Separately deployed applications additionally need installed bindings, defined delegated identity or service authority, version compatibility and result correlation. Exporting a custom capability does not automatically implement it or map it to a trusted handler.

Review source/version/delivery bookkeeping for reusable runtime metadata, preserving business source identities where they link durable records across operations. Separately assess common services such as PDF generation and incoming email as standard capabilities. Room reservations, membership eligibility, commissions and report measures retain application-specific rules; their presence here alone does not justify compiler knowledge of these products. Custom external-provider mappings still need explicit contracts.

Other proposed reusable workflow/service facilities remain brainstorming candidates. Import/export and app composition are now recorded in DESIGN and the source drafts. Three later JEV consultations assessed composition alternatives, including local versus schema-only imports, but not the complete grammar or migrated source catalogue. No compiler/runtime has implemented them.

### Exact grammar and initial parser follow-up

[GRAMMAR](../GRAMMAR.md) now fixes logical statement/attribute boundaries, contextual production selection, uniform reusable type paths, bounded suffixes, query extent and inline versus indented forms. [The initial parser](../tools/can_parser.py) builds syntax trees with physical start positions for declarations, expressions, types, effects, routes and examples.
