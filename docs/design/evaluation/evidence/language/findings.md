# Consolidated language/business findings

Static contract evaluation against `../../baseline-20261004T041647Z/snapshot/`. These are supported source-level causes, not executed failures. Severity describes the affected required workflow; it is not a product-wide verdict. Recommendations are proposed, not applied. File/line references below are within that baseline.

## L1 — A submitted expense may name someone unable to decide it

**Company/task:** P, J2 eligible assigned reviewer and recovery. **Type:** app omission; significant trust/workflow friction.

**Evidence/cause:** `draft/CanExpense.can:40` permits draft authoring; `:42–44` submit checks a distinct reviewer and `can_work(reviewer,location)`; `:21` then locks reviewer with the submitted evidence. `draft/shared/Employees.can:9` tests only active employee, active membership and location. The Employee `role:text` (`:6`) is work description, not `expense.reviewer`. `decide` (`CanExpense.can:50–57`) requires both the declared reviewer role and the assigned account. DESIGN.md:276,280–282 makes those explicit independent grants. A valid active colleague without that role can therefore be assigned and submitted, but cannot decide; no submitted reassignment/withdraw path appears among the five scenarios. This violates the app's eligible-reviewer outcome (`CanExpense.md:11,15,29,54`). Root independently confirmed the causal trace. An owner could grant the colleague a new reviewer role, so this is unreviewable under current assignments, not a claim of permanent impossibility.

**Smallest improvement:** add the existing `reviewer(expense.reviewer)` subject predicate to submission eligibility. Define a narrow authorized recovery for a later reviewer revocation (for example cancel/supersede the undecided submission and create a new draft with a replacement reviewer while retaining evidence); do not remove the submitted lock. **Benefit:** fewer trapped claims and no authority-expansion workaround; amount/receipt history remains intact. **Tradeoff:** one admission predicate and an explicit recovery business decision/example; adding a role does not by itself solve later revocation. **Re-evaluation:** under the same P actors, try active nonreviewer, valid reviewer, self, reviewer revoked after submission, and stale recovery; retain receipt and decision history. Source trace can establish guards/paths; execution remains later validation.

`submit` also omits current claimant location authorization, unlike CRUD/correct (`:40,:67`). The requirement sentence at `CanExpense.md:21` follows the correction description, so this is an explicit clarification for P's current-scope rule, not an additional proven universal language defect.

## L2 — Periodic work can stop completely above its bound

**Company/task:** W composed booking/candidate cleanup; outage and growth recovery. **Type:** app progress defect under a concrete backlog; significant.

**Evidence/cause:** DESIGN.md:334 defines `for limit=N` as all-or-nothing failure when more than N results match. `draft/CanBook.can:239–272` runs ready and cleanup once per minute across the team's matching attempts with limit 100; `draft/CanPropose.can:253–263` scans expiring/releasing revisions with the same bound. With 101 eligible rows, the first scan fails without changes. The next tick has the same 101 rows, so it cannot drain them. CanBook's successful cleanup eventually sets `released` (:271–272), which is good exclusion once reached; it does not rescue a batch that cannot start. This is conditional deterministic reasoning, not evidence that W already reaches that backlog. Bulk cancellations or delayed delivery can accumulate it without changing W's 3,000 bookings/month scale. All five periodic handlers and 214 written bounded loops were inventoried in `corpus.json`; not every bounded loop has this defect.

**Smallest improvement:** trigger one existing typed per-attempt/per-revision continuation from each transition, using existing `emit`/`schedule`, and process it under the same guards and identity. For a periodic catch-up contract that truly needs batches, specify resumable selection and progress before claiming support; simply raising 100 moves the failure point. **Benefit:** backlog drains independently of total eligible count; per-record scope avoids repeatedly scanning unrelated work. **Tradeoff:** more durable work identities/dispatches and cancellation/retry obligations; per-record work may increase provider/storage cost. **Re-evaluation:** same success/compensation cases with 99, 100, 101 and 1,000 eligible records, provider delay and duplicate occurrences; assert every eligible record progresses, no repeated charge/release, original commitment remains. Draft traces establish no global all-or-nothing scan; latency/throughput need later execution.

## L3 — Some inline examples do not describe valid business invocations

**Company/task:** W J4 delegate revocation and company review; language-wide trust in colocated examples. **Type:** example defects plus narrow test-actor contract omission; significant specification friction.

**Evidence/cause A:** `draft/CanMail.can:45` requires every stored Delegate to reference a verified Contact. Assume no second verified Contact for that account in the company, as in the example. The collection example seeds `delegate` and `delegate_contact` (`:116`) and sets the latter unverified in `:121`, expecting `error(rule_failed)`. DESIGN.md:382,390 requires fixture overrides to satisfy invariants before invoking. This row fails setup, never demonstrating collect's rejection. More deeply, a production contact verification revocation while that Delegate remains stored conflicts with the same invariant (even setting delegate.active=false does not remove it), while Delegate delete is disabled (`:68`). Root independently confirmed the invariant/setup causal trace. The ordinary denial outcome is correctly expressible by current `permitted_collector` (`:35`); using current eligibility as a permanent historical invariant obstructs revocation.

**Smallest improvement A:** retain immutable relationship validity, put current verification/active eligibility at Delegate admission and collection decision, and keep historical inactive grants after revocation. Keep a valid rejection row for inactive delegate; add current-contact revocation through a valid production transition. **Benefit:** ordinary revocation works and example observes actual rejection. **Tradeoff:** author must distinguish historical relationship validity from live eligibility; deliberate current-query checks remain necessary. **Re-evaluation:** revoke verified contact with existing delegate, then collect; reject without erasing history. Test setup must succeed first.

**Evidence/cause B:** DESIGN.md:380 defines `as=members` and declared roles as the same `self` account, plus public/outsider, but does not define `authenticated` as a test selector. Mail :71,81 use that selector. More decisively, Mail :74/:83 expect `members -> error(forbidden)` for `by=authenticated` operations even though self has the seeded administrator/recipient identity. `draft/CanCustomer.can:56–57` assigns those to self; `has_role` at :26 does not reject operator membership. A member is authenticated and does not lose its seeded customer identity. This is not an auth implementation absence.

**Smallest improvement B:** explicitly define the needed signed-in external test actor using the existing actor-selection surface and state which account/membership it receives; correct member cases to their actual authorization outcome, and test denial with an independently unauthorized account/grant. **Benefit:** separates “signed in,” operator membership, and customer authority in reviewable tests. **Tradeoff:** a little test-context specification; never make production `authenticated` exclude staff just to satisfy a table. **Re-evaluation:** evaluate identical self identity under member/customer roles, external signed-in unauthorized account, public and revoked grant; derive exact forbidden/rule_failed from by/guard order.

**Evidence/cause C — bounded later experiment:** Both matched expense-layout subjects require a third distinct current member for the representative positive claimant → first reviewer → finance approver case, but DESIGN.md:380 supplies only self/other in the row team and outsider in another team. Selecting a role still invokes as self. Single layout `after/ExpenseWorkspace.can:89` and packages layout `after/CanExpense.can:102–103` independently record the limit. Their guards express the production separation of duties; the gap is faithful test setup, not the production workflow. Using outsider in a seeded historical state may pass local equality checks but does not establish the same three-current-member journey. See [final experiment review](experiment-final-review.md) for precise scope and source references.

**Smallest improvement C:** specify test-only additional account/membership/role provisioning and binding through the existing fixture/example surface. **Benefit:** positive separation-of-duties cases become expressible without fake outsiders or production scaffolding. **Tradeoff:** deterministic account setup and caller selection require a small explicit contract. **Re-evaluation:** three current actors, successful finance approval, finance rejection/correction retaining both old decisions, threshold/stale-version denial and gated reimbursement. This is a narrow missing contract; no syntax or implementation is proposed as already available.

## L4 — Optional business connections are mandatory in current package closures

**Company/task:** W J4 physical mail with external paid-service evidence and no automatic fee invoicing; adoption of a useful focused app. **Type:** app/package composition friction, not proof that small apps require separate deployment.

**Evidence/cause:** CanMail.can:25 permits `term=null`, paid evidence and `billing=false`. Yet `:7` imports executable member_terms, `:8` locally imports invoice.Charge, and `:9` binds Billing. DESIGN.md:81,89 includes entire executable owner packages for local production symbols; no declaration pruning is assumed, and unknown capability implementations fail deployment (:551). Thus avoiding runtime fee sends does not omit provider setup or the imported invoice/membership closures. CanRent.can:40 similarly imports propose value types/pure function through ordinary local dependency semantics, which also includes proposal workflows, Mail, Rooms and Documents imports (CanPropose.can:6–13). File separation alone changes nothing.

**Smallest improvement:** first move shared value contracts/pure helpers to a coherent existing or deliberately named contract owner, and place optional integration workflows in selectable packages where the same models/operations stay with their owner. Where a bound interface already supplies the value schema, import that schema in the existing bound group rather than creating an extra executable dependency. **Benefit:** truthful standalone setup and smaller agent context/dependency obligation. **Tradeoff:** a few explicit package/import boundaries, and integration variants must still preserve one owner and canonical operation; this is not free pruning. If a clean split cannot preserve the workflow, compare a narrow optional connection contract in E102 rather than fake bindings or copied app files. **Re-evaluation:** compose a paid-evidence mail app with no invoice/membership provider and the full W variant; compare reachable runtime bindings, same privacy/collection paths, no duplicate owner, identical identities after file moves. No claim of measured provider savings until A/C costs are supplied.

## L5 — Report completeness is carried but not enforced consistently

**Company/task:** W J3 source-truth reporting. **Type:** app/contract inconsistency, independently confirmed by Root.

**Evidence/cause:** CanReport.can:21 carries `Checkpoint.complete`; :47–49 checks only location inclusion and copies state; :56 refuses pending/null/partial/unavailable but does not check complete. A typed fresh checkpoint with complete=false and empty rows reaches numeric aggregation (:58–67); renewal/backlog is zero and cash zero when currency selected. CanReport.md:34,52 forbids missing/partial source data as exact zero. A producer may intend fresh=>complete, but that implication is not an invariant in the displayed contract. An explicitly complete empty source must still return genuine zero. Root independently checked the schema/receiver path and found no declared implication forbidding the input combination; DESIGN.md:171 defines empty numeric sum as zero.

**Smallest improvement:** enforce checkpoint state/completeness consistency at existing ingress and refuse exact measures when complete=false; identify every expected source in the aggregation contract when reports span producers. **Benefit:** incomplete producer evidence cannot silently look like inactivity. **Tradeoff:** some useful partial numbers need explicit labels rather than a single exact result; adapter and app agree on one completeness definition. **Re-evaluation:** fresh+complete+empty, fresh+incomplete+empty, unavailable, lagging complete, missing producer, mixed currency, duplicate reversal and changed source revision at the same report boundaries. Retain valid zero-denominator behavior. Execution remains unverified.

## L7 — Historical SaaS intake is not the same operation as current CSV creation

**Company/task:** P's2,000 historical receipts/records and W's20,000 bookings/5,000 invoices. **Type:** required migration workflow not fully specified for these replacement cases; audience/scope condition.

**Evidence/cause:** DESIGN.md:607–615 imports the current writable operation schema, at most1,000 rows/review, with per-row checks. File inputs require authorized control/binding (:611), not CSV opaque IDs. Canonical metadata is protected (:101); Expense create exposes draft fields only (CanExpense.can:40), while submitted decisions/reimbursements are locked (:21–24). **Smallest improvement:** specify one bounded steward-assisted import protocol using canonical authorized intake for valid current records plus explicit historical evidence/date/provenance mapping; where past authority cannot be reconstructed, retain a readable immutable archive with links and disclose the limit. No guessed old schema or silent status mutation. **Benefit:** honest switching effort and preservation of required company evidence. **Tradeoff:** mapping/review/support and possibly retained archive subscription; bulk-file handling and source validation need a stated contract. **Re-evaluation:** import P's same two thousand receipts and W's linked booking/invoice sample, with duplicates, missing source account, invalid file, partial success and retry; compare exact evidence/references and staff effort. Inspectability is possible now; time/correctness measurements require later implementation/data access. This is not a claim that no import can be designed with existing constructs.

## L8 — Resource history repeats the entire growing booking collection

**Company/task:** W accurate historical utilization and affordable ordinary booking changes. **Type:** app evidence structure with a demonstrated growth cost; significant, magnitude conditional.

**Evidence/cause:** CanRent.can:159–165 defines a locked ResourcePolicy whose value contains every current resource.Booking and VenueReservation plus windows/downtime. It is appended after many state changes; quote_accept :749 and :753 appends twice in one operation. Historical reporting :241–254 reads all those policies and their embedded collections to reconstruct boundaries. No ResourcePolicy retention is declared. For B sequential nonarchived bookings at one resource and only one snapshot per creation, logical booking-value copies are at least B(B+1)/2; actual extra state changes add more. B=100 gives5,050 copies, B=1,000 gives500,500, without guessing serialized bytes or runtime latency. Snapshot copying itself is visible in desired MJS; C confirmed materialization and55 call sites. The source purposely preserves historical source truth; simply using current mutable rows would invalidate reporting.

**Smallest improvement:** first coalesce redundant intermediate snapshots within the same committing operation when only the final same-admission state is observable. Then compare narrower immutable resource-policy changes and booking/occupancy facts with stable identity/revision against bounded full checkpoints. Preserve the same historical numerator/denominator/timezone and missing-history result. **Benefit:** smaller owner work and retained history while keeping truthful reports. **Tradeoff:** delta reconstruction/checkpointing, late corrections and retention become more explicit and harder to review; bounded full snapshots can be simpler for a very small retained horizon. E102 assesses this tradeoff rather than prescribing a general event-sourcing primitive. **Re-evaluation:** same historical report before/after bookings, cancellation, revised capacity, daylight-saving dates and late checkout; measure logical facts/materialization at100/1,000/10,000 bookings, and compare exact report contributions. Provider CPU/storage/limits and latency remain future measurements, not asserted failures at W's aggregate workload.
