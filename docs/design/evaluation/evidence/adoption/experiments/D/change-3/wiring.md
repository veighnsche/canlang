# Necessary project wiring (draft)

Copy `equipment/` into an ordinary Django 5.2 project. Include `path("", include("equipment.urls"))` in its root URLconf. Add `equipment` alongside the standard `auth`, `contenttypes`, `sessions` apps; enable the standard session, CSRF, authentication and security middleware and DjangoTemplates with APP_DIRS plus request/auth context processors. Set LOGIN_URL, LOGIN_REDIRECT_URL, LOGOUT_REDIRECT_URL as in test_settings.py. Host-owned SECRET_KEY, allowed hosts, HTTPS, secure session/CSRF cookies and database credentials are deployment configuration, not supplied secrets.

Production concurrency contract: PostgreSQL (Django backend); `transaction.atomic` and `select_for_update` serialize owner mutations/intake and protect versions. SQLite test settings only exercise sequential expectations; SQLite does not provide these row locks. Generate the initial migration from these models with `manage.py makemigrations equipment`, then apply it. No migration history or existing records are assumed. No admin routes are exposed for requests/evidence/intake: they would bypass the application policy unless separately constrained.

Operator provisions Company(pk=1), departments A/B/C, 25 Django users and Memberships using ORM/framework administration; exactly these three department codes are allowed, and operational setup must create all three. User.username must be the lowercased full email (<=150 chars); set the email field to the same address. Passwords use create_user/set_password. Membership is the current department; manager assignments use Department.managers. Finance/operation job labels and Django staff/superuser status confer no application scope. Provisioning is intentionally not exposed to ordinary employees. No open registration or invented employee-directory provider.

Official MCP Python SDK 1.26.0 FastMCP stdio adapter: a trusted company-operated MCP client launches `python -m equipment.mcp_server` with DJANGO_SETTINGS_MODULE and EQUIPMENT_MCP_TOKEN in its protected environment, sharing the Django project and database. Browser login + CSRF-protected POST issues an eight-hour signed token. Every asynchronous tool calls one sync_to_async(thread_sensitive=True) adapter, which revalidates token_user and calls the same synchronous service function as the browser; no ORM runs in the SDK event loop. Set CONN_MAX_AGE=0 for the MCP process. Staff use forms/chat, not source. Client operator configures the subprocess/credentials once; the selected chatbot must support stdio and protected per-user credential configuration. That client integration is external wiring, not claimed as a supplied chatbot product or automatic OAuth. No network MCP endpoint, custom SDK transport or authorization server is invented. Password change/user disable/membership disable prevents subsequent tool calls; browser logout alone does not revoke the independently authorized eight-hour token.

Draft tests: with dependencies already available, from this initial directory run `python -m django test equipment --settings=test_settings`. Tests use Django's test schema creation, not a migration claim. This attempt only parsed Python syntax; Django/SDK are absent from the generation environment. No application execution, browser rendering, SDK handshake, database lock test, accessibility audit or deployment was performed.
