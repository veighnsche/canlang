# Conditional ownership economics

These calculations are scenario arithmetic for hypothetical profiles P/W in journeys.md, not provider invoices, market subscription quotes, customer interviews or measured engineering estimates. Horizon is 24 future months; economic amounts use USD scenario units without currency-conversion claims. Business workflow currency remains EUR. Existing sunk implementation spending is excluded. Sources: frozen REQUIREMENTS.md:9–17, DESIGN.md:15–19,81–91,493–550,741–824; C's primary-provider evidence in `../../interfaces/provider-facts.md`; B's rules/behavior handoffs. Low/high are deliberately materially different support assumptions; neither is a statistical bound.

Formula: net savings = `(24 - overlap months) × actually avoidable monthly subscription - incremental future setup - 24 × incremental recurring ownership cost`. Recurring difference includes technical steward, employee/admin work, platform/service provision and incremental providers on BOTH sides. Retained email/accounting/payroll/payment/access services cancel only if actually equal; additional paid seats, tax, commitments or usage must be added explicitly. One composed Can solution earns one avoided suite bill, not one bill per module. Low-code/configuration incumbent costs are included as future setup and ongoing staff/steward work; no assumption incumbent untouched costs zero.

## Workload drivers and source effects

P: 80 expenses/month; at 2MiB receipt average, about 160MiB/month plus preserved corrections/audit and backups. At 24 months about 3.75GiB new receipt bytes before retained initial data and physical disposal. This is byte arithmetic, not measured storage compression or bill. J1 requires no outgoing email or payment binding merely to create a private record tool. W: 3,000 bookings, 500 invoices, 300 mail items and 30,000 notices/month; byte/operation cost depends on actual attachment size and provider mapping. Replay/status receipts and fixed outbound content are part of ownership cost and truthful outcomes, not optional complexity to delete for shorter source.

CanDo's `poll=5s` active-session refresh (CanDo.can:134; DESIGN shared polling) yields 720 ticks per active user-hour. 12 staff × 2h/day × 22 days = 528 staff-hours/month -> 380,160 visible refresh opportunities/month; its five-source work mapping can create up to 1,900,800 remote source calls absent suppression/coalescing. Source contract states hidden/session stop, one chain in flight and coalescing, so this is an intentionally loose upper scheduling bound, **not observed traffic**. CanDo is optional for W's selected replacement: exclude its bill when unused. Review longer polling/explicit refresh under the SAME freshness/task-availability criteria before recommending a default change; performance/efficiency is unverified.

B identifies concrete fail-stop backlog in CanPropose expiry scans: `for ... limit=100` plus DESIGN.md:334 all-match budget can reject every run at 101 matching rows. This is a source-contract consequence, not measured runtime throughput; W 3,000 bookings/month can plausibly form an outage burst, frequency unknown. Smallest remedy owned by B: reuse stable bounded continuation/checkpoint work so each tick advances without losing permission/replay/cleanup guarantees; additional cursor/work state has cost.
