# Owner-state searches in mutation rules

Status: the initial source-`Require` and confined any-plus-first repair is
implemented. A checked void `first` null branch can now use one owner-selected
row as its authorized update target or create when absent; copied selected
fields without separate value proof are refused. `CanCustomer.accept` now
composes the helper `all` observations with the direct any-plus-first pair,
matches its final Emit, and stages exactly one declared event in the owner
transaction. Hidden rows, unrelated parents, races, and an unrelated Mail
binding have installed-runtime coverage. Other consumer-specific proofs
remain future work. The observations below describe the runtime before the
repair. The latest recovered-draft 2026-10-21 24-source compile has 86
diagnostics (`complete:true`, `omitted:0`). Earlier repairs cleared nine of the
fourteen helper-contained `ChildOf` guard refusals, while
five remain. Two viewer `first` sites cleared. Nineteen original `first`
correspondence diagnostics remained in the preceding 87-diagnostic capture;
the original `CanCustomer.accept` refusal is the one newly cleared site, so
eighteen remain.

## Contract and observed break

A mutation `require`, CRUD `when`, lock, invariant, or trusted-handler decision evaluates its pure queries and helpers over bounded state at its storage owner. The evaluation site determines authority; a helper declaration does not carry owner authority into a viewer call. A decision's data is available to decide the operation, but is not a read grant or a result-disclosure dependency. Ordinary queries and `read=true` bodies remain viewer-filtered; an explicit `read=true scope=authority` report has its own declared output boundary. This is the contract in [DESIGN §4](../specification/DESIGN.md).

The [runtime reproduction](../zero-diag-big-three.md#1-searches-inside-rules-historically-30-diagnostics) isolates a compiled leading `require not has_block(anchor, actor)`. A hidden blocking `Secret` row is present in owner state, but the mutation commits because the helper's `any(Secret...)` scans the caller's visible domain. An unreadable `Anchor` is also rejected before the guard despite valid mutation admission. Removing `active_member` from the helper prevents the otherwise identical guard from reaching evaluation. These are three separate failures: wrong scan authority, an extra viewer-read prerequisite, and proof coupled to a membership builtin.

The narrow source-`Require` profile already compiles and runs, so the original “~30 searches refused” description is not a current diagnostic count. The 2026-10-20 91-diagnostic capture contains no direct source-`Require` refusal. This design concerns a real runtime correctness defect and the adjacent proof gap; it does not claim that the other diagnostics share its cause.

The 2026-10-18 “general native query and pre-write guard composition” entry in [DECISIONS.md](../specification/DECISIONS.md) says the implemented contained source-data query still projects candidates through ordinary read policy. That describes the current bridge, but conflicts with the general decision-authority rule in DESIGN §4 and with the hidden-blocker reproduction. This design chooses the language contract: the decision uses owner rows, while result and viewer reads keep their own grants.

Further compiled-runtime probes cover a direct leading `require not any(anchor.Secret as secret, ...)`. It emits a native receipt but still commits past a hidden child blocker. Inspection of the emitted module confirms that this direct expression uses `nativeScenarioRequire` and `executeScenarioReceiptRequire`, the **same source-Require path** as the root helper. A root `Secret` query whose predicate reads `secret.parent` also exhibits that path's viewer-filtering mismatch. A separate admitted any-plus-first composition does use `executeScenarioReceiptAny` and State's `executeScenarioReceiptQueryMode`; a hidden active child and visible inactive child make its leading guard pass incorrectly and let a `D` create commit. With only a hidden inactive child, the guard passes but its later decision-only `first` returns null and rejects incorrectly. Thus two distinct runtime seams and two query consumers within the second seam are observed, despite similar surface syntax.

Other boundaries are distinct: a visible row with `blocked` withheld returns `forbidden` instead of the business verdict; a model with no `.read` policy lets a blocking row be ignored; 200 nonblocking rows pass the owner work bound and 201 fail closed with `Owner mutation query exceeds its row bound.` A helper containing `any(anchor.Secret...)` does **not** enter the source-`Require` profile: `source_require_any_member` recognizes a declared stored array field, not an implicit `ChildOf` collection. It emits no receipt disclosure; with `active_member` installation fails for lack of that disclosure source, and without it the generic scenario fails on the ruled model. The direct contained `any` is admitted by the separate `source_require_contained_any` checker. Both admitted root and direct child guards then reach the same viewer-projection bug.

## Chosen boundary

Give an authenticated decision occurrence a private **owner-decision observation**. State issues it only while executing the genuine admitted operation at the occurrence's original stage, with the admitted owner, team, fixed `now`, source identity, model parameters, and bounded owner view. Cloudflare binds the checked generated guard to that observation. The generated helper receives the same observation through its existing context, so a nested query inherits the consuming site's authority. No caller input, source-visible `authority` option, ordinary `read-predicate` callback, or public storage port can create this mode.

This should be a distinct State/Cloudflare path, backed by the existing `OwnerModelPolicyViews` and owner navigation. Do not broaden `readRecordsAtSourceObservation`'s `read-predicate` lifetime or turn on its `read-policy` control flag globally: both serve viewer reads, and the latter projects policy fields rather than the full decision row. The existing CRUD candidate path already demonstrates bounded `views.final.query({authority:'owner'})` plus native row views; the source-`Require` bridge should use the same owner-session boundary rather than a second storage authority system.

There are two reproduced runtime seams for this private decision mode. The source-`Require` adapter must receive owner rows instead of projecting its anchor and scans through `.read`. The receipt-query `any` in the admitted any-plus-first composition must evaluate its checked leading-guard predicate over the complete owner domain; currently `executeScenarioReceiptQueryMode` feeds that domain into viewer-only `queryRecordsObserved`. A private owner-domain evaluator must preserve candidate order, checked CONTROL-field markers, short-circuit, and query handle. The companion `first` is a separate occurrence: in the tested source its selected row is used only by `require c!=null`, so that decision must see the owner domain too. A generic query option must never switch a result-bearing or viewer query into owner mode.

Classify each query occurrence through its checked use-def closure, including pure helpers and local `let` aliases. Mutation `require`, effect-controlling `if`/`match`, and target selection for an authorized write consume owner decisions at their original stages. An ordinary `read=true` body or a query used only to form a viewer result stays viewer-filtered; an explicit `scope=authority` report is a separate authored disclosure boundary. When one selected row serves both a mutation decision and a return, select it once under owner authority at the authored stage, then enforce the return's own row, field, control and replay disclosure; a hidden selected row may decide the operation without becoming a readable result. The same rule applies to fields copied into effects or external payloads: their destination and transport need their own checked flow, and the private guard observation alone supplies none. If the compiler cannot prove every consumer of a mixed binding, refuse that shape explicitly. Re-evaluating the query later under viewer authority would change which row was chosen and break source order.

Give generated code only an opaque, stage-bound selected-row handle with getters for the fields and relationships in that checked closure. Raw owner rows, unchecked field access and an untracked cast into a result or effect must remain unavailable. A mixed query keeps one original selection but separate execution and disclosure dependency records.

This matters for the original diagnostic group: of 21 first-query correspondence sites, six are derives whose authority depends on where they are invoked (two occur in `CanRent`'s explicit `scope=authority` report), two are ordinary `read=true` preview queries and must stay viewer-filtered, and thirteen are mutation-body queries with varying branch, effect, guard and return consumers. The proof should follow each actual call site and binding, not label all 21 as a single owner-query profile.

The thirteen original mutation-body sites break down by actual use, rather than by the `first` syntax:

| Sites | Selected row's consumers | Required treatment |
| --- | --- | --- |
| `CanCustomer.accept`, `CanInvoice` commercial history, `CanMember` renewal and seat (4) | Presence/branch and an authorized create or update target | Owner decision selection at the original `let`; pin the selected row for the subsequent write. |
| `CanBook` previous attempt, `CanInvoice` defaults, `CanRefer` credit, `CanRent` adjustment, `CanLeave.request` category and allowance (6) | Guard/branch plus fields or references used by later effects | Owner decision selection; separately prove each field/reference flow to its effect sink. A send payload does not inherit the guard grant. |
| `CanRefer.settle`, `CanPurchase.receive` (2) | Idempotency decision and possible `return existing` | Owner decision selection; returning the selected row requires independent current and replay-time result disclosure. |
| `CanEvent.change_schedule` (1) | `retained?.account` copied into a new row, with no guard use of `retained` | Keep ordinary viewer authority unless a separate, explicit effect-source authority contract is established. This occurrence cannot borrow owner-decision authority from nearby guards. |

The four other derive sites are `CanInvoice.first_paid_invoice`, `CanRefer.latest_capture`, and `CanShift.previous_work`/`next_work`: their invocation in a mutation or handler decision gets that site's owner authority, while the helper declaration itself grants none. The two `CanRent.saved_rows` occurrences feed an expressly authorized report result, whose `scope=authority` and output proof own their disclosure. The two `CanLeave.preview` occurrences are ordinary viewer reads. This classification fixes the semantic lane for the original `first` diagnostics; accepting each source shape still requires its exact compiler correspondence.

At that boundary:

- Bind the first required Model parameter to its exact admitted row and version. Bind further Model parameters, when supported, through the same owner session and their admitted versions. Do not project either through `.read` merely to decide the mutation.
- Read the complete, bounded owner model/parent domain before applying authored `where`, `any`, `all`, `count`, `first`, or ordering. Include an empty domain in the observation. Use the owner's archive, expiry, team, parent, and row-work rules; exceed a bound with an error, never a truncated answer. Decode fields and references from genuine owner rows through owner navigation. A missing read policy is no obstacle to a decision read.
- Keep generated predicates pure: no effects, raw storage, recursive diagnostics, or fabricated row/reference binding. Preserve authored evaluation order, lazy branches, short-circuit and error propagation. `any([])` is false, `all([])` true, and `first([])` null under the existing language rules.
- Keep `active_member` and role facts on the admitted Identity/team observation, with their own exact checked occurrence and live revalidation. They do not select row-query authority. A guard with zero membership calls is valid and still needs the same source proof.

## Source proof without a membership dependency

The compiler already has two useful facts for source-`Require` guards: a `CheckedDecisionSite` at the leading/body `require`, and an independently recollected boolean observer in `serialize_scenario_requires`. The verified JS module associates the original emitted function with source, owner, node, statement, typed parameters, and complete call closure through `canScenarioRequireSource`. Use these facts to publish and load a bounded **scenario-Require site inventory** independently of `canMembershipSources`. Direct contained `any` belongs to this inventory too; its compiler admission has a separate exact-domain proof, while its runtime observer is the same. The any-plus-first composition instead emits a checked `queryAny` call record, source query ID, predicate callback marker and exact leading-`require` stage. Bind its owner-decision mode to that original occurrence and active mutation frame; a bare `queryAny` descriptor or callable predicate is insufficient. Its later `queryFirst` metadata already pins source, query, `let` binding and statement spans, while today's `guardConsumed`/`presenceConsumed` marks cover only narrow single-query skeletons. Extend that checked correspondence with the exact consuming `require` and complete use-def closure; do not infer decision authority merely from a nonnull `first` result or relax it because another query shares the operation.

For a helper's implicit `anchor.Secret` collection, the compiler should prove the whole substitution from the helper's formal `anchor` through every checked call frame to the admitted, versioned scenario parameter. It must verify that `Secret` is declared `ChildOf` that exact parent model and that the runtime domain is restricted to that parent in the same owner and stage. The helper declaration alone cannot provide this proof; any caller whose actual argument lacks the required parent lineage stays refused. This extends the direct contained-domain proof without turning an arbitrary helper collection into an owner-wide scan.

At installation, bind each checked inventory once to the verified assembly, artifact source hash, and actual generated operation definition. For source-`Require`, invocation compares the function's WeakMap identity, owning site and position, complete call closure (including an empty one), typed parameter order, and actual admitted values/record references. For receipt queries, it compares the exact query ID, source call, callback marker, binding and consumer site. State checks the bound site and active owner stage before issuing either observation. Membership handles remain an additional check only for sites that actually call `active_member`; their absence cannot invalidate a pure guard. A `read-predicate` syntax observer in the current serialized metadata is evidence about the expression, not permission to run the guard as a viewer query.

This retains the present fail-closed source/fresh-IR checks. It does not accept arbitrary generated functions, copied predicates, different source bytes, or a helper invoked from another consumer as owner decisions.

## Commit and disclosure semantics

Evaluate each guard once at its authored stage. A leading `require` sees the initial owner view; a pre-write body `require` sees the provisional view after preceding admitted statements. A future post-write decision must have its own stage-specific owner view. Record the reached owner rows, complete query domains (including negative scans), fields, and Identity facts so the execution is tied to that observation. The source-`Require` observer must capture owner candidates without reprojecting them through `sourceReadPolicies`; a contained query's parent proof must bind the genuine admitted/staged owner parent without adding a viewer read prerequisite. The receipt-query `any` must likewise retain its complete owner candidate domain and executed CONTROL markers through commit revalidation, without a viewer projection of those candidates. Do not re-run the business expression against the final overlay: the operation's own later create, set, or delete may intentionally change the domain it tested.

Before commit, revalidate the observed Identity facts and the fixed storage revision, then rely on the expected-revision commit fence. If another writer inserts, changes, or removes relevant evidence, retry from fresh admission and re-evaluate at the original stage. The existing race probes show that both pre-revalidation and late-at-commit inserts already trigger this retry; owner-state evaluation must make the retried hidden blocker visible to the guard. Rechecking a guard's fields or query IDs through **viewer** grants is wrong; final write authorization, locks, invariants, and result disclosure have their own checks. Do not require the final state to equal the earlier guard domain after this operation's own writes.

The private observation supplies verdicts and opaque selected values only to checked in-operation consumers. It grants no caller result, saved receipt field or external payload by itself. A false `require` produces the existing generic `rule_failed` and no domain effects; validation/work-bound failures remain fail-closed without hidden row values in outward messages. Successful results and saved receipt disclosure still use their separate checked data and control dependencies and viewer grants. If a result or result-selecting branch depends on guarded data, its own disclosure proof must cover that flow; execution authority supplies no shortcut. Returning an unreadable Model can therefore be withheld or refused by result disclosure without making its read grant a prerequisite for a scalar-returning mutation. Replay uses the saved outcome, not a new guard evaluation.

## First implementation profile and checks

The first implementation target includes the currently admitted leading/pre-write source-`Require` profile, including root helper and direct contained guards, and both checked decision occurrences in the any-plus-first composition: its leading `any` and decision-only `first`. The helper-contained `ChildOf` collection needs its own exact source/domain proof before it can join source-`Require`; until then, compilation should refuse it explicitly instead of emitting an artifact that cannot install. Keep unsupported `BodyIf`, post-write guard, handler, and arbitrary effect-tail shapes refused until they have exact source and stage proofs. The same authority contract applies when those profiles are later supported; this design does not silently widen them. Existing owner-view implementations for CRUD `when`, locks, and invariants should be checked for conformance, not replaced merely because these bridges are wrong.

The decisive installed-runtime integration cases, on helper and direct contained source-`Require` shapes, are: visible and hidden blocking rows both reject; no blocker commits; an unreadable anchor with authorized mutation and scalar result commits; the helper guard without `active_member` evaluates; empty and contained domains retain their language results; a row with withheld fields does not become false/absent; a hidden blocker inserted during evaluation forces retry and rejection; own writes after a passing guard do not retroactively change that decision; secret rows never enter the result or saved disclosure. The any-plus-first case must reject the hidden active child even when a visible inactive child satisfies the later `first`, and commit with only a hidden inactive child when that `first` is consumed solely by `require c!=null`. A `read=true` query over the same child stays viewer-filtered. The 200/201-row boundary must still refuse overflow. Use the compiled artifact, real State owner session, Identity and storage ports. These are behavior checks, not a request for unit tests.

The remaining implementation qualification is bounded: prove the decision/membership bindings close on every success and failure path, generate exact use-def/source correspondence for each site in the table, and run the supported profiles through installed runtime without granting ordinary viewer reads owner access. The currently declined original-app shapes have not been executed, so their individual runtime outcomes remain unknown. Parent and withheld-field mismatches and the current row bound are observed directly. The specification's content-expiry contract remains a separate infrastructure gap: current State storage source explicitly says its S2 query excludes archived rows while content expiry is a later slice. An expiry probe cannot qualify this guard design until that owner-wide lifecycle behavior exists.

## Implementation plan for the first blocker

Keep this work scoped to rule-search authority. The first deliverable is correctness for the two installed-runtime paths already reproduced, including explicit refusal for source shapes that cannot yet be proved. Broad acceptance of the original app's declined `first` queries is a later deliverable; their diagnostics are not a reason to give every mutation query owner authority.

1. **Bind decision sites independently of membership.** In compiler analysis, publish an exact inventory for each checked source-`Require` occurrence: owning operation, original statement/stage, typed input bindings, full pure-helper closure and admitted query domains. In emitted JS and Cloudflare installation, bind that inventory to the verified assembly/function identity and reject mismatches. Keep `active_member` on its own Identity proof. For helper-contained `ChildOf` scans, either prove formal-to-actual parent substitution through the entire call chain or emit a specific compile diagnostic before installation; do not produce an artifact that fails only because a membership-source entry is missing. This phase can be checked with the current no-membership and helper-contained probes before changing query authority.
2. **Repair source-`Require` observation.** Add a private, stage-bound owner-decision observation to State and its Cloudflare source-`Require` adapter. Resolve admitted parameter rows through owner state, scan complete bounded owner domains, and evaluate the checked pure guard without viewer projections. Retain the existing owner/team, row-work, revision, Identity, negative-domain and expected-revision fences. Install the root-helper and direct-child reproductions as integration cases: a hidden blocker rejects, no blocker commits, unreadable anchor does not add a viewer-read prerequisite, withheld decision fields are read at owner authority, and races retry into the correct verdict. Ordinary reads and saved results remain on their present disclosure path.
3. **Repair checked receipt-query decisions.** Bind the leading `queryAny` occurrence in the any-plus-first fixture to its original `require` and issue the same private owner observation. Bind the later `queryFirst` occurrence separately to its `let` and consuming nonnull `require`, including the exact parent/version and query order. State must select from the bounded owner domain at that authored stage; the checked callback and selected-row handle may inspect only proven fields. A hidden active child must reject even beside a visible inactive child; a lone hidden inactive child must satisfy the later presence check. Do not widen the existing viewer-only query engine's public mode or infer decision authority from the `first` metadata alone.
4. **Extend use-def proof by consumer, one supported shape at a time.** For every query occurrence, trace aliases and pure-helper calls to all terminal consumers and label each edge as decision, authorized write target, internal effect value, external payload, or caller result. If any decision consumes a selected row, select once under owner authority at the original stage and retain an opaque identity/version handle; do not rerun the query under viewer authority for another consumer. A write target may use that handle only after its normal operation/row/version checks. Scalar or reference values copied into effects, messages, deliveries, or results require their own exact source-to-sink authorization and disclosure proof; the guard observation is insufficient. In this first implementation, decline a mixed field/value or result flow when that independent proof is absent. Do not emit a runtime artifact that guesses a grant or silently substitutes null. The compiler should report the unsupported sink and source query. `CanEvent.change_schedule` stays viewer-selected because its query is effect-data-only. `CanRefer.settle` and `CanPurchase.receive` need both owner decision selection and independent return/replay disclosure before acceptance. This rule gives a concrete safe outcome for all thirteen classified sites without pretending they all fit the initial runtime slice.
5. **Validate at the installed boundary, then address remaining diagnostics.** Run compiled fixtures through verified assembly, Cloudflare invocation, State owner session, Identity and storage ports. Check empty/contained scans, `any`/`all`/`first` semantics, short-circuit order, 200/201-row bound, withheld fields, no-read-policy rows, stale Identity and revision retries, post-guard own writes, returned/replayed hidden-row withholding, and unchanged ordinary `read=true` behavior. Run the repository's no-unit-test guards and relevant integration/end-to-end suite; add no unit tests. After the first two paths pass, recompile the original app and classify remaining diagnostics by the consumer map above. Advance only profiles whose exact source, stage, owner domain and sinks are proved; leave other profiles with explicit diagnostics. Content expiry is not a success criterion for this change until the separate storage lifecycle work exists.

The initial repair is complete when both reproduced runtime paths give owner-state business verdicts, the membership-free guard installs and runs, unsafe helper-contained shapes fail at compilation, and viewer/result disclosure does not widen. Clearing all 21 `first` correspondence sites is not part of that initial completion claim.
