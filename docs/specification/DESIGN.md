# canlang v1 design

Status: chosen language design, October 3, 2026. A Rust compiler now implements source parsing, analysis, selected code generation and native runtime paths; permanent witnesses qualify named Decimal, expression, call, BDD-fixture and string behaviors, not complete application workflows or every backend/host. See the [compiler implementation and qualification summary](../../compiler/README.md) and current [compiler completion status](../../implementation/compiler-completion/status.json). [REQUIREMENTS.md](REQUIREMENTS.md) owns the product goals, this document owns semantics, and [GRAMMAR.md](GRAMMAR.md) defines exact source syntax. [DECISIONS.md](DECISIONS.md) retains the history and identifies superseded draft choices.

The target is a company business application: records, permissions, rules, workflows, and a standard browser/MCP interface. An app does not implement authentication, retries, HTML widgets, or database coordination itself. Unknown words never install imagined business behavior. Adoption and dependable generation take precedence over preserving ambiguous draft shorthand.

## 1. Source and composition

Source is UTF-8. Identifiers match `[A-Za-z_][A-Za-z0-9_]*`, are case-sensitive, and use `.` for qualification. One space forms an indentation level; tabs in indentation/code are errors. Newlines end statements outside `()`, `[]`, and `{}`. A semicolon separates leaf statements in the same context; empty/trailing semicolons and suites attached to a sequence are errors. Compound headers occupy their own logical line. Strings use JSON double-quoted syntax. There is no string interpolation: use typed formatting expressions. Keywords are contextual, so a field may be named `from` or `end`; `true`, `false`, `null` and prefix `not` retain their roles at expression-primary position. [GRAMMAR.md](GRAMMAR.md) settles lookahead, attribute boundaries, delimiter joining and inline/block forms.

`#` at the start of a source line attaches description metadata to the next declaration at the same indentation. Consecutive prose lines join with a newline. A single final `@{nl="..."}` suffix translates the whole joined description (§9.1); bare prose stays static literal metadata in its logical owner's source language. `#= message_path` references an actually reused static zero-parameter message, with no space between `#` and `=`; it cannot mix with prose or another reference. `##` is recognized first and is an ordinary ignored comment. Blank lines or `##` between a description and declaration do not change attachment. An unattached description is an error. `desc=` is compact inline description metadata on fields and signature parameters only (see §9.1); `description=` is not declaration metadata. Business fields named `description` are ordinary data.

The app description is required. Descriptions apply uniformly to packages, models, fields, operations, pages, capabilities, and other declarations. Multiline field declarations permit attached field descriptions, and fields/signature parameters accept the compact inline `desc=` form; both populate one description slot (see §9.1). Standard CRUD descriptions are generated; custom user-callable scenarios require a description explaining their business effect. Internal handlers may have descriptions, but none become executable behavior.

A compilation selects exactly one app for deployment; the project may contain many app declarations. Supply the project root and an entry `.can` source. If that source declares more than one app, select the app by name. The compiler indexes `.can` app/package declarations within that root and follows composition and imports to determine inclusion. There is no authored build manifest or source registry, no ancestor-directory search, and no automatic execution of neighboring files. Discovery alone never deploys a declaration. Files have no namespaces, initialization order, or runtime effects.

App identity and its required `#` description belong in the actual business source. `app Name uses=[member,...]` selects named packages or other declared apps for the product. Apps and explicitly named packages share a project-wide namespace; duplicate or ambiguous authored identities are errors. A small app without `uses` also owns an implicit package identified by that same app name: one indexed declaration supplies both app selection and package ownership, rather than introducing a second conflicting declaration. Composition recursively expands app members, rejects app-composition cycles, and includes each canonical package once, including implicit bodies reached through multiple selections or imports. A package can be selected from any file without changing its identity or ownership. `uses` selects product membership; package-level `use` imports an exported symbol and grants no privileges. There is no membership inferred from file proximity or matching app/package names.

Every selected app starts with language-version-pinned defaults: workerd, D1, `auth email password`, teams, daisyUI/HTMX, the generated MCP interface, `theme mode=system accent=blue density=comfortable`, locale default `"en"`, and the file policy in §8. Do not repeat those declarations. Permissions, roles and business rules remain explicit. Optional `context` immediately follows the app it configures and contains actual theme/file-policy/locale differences or named Cloudflare resource declarations. Omit an empty context. Auth/runtime/storage words retain their canonical meanings but spelling their unchanged defaults is unnecessary; unsupported alternatives are errors, not new authentication patterns. Explicit contexts of composed apps merge by resource name/setting: identical explicit values coalesce, incompatible explicit values produce a diagnostic instead of silently overriding or provisioning another deployment. Apply language defaults after merging explicit values, so an omitted value is not a conflicting assertion. Imports of dependency packages do not import another app's context. Every included package's resource references resolve through these defaults or the selected app's merged explicit context.

Small-app form:

```can
# Track the team's work.
app Tasks
Given
 export Todo { title:text trim, done:bool=false }
 policy Todo read=members
When
 crud Todo by=members fields=title,done
Then
 page / title="Tasks"
  form Todo.create display=inline
  list Todo
   edit
   delete
```

This is the app's implicit package `Tasks`, selected by omitting `uses` and supplying its Given/When/Then directly. Its models and operations have identities such as `Tasks.Todo` and `Tasks.Todo.create`, unchanged when Tasks is selected alone or included by another app. There is no generated `main` segment, assembly prefix or alternate alias for that owner. Existing explicit package identities retain their meanings.

Each implicit app has its optional context immediately after its app declaration, then any package imports before one complete ordered Given/When/Then body. That body ends at the next top-level `app`, `package` or `migration` declaration, or end of source. Multiple implicit apps and independent named packages may occupy the same file; file placement adds no membership. An app with `uses` cannot also supply an implicit body. It may have grouped message-only imports after its optional context for localized app metadata; those imports create no business package. A bare app without a complete body is an error, not a request to infer neighboring packages. A migration cannot interrupt incomplete Given/When/Then sections.

For two small apps Tasks and Notes, `app Office uses=[Tasks,Notes]` selects the distinct canonical packages Tasks and Notes without rewriting either body. Nested composition and import paths deduplicate each owning package; they never create another instance of its models, roles, handlers or work. Selection still merges the included apps' explicit contexts, while a symbol import retains the dependency/exposure rules below. Composition does not alter declared page routes or resource names: duplicate normalized routes and incompatible explicit contexts remain errors. [The task reference source](../../examples/TeamTasks.can) demonstrates two implicit apps and their composition in one file.

File moves and a different selected composition do not rename an implicit package. Renaming its authored app identifier does rename its model, role, operation and other declaration identities, including generated tool names; this requires explicit identity migration for deployed state/interfaces. Extracting its body into a differently named explicit package likewise changes identity. An explicit package cannot reuse the unchanged app's name under the existing shared namespace. No automatic rename, data transfer or compatibility alias is inferred. Separate deployments still have separate runtime state and authority. Explicit-package form names its members on the app declaration:

```can
# Manage customers and their work.
app Office uses=[crm,work]
package crm
 Given
  export Customer { name:text }
  policy Customer read=members
 When
  crud Customer by=members fields=name
 Then
  page /customers title="Customers"
   list Customer
    edit
package work
 use crm {Customer}
 Given
  Task { customer:Customer, title:text }
  policy Task read=members
 When
  crud Task by=members fields=customer,title
 Then
  page /tasks title="Tasks"
   list Task
```

Each package has exactly one ordered Given/When/Then structure; sections may be empty. A package block belongs to one source location and can move between files without changing meaning. Multiple named packages and app declarations can occupy one file. Package-only source files remain valid dependencies. Named packages are selected explicitly even for a single-package app, for example `app CanDo uses=[todo]`. Business models and operation interfaces belong to packages; service connections are package imports, described below.

Composed products need only their own description and selection alongside real business source; no per-profile wrapper file is required:

```can
# Reserve workspace and manage paid membership benefits.
app Workspace uses=[CanRent,CanMember]
```

Product membership controls default public exposure. Selected packages contribute their pages, authorized model read/list, publicly permitted enabled CRUD tools, and user-callable scenarios. The owning CRUD exposure exception in §5 limits publication without disabling canonical internal execution. A plain import of a production business symbol includes the whole owning executable package internally, preserving its models, policies, invariants, CRUD, hooks and trusted handlers, then recursively resolves its imports. Message-only and fixture-only groups have the bounded asset/test inclusion rules below. An executable dependency's inclusion does not automatically mount its pages or publish all its tools. A selected page's explicit imported form/action/edit/delete reference exposes that canonical user operation to both UI and MCP, with unchanged permissions and subject to its owner's CRUD exposure exception; an explicit excluded public reference is an error. Imported model reads needed by selected queries, forms or typed operation inputs use the same bounded authorized read/list interface. An internal `call` does not independently publish its target as a tool. Trusted handlers never become tools. Included dependency packages may require resources even when their pages are unselected; declaration-level pruning is not assumed.

`export` prefixes a declaration at its existing indentation: `export Customer {...}`, `export contract Charge {...}`, `export scenario prepare(...) by=...`, or `export event Settled {...}`. Named models, contracts, roles, pure functions, user-callable scenarios, events, capabilities, judgments and named messages can be exported. Declarations are package-private unless exported. An exported model exposes its type and enabled generated CRUD identities, not permission to read/write its records. Exported fixtures are visible only in test compilation; they never enter production interfaces. Trusted handlers cannot be exported as callable operations. Descriptions still attach to the declaration following the modifier.

`use package {Name,Other as Alias}` imports explicitly enumerated exported declarations. The provider is either an explicitly named package or a small app's owning implicit package, using the same canonical form: `use Tasks {Todo}` imports the exported model above. App selection and symbol import remain different operations: `uses=[Tasks]` selects the app and its context, while `use Tasks {Todo}` includes its owning dependency without importing app context or mounting every page/tool. An app defined with `uses` has no aggregate package to import; name the actual owning packages instead. Bound imports from an implicit owner extract its exported interface schemas with the same rules as named packages. Each member's local name is its symbol name unless an alias is supplied. Use this same grouped form for a single member: `use crm {Customer}`. Within a consumer package, declarations sharing provider and deployment binding belong in one group; no wildcard imports, implicit name search or separate export-name lists. Imports are unordered declarations, so grouping does not introduce initialization order. Duplicate imported members/local names are errors. Without a `use`, a cross-package reference is an error, including a qualified reference. Shared context has no owning package and refers to resource types by their fully qualified names, for example `key=booking.Calendar`. An import grants name visibility, never data access. Types and operations retain stable `package.Name` identities; generated CRUD lives under `package.Model.operation`. Dependency cycles between stored model references are allowed; containment, derived-value, hook, and synchronous call cycles are errors. A model, its policies, its invariants, and its canonical CRUD belong to one package. Other packages can `call` its imported operations, but cannot directly mutate it or extend its policy. `export` grants import visibility; product selection and explicit interface references determine exposure, and existing permissions still govern every invocation. The earlier individual `use package.Name` spelling is superseded.

`use invoice {BillingV1 as Billing} from=deployment.billing` imports an exported capability and binds it as a package-local service. `from` applies to every member in its group, so members with different deployment bindings or local imports must stay in separate groups. It replaces a separate adapter declaration. The consumer uses `send Billing.charge` and `on=Billing.settled` with the existing asynchronous delivery semantics. `use member_terms {AccessEvidence} from=deployment.membership` imports a named structural value type from that interface without creating another service. Reusing the same deployment binding shares its configured implementation; aliases remain package-local. Standard interfaces use the same syntax, for example `use std {EmailV1 as Mail} from=deployment.mail`. An exported judgment uses that same bound import form; its declaration derives the typed evaluate interface and result schema (§8.2), rather than requiring a second hand-authored capability.

Plain imports of production business symbols resolve executable packages through the compiler-derived index. A group containing only message symbols instead resolves pure message assets and their reachable parameter schemas, without including the provider's models, handlers, pages, app context or tools; a mixed group keeps its business symbols' ordinary inclusion semantics. Bound imports resolve only a versioned exported interface and its reachable value types through that index; the provider's executable package need not participate in the consumer app. The compiler extracts schemas and their referenced localization assets from owner declarations without authored interface-source lists, a Connections.can file, or copied consumer contracts. Discovering a bound provider never compiles its models, pages, hooks or background handlers into the consumer. Exported operation signatures also derive from their canonical declarations. A custom capability remains necessary for an external service boundary whose contract differs from a user-callable scenario; exporting it does not automatically map it to a trusted handler. Deployment installs the implementation and explicit wire mapping. An imported external interface does not create local records, grant service authority or make remote mutations atomic.

A bound import can also name an exported user scenario, for example `use maintain {inspect} from=deployment.maintenance`. Its owning parameter/result types must be exported; their reachable schemas are extracted without importing stored provider records. The operation's canonical identity, input constraints and description are reused. The deployment binding pins the compatible owner interface and delegated identity mapping; it does not grant a trusted handler's authority. Existing forms submit that operation through the asynchronous `send` path, with typed completion/receipts as in §§8–9. Local imports retain the existing `call` path and owner transaction rules. No consumer `perform` wrapper or copied capability signature is needed for this same operation.

## 2. Data and types

`Model {fields}` declares a stored team-scoped model in Given. Team ownership is the language-version-pinned default, including exported models; it is not inferred from a filename, package, import, composition, neighboring declaration, or model-reference field. `Model in Parent {fields}` explicitly creates a child with an implicit required, immutable `parent:Parent`; it inherits the parent's team and storage owner. `Model in app {fields}` explicitly declares app-scoped data and requires policies. A child is accessed as `parentRecord.Child`; that is a typed collection, not a copied relation. Other relationships are explicit model-typed fields. Changing containment or team is not an ordinary update.

Omitted ownership always means team, never parent containment or app scope. The selected app retains its existing team-resolution and admission rules: a default does not create or select a team, supply a missing team context, or grant membership. Public record access still resolves team from the record, and trusted handlers still obtain it from their verified occurrence. Storage placement remains separate: `Model at=Binding {fields}` is team-scoped at that binding, while explicit children retain inherited placement. No package or context setting changes the ownership default.

This shorthand applies only to stored declarations in Given. `contract`, `event`, capability value schemas, fixtures and constructor/struct expressions retain their existing meanings and do not acquire ownership. A model-reference field does not introduce a protected parent binding. Scope grants no reads or writes: absent read policies deny, operation authority remains explicit, and field grants, uniqueness scope, references, invariants, locks and versions still apply. The redundant `Model in team` spelling is invalid; its diagnostic directs the author to omit `in team`. The explicit parent/app forms are actual ownership choices, not alternate spellings of the default.

Every record has `id`, `version`, `created`, `updated`, `created_by`, `updated_by`, and nullable `archived_at`. These names are reserved. IDs are opaque strings; attribution names stable accounts or trusted sources and survives membership removal. A model name denotes a type/collection, **never a current record**.

A created row has version 1 throughout its creating transaction, including create-hook adjustments. Ordinary references to an existing row expose its admitted version `v` throughout the owner transaction while field reads observe ordered provisional changes. An accepted `set`, CRUD update or archive reserves `v+1`, even for a normalized same-value write. Further writes/calls/hooks to that row do not advance it again. Update-hook `event.before.version` is `v` and `event.after.version` is the reserved `v+1`; create-after is 1. Permanent removal has no after record; its deleted event carries `v+1`. A child write does not advance an unwritten parent. Failed operations advance nothing; receipt replay reapplies nothing. This write-intent rule intentionally produces history/version changes for accepted no-op writes. Locks compare stored values, not modification metadata.

| Type | Value and boundary |
| --- | --- |
| `text`, `bool`, `int`, `decimal` | Unicode string, boolean, signed 64-bit integer, exact decimal with at most 38 significant digits and 18 fractional digits; overflow is an error |
| `enum(a,b,...)` | Closed set of identifier values, serialized as strings |
| `email`, `url` | Validated strings; URLs limited to HTTP(S); email verification belongs to auth |
| `locale` | Validated canonical BCP 47 language tag for presentation/recipient preferences; no authority or timezone inference |
| `date`, `datetime`, `duration`, `timezone` | Calendar date; millisecond-precision UTC instant; integer milliseconds; IANA zone identifier |
| `currency`, `money` | ISO currency code; `{minor:int,currency:currency}` with pinned currency minor-unit scales |
| `user`, `member` | Stable account reference; team-scoped membership reference with retained attribution |
| `Model`, `Model.field` | Record reference; reuse a field's value type and validation constraints |
| `Contract` | Named structural value, stored by value, not a live model reference |
| `action(Operation,...)` | Finite reference to declared user operations, carrying protected record bindings; not executable code or a permission grant |
| `delivery(Operation)` | Opaque association to one durable delivery of the named bound operation; read-only receipt observation, not business completion |
| `file`, `secret`, `json` | Completed immutable R2 reference; server-only opaque secret; opaque bounded JSON |
| `T[]`, `T?`, `A\|B` | Homogeneous ordered array, nullable value, tagged union of named types |

`contract Address {street:text,city:text}` defines a structural type. Contract fields follow model field rules but have no ownership or metadata. JSON has no arbitrary property access. `if value is Contract` validates a JSON value against that closed contract (including bounds, defaults, and rejection of unknown fields), and narrows it within the true branch; failure takes the false branch. A union's wire value is `{type:"QualifiedType",value:...}`; common compatible fields are readable, and `if value is Type` narrows a branch. A model reference is not an embedded copy of its record.

Stored field forms are deliberately distinct:

- `name:T` requires a non-null create value.
- `name:T?` defaults to null; explicit null is legal.
- `name:T=expr` supplies a non-null default on creation only.
- `name:T[]` defaults to `[]`; `T[]!` requires an array input.
- `name:T server=expr` supplies the server value on creation and excludes it from client inputs. `secret` fields always require server initialization.

A bare scalar without a default/server expression is required and non-null, matching operation parameters. Scalar `!` is not supported; `[]!` remains the explicit required-array-input form. A missing required value is an error, never an inferred business value. Nullable, defaulted and server-owned fields retain their existing creation behavior; partial updates still distinguish an omitted change from explicit null. A default's context requirements are checked at every creation path: for example, `submitted_by:user server=actor` requires an authenticated creator; a trusted handler cannot supply a null actor to that field. Field modifiers are `trim`, `min=`, `max=`, and `unique`; text/array min/max measure length, numeric min/max measure value, and bounds are inclusive. Constraints run after normalization. Explicit `invariant` handles strict inequalities and relationships. `unique Model fields=a,b [where=expr]` declares a composite uniqueness constraint within its containing parent, team, or app. Null values do not participate unless the predicate explicitly includes them. Retained archived rows participate.

For a contained model, creation defaults and server initializers additionally bind `parent` to its required, resolved containing record. For example, `Step in Checklist {assignee:user=parent.parent.user}` defaults to the checklist employee's user. The normal parent/team/storage checks precede evaluation; this binding supplies no new read or write authority. Parent/reference reads use the current creation authority and the same transaction fence as other business reads. Every canonical CRUD, internal `create` and fixture creation path uses the same default. A supplied value replaces an ordinary default; explicit null still fails a nonnullable type. Defaults do not run on update, and later parent changes never rewrite stored children.

There is no partially initialized `row` or implicit sibling-field scope in an initializer. `parent` is available only for actual containment, including nested parent navigation; a top-level model, contract or event does not gain it. It is a contextual binding protected from authored shadowing while active. Evaluate missing field initializers in declaration order after resolving the parent, using the invocation's fixed facts; normal type/normalization checks and candidate guards still apply. Failed evaluation rolls back that creation transaction. Existing receipt replay retains the originally resolved values rather than rerunning defaults. The [parent-default consultation and witness](../../design/jev/parent-field-default-20261004/review.md) records the alternatives; no dependent-sibling initialization language is introduced.

`derive Model.field:T = expr` defines a read-only computed field in scope `row:Model`. `derive name(p:T,...):R = expr` defines a pure function. Parameters and result types are explicit; obvious local values and generated CRUD schemas are inferred. Derived model fields accept the same caption/value label map as stored fields, with checked resolved enum/bool cases and shared nullable presentation; labels supply no initializer or grant. Field type references remove repeated enum/bound definitions. Derived definitions cannot recurse, perform effects, or depend on incidental UI state.

A type path can resolve to a named type or a declared model/contract/event/computed field's value type. Field reuse carries representation, nullability, normalization and value bounds. It does not copy creation defaults, server initialization, required-array input metadata, uniqueness, ownership or permissions. Modifiers on the receiving declaration still require compatibility checking. The bounded grammar permits a named union, one array suffix and then one nullable-container suffix: `A|B[]?` is a nullable array of union values. Nullable elements, nested arrays and grouped types are outside v1. Apply suffixes to the resolved reused type: an additional array suffix on an array/nullable type and a redundant nullable suffix are errors. A reused nonnullable array can accept field-only `!`; resolving whether a qualified path denotes such an array requires the checker.

Reference examples use only declared domain fields. There are no magical `predicate`, `time_ranges`, `immutable_amount`, or provider-controlled field types. Represent business structures with contracts and canonical rules.

### 2.1. Typed operation references

`action(inspect,complete_account,...)` is a closed value type over explicitly imported or local user mutations. Each target retains its canonical owner and optional deployment binding; aliases do not change identity. Targets must be enabled user mutation operations in the registry, never trusted handlers, arbitrary strings or runtime-discovered schemas. Read forms retain their existing static operation form. The type can be nullable or stored by value in a contract/model like other structural values. It adds no new business operation.

`action(inspect,{inspection=row})` constructs a reference without invoking it. Bind every record-typed parameter with its identity and expected version. Non-record business arguments remain inputs to the canonical operation. Arbitrary partial argument binding, conversion from text/JSON and mutable target/binding fields are unsupported. The compiler derives the remaining form schema from the one owner signature. A locally constructed reference has no remote seal or additional authority.

For remote work projections, the installed source adapter supplies a runtime-validated sealed reference: origin binding, canonical target/interface revision, authorized principal/team, protected record identities/versions and expiry. A declared action type is the target allowlist. The deployment mapping states which authenticated source can project each target and how its display reference, revision and location identify those protected records. Ingress rejects mismatches, unknown targets/origins, substituted records, tampering and incompatible schemas before storing an actionable projection. Display strings are never routing or authorization inputs. Stored references cannot be transferred to another principal/team; expiration, source edits and interface incompatibility invalidate them. No source adapter or list/read projection is generated merely by exporting an operation.

An invocation still rechecks current owner access, record versions and business guards. Remote delegation uses separately issued audience-specific credentials, never passes an incoming browser/MCP bearer token downstream, and accepts no caller-supplied actor/team grant. Source authorization failure cannot become a privileged service call. Transport/seal checks establish provenance; they do not replace the operation's authorization.

`call reference {arguments}` and `send reference {arguments}` use the existing effects: `call` accepts only local targets and stays in one owner transaction; `send` accepts bound remote targets and returns the existing delivery receipt. Fixed record arguments come from the reference and cannot be resubmitted or changed. An authored argument object must type-check against every possible target's remaining inputs; incompatible heterogeneous signatures are a diagnostic. A constructor has a singleton target type. The generated form can select its compiled target schema without introducing untyped authored dispatch. A shared runtime receipt correlates binding, target, protected records/versions, principal/team and operation ID. Pending, conflict/validation failure, failed, unknown and fulfilled outcomes remain distinguishable. Fulfilled means the owning mutation committed, not that the projected business item is done. An admitted remote reference becomes unavailable for a second new invocation until a fresh source projection; retries/replay reuse the original operation identity and receipt. A pre-admission validation failure preserves editable inputs. State-sensitive business completion requires a new authorized source projection, without automatically rewriting the consumer's stored work state.

### 2.2 Complete typed invocation values

`invocation(Operation,...)` is the one closed complete-call value type for local enabled user mutations. It derives the complete normalized input schema and protected reference/version envelope from the owning operations, without copied consumer DTOs. `invocation(Target,{arguments})` constructs a singleton, and `call value {}` invokes with the actual current caller through canonical owner admission. It is immutable data, not approval, code or delegation. `action(...)` retains its separate purpose: bind protected record inputs and leave remaining input for an operation form. Neither value grants authority.

The accepted [full invocation contract](../../design/complex-apps/workbench.md#full-invocation-contract) is normative for construction, provider-result validation against the original authorized typed reference set, exact arguments/versions, null versus omitted updates, full current disclosure, compatible results and fixture provisioning. Provider output cannot mint protected references or replace current versions with arbitrary IDs. A trusted callback cannot impersonate a saved requester. CanWorkbench's explicit user continue/approve flow supplies the concrete witness; remote invocation values and autonomous delegated actors are outside this initial boundary.

## 3. Expressions, queries, and scopes

An expression is a literal, lexical name, field access, list/struct value, typed function call, query, or operator expression. Struct literals use `{field=expr}`; `{field}` means `{field=field}`. A contract value is `Address {street,city}`. Operators from lowest to highest precedence: `??` (right-associative), `or`, `and`, prefix `not`, comparisons (`== != < <= > >= in is`), `+ -`, `* / %`, unary `-`, member access/call (including `?.` for member reads). Boolean operators short-circuit. Mixing `??` with `and` or `or` in the same unparenthesized expression is an error; group the intended boolean or fallback subexpression explicitly. Chained comparisons are forbidden. Calls accept positional arguments followed by unique named arguments, with no later positional argument. No implicit truthiness, string/number coercion, assignment expression, or arbitrary JavaScript.

Null equals null; other ordered/arithmetic operations on null are type errors unless narrowed by a preceding check. `value ?? fallback` is the sole null-fallback form; the earlier `coalesce` builtin is removed. Enum literals require a uniquely expected enum type. A string literal can inhabit an expected validated string-like type, such as currency, email, or URL, after validation; this does not coerce an arbitrary text variable. Unresolved bare identifiers are errors. Indexing arrays uses zero-based integers and `at(array,index)` returns a nullable item; no unchecked `[]` indexing. Currency values never coerce to decimal.

`receiver?.field` is pure, read-only member access on a nullable receiver. It evaluates the receiver once: null yields null, otherwise it performs the ordinary typed field access. The result is the selected field's type made nullable, with no nested optional wrapper. Each nullable hop requires `?.`; ordinary `.` still requires a non-null receiver. A statically non-null receiver uses ordinary `.`. Optional calls, indexing and mutation targets are not introduced. Invalid field/type access and authorization or business failures remain errors rather than becoming null. The operator supplies no directory access or additional privilege.

For `left ?? right`, `left` must be nullable with underlying type `T`; `right` must have compatible type `T` or `T?`, without coercion. Evaluate the left once, and evaluate the right only when the left is null. False, zero, an empty string and an empty array are values, not reasons to choose the fallback. A non-null right makes the result non-null; a nullable right leaves it nullable. Both operands must type-check and retain the existing dependency/return-disclosure rules, even when one is not evaluated. Arithmetic binds more tightly, so `(row.until ?? now)-row.from` requires grouping around the fallback. In a function argument, `overlaps(from,until,entry.from,entry.until ?? now)` uses the argument boundary to delimit it.

A true equality between a safe-access result and a statically proven non-null value narrows every traversed nullable receiver and the selected value to non-null in that continuation, including following `and` operands. For example, `event.result?.source==revision.id` proves `event.result` non-null when true because record IDs are non-null. Equality to null, comparison to a nullable value and `!=` do not supply this true-branch narrowing fact; keep the necessary explicit checks. This is a typing fact, not an inferred business permission or a rule that moves guards ahead of effects.

Lexical names are parameters, `let` values, query aliases, imported declarations, and fixed context: `actor:user?` (stable `user.id:text` is readable; no account-directory fields), `team:Team` when applicable, `now:datetime`, and `operation:OperationContext` with read-only `id:text` and `source:text` fields. Team exposes `id` and `timezone`; a membership exposes `id`, `user:user`, and `team:Team`. Authenticated/member/role authorization narrows actor to non-null. Trusted handlers have `actor=null`; attribution uses their verified source, and team is derived from the verified occurrence, never an arbitrary payload grant. `now` is fixed at admission across internal retries; generated IDs and random values are also stable across retries. `row` is bound only inside a model policy/invariant/derive/lock or a collection child; scenario bodies use their named record parameters. Bare field selectors in UI attributes such as `columns=title,done` are schema selectors, not general expressions. There is no fallback search through unrelated records for a matching field.

Queries have one form, starting from an ordinary expression yielding a model, parent-child collection, array, or typed collection-valued local:

```can
Model as item where predicate order=-item.created select expression
invoice.Line as line select line.quantity*line.price
```

`where`, `order`, and `select` are optional and ordered as shown. An omitted select yields records. Aliases are required when an expression accesses an element. Query values can feed `count`, `sum`, `min`, `max`, `any`, `all`, `first`, or a presentation collection. `any(domain as x,predicate)` and `all(domain as x,predicate)` separate the domain from the predicate. `all` of an empty domain is true; `any` is false. Require `count(domain)>0` separately where necessary. `first` returns nullable and requires stable ordering. `min`/`max` of an empty domain are null; numeric sum is zero; money sum requires an explicit currency when the domain may be empty: `sum(query,currency)`.

The query tail binds after ordinary operators and follows `archived=include`, `as`, `where`, `order=`, `select` in that order, each at most once. Clause values end at the next clause or enclosing argument/header boundary; parenthesize a query used within larger arithmetic. Query `order=` takes one expression. UI field selectors and fixed ordering take selector lists; preference ordering uses the closed §9 default/exception map, so their commas cannot consume an aggregate's second argument or an example cell. The first domain alias in `any`, `all` and `group` is visible in their second expression; ordinary calls do not create that scope. Loop bindings and query aliases are distinct. [GRAMMAR.md](GRAMMAR.md#expressions-and-values) specifies exact boundaries.

Default record queries exclude archived and expired rows. `Model archived=include` includes archived rows but never expired content (§7.1). Record ordering defaults to `created,id`; ID is appended as a final tie-breaker. `group(query as item,keyExpr)` binds that alias in its key expression and produces typed `{key,items}` groups, usable in queries and reports. For example, `group(selected as expense,expense.status)`. It never invents fields or a callable function from a group name.

Ordered scalars are int, decimal, duration, money, date, datetime, text, email, url, locale, timezone, currency and byte quantity. Numeric comparison between int and decimal promotes int exactly inside that operator; it is not a general assignment/argument cast. Validated string-like values compare their string representation with text or the same validated subtype; ordering is Unicode scalar order. Different validated subtypes do not acquire mutual conversion. Money comparison requires matching currencies. Enum cases support typed equality/membership, not ordinary relational ordering. Byte quantities have comparison, not arithmetic. Array/contract equality is typed structural equality; references compare identities of their declared reference type. Opaque secret/file/action equality is not newly defined by this matrix; preserve their existing permitted operations. `is`, `??` and safe-access narrowing retain their current contracts.

Integral arithmetic and unary negation are checked at the result boundary, including signed-minimum negation. Integer and duration remainder use the quotient truncated toward zero, so the remainder has the dividend's sign; a zero divisor fails. `duration/int` must produce an integer millisecond count or fail. Datetime results stay in the supported calendar range; constructors reject nonzero sub-millisecond RFC3339 fractions rather than silently truncating. Calendar changes use the existing date helpers, not invented date arithmetic.

Decimal arithmetic computes the mathematical result, rounds half-even to at most 18 fractional places, then checks the 38-significant-digit representation bound. An exact terminating result needing fewer places is retained; trailing zero normalization does not change its value. Out-of-range results, division by zero and invalid inputs fail; no NaN or infinity. Decimal literals/inputs remain checked representations rather than silently rounded inputs. Money-valued arithmetic and `money` construction round once at each operation's final boundary to the pinned currency minor-unit scale, half-even, then check `minor:int`. A money/money ratio has no currency unit and uses decimal rounding. Numeric/duration aggregates compute their mathematical total and apply their result check once; money aggregation validates every currency and sums minor units without per-row conversion. These failure rules do not manufacture new public business error codes.

Builtin names are closed and typed (`random_secret` is restricted to server defaults): `count`, `sum`, `min`, `max`, `any`, `all`, `first`, `group`, `flatten`, `at`, `abs`, `round(value,scale)`, `lower`, `upper`, `trim`, `contains`, `starts_with`, `join`, `format`, `app_url`, `active_member`, `overlaps`, `local_date`, `local_instant`, `add_days`, `add_months`, `date_year`, `weekday`, `dates`, and `money`, `date`, `datetime`, `action`, `invocation`, `choose`, and `random_secret`. Their meanings are ordinary typed operations, with these important boundaries:

- `flatten(domain)` expands exactly one bounded collection layer. All child collections have one element type; outer then inner iteration order and duplicates are preserved. Empty input yields an empty typed array. Input traversal, result size and shared work bounds all apply; exceeding any bound fails rather than truncates. Query projection never flattens implicitly. This enables interval endpoint/report projections without temporary business records or a separate interval-union primitive.
- `format(template,values)` uses named `{key}` substitutions and cannot execute code. The message overload `format(descriptor,locale=target)` resolves localized outbound text as specified in §9.1; it does not reinterpret ordinary templates. Output sinks apply their existing escaping. No arbitrary formatter plugins.
- `overlaps(aStart,aEnd,bStart,bEnd)` tests non-empty half-open ranges. `add_days(value:date,days:int)->date` adds calendar days; a duration added to a datetime is elapsed time, not local calendar time.
- `add_months(value:date,months:int)->date` adds signed Gregorian calendar months, clamping the original day to the last valid day of the target month. Recurrence uses the original anchor plus the absolute cycle offset, never the previously clamped date: January 31 +1 month becomes February 28/29; the same anchor +2 months becomes March 31. Multiplication/date overflow fails. This contract follows calendar clamping rather than [RFC 5545's invalid-date skipping](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.3.10); interoperable RRULE parsing is not introduced.
- `date_year(value:date)->int` returns the Gregorian year; `weekday(value:date)->int` returns ISO Monday=1 through Sunday=7. Dates are proleptic Gregorian years 0001–9999. The language version pins zone data and calendar semantics.
- `dates(from:date,until:date,limit:int)->date[]` enumerates consecutive dates in ascending half-open `[from,until)` order. Equal endpoints give `[]`; reversed endpoints, nonpositive limit, overflow or more than `limit` dates fail. The limit must fit the shared work budget. It is a work bound, not truncation or a universal entitlement/booking horizon. Inclusive business intervals use `add_days(until,1)` explicitly.
- `local_date(value:datetime,zone:timezone)->date` returns the civil date of an instant in the specified pinned IANA zone; it does not change the instant or business timezone.
- `local_instant(date,time,zone,fold)` requires `fold=earlier` or `later` for an ambiguous local time; nonexistent local times fail. `time` is a validated `HH:MM[:SS]` string here.
- Decimal rounding and money multiplication/division use half-even. `money(decimal,currency)` rounds once to that currency's minor units. Add/subtract/compare money only with matching currencies. Currency conversion requires an explicit typed provider/result workflow.
- `app_url(path:text)->url` joins one app-relative slash-prefixed path to the deployment's trusted public HTTP(S) origin and mount prefix. It never trusts a request Host header or guesses an origin. Reject absolute/protocol-relative paths, backslashes, malformed percent encoding, decoded path separators or dot segments and userinfo; query/fragment suffixes must be properly encoded. Canonicalization cannot escape the configured prefix. The deployment origin is fixed trusted context, not an app-authored repeated constant. This pure link construction grants no access; existing route/record/recipient checks remain mandatory.
- `active_member(person:user,team:Team)` checks current membership for the supplied account; it is not a history-visibility predicate.
- `date("YYYY-MM-DD")` and `datetime("RFC3339 instant")` are checked constructors. Source duration literals are integers suffixed `ms`, `s`, `m`, `h`, or `d` (a day is exactly 24 hours); byte literals use `B`, `KiB`, `MiB`, or `GiB`. Overflow fails. Quotas and recurring intervals must be positive.
- `random_secret()` produces 32 cryptographically random bytes represented as an opaque secret. It is permitted only in server defaults, is never client-readable, and reuses the same value for the same committed operation identity.

This notation describes checker signatures; it is not new authored generic syntax, a callback system or first-class callable type. `C<T>` is a bounded homogeneous ordered array/query domain. `O` denotes the nonnullable ordered scalars listed above. `S` is text/email/url/locale/timezone/currency. `K` is text/bool/int/decimal/enum/email/url/locale/timezone/currency/date/datetime/duration/money/user/member/same-model record identity, optionally nullable. `Display` is nonnull text/email/url/locale/timezone/currency/bool/enum/int/date. Decimal/money/datetime interpolation is outside this plain-template overload until canonical encodings are specified; localized display retains §9.1’s typed contract. Reused constrained fields are checked against these representation signatures; a builtin result does not copy a field's creation metadata or arbitrary bounds.

A statically written nonempty array literal is the nonempty proof supported here; a general query/collection remains potentially empty even if a preceding business guard suggests otherwise. Thus `max([1,count(...)])` and `min([until,grant.until])` are nonnullable, while general `min`/`max` and `first` remain nullable. `first` requires stable ordering; record queries retain `created,id` and arrays their authored order. Empty int/decimal/duration sums yield their typed zero. Money sums require an explicit currency unless a nonempty literal supplies it; amounts and any explicit currency must all match. Money min/max also reject inconsistent currencies. `any`/`all` accept the special existing alias-scoped predicate expression, not a callback; empty-domain results remain false/true.

`group` groups by typed equality (including one null group), preserves item encounter order and emits groups in first-encounter order. It supplies only `{key,items}`. `at` returns null for negative or out-of-range indices. `abs` has the same overflow boundaries as negation. `round` accepts integer scale 0–18, uses half-even and returns decimal; other scales fail.

Text length and substring/prefix matching count Unicode scalars, not bytes or grapheme clusters. `lower`/`upper` use full default Unicode case conversion including contextual mappings, and `trim` removes the pinned Unicode White_Space property at both ends. No normalization or locale tailoring is implicit. Text transformation results are text, so they do not promise preservation of email/URL/locale validation. `contains` and `starts_with` are exact case-sensitive scalar matching. `join` follows domain order and yields empty text on an empty domain.

Plain `format` supports named `{key}` substitutions and doubled literal braces. All placeholders must exist in its closed Display-valued object; malformed/missing placeholders fail. Extra object fields are allowed. It preserves text/validated strings and enum spellings, writes bool as `true`/`false`, int as signed base-10 digits, and date as zero-padded `YYYY-MM-DD`. It performs no locale conversion or executable formatting. The message overload requires the existing explicit `locale=` argument, with null selecting the app default (§9.1); its presentation provenance/restricted sinks remain unchanged. The finite Display set intentionally excludes decimal/money/datetime plain interpolation; use the existing typed presentation/message path for those values. No locale-dependent or implementation-dependent string coercion is accepted.

`overlaps` accepts either four dates or four datetimes and tests nonempty half-open ranges; empty or reversed ranges return false. `local_instant` keeps validated `HH:MM[:SS]` time and explicit fold resolution; nonexistent times fail. `date`/`datetime` accept checked text only, not arbitrary numeric casts. `action` requires a statically canonical enabled user mutation and exactly all protected record bindings, preserving §2.1's singleton result and remaining canonical input schema. `random_secret` keeps its existing server-default-only restriction and stable 32-byte secret behavior; inclusion in the closed catalog does not make it generally pure or client-callable. All calls enforce named/positional argument order, unique argument names and these exact arities.

Function signatures and argument counts are checked; a convenient function name never supplies an undeclared implementation. Large queries may use SQL aggregates; runtime limits must reject an oversized invariant calculation, never calculate it over a truncated page.

A bare identifier resolves to its nearest visible lexical binding first. Expected enum typing does not replace an existing binding with a same-spelled enum case. Only an otherwise unbound identifier can denote a case of one uniquely expected enum type. If the binding has an incompatible type, report the mismatch at its use; do not search for a different meaning. Object shorthand follows the same lookup. Field selectors and declaration/operation paths retain their separately specified resolution rules.

Duplicate authored bindings in one scope are errors. An ordinary nested suite or query may shadow an outer authored binding. A new local binding is introduced after resolving its initializer; a query alias is introduced after its domain and has precisely the scope described in GRAMMAR. Authored bindings cannot hide an active injected `actor`, `team`, `now`, `operation`, or the context-specific `row`, `event`, `preferences`, `result` or `before`. These are contextual facts, not globally reserved spellings. A language-created nested collection context may introduce its own `row` as already specified, retaining the enclosing record chain. A query or parameter called `row`/`event`/`before`/`result` remains legal where that contextual binding is absent. Closed builtin names cannot be replaced by package declarations; ordinary authored locals may hide callable or actor-predicate names, in which case an incompatible later use is an error.

Signature defaults are pure and checked/evaluated from left to right. Each default may use earlier resolved parameters, imported pure declarations and the fixed facts available at that signature's pre-authorization types; it may not use itself, a later parameter or a body binding. A supplied argument takes the place of its default. Authorization does not retrospectively make `actor:user?` nonnullable inside a default. Existing dependency/read-disclosure checks still apply to queries and calls; this rule grants no pre-authorization record access. Field creation defaults/server initializers retain §2's creation-context checks and do not acquire a new implicit sibling-field scope from this signature rule.

## 4. Permissions and rules

The default `auth email password` primitive provides verified-email registration, sign-in/out, expiring email-token recovery, sessions, and MCP authorization. Default `teams` support adds owner-managed membership, expiring verified-email invitations, roles, team selection, and a team timezone (UTC until configured). Neither needs a source setup line. Deployment provisions the first owner. `role billing` declares an owner-assigned team role; `owner` and `members` are built in. Roles retain package-qualified identities and export/import visibility: equal names in different packages do not merge. Declaring a role neither assigns it nor grants data access. V1 roles support only team scope; `in=team` is redundant invalid syntax, with a diagnostic to omit it, and other role scopes remain unsupported. App authors do not implement alternative login or role tables.

`members`, `owner`, a declared role, `authenticated`, and `public` are actor predicates. They can combine with boolean record predicates. At team scope they test the resolved team. `actor` is null for unauthenticated public requests. Membership management rejects removal/demotion of the last owner; invitation acceptance verifies the addressed email and cannot grant a role beyond the stored invitation. A completed membership removal prevents new admissions; an already admitted operation may finish. On D1 the fenced commit also detects intervening membership changes. Historic membership references remain readable where record policies permit; new member assignments must be active.

A declared role also accepts one explicit subject: `salesperson(person)` returns bool for `person:user` in the current verified team. This is a role predicate application using ordinary call syntax, not a first-class callable/value type. Resolve the callee by normal lexical/import rules; its declaration must be a visible declared team role. The existing bare `salesperson` is the canonical literal-actor spelling; `salesperson(actor)` is redundant and diagnosed, while another expression may evaluate to the same account. Built-in `owner`, `members`, `authenticated` and `public` do not gain a call form; `active_member(person,team)` remains the existing explicit membership test. No-team contexts cannot evaluate a declared team role.

The subject must be an active member of that team with the explicit package-qualified assignment; a team owner does not automatically hold every declared role. Missing, inactive or foreign-team membership yields false. Use current admission authorization state and the same commit fence as caller-role checks. The predicate provides neither account enumeration nor record access, never switches actor, and never narrows actor to nonnull merely because another subject holds a role. It can restrict prospective assignments but must not be a stored historical invariant that invalidates old records on later revocation. No role-name strings, dynamic role values or second role storage are introduced.

For the authenticated caller only, `actor.email:email` and `actor.email_verified:bool` are read-only admission facts supplied by canonical auth. They permit explicit addressed-invitation acceptance without a parallel identity service. Other user references do not expose those properties or a global email directory; request inputs cannot override them.

```can
policy Candidate read=recruiter
policy Candidate read=interviewer where=row.interviewer!=null and row.interviewer.user==actor fields=name,interview_at
invariant Line: row.quantity>0
lock Invoice fields=customer,total when=row.status!=draft
```

Policies grant **reads**, including files. No policy means deny. Matching grants union their fields for matching rows; omitted `fields` grants ordinary fields and safe record metadata, never secrets. Identity/team/parent boundaries always apply. Public and external-user grants are explicit exceptions to membership requirements, evaluated in the resolved record/team scope. New cross-team record relationships are rejected.

User queries apply row/field permissions before filters, searches, ordering, counts, aggregates, relationship expansion, and serialization. A derived value is readable only if its data dependencies are readable. A confidential aggregate needs a specifically authorized read scenario with `scope=authority`, described below. No separate `projection` primitive duplicates policy field grants.

An explicit policy field selector may descend to a leaf of a singular embedded typed value, including a delivery observation. Every interior component must be a typed value, never a model/user/member reference, array, JSON, file, secret or action. A leaf grant includes only that leaf and necessary nullable-prefix presence, not its container, ID or siblings; it cannot grant another record's fields. Unknown/unsupported paths fail checking. Matching grants union paths; a parent grant subsumes descendants, never conversely. A derive still requires its own grant and exact readable leaf dependencies: `fields=notice_state` alone cannot read `row.notification?.status`, while adding `notification.status` can. No authority derive or automatic declassification is introduced.

Viewer queries, ordering, counts, history and serialization preserve these exact paths. Denied leaves are withheld, never represented as null. An authorized null prefix may serialize null; a nonnull status-only projection may serialize `{notification:{status:...}}`, with no handle/locator/ID/result/error. Such a partial projection is not an assignable delivery value or lookup authority. Result/error leaves additionally retain independent operation/content/file/lifetime checks. [The focused status-only witness and divided JEV advice](../../design/delivery-leaf-grants-20261004.md) record the concrete adoption benefit, permission costs and unexecuted boundaries.

Pure queries inherit their declaration's evaluation authority. Read-policy decisions, invariants, pre-state locks, CRUD `when` and mutation/trusted-handler decision expressions inspect bounded authority state at the resolved storage owner; they do not recursively apply read policies to their decision scans. Derives inherit the caller's mode. Team/parent/storage boundaries, expiry and work bounds still apply. A policy may inspect its own grant-table model without recursively evaluating that model's read policy. Pure derive/call cycles are invalid. Ordinary viewer queries and `read=true` bodies remain permission-filtered; authority decision data does not become a result grant. The existing explicit `scope=authority` report boundary remains required for confidential outputs.

`invariant Model: predicate` is a pure invariant in `row` scope, checked for every affected row in the proposed final state. Dependency analysis rechecks relevant rows when referenced data changes; oversized dependency work fails with a bounded-work error. Deleting a referenced row fails unless references have been removed in the same operation. Invariants do not emit events or perform effects. `invariant` is the sole Given introducer; the former Given `require Model: predicate` spelling is invalid. Execution guards, presentation gates and migration/backfill checks retain `require`. Both words remain contextual names outside their syntax slots.

`lock Model fields=... [when=predicate]` evaluates on the **pre-state**. An omitted predicate means true: the fields are always locked, so do not repeat `when=true`. If the predicate is true, those field values cannot change and the row cannot be removed, including through scenarios or hooks. The sole lifetime exception is whole-record disposal after declared expiry (§7.1), not early deletion or field editing. The transition establishing a conditional lock may set final values. A child rule may inspect `row.parent`. Archival preserves locked values. No separate freeze/immutable/snapshot variants: copy selected values into typed snapshot fields with `set`/`create`, then lock them. Audit history is automatic.

Operation `by` governs its writes independently of generic CRUD input fields. All paths still enforce ownership, invariants, locks, versions, and reference validity. Scenarios may inspect authority data needed for their rules; this does not grant callers access to that data. Guard failures default to a generic business-rule error; diagnostic messages must not disclose confidential values, including arguments omitted by the selected translation.

## 5. Canonical operations

```can
crud Todo by=members fields=title,done,assignee
# Complete an open task.
scenario complete(todo:Todo) by=members
 require not todo.done
 do set todo {done=true}
```

There is at most one `crud` declaration per model. It generates create, update, and delete operations. `fields` is the update allowlist and, unless a different `create_fields` is supplied, the create allowlist. Do not copy an identical list into `create_fields`. `create=none`, `update=none`, or `delete=none` disables that operation. `when=predicate` applies to each normalized proposed create/update row and the existing delete row. Prepare defaults and server-owned fields without staging this write, evaluate the predicate, then stage only on acceptance. Field reads through `row` observe the candidate; model scans observe the provisional owner store immediately before this write, including earlier effects but not this candidate write. Updates still leave the old stored row visible to scans during admission. Delete admission runs before removal. Final invariants inspect the completed provisional state. Mandatory cross-path business rules belong in invariants/locks. All required create fields must be supplied, defaulted, or server-owned. A child create takes its protected parent binding. Create defaults do not run again on update; omitted update fields are unchanged, and explicit null clears a nullable field.

`expose=create,update` is an optional closed publication allowlist on the owning CRUD declaration; its selectors are enabled `create`, `update` and/or `delete`, or sole `none`. Omission permits all enabled generated CRUD. Duplicate/unknown/disabled selectors and combining `none` with another selector are errors. This one exception constrains product selection, explicit public UI references, MCP discovery and generated external routes; another product or import cannot override it. Permitting an operation does not itself publish an unselected dependency. Model read/list and existing field grants are unchanged.

An excluded operation remains enabled in the same canonical registry for ordinary internal calls/effects with its original lifecycle, actor/team, inputs, expected versions, `by`/`when`, locks, invariants and replay rules. Exposure adds no privilege or business guard. `delete=none` still disables the lifecycle and cannot be restored by exposure. Contradictory public forms/actions/edit/delete controls fail checking rather than silently creating an alternate route. Inline examples may test canonical admission without publishing a tool. This keeps a reason-bearing business action's internal canonical delete while omitting its unusable direct public interface; no wrapper product or second deletion API is required. [The standalone Can/JS witness and consultation uncertainty](../../design/canonical-exposure-20261004.md) preserve the alternatives and unexecuted discovery boundary.

Omitted deletion mode means archive: delete archives the row and its contained subtree, atomically. Do not repeat `delete=archive`. It does not create a second archive API. `delete=remove` permanently removes an unreferenced row/subtree and is explicit; `delete=none` preserves an intentional prohibition. Existing references to archived rows remain valid for authorized history; new references cannot target them. Archived rows cannot be edited; restoration is outside v1. Audit/receipt retention is independent of deletion.

existing result descriptor. The [enum-result check](../../compiler/tests/enum_result_runtime.rs)

Optional operation-owned input assistance is authored on the parameter, for example `assignee:user choices={read=reviewer_choices(document=submission.parent),value="user",labels=["name","role","home"]}` or `region:Region choices={read=region_choices(country=country),labels=["name"]}`. The compiler derives the canonical owning read, checked input paths, candidate value and labels from declarations, and publishes version 1 metadata on the existing input descriptor. A checked read returning a nonnullable one-dimensional stored-model collection publishes its canonical model-array result, such as `approve.Employee[]`; each value keeps the existing model-reference wire representation. Choices grant no authority, execute no read themselves and change no final input, default or server guard. Artifacts carrying choices require `interfaces.input-choices@1`; a consumer must support that feature before admitting the artifact. Viewer-authorized read execution, current draft binding, cancellation, stale-response fencing and form controls retain their owning consumer scopes. Labels preserve declared reference identities; they introduce no directory or file enrichment.

External mutation admission authenticates the caller/resolves the authorized team and checks `by` before the body. Record inputs resolve their declared type, owner/team, lifetime and expected version within that boundary. The operation’s authored guards govern permission to mutate that record; an ordinary viewer read grant is not an extra universal write prerequisite. This retains §4’s separate read/write permissions rather than silently granting reads to make a write possible. An unreadable record supplied by opaque ID confers no authority: the same owning guards still run and may reject with the generic `rule_failed` without exposing confidential values. Missing, expired or foreign-owner references remain `not_found`; ordinary read/look-up interfaces hide unreadable rows, and page pickers remain viewer-filtered. Return values and changed-record projections still obey their existing disclosure rules, and file attachment authority is checked independently. A caller with only broad operation membership cannot bypass a missing per-record business guard; such a missing guard is an application defect, not inferred permission from an ID. Trusted handlers retain their verified source authority and local calls retain their unchanged caller.

The effect vocabulary is finite:

| Statement | Meaning |
| --- | --- |
| `let name=expr` | Immutable local binding |
| `require expr [message=expr]` | Reject without committing if false; message is literal text or a message descriptor |
| `create Model {fields} as name` | Insert and bind a record; child inputs include `parent` |
| `set record {fields}` | Assign named fields; no implied copies or model-name rebinding |
| `transition record.field source -> target` | Validate and stage one operation-owned machine edge |
| `delete record` | Apply the model's declared deletion mode; allowed only if deletion is enabled |
| `call operation {arguments} [as name]` | Invoke a canonical operation in the same transaction/context; recheck its `by`, rules and ownership |
| `if expr` / `else` | Indented conditional branches |
| `match expr` / `case name` | Exhaustive branches for one nonnullable finite enum |
| `for item in query limit=N` | Bounded loop; fail the entire operation if more than N items would be processed |
| `emit Event {fields}` | Persist one typed domain event for post-commit handling |
| `send Target.operation {arguments} [when=predicate] as delivery` | Persist a typed external delivery intent; returns a receipt, not provider success |
| `schedule key at=instant event=Event {fields}` | Replace one named pending occurrence at this owner; key is a text expression |
| `cancel key` | Cancel the named pending occurrence if not dispatched |
| `return expr` | Return one statically typed result and end evaluation |

Each scenario has one lowercase `do` execution body. An inline `do` may contain simple statements separated by `;`; a block `do` contains any statements. It replaces the earlier lowercase `then` spelling, which is no longer a body introducer. Leading `require` checks and the body execute in written order; further `require` checks may occur inside the body, including between effects. A failed check rejects the whole provisional mutation. `do` also introduces pure read bodies and trusted-handler bodies; it creates no additional transaction or authority. Attached `examples` stays outside the execution body and is test-only. Uppercase package `Then` still declares presentation. No nested `atomic`: a mutation is already one atomic unit at its inferred owner. No `clear`, `insert`, `upsert`, `append`, `snapshot`, `freeze`, arbitrary SQL/JS, or free-form effects. Collections stored by value are replaced through `set`; large mutable child collections are models.

`match expr` is optional strict enum handling; ordinary `if`/`else` keeps its existing intentional fallback behavior. Evaluate the subject once at its written position, including an admitted awaited observation, before any selected arm effects. Every current case of that exact checked subject enum must have one `case name` arm. Added, missing, duplicate and unknown cases fail checking. Case names are subject-domain labels, so an unrelated lexical parameter with the same spelling does not capture them; names used inside the arm still obey ordinary lexical resolution. Every arm has its own nonempty body and lexical scope. A result-bearing scenario needs an actual return on every reachable arm path, not merely a complete list of labels. Explicitly guard a nullable subject and handle null outside the match. Wildcards, multiple-case lists, guards, destructuring, tagged unions and catch/recovery are outside this first surface; `_` is rejected as a case label. Migration mapper permissions are unchanged. Matching grants no authority and changes no transaction boundary: arm effects and later statements retain source order and the owning operation's normal failure behavior. Native compiler witnesses qualify checked coverage, null guards, lexical scopes, returns, one evaluation and ordered failure propagation; durable rollback and complete provider applications keep their separate consumer scopes. Case-header completion offers remaining cases of the checked subject as enum members, including a partially edited case name, without capturing same-named lexical parameters. Arm-local unused/shadowed bindings and statements after `require false` retain their own scope; one rejecting arm does not mark another arm unreachable. The formatter preserves nested arm scopes, explanatory comments and statement order, and the LSP forwards checked coverage, description refusals and arm-local lint diagnostics through its existing protocol.

Cross-package `call` is the only way to mutate another package's model. It participates in the caller's operation identity, invokes no network request, and cannot recurse. Direct parameter assignment is never storage mutation. A scenario cannot synthesize user privilege or trusted source status.

Every authored `require` has the same rejection semantics, including leading checks in trusted handlers. False means the safe business error, default `rule_failed`, and rollback of all provisional domain changes, events, deliveries and attachment links. A trusted business rejection is a terminal failed occurrence; transient runtime failures retry the same occurrence. Lifecycle `skipped` describes superseded/cancelled/ineligible work or a false dispatch `send when`, not a false authored `require`. Inline examples observe the ordinary business error, without committing rejected domain effects.

Mutation results default to a receipt plus authorized changed-record projections. Explicit mutation returns may contain literals, input values, generated receipts, and readable record values. Private authority-derived scalars cannot leak through return values; the compiler tracks these dependencies. A deliberate privileged report uses `scenario ... read=true scope=authority -> Contract by=...`: its typed result is an explicit information grant to `by`. Ordinary `read=true` uses viewer queries, allows only pure statements, and has a required result type and return on every path. Source-scoped reports must have a description identifying the information exposed. Mutation success/failure can inherently reveal the stated operation's permitted business outcome, such as availability; it never returns hidden rows or SQL diagnostics.

### Stored field state machines

A stored scalar enum opts into lifecycle protection with `machine`. Its constant default is the initial state; nullable, array, server-initialized and nonstored fields cannot be machines. Existing enum fields retain ordinary `set` behavior.

```can
Given
 Job { status:enum(idle,queued,generating,ready,failed)=idle machine }
When
 scenario start(job:Job) by=members
  do
   transition job.status queued -> generating
Then
 page / title="Generation" poll=2s
  list Job
   alert
    require row.status==generating
    text "Generating"
   alert
    require row.status==ready
    text "Generation complete"
```

`transition record.field source -> target` executes at its written position in a mutation `do` body. Both endpoints are constant declared cases. The compiler derives graph edges with the canonical scenario or trusted-handler identity, including conditional/loop sites; identical endpoints owned by different operations remain distinct. Existing parameters, `by`, business guards, record versions and ownership rules continue to apply. Synchronous hooks, pure reads and migration mappers cannot transition. Self-transitions are permitted and count as writes.

The mutation pipeline validates the edge and its operation identity, then compares the source with the current provisional field. A source mismatch is `rule_failed`; malformed or undeclared edges are `validation`. Ordinary `set`, CRUD patches, creation inputs and hook rewrites cannot assign a managed field, even to its current value. Production creation owns the initial default. Fixtures and migrations may contain any valid declared state as a stored snapshot; they neither imply that earlier edges ran nor reset an existing row. Activation validates retained and mapped states before publishing the target schema. Locks, invariants, authorized reads, deletion and retention remain independent constraints; a terminal state does not freeze other fields automatically.

Ordinary record references keep their admitted version while domain field reads through the reference or an alias observe ordered provisional changes. Multiple effects on an existing row reserve one transaction version, with ordered history entries and one final committed row. A later failure rolls back every staged effect. Receipt replay and stale reference admission retain their existing owners. An explicit version or occurrence/correlation guard is still necessary for delayed completions after leaving and reentering a state; the state name alone is insufficient.

Frontend state views reuse presentation `require` gates. These predicates run on the authorized row projection, so omitted fields remain unavailable. `page poll=2s` requests authorized partial HTML at the configured whole-second cadence (1s–1h) and updates the view; it preserves the selected URL query/team, editable control values and focus while applying fresh server action/version/CSRF metadata. Withdrawn controls disappear. Failed, full-document, foreign-context or stale navigation responses stop painting. Polling pauses while hidden and resumes on visibility or cached back navigation. The HTTP dispatcher owns the page shell; generated render functions return content only. Visibility is advisory and never grants permission to transition.

Artifacts gate machine metadata with `state.machines@1`, including checking the loaded state producer's capability. Generated mutating scenario parameter bindings use an explicit `inputStyle="parameters"` marker and `state.parameters@1`; legacy unmarked callable envelopes remain supported. The public `transition` producer is state-owned and is exposed through the stdlib facade and the generated Cloudflare binding.

This first implementation is a flat stored lifecycle. Named reusable graphs, hierarchy, parallel states, history states, entry/exit callbacks and eventless cascades remain future design work. [Generation.can](../../examples/Generation.can) is an executable lifecycle viewer and declared scenario example, not an image provider integration. The compiled end-to-end witness covers canonical invocation and projected state rendering; broader generated form/action adaptation and provider/worker delivery keep their existing qualification boundaries. Complete generated hook/lock/invariant wiring and hook-version observations are not qualified by this change; the canonical seam normalizes transaction versions after pipeline rule evaluation.

### 5.1. Inline behavior examples

`require` and `do` define production behavior. An attached `examples` block checks that behavior through concrete cases. It does not change the operation. This is the BDD testing surface: shared fixtures are Given, the operation is When, and expected observations are Then. Package Given/When/Then sections retain their declaration meaning; each example inherits its action rather than repeating those headers.

```can
Given
 Expense { amount:money, submitted_by:user, status:enum(submitted,approved)=submitted }
 role reviewer
 policy Expense read=members
 fixture pending=Expense {amount=money(25,"EUR"),submitted_by=other}
When
 # Approve a submitted expense from another teammate.
 scenario approve(expense:Expense) by=reviewer
  require expense.status==submitted and expense.submitted_by!=actor
  do set expense {status=approved}
  examples expense=pending
   as,expense.status,expense.submitted_by -> expense.status
   reviewer,submitted,other -> approved
   reviewer,approved,other -> error(rule_failed)
   members,submitted,other -> error(forbidden)
   reviewer,submitted,self -> error(rule_failed)
Then
```

There are two test-only declarations, with one way to express each:

- `fixture name=Model {fields}` in package Given describes shared initial records; `fixture name=user {}` provisions a same-team test account and `fixture name=file {}` provisions a finalized test file, as specified below. Model fixtures use the existing field rules, including defaults, explicit parent/reference bindings, and constraints. Required fields must be supplied; no solver invents valid business data. Fixtures may reference other fixtures; cycles are errors. Fixtures are visible only to examples, and their names cannot collide with production declarations.
- `examples parameter=value ...` inside a scenario supplies its common input bindings. A CRUD declaration uses `examples create`, `examples update`, or `examples delete` followed by common generated-input bindings. Optional `seed=[fixture,...]` includes initial records needed by collection queries even when they are not operation parameters; referenced input fixtures and their dependencies are seeded automatically. Multiple blocks are allowed for different datasets, with the same syntax. For the ordinary one-operation form, the first child line is the table header `inputSelectors -> observationExpressions`; remaining lines are rows `inputValues -> expectedValues`. Commas separate columns outside brackets/braces/parentheses. A row must match the header's arity. A scenario may instead attach a shared-state `examples`/`do` sequence, specified below; the two body forms cannot be mixed.

For a table, the enclosing scenario/generated CRUD operation supplies the action and input schema. Header selectors name declared inputs, including whole typed contract/event values, generated CRUD changes such as `changes.title`, or fields of a fixture-bound record such as `expense.status`. Record-field selectors alter the row's **initial fixture state**, not the submitted update. Common bindings plus row values must supply every required operation input. Optional/defaulted inputs keep the operation's existing semantics. Input expressions are evaluated against the isolated initial state.

Each row gets a fresh team, deterministic accounts `self` and `other` in that team, and `outsider` in another team. These names are user references, not production globals. Fixtures are seeded as self; source `actor` defaults during seeding resolve to self. `as` selects the caller: a user-fixture reference or explicit `self`/`other` selects that account with its provisioned grants; `members`, `owner`, or a declared role invokes as self with that membership; an array such as `[owner,reviewer]` supplies combined roles to self; `public` is unauthenticated; `outsider` is the other-team account. Without an `as` column, the caller is self as an ordinary member. Fixture data and role selections are test-only; requests cannot grant themselves these identities.

Model fixtures describe typed **stored snapshots**, not client create requests or evidence that earlier operations executed. They may explicitly initialize domain fields declared `server=expr`, including `submitted_by=other`; this grants no production client write permission. Omitted server/default expressions evaluate as self. Reject authored reserved `id`, `version`, `created`, `updated`, `created_by`, `updated_by` and `archived_at`, unknown fields, invalid representation types, invalid references and invalid attachment setup. Row selectors may vary domain snapshot fields, including server-initialized domain fields, but never reserved metadata or user/file recipe internals. Snapshot construction does not invoke CRUD hooks or emit business events; a locked historical value is initial state, not an authorized edit of a pre-existing locked row. Fixture instantiation and simultaneous row overrides must satisfy all stored-data invariants, uniqueness, containment, lifetime/reference and file rules before any invocation. An invalid fixture fails setup; it does not count as the expected operation rejection. To test invalid inputs, change an operation input column. Input cells must have the declared representation type; business bounds and constraints are checked by the actual invocation, so an out-of-bounds input can be a rejection example. Fixture-field overrides are setup, whereas ordinary input/CRUD `changes` cells are submitted values; an invalid stored snapshot cannot be relabeled as invalid input. The runner loads referenced/seeded fixtures once per row, establishes their containment and references, and invokes the registered operation exactly once through its normal authorization/validation/commit path. Record IDs/current versions, operation identities, clock, and random defaults are deterministic test infrastructure. Fixtures start at version 1. `request` selectors can override declared wire-envelope fields, such as `request.expense.version` or `request.record.version`, to submit a stale version while preserving the real fixture version. They cannot create undeclared inputs or bypass validation.

Right-hand header expressions are read-only observations over freshly reloaded fixture records and `result`, the normal operation response. Expected cells are typed values independent of the implementation. A successful row requires operation success and compares every observation to its expected value. `error(code)` replaces the entire expected row: it requires that exact business error and verifies no domain writes, attachment relationships, committed events, or delivery intents were added or changed. Runtime rejection receipts/logs may still be recorded. Failing setup, unexpected errors, and failed assertions report the declaration, row, and mismatched observation.

Trusted handlers can attach examples using their inferred `event` input; the test runtime creates a typed verified source envelope and never exposes that capability through UI/MCP. External effects remain inspectable queued intents in the isolated state; examples do not dispatch live network calls. The runner does not substitute a different business implementation or skip policy checks. Provider delivery and the shared runtime's own concurrency/transport contracts are tested by that runtime's test suite; these tables make no claim to simulate all distributed failures.

Compilation emits a separate test artifact from fixtures/examples in the same source. Production execution and tool schemas omit them. Imported fixture members are test-only too: erase them before production import/dependency resolution and resource inference, omitting a group if no production members remain. Mixed groups retain the ordinary dependency semantics of their production members. The design adds no app-level test library, copied step definitions, separate test files, or generated expectations derived from `do`. Example count has no effect on app behavior. The initial parser recognizes tables and fixture declaration shapes; the sequence body introduced below is not yet parsed. Fixture provisioning, semantic checks and the example runner remain implementation work. The notation below is not an executed business-test result.

For each row, establish valid untouched baseline declarations and input bindings, evaluate all cells once against that baseline, then apply independent initial overrides together and validate the resulting setup once. Common input bindings establish the baseline and can be replaced by row selectors. Row-header selectors themselves must not overlap: reject duplicate paths, ancestor/descendant paths, and paths through different aliases that identify the same fixture field, even if supplied values happen to be equal. Assigning a reference edge conflicts with any other selector traversing that edge. Resolve alias conflicts against the untouched state, not against an earlier column's mutation. `request.*` changes the wire envelope and is distinct from fixture-state changes. Unsupported/conflicting selectors and invalid fixture setups are setup/compile diagnostics, never successful `error(code)` operation assertions.

An isolated table may additionally select the whole `status`, `result` or `error` of a directly named operation-resolved delivery recipe, for example `attempt.status,attempt.result,attempt.error`. This varies initial setup, never a published receipt: reserve deterministic references and plan valid baseline snapshots/normalized requests, evaluate all cells once, combine initial envelopes and model overrides, validate the final setup, then provision each protected receipt once before invocation. Request normalization is frozen against the untouched baseline; later model overrides do not recalculate it. A model invariant observes the final combined envelope. Invalid baseline declarations cannot be repaired by a row. Setup emits no send, callback or business completion.

Only direct recipe roots (including aliases resolving to that declaration) permit these three selectors. Request/binding/identity/authority fields, descendant result/error patches and traversal through stored associations such as `item.notice.status` are forbidden. Alias conflicts are checked before provisioning. Replacing `item.notice` with another valid fixture or null changes only that model's initial association. Full target-result/status/error consistency and finalized-file provenance still apply; cells cannot manufacture file authority. Sequence-time recipe writes remain unavailable. The [bounded selector witness and consultation evidence](../../design/delivery-recipe-overrides-20261004.md) specify setup order and negative diagnostics without claiming an implemented planner.

For example, `event,event.reason` conflicts because it assigns both a whole value and a child; `booking.resource,booking.resource.active` conflicts because it changes a reference and traverses it. If two input bindings refer to the same seeded record, `left.title,right.title` conflicts. `booking.status,request.booking.version` is independent state/envelope setup. A common `event=fixture_value` plus the row selector `event.reason` remains legal; common bindings are the intentional baseline, not a second header patch.

#### Same-team user fixtures

```can
fixture claimant=user {}
fixture first_reviewer=user {roles=[reviewer]}
fixture finance_approver=user {roles=[finance]}
```

`user` is a test-only recipe in the existing fixture declaration, not a production account constructor. Each declaration provisions a distinct active member of the row's current team, also distinct from `self`, `other` and `outsider`. Identity derives from the canonical fixture declaration and isolated row; import aliases reuse it, internal setup retries preserve it, and separate rows never share accounts or grants. This expresses three or more current-team actors without using a foreign account or adding production records.

Every provisioned test account (`self`, `other`, `outsider` and user fixtures) has its own deterministic valid email under reserved `example.test` and `email_verified=true`, supplied through the same canonical-auth admission facts as production. The address is stable for that account within the isolated example and across internal retries; authors need not hard-code its generated spelling. Only the current authenticated `actor.email`/`actor.email_verified` are readable, as §4 specifies: `other.email`, named-user email properties and account-directory queries are not introduced. During snapshot seeding `actor` remains self, so `email=actor.email` matches a later self invitation/claim call even if other steps use different callers. Public invocation has no actor; selectors/request overrides cannot fabricate or change auth facts. Unverified-address/auth-provider cases remain shared auth tests until an explicit test capability is specified; no email is actually sent.

The only recipe attribute is `roles`, a static list of `owner` and/or visible declared role identities. Omission or `[]` grants ordinary membership only; membership is implicit. Reject duplicate roles, unknown names, `members`/`public`/`outsider` entries, dynamic expressions and all other attributes. A role grant uses its owning declaration identity, including imported aliases; it confers exactly the production authority that role denotes, not universal record access. User fixtures are immutable setup recipes: selectors cannot patch their fields, team, membership or roles. Inactive/external-account recipes and grants added to the built-in `other` are outside this extension; use a named user fixture for a noncaller grant.

`as` accepts exactly one provisioned user-fixture reference, `self`, `other`, or an existing caller selector. A fixture caller keeps its declared roles; selecting it does not grant roles to self. Legacy role selectors and role arrays still apply to self only, with no inherited grants from another row. Do not mix user identities into role arrays or accept arbitrary production user expressions as caller selectors. Names and aliases must resolve unambiguously. Omitted `as` remains ordinary-member self, independent of which user recipes are present. Trusted handler examples retain their verified source context; `as` cannot impersonate a user for a trusted handler.

Load user recipes reachable from the explicit seed, common inputs, or selected row's input/caller cells and their dependency closure. Provision their identities and grants before dependent model/file fixtures, then evaluate ordinary fixture defaults as self and apply row overrides. Observation/expected expressions do not implicitly seed users; explicitly seed an otherwise unreferenced account needed for an observation. File recipe `owner` additionally accepts a named user fixture with this same dependency rule; omit it to retain self ownership. File attachment admission still runs as self during seeding and as the selected caller during invocation. Selecting another caller never rewrites seeded server-owned fields, authorship, or file ownership.

These additions enable positive noncaller-role and three-member operation examples. Every table row still invokes one enclosing operation exactly once. Isolated rows seeded at successive historical states do **not** execute a claimant→reviewer→finance journey or establish that earlier authorized transitions produced that history. Use the explicit shared-state sequence below when earlier authorized transitions themselves are part of the required evidence. Account provisioning, grant validation, caller resolution and sequence execution remain proposed semantics, not implemented behavior.

#### Shared-state examples

Keep tables for an isolated operation. When the required evidence depends on earlier committed operations, attach an `examples` block with a `do` body to one of the participating **user scenarios**:

```can
examples seed=[reviewer_one,reviewer_two]
 do
  call Expense.create {purpose="Travel",amount=money(25,"EUR")} by=other
  let draft_claim=first(Expense as claim where claim.submitted_by==other)
  draft_claim!=null -> true
  let original_version=draft_claim.version
  call submit {expense=draft_claim} by=other
  let submitted_claim=first(Expense as claim where claim.id==draft_claim.id)
  submitted_claim!=null -> true
  submitted_claim.status -> submitted
  call approve {expense=submitted_claim} by=other -> error(forbidden)
  submitted_claim.status -> submitted
  call approve {expense=submitted_claim} by=reviewer_one request={expense={version=original_version}} -> error(conflict)
  call approve {expense=submitted_claim} by=reviewer_one
  let approved_claim=first(Expense as claim where claim.id==draft_claim.id)
  approved_claim!=null -> true
  approved_claim.status,approved_claim.decided_by -> approved,reviewer_one
  call approve {expense=approved_claim} by=reviewer_two -> error(rule_failed)
  approved_claim.status,approved_claim.decided_by -> approved,reviewer_one
```

This is the sequence alternative of the existing `examples` declaration, not a new package-level test declaration or a production scenario. Its header accepts only the optional `seed` binding; all operation arguments are explicit at their call site. There is no implicit call to the enclosing scenario. Require at least one explicit call to that scenario and at least one observation assertion or exact expected-error call. The source location identifies the example; no additional authored test name, copied signature, step definition, or separately maintained workflow manifest is required. Existing tables and their common inputs remain unchanged. A generated CRUD operation can be a sequence step; CRUD declarations and trusted handlers retain their table form in this bounded version.

The nonempty `do` body contains only immutable `let`, test calls and observation assertions. There are no direct writes, fixture patches, grant changes, loops, branches, provider calls, trusted-handler impersonation, sleeps or nested sequences. Bindings are inside `do` and obey ordinary lexical/type rules. A call has the form `call Operation {arguments} by=caller [request={...}] [as name] [-> error(code)]`. Resolve `Operation` to an accessible local canonical user scenario or enabled generated CRUD action; operation/action schemas are derived from that declaration. Bound remote services and trusted entry points cannot be invoked directly here. A production `call` inside an invoked scenario retains its existing same-transaction/same-caller semantics.

Every test call requires `by` to select exactly `self`, `other`, `outsider`, `public`, or a named user fixture. This selects the caller; it is not a role expression or an authority bypass. Role names and role arrays are intentionally unavailable at sequence call sites: grants are provisioned once from user fixtures, so changing caller cannot silently grant or revoke roles between steps. Use a named `user {roles=[owner]}` fixture when owner authority is needed. Ordinary `self`/`other` stay active members, `outsider` is authenticated with no membership in the example's current team, and `public` is unauthenticated. The resolved operation/team stays the example's team when outsider calls; the runner does not switch the data under test to outsider's other team. `authenticated` is a production predicate, not a caller selector in either example form. To exercise an external customer's grant, reference outsider in the explicit customer relationship and call as outsider; mere operator membership does not remove a customer's separate rights. An account reference to an explicitly external user is not a foreign-team stored-record reference.

Resolve each call's `by` identity before evaluating its inputs and request callbacks: those callbacks see that caller's canonical `actor`/authentication facts and the fixed example clock. Between calls, `let` and assertions see the last selected caller (initially self); an expected rejection retains that caller and clears `result`. Inspection privileges never become operation authority: production admission reconstructs its real authority independently.

Each test call obtains a fresh ordinary admission, operation identity and transaction. Run its actual `by`, input normalization/bounds, typed reference/version admission, written guards/effects, invariants, locks and disclosure. Authentication/team/`by` checks precede body guards; a denied `by` yields `forbidden` even when a body guard would also fail. Missing/foreign-owner/expired record admission yields `not_found`; stale submitted versions yield `conflict`; validly represented inputs outside their declared input bounds yield `validation`; authored guards, stored invariants and locks reject with `rule_failed` unless the production contract explicitly specifies a different safe code. This is not a global reordering of authored checks or existing replay handling. `error(code)` accepts one exact documented business-code literal; a parse/type/name/setup failure, assertion mismatch, unexpected exception or provider outage cannot satisfy it. Derive every expected code from the operation's real admission and first failing check, never from a hoped-for denial category.

Seed the fixture dependency closure once before the sequence, including references from all call inputs/callers, request expressions and `let` initializers; references used only in observations/expected values still require explicit seeding. No later step provisions more records or resets the initial snapshot. Pure expressions evaluate in written order. Before each statement, fixture names resolve to freshly reloaded state, including current record versions; callers do not rewrite fixture ownership. A `let` captures an ordinary immutable value, including a record's version at binding, rather than a magic live alias. Re-query/rebind a newly created record before a later mutation if an intervening call changed its version. A typed business result may be bound with `as` only when the selected operation actually declares that result; neither changed-record metadata nor an operation-local `create ... as` invents a result for a void operation. A rejecting call cannot bind a result. A `let` query plus explicit nonnull assertion can discover a new stored record when the operation returns no business value.

The optional `request` object alters only declared wire-envelope fields supported by table `request.*` selectors. For example, `request={expense={version=original_version}}` submits a captured stale version while leaving the actual record unchanged. Unknown/protected fields, attempts to grant identity/roles, conflicting input paths and invalid envelope shapes fail setup/checking. No request override can bypass normal admission. Each step's request identity is distinct and stable across internal retries; this form does not author replay identities. The isolated clock remains fixed through the example, with a separately fixed admission context per call; a sequence demonstrates commits and causality, not elapsed time or background delivery.

An observation statement is `expression,... -> expectedValue,...`, with nonempty equally sized tuples and independently authored typed expected values. It reads reloaded isolated stored state, test bindings and the most recent successful business `result`; inspecting stored state grants no operation or returned-data privilege. A sole Boolean observation `condition -> true` supplies the normal true-branch type narrowing to following test statements, including a nonnull check. No other matching value introduces new narrowing rules. Compare records/files by their existing reference identity and other values by declared typed equality. Assertions neither write data nor invoke business operations. Unexpected rejection or a mismatched assertion fails the example immediately. Successful calls commit before the following statement. An expected-error call must return exactly that error and leave domain state, attachment links, committed events and delivery intents unchanged relative to **immediately before that call**, retaining all earlier successful commits; it clears the current `result` and execution then continues. Runtime rejection receipts/logs are allowed as for tables. Final cleanup isolates the whole sequence from every other example.

Sequences can now describe real submission, separate review, finance recording and correction calls with independently checked history. They do not prove runtime behavior until an engine executes them. External integrations remain queued inspectable intents with no live dispatch; timer/provider outcomes and role revocation require real existing canonical operations or remain outside this bounded form, never direct fixture edits between calls.

This extends the existing fixture declaration, not the production value grammar. Rejected policy, invalid sample or failed finalization fails setup; it cannot satisfy `error(code)`.

Referenced file fixtures load automatically through the existing dependency/import/export rules before their dependent records or invocation inputs. Row/declaration identities are deterministic and stable across internal setup retries. Physical content deduplication cannot collapse reference identity. To test a foreign upload rejection, pass a valid unattached foreign file to the operation; attaching it illegally during seeding is a setup failure. Invocation rechecks attachment authority and limits under its actual caller.

Provision files and seed valid records before recording the operation's rejection baseline. ## 6. Handlers and events

`by=` means a user-callable operation. `on=` means a typed trusted source. They are mutually exclusive. Handler input is inferred from that source and bound to `event`; handlers declare no client parameters and never become MCP tools. `scenario name on=Source` retains the same require/do body.

A declared-event handler may select `each=Model [as child]` or
`each=event.parent.Child [as child]`. The first selects a same-package stored
model; the second requires a nonnullable event reference and that parent's
contained collection. The optional alias is a checked stored child reference
in the handler body. It cannot hide contextual facts or collide with a source
event field in the current flat private admission profile. The compiler emits
the existing cohort descriptor and private event invocation metadata, adding
one required ID-only child reference to the exact selected model. Its input
name is the authored alias, or reserved `$cohort` when no alias is authored.
The callable remains private and requires `state.cohorts@1`. A target must
join that metadata to its canonical child invocation and current row loading
before advertising the capability. The [source/native compiler check](../../compiler/tests/cohort_trigger_runtime.rs)
qualifies child identity, bindings, written effect order and failures; frozen
membership, child transaction/replay and the complete fanout workflow remain
runtime qualifications. Periodic, lifecycle and delivery-progress cohort
lowering still reports an explicit unsupported diagnostic.

| Source | Contract |
| --- | --- |
| `Model.create`, `.update`, `.delete` | Pre-commit CRUD hook; `event.before`, `event.after`, and `event.input` have generated types; unavailable record side is null |
| `Model.created`, `.updated`, `.deleted` | Committed change event with record ID, owner, resulting version, and occurrence ID |
| `teams.member_removed` | `{team_id:text,membership_id:text,user:user}` with retained removed-account attribution |
| Declared `Event` | Payload from `event Event {fields}` and `emit`/`schedule` |
| `every(5m)` | Runtime tick with scheduled and actual instants |
| `instrumentation.error` | Bounded standard ErrorReport from generated runtime/browser reporting; server stamps source/context and validates untrusted browser fields |
| Named queue or adapter event | Payload from its declared contract, verified by its ingress |

At most one hook per model/CRUD operation. Hooks run on the proposed state before invariants/locks/commit, can reject or adjust it, and cannot introduce new client parameters. On create, event.before is null; on update both record sides exist; on archive-delete after is the archived record, and on remove-delete it is null. Before/input are read-only. `set event.after {fields}` adjusts the pending create/update record without recursively invoking CRUD; a delete hook can reject but cannot adjust its target. They cannot call back into the triggering CRUD. Scenario effects also emit committed model-change events; they do not pretend to be CRUD or re-run CRUD hooks. Rules that must apply to all writes therefore belong in Given invariants/locks. A committed event handler is a later transaction; it cannot retroactively reject its source operation.

Committed-event payloads are immutable identities, not an implicit historical record snapshot. Loading their record reads current authority state; obsolete work must check current guards. Declare event payload fields for values that must be preserved at emission. Each handler receives an independent stable occurrence identity, and duplicate deliveries replay its receipt. Do not infer events from enum names or scenario names.

Error reporting cannot participate in the transaction that failed. Instrumentation dispatch is bounded and best effort, strips credentials, records drops, and excludes failures of its own reporter to prevent loops. A handler can forward `event` to a declared error-reporting adapter; naming CanCatch or Sentry alone supplies no integration.

Recurring `every(duration)` ticks are UTC-epoch aligned; missed periods coalesce to one current occurrence. Calendar-specific schedules compute an explicit `at` instant with §3's pure helpers and `local_instant`. Month-end policy, working days, missed-cycle recovery, cancellation and renewal consent remain authored business rules; no general recurrence grammar or automatic monthly billing is inferred. A dynamic schedule key is unique within app/owner/package, independent of the calling operation, so booking, rescheduling, and cancellation can address the same key. Cross-package changes call the owning package's operation. Replacement and cancellation commit with business changes. Handler guards run again when due. Replacing a pending occurrence supersedes it; already admitted work or provider-accepted messages may complete. A superseded/cancelled occurrence also supersedes its undispatched delivery intents. A send's optional `when` is a pure dispatch guard over current owner state and retained lexical inputs; omitting it means unconditional delivery of that committed event. State-dependent notices declare that guard. Dispatch atomically checks supersession and the guard before claiming the provider call; false means skipped. Business-operation admission guards are not implicitly rerun after their effects. Persist pending, delivered, failed, and uncertain outcomes. A false authored handler require is a terminal business failure; a transient runtime failure retries the same occurrence.

An `every` handler infers its data scope from owner-bound queries, writes and local-call dependencies. Team-D1 handlers receive one independently admitted occurrence per extant eligible team; exclusively app-scoped handlers receive one app occurrence. Each occurrence has a concrete verified team/storage context, its own receipt and bounded transaction. Mixed incompatible scope families or cross-owner atomic bodies fail checking. Identity includes selected app, compatible canonical handler contract, concrete owner and UTC epoch slot; compatible releases do not mint duplicate ticks. Missed slots coalesce per scope, new scopes begin at the next slot, and removed scopes admit no future work. V1 recurring fanout covers D1 team/app scopes. Root-bound `every` is unsupported until authoritative root coverage has a specified contract; an eventual root index is insufficient. Root recurrence uses existing explicit record-bound `schedule`. No authored tenant loop, cron file or fabricated actor is introduced.

Email is `send Mail.send` through the standard email contract, inside a business or event-handler scenario. It is not a second free-form workflow language under Then. Then is exclusively presentation; earlier standalone `email ...` draft lines migrate to typed handlers. Notification content, recipient, and schedule are business choices; delivery bookkeeping is runtime behavior.

## 7. Storage, consistency, and retries

Every mutation has one authoritative storage owner. D1 is the default. A first-class binding can move a whole related group:

```can
# Coordinate each calendar's bookings.
app CalendarDemo
context
 binding Schedule DurableObject key=CalendarDemo.Calendar
Given
 Calendar at=Schedule { name:text }
 Booking in Calendar { start:datetime, end:datetime }
 invariant Booking: row.start<row.end
When
Then
```

Each Calendar ID selects one SQLite Durable Object instance; its children inherit it. New root IDs derive deterministically from the complete operation identity, including the originating principal/team/operation, so a fresh replay routes to the same owner. Child references include their root routing identity. The runtime supplies a root-ID/owner directory and authorization context, not a writable D1 duplicate of those records. The directory is an eventual discovery index updated through committed owner work; it never decides record access or availability. A returned root ID routes directly even before indexing completes. Team-scoped browsing of roots uses that directory and loads authorized owner records with bounded fan-out. Cross-owner joins/aggregates are forbidden in business mutations; read views are explicitly eventual. A reference can identify another owner but cannot imply an atomic read or write there. Invariants must live entirely within one owner. Cross-owner workflows use durable events and explicit pending business state. Atomic owner transfers are outside v1.

CRUD and scenarios infer their authority from mutated records and dependencies. A call targeting more than one owner instance fails before commit. Pure shared constants are allowed; mutable remote configuration needed for a decision must be copied into authoritative state with declared version semantics. Admission-time authentication, role, and active-membership facts are a trusted context snapshot, with the revocation boundary in §4; they do not imply a cross-D1/DO transaction. Business eligibility requiring atomic revocation must live at the same owner as the decision. No per-scenario authority selectors, user-written reservation mirrors, or pretend transactions across services.

D1 does not provide a JavaScript transaction callback for arbitrary read/branch/write workflows. V1 uses a **database-wide optimistic revision fence**:

1. Read the primary revision before all state-dependent reads, including permissions, receipts, relations, and aggregates.
2. Evaluate bounded pure DSL against those reads and proposed local changes. No externally observable effects occur.
3. In one D1 SQL batch, assert the same revision, apply writes/constraints/history/receipt/outbox, and increment the revision. The assertion must raise an SQL error on mismatch; a zero-row update is insufficient.
4. A failed assertion rolls back the entire batch and retries evaluation, at most three attempts. Submitted stale record versions still produce a conflict, not an automatic overwrite. Exhausted contention returns a retryable error.

All runtime writers participate, including membership, delivery bookkeeping, and migration writes. External raw writes invalidate the contract. Revision values never reset while admissions continue. Reads use the primary in v1. Pure read operations validate the revision again after dependent reads; changed revisions retry rather than return a mixed authorization snapshot. A successful mutation rechecks current read permission before serializing its result.

This is our proposed execution strategy based on [D1's transactional batch guarantee](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch), not a performance result. A prototype must establish acceptable contention/latency before claiming production readiness. Durable Objects use their local SQLite transaction semantics; workerd without provisioned bindings does not supply Cloudflare services.

Mutation envelopes include a stable UUIDv7 operation ID and expected versions for existing record inputs. The runtime generates these for browser forms; MCP exposes them as protocol inputs without `.can` boilerplate. Receipt identity includes app, owner/team, principal, fully qualified operation, and ID. Authenticate and locate/check a receipt before version checks, dynamic defaults, or business evaluation. Hash normalized explicitly supplied inputs (including their submitted versions), distinguishing omission from null; persist originally resolved defaults separately. Different reuse conflicts. Completed replay returns the saved outcome projected against current access, even though its submitted versions are now stale. A repeated request with the same identity never intentionally initiates a second external payment.

Runtime defaults: identities older than 24 hours are rejected, with five minutes of future clock tolerance; ordinary receipts remain at least seven days. First check for an existing receipt, then enforce age for an unseen identity. After receipt expiry an old identity cannot execute anew. Trusted occurrence IDs are runtime-owned and retained through the entire retry horizon. Payment identities remain associated with their payment records. Audit history defaults to 90 days; longer business evidence is declared as actual retained records. Deployment may lengthen retention, and must never shorten it below replay/retry requirements. Restores stop admissions and invalidate in-flight attempts before resuming.

Every external effect is a durable outbox item committed with its originating state. Its identity derives from operation ID, source declaration, and deterministic occurrence index. Delivery uses exponential backoff with jitter, at most eight attempts within 24 hours by default; capability contracts may require a longer reconciliation period. Permanent errors stop retries. Recovery scans find unsent work without depending on an in-memory callback. Provider uncertainty remains uncertain until reconciled; retries reuse the original provider identity. Dead-letter/failed items are visible to authorized operators.

Cloudflare Queues provide [at-least-once delivery](https://developers.cloudflare.com/queues/reference/delivery-guarantees/); outbox receipts and current-state guards handle duplicates and reordering. No exactly-once external delivery promise. Schedules use a shared D1 due-work dispatcher or the owner's Durable Object alarm, selected by runtime. App source declares timing, not a Cron/alarm plumbing layer.

### 7.1. Declared retention

`retain Model until=expr` in Given is the single canonical model lifetime declaration. At most one belongs to a model. `expr` is a pure `datetime?` in `row` scope. A null result supplies no independent deadline; it does not remove any finite containing deadline. Its dependencies are bounded entirely at its storage owner; it cannot use a sliding `now`, caller identity, operation state or random values. For example, `retain Transition until=row.occurred+row.parent.history_days*1d`. No declaration also means no independent lifetime. For a closure-driven lifetime, an authored close operation can store a nullable deadline on the owning parent and reopening can clear it; the child refers to that recorded deadline. No sentinel date, sliding renewal loop or new conditional expression syntax is needed. A contained child inherits a parent's effective deadline; an explicit finite child deadline must be no later than any containing ancestor's finite deadline. Validate affected lifetimes on the proposed final transaction state, including configuration changes; reject conflicts or oversized dependency work, never silently shorten a requested lifetime.

At deadline<=admitted `now`, the owner runtime irreversibly expires the row and its contained subtree, including archived records. Queries, record lookup, forms, MCP, history content and file downloads deny expired content even before physical removal. Runtime lifecycle stamps are protected state under the same revision fence; every relevant admission evaluates due expiry before allowing a write. Extending configuration, clearing a nullable deadline through an authorized reopening, or establishing a later closure affects only unexpired data and cannot resurrect an expired row awaiting disposal. Evaluate due expiry against the pre-write lifetime before admitting those changes; an inherited finite deadline continues to apply even when the child expression is null. Already admitted operations follow the owner-fence rules. Expiry is independent of enabled user CRUD and produces no cleanup tool, synthetic user identity or authored timer loop.

Lifecycle disposal does not invoke CRUD hooks. Physical removal emits the existing identity-only committed deletion source; handlers see current availability and cannot recover expired content from it. No new domain workflow or notification is inferred from expiry.

This declaration explicitly permits whole-record disposal of expired locked evidence. It permits no field change, premature removal or general trusted lock bypass. Physical disposal is a bounded owner transaction preserving invariants and references: **every stored incoming reference** outside the removal set blocks removal, including archived/expired referrers. An eligible owner-local closure may dispose expired cycles together if it fits the work budget; otherwise it remains visibly blocked. Cross-owner references cannot be cleared by a pretend atomic cascade. Stored uniqueness also remains reserved until physical disposal; a hidden expired row may block a new conflicting key. Admission may perform bounded eligible disposal before allocating that key, but must return retryable `busy` with safe retention-block details if disposal is impossible rather than bypassing constraints or claiming success.

The runtime uses stable resumable cleanup batches over stored rows, not a `for limit` that silently truncates. Track logical expiry, physical backlog, blocked references and retry failures for authorized operators. No exact erasure second is promised. Commit attachment/reference release before retryable R2 deletion; other valid attachments preserve shared objects. The receipt/attachment horizon and external provider copies may delay physical erasure and must be reported separately from local visibility. Lifecycle retention applies to copies in local audit snapshots, response receipts and outbox payloads as well as the original fields: discard expired content, skip undispatched work that requires it, and keep only explicitly safe attribution/outcome and replay metadata. Replayed mutation responses may have `result=null` when saved result content expires or current access withholds it; keep the safe committed status/operation identity, never synthesize a schema-invalid partial result or re-execute the mutation. Retention does not recall provider-accepted content. Deployment may lengthen audit metadata retention for replay, but cannot silently extend the lifetime of declared sensitive content.

Replay identity is independent of business-history expiry. A verified ingress mapping must establish its configured source/site namespace and preserve a stable producer event ID through queued work, retaining owner-scoped keyed digests/technical outcomes through the declared retry horizon. A public browser key does not authenticate a visitor or establish that event content is true. Raw user-controlled event text is not automatically safe metadata. A repeated event cannot become new work when its business row or snapshot expires; an unseen expired/too-old occurrence is rejected. Expiring a digest must not permit reuse of its old identity: the ingress must enforce verifiable occurrence age or retain a safe tombstone. If the source cannot establish this identity/replay boundary, deployment must reject that ingestion contract rather than rely on purged data for deduplication. Applications still recheck their business timestamp window when delayed queued work is processed.

## 8. First-class services and integrations

The v1 service registry is finite. These declarations are recognized and typed, rather than raw environment handles:

| Declaration | Contract |
| --- | --- |
| `database D1` | Default authoritative relational storage and generated indexes/migrations |
| `binding Name DurableObject key=RootModel` | Per-root authority described above |
| `file` use; optional `files types="application/pdf,image/png"` or `files max=20MiB` in context | Implicit R2, bounded upload, immutable completed file references, authorized download; declarations specify only changed policy values |
| `queue Jobs type=Work` | `send Jobs.publish {value}` and `on=Jobs` typed delivery; bound Queues transport |
| `cache KV ttl=5m` | Runtime cache for explicitly public, reconstructible presentation assets/results; never permission, session, receipt, or invariant authority |
| `analytics Events {kind:text,value:decimal}` | `send Events.write {kind,value}` to Analytics Engine; telemetry is not authoritative billing/audit data |

Application-owned queues/telemetry have declared deployment quotas; overload records failure rather than pretending success. KV is an optional runtime optimization; no second user data CRUD API. Additional Cloudflare products can add versioned typed registry contracts when needed. Workers AI, Vectorize, Workflows, and arbitrary product SDK surfaces are not silently included in v1. These boundaries do not prevent future first-class support.

D1 is already the app default. Runtime-included declarations using `file` imply one R2 file store for the selected app; apps without file use require none. Schema-only provider discovery does not provision its file storage. The language-version-pinned upload default is `types="application/pdf,image/png,image/jpeg,text/plain" max=10MiB`, defined here once. It matches the former uniform draft setup. A `files` context declaration supplies only actual deviations; omitted attributes inherit the baseline. R2 is implicit in the files primitive and is not repeated in source. Defaults never grant access or infer an attachment from a URL. Whole-package dependencies containing file fields use this same store, even when their pages are unselected. Compose explicit file-policy values before applying defaults, rejecting conflicting explicit values. Additional app-specific upload requirements remain reviewable; these defaults are not a claim of complete acceptance coverage. Queue/analytics declarations retain their explicit names and schemas. Declarations in an unselected app do not configure another app merely because both occur in the same file.

R2 uploads have a generated runtime flow: authorize intent, enforce type/size/quota, upload, finalize, attach the resulting reference. A partial upload is unusable. MIME labels alone do not validate content; supported formats are checked by runtime. Unattached uploads expire; replacing a reference never overwrites content. Attaching a file requires a finalized upload owned by the current app/team/principal, or an existing attachment the caller may read; recheck destination field limits. Possessing an opaque file ID alone grants nothing. Download is allowed through an owning record/field the caller may read, without requiring access to other owners of the same object. Links cannot grant more access than that flow. Completed but unreferenced objects are garbage-collected after the receipt/attachment horizon.

Browser and supporting chatbot hosts use this **same upload flow**, not a business upload scenario. The generated runtime exposes a versioned HTTPS host bridge. MCP initialization advertises it once in `_meta["org.canlang/fileTransfer"]` as `{version:1,intents:"https://selected-app-origin/files/intents"}` when selected runtime declarations use files. This is a Can extension using MCP's [metadata extension mechanism](https://modelcontextprotocol.io/specification/2025-11-25/basic/index#meta), not a standard MCP byte-upload capability. A host validates the HTTPS origin against its connected app and accepts no model-supplied endpoint or credential. File-valued generated JSON schemas annotate their existing opaque-string slot with `format:"can-file"`; this identifies the kind of input, not a separate schema or authority. The host reads canonical tool/field schemas rather than copying them into app source. Metadata does not grant file access.

The bridge v1 contract has three steps, shared with generated browser controls:

1. `POST /files/intents` receives `{upload_id,operation,field,arguments,name,type,size}`. `operation` is an exposed canonical mutation identity; `field` is a JSON Pointer to its writable file input, including a CRUD changes slot when applicable. `arguments` contains available canonical operation arguments and protected action-handle context; its selected file slot is absent. This preparatory request may omit unfinished ordinary inputs, but cannot invent inputs, override protected bindings or treat missing values as passing checks. `upload_id` is a stable caller-generated retry identity separate from the later business `operation_id`; size is a canonical nonnegative integer string. The runtime resolves the same app/user/team and current operation authority, checks writable input shape and effective file policy/quota, and requires any record/parent context necessary for the intended upload. Unknown or unavailable required context fails safely. Business guards whose complete inputs are not yet available remain unevaluated; upload admission never establishes business acceptance. Return `{intent_id,content,finalize,expires_at}` with opaque intent identity and generated same-origin HTTPS destinations, not storage credentials. Filename and claimed MIME/size remain untrusted metadata.
2. The authorized host sends the actual selected bytes with `PUT` to `content`. The runtime enforces byte limits, actual supported content/type and quota while receiving them. An incomplete or rejected transfer cannot yield a usable file. The host never asks the model to encode the file as a tool argument, and local paths or URLs are not accepted in place of bytes.
3. `POST` to `finalize` checks current principal/team/intent rights and validated complete content, then returns `{file:opaque_file_id}`. Repeating the same completed intent returns its same immutable reference; conflicting retry identity/context or replacement bytes fail. Finalization does not create/update a business record. The host supplies the reference to the original canonical mutation, which rechecks all current admission, versions, field/attachment permissions, limits and ordered business guards. A denied operation leaves an unattached object under the ordinary cleanup horizon, not a partially committed receipt.

Bridge authentication uses an app-audience runtime authorization for the same principal/team as the MCP connection; MCP tokens are not blindly forwarded to another audience or origin. The shared runtime authorization layer establishes that relationship, with no identity/team arguments or reusable public upload URLs. Existing readable attachments can be used directly without reuploading, under the same final attachment rules. Hosts that do not implement this extension must offer the generated browser upload handoff and return its authorized finalized reference, or report that a new attachment cannot be supplied. They cannot silently omit a required file or claim an upload succeeded. MCP [resource retrieval](https://modelcontextprotocol.io/specification/2025-11-25/server/resources) is not a client upload mechanism. Unsupported hosts do not become attachment-capable merely because they support tools.

For CanExpense, a supporting host binds the existing `expense.Expense.create` receipt slot and Employee parent through the canonical schema, transfers selected receipt bytes, then calls that same create operation with its finalized file and business inputs. Oversized/malformed/partial transfers yield no file; a different team's reference or a newly revoked caller fails ordinary admission; a valid completed receipt follows the declared Expense workflow. No `.can` upload lines, second MCP server, binary business tool or hand-authored per-app transfer contract is required. The bridge, host adapter and successful end-to-end receipt task remain unimplemented; [three consultations and the contract reasoning](../../design/jev/mcp-file-handoff-20261004/README.md#source-assessment) provide draft evidence only.

Bound file-valued results become successful typed completions only after canonical receiving-app finalization has checked immutable bytes, content/MIME, size and quota. A foreign ID, URL, structural file object or transport success is insufficient. Internal provenance binds receiving app/team/storage owner, verified originating principal/source, adapter, delivery and result path. That completion may attach only its own finalized result, under current destination limits and authored correlation/owner guards; its handler retains `actor=null`. Finalization identity is stable per delivery/result path and ordered item position; retries reuse immutable content, and conflicting content fails. Existing receiving-store content is reusable only with verified provenance. Transfer occurs before the completion transaction, not atomically with it; rejected handlers leave no attachment link and orphan content follows the existing cleanup horizon. No new transfer DTO, per-app download helper or blanket attachment privilege is introduced. These remain unimplemented adapter/runtime contracts.

The same receiving-app finalization applies to file fields in verified capability events, including incoming email attachments. Its provenance uses the configured source/adapter, authenticated event occurrence identity, schema field path and ordered item position in place of a request delivery/result path. An event payload cannot appoint its own trusted source or confer file ownership. Finalize before admitting the typed event; replay reuses those immutable files, conflicting bytes for the same occurrence fail, and the handler may attach only files finalized for that occurrence under its destination/correlation guards. A raw external file ID never becomes an authorized attachment merely because the event schema says `file`.

Structural `contract` defines data. `capability` defines external operations/events:

```can
contract ErrorReport { message:text, occurred_at:datetime }
contract ReportAccepted { reference:text }
export capability Errors version=1
 report(value:ErrorReport) -> ReportAccepted
```

The provider owns these declarations. Its consumer declares `use provider {Errors as Catch} from=deployment.Catch` at package scope; the exported interface carries the reachable ErrorReport/ReportAccepted schemas.

Capability operations have typed inputs and eventual provider results. `-> R` describes that provider result, not the enqueue receipt. `event changed {fields}` inside a capability declares a verified inbound event; `on=Catch.changed` selects it. `DeliveryResult` remains the runtime `{id,status}` receipt summary. `send Catch.report {value}` persists work and returns `delivery(Catch.report)`, the protected association specified below; synchronous provider results are not available inside a business transaction. Adapter completion is exposed as the typed `Catch.report.completed` source, carrying `{delivery_id,status,result:R?,error:DeliveryError?}`; success has a result, failure has a typed safe error, and uncertainty is not success.

Bound exported user operations reuse the same delivery path. The provider result is the canonical operation response, and `Target.completed` carries its typed completion; no duplicate consumer result contract is required. Adapter transport success alone cannot establish owner commit. Invalid provider result schemas produce a typed failed completion, not a silently pending request. A delegated work-list reply must state the status of every configured source, with unique known source keys; missing, duplicated or unknown entries fail projection validation. Bounded typed items and source statuses establish fresh/partial/unavailable views explicitly. Each actionable item must belong to a fresh source and carry its verified reference; an unavailable/stale source cannot expose an executable old action. Its authorized summary/detail supplies the business context needed to answer the form, such as a frozen checklist. The runtime does not invent those instructions or read hidden owner fields to fill a gap.

A capability implemented by a Can owner must specify its exact operation-to-ingress and committed-outcome mappings in that owner's interface contract. A trusted ingress event is not a successful operation result. The installed binding authenticates the producer, fixes the allowed team/resource namespace and carries the original delivery, canonical operation kind and immutable request digest in the verified causation envelope. Resolve authority from declared request references; cancellation before creation must use explicit resource/owner routing and an owner tombstone where required, never an eventual mirror lookup or guessed global scan. Reusing a logical source with different arguments fails instead of changing its meaning.

An emitted outcome can complete only the matching originating delivery after the owner's transaction commits. The adapter uses retained causation metadata, not business source text alone, to distinguish charge/cancel/refund or hold/confirm/release. A rolled-back handler cannot publish a success; business rejection maps to the safe typed failed receipt, and missing/uncertain commit evidence remains unknown. Transport success may carry `OperationOutcome.state=pending` when the owner committed a pending business state; it cannot claim fulfillment or payment. Later domain-change events retain their own verified source/revision identity and do not complete unrelated requests. Mapping may serialize an existing declared outcome but cannot invent an owner operation, result fields, delegated role or cross-owner atomicity. These are explicit binding obligations using existing capability/event primitives, not another app-authored build manifest.

Deployment binds an adapter to a versioned implementation of that contract. For another canlang app or a typed HTTP/service binding, the contract and explicit wire mapping are sufficient; vendor-specific authentication, signatures, pagination, and error mapping belong to that adapter implementation. The compiler checks the small declared contract, never the entire Sentry/Stripe API or the identity of CanCatch. No runtime contract discovery, version guessing, or automatic compatibility negotiation. Secrets are server-only; public intake configuration is separately declared in the capability manifest.

Standard runtime contracts use the same bound-import mechanism. Declare `use std {EmailV1 as Mail} from=deployment.mail` in the consuming package. The version is part of the stable exported name and manifest; it does not negotiate with a provider at runtime. Earlier `adapter ... capability=... from=...` source migrates to this single import form.

| --- | --- |
| `std.EmailV1` | `send(to:email,subject:text,body:text,attachments:file[]=[]) -> EmailAccepted`; result contains `reference:text`. Sender identity is deployment configuration; body is escaped plain text. Attachments reuse finalized immutable file references and ordinary source/destination authorization at admission; the committed outbox freezes their versions with the recipient. PaymentState contains `reference:text`, `revision:int`, nullable `provider_reference:text?`, `amount:money`, `status:enum(pending,unknown,succeeded,failed)`, nullable `checkout_url:url?` and nullable `failure:enum(transient,action_required,permanent,cancelled)?`. The failure classification is present only for a definite failed outcome; it never classifies pending/unknown acceptance as retryable. A monotone per-attempt revision orders normalized provider observations; same revision has identical business content, and consumers reject older observations. An unchanged observation retains its revision. A verified contradictory later success is retained as money evidence and a review exception, not dropped to preserve an earlier failure claim. The adapter contract must normalize provider events with authenticated account/reference/kind/amount checks; vendor timestamps alone are not an ordering guarantee.

`collect` without consent requests ordinary customer checkout. Supplying consent requests off-session collection; the installed payment binding validates the current mandate against the merchant/team, canonical customer, amount/currency, scope and expiry at dispatch. The text reference is not proof of consent. A missing, revoked, unsuitable or unsupported automatic mandate yields definite `failed`/`action_required`; it cannot silently fall back to charging another mandate. A new interactive invocation through the same operation can recover after that definite failure. No separate preflight authorization query is required, since its answer cannot authorize a later payment. Source applications retain their current consent check and frozen cycle identity as well; adapter authorization does not invent business consent.

`cancel(reference)` disables new use of that attempt's checkout. If collection may already have been accepted, its state remains pending/unknown until reconciled; cancellation is not a refund. `failed` with `failure=cancelled` asserts that the provider definitively prevented collection. A succeeded attempt remains succeeded and requires an explicit refund. An unknown reference yields a typed failure, never a synthetic safe-to-retry receipt. A refund has its own logical reference and referenced collection; collection/refund amounts must be positive. Runtime metadata supplies delivery/provider idempotency identity. A reference remains unique within its adapter account; retrying the same logical request retains it, and changed customer/amount/consent under that reference is rejected. A new attempt after a proven failed attempt gets a new identity under the app's finite retry policy. A zero-value invoice is settled by a business operation without a provider. Redirects and timeouts never establish settlement. These surfaces exclude vendor subscription, tax or marketplace engines and remain proposed unimplemented contracts.

Standard result/error types have closed schemas. Named standard payloads such as `std.PaymentState` and `std.ErrorReport` can be imported with the same `use` form as other contracts. `std.OperationOutcome` is the shared structural workflow result `{source:text,revision:int,state:enum(pending,confirmed,unavailable,failed,unknown,released),reference:text?,detail:text?}`, preserving the former shared Outcome shape without repeating its declaration in each owner. This is an application-reported result, distinct from a transport receipt; it does not automatically confirm or release any business record. DeliveryResult has `id:text` and `status:enum(pending,succeeded,failed,unknown,skipped)`; DeliveryError has `code:text` and a safe `message:text`. All required standard fields are non-null unless stated nullable. Unknown capability implementations fail deployment; their names do not authorize imagined code generation.

`DeliveryError` remains the single closed `{code:text,message:text}` payload. Both fields are required and non-null. Its code is a stable safe machine classification supplied by the versioned adapter mapping, not a guessed provider enum or raw error; its message is a safe explanation, never machine control flow. Redact both before admitting a completion: no credentials, tokens, provider bodies, stack traces or confidential account data. Use a generic classification/explanation if specificity cannot be disclosed safely. Stored/displayed errors still obey their owning field/record grants. There are no `details`, `retryable` or provider-response fields.

Validate completion status and payload together before the handler. `succeeded` carries the declared result and `error=null`; `failed` carries `result=null` and a non-null DeliveryError; `unknown` carries `result=null` and a safe diagnostic error or null; `skipped` carries `result=null,error=null`. A nullable/no-result operation follows its declared result type rather than inventing a value. Pending is a receipt, not a completion occurrence. Inconsistent envelopes are invalid setup/input, including in fixtures, and cannot satisfy a business-error expectation. Successful typed delivery does not manufacture a successful domain outcome: a valid declared result can itself report pending/unavailable business work.

Neither error field authorizes retry or proves no remote effect occurred. `unknown` retains uncertain acceptance/commit, including a timeout after possible commit. `failed` is definite delivery/typed-result failure, which can include an invalid result schema after remote effects. Reconcile/retry/replay through the existing operation identity, adapter and owning business rules; a retry of the same delivery retains its identity. `skipped` means the existing undispatched/superseded/ineligible work, never an authored business guard failure. [Focused contract and fixture evidence](../../design/delivery-error-20261004.md) retains these boundaries without a new type or primitive.

### 8.1 Associated typed deliveries

`delivery(Target)` names one resolved bound capability operation or bound exported user operation, retaining canonical declaration/binding identity through aliases and deriving its result schema. Nullable stored fields default null: no associated attempt. There is no structural constructor, raw-ID cast, global receipt directory or added privilege. Existing `send Target {inputs} [when=predicate] as attempt` produces this type; ordinary `set row {notice=attempt}` associates it atomically with the business transaction. Assignment requires a compatible target and the same originating storage owner/app/team, from the current send result or an existing same-owner value authorized for that mutation. A caller-submitted receipt summary is not a constructor. Replacement selects the current attempt without cancelling or erasing the old one.

Read-only properties are immutable `id:text` plus `status:DeliveryResult.status`, `result:R?` and `error:DeliveryError?`. The containing record and exact whole-field or explicit value-leaf grant are required; operation-result, safe-error, attachment and lifetime checks additionally constrain contents. A text ID grants no lookup. Standard field presentation shows localized transport status, never automatic recipient/body/provider/result expansion; explicit source projections select authorized content. Null uses the shared not-requested caption, not a new status case.

Each read obtains an immutable authorized receipt observation at the current owner checkpoint. Mutable status/result/error dependencies in guards, locks, queries, invariants or effects enroll the receipt observation revision in the existing read fence; intervening updates invalidate/retry evaluation under ordinary conflict rules. Identity alone needs no status precondition. Receipt progress does not change the referring domain row's version, invoke hooks, unlock it or perform business transitions. Assigning/replacing the reference remains an ordinary versioned domain write. No cross-owner atomicity or automatic rewrite of referencing rows is implied.

Retain the safe identity/status summary while its authorized reference is legally retained and through the replay horizon. This does not extend retention of outbound content, provider payloads, error details or file bytes. Expired/withheld contents read null even when a succeeded summary remains; read-time redaction is not an invalid incoming completion. Presentation distinguishes succeeded-with-unavailable-result from pending/failure without disclosing the withholding reason. Never reconstruct, redeliver or rerun callbacks to refill it. Removing/replacing a reference cannot shorten outstanding provider/replay obligations. Independently frozen business evidence and domain attachments retain their own rules.

Explicit `on=Target.completed` handlers remain for domain reactions: compare current association `.id` to `event.delivery_id` and retain source/revision/state checks. Old attempts update their own receipts only. Provider success is independent of callback success. Approval, payment, recipient reading, retry/reconciliation and business completion are never inferred. Pure receipt-copy callbacks are unnecessary; separately meaningful outcomes and validated attachment effects remain authored.

Test-only operation-resolved recipes use existing `fixture name=Target {request={...},status=...,result=...,error=...}`. Require complete normalized operation inputs (ordinary defaults may apply); only these four recipe attributes are authored, with pending/null/null defaults. Isolated tables reuse one recipe per distinct request and vary its whole initial status/result/error through §5.1 selectors; keep distinct declarations where a test requires independently identified attempts, such as a superseded completion. The isolated runner validates request references, result/error shape, completion consistency and finalized-file provenance, freezes final text/locale/release and provisions owner/team/ID/revision once after final setup validation. No authored principals, grants, bindings, provider identity or mutable receipt patches. Same-owner model snapshots may reference the provisioned handle. Provisioning does not execute send or prove its guards/provider lifecycle; callback fixtures and real user-call sequences stay distinct. Old text-ID migration requires actual owner/binding/delivery evidence, never a cast or fabricated success.

[Complete contracts, source/JS/BDD witnesses and three JEV consultations](../../design/delivery-association-20261004.md) preserve alternatives and uncertainty. Type checking, observation, fixture and migration support remain unimplemented.

#### Observable progress on associated deliveries

For manifest-declared observable original operations, `delivery(Target)` additionally exposes nullable read-only typed `progress` and `Target.progressed` carries `{delivery_id:text}`. The accepted [associated progress contract](../../design/complex-apps/chat-media.md#associated-progress-contract) is normative. The pinned standard interface declares once which start/cancel/reconcile results and authenticated events update the original operation, using the same verified binding/owner/team, immutable request identity/digest and normalized snapshot rules. Consumers do not repeat that wiring or mirror sequence/content/state into business models.

Progress and its notification commit atomically. Durable notification/recovery is independent of business finalization; current-snapshot rereads permit coalescing and idempotent callbacks. Explicit reconciliation can re-notify unchanged progress. Technical retries and visible business failures retain their ordinary distinction; no blanket automatic retry of rejected business rules is introduced. Transport success and job success differ. Content access, nested field grants and finalized-file provenance remain enforced on every read. Apps still own resource policy, once-only allowance settlement, admitted assistant/image records, publication and human approval.

### 8.2 Typed generation, judgments and mailbox input

These are accepted **draft contracts**, not available implementations. Their canonical schema catalogs and detailed provider normalization are maintained once in [chat/media standard schemas and adapter normalization](../../design/complex-apps/chat-media.md#standard-schemas-and-adapter-normalization) and [Inbox's judgment typing contract](../../design/complex-apps/inbox.md#accepted-minimal-declarationtyping-contract) / [Mailbox interface](../../design/complex-apps/inbox.md#accepted-mailbox-interface). `std.TextGenerationV1` and `std.ImagesV1` use ordinary bound capability imports, `send`, associated deliveries and verified `changed` events. Their stable request identity and revision select one immutable request; cumulative output has a strictly increasing adapter sequence, so reconnect rereads retained authorized state without resubmitting a prompt. Stop requests and provider-confirmed termination differ. Unknown outcomes retain reservations and never imply cancellation or zero usage. Terminal execution fields cannot change; initially unknown usage may settle once in a later sequence. Finalized image files retain normal attachment authority. Static choices derive their finite cases; `options=runtime` derives typed request-local candidates, optionally alongside fixed authored choices. It derives one typed `evaluate` operation and result rather than making authors repeat matching output schemas. `std.MailboxV1` normalizes verified provider email events and reviewed replies. Provider IDs, content completeness and finalized attachments are explicit. A sender address is not proof of company membership. Stable reply identity binds exact reviewed arguments; unknown acceptance is reconciled without blind resending. Provider acceptance is not recipient delivery. The company app owns disclosure through routing, corrections and response approval; MIME decoding, credentials and transport evidence belong to the adapter.

### 8.3 Model-bound knowledge corpora

A Given `corpus Handbook model=Revision scope=parent.parent title=title content=body,attachments where=eligibleExpression from=deployment.knowledge` derives indexing and a bounded typed answer/cancel/reconcile/refresh interface from one owning source model. Revoked, withdrawn or superseded used context withholds the whole answer. No model-supplied arbitrary URL/HTML or ordinary text getter bypasses this boundary. Citations establish source provenance, not proof of natural-language entailment.

The binding uses the existing protected observable-delivery mechanism. Its generated opaque answer type is rendered by the shared content component and identical authorized MCP serialization; it is not user-constructible or convertible to ordinary text/provider input. ## 9. Browser presentation

#### Page admission and shell discovery

The compiler derives one page descriptor from each owning `page` declaration. Its title, attached description, optional group caption and order are static data, including localized message descriptors; message arguments in these slots must be context-free constants. They may not depend on a row, a page result, preferences, caller details or a business query. Such values belong inside the page body. The descriptor is generated output, not a second authored navigation registry or permission schema. The same descriptor serves the sidebar and the route dispatcher.

Page **admission** means that the current context may enter the page; it does not mean that its lists contain rows, every field is readable, every action is enabled or every later data load will succeed. Derive the minimum authentication and resolved-team context needed by unconditional page data/expression dependencies. For model collections, use the declared read-policy alternatives' authentication requirements, not a query for a matching row: an explicit public alternative allows a public context, an authenticated external-user alternative does not imply team membership, and member/owner/team-role alternatives require membership. Exact row predicates, field grants and business roles continue to filter their ordinary reads; they are not promoted into extra page guards. After context admission, a lack of matching readable rows/fields gives the ordinary empty/withheld view. A model with no read policies remains deny-read and contributes no invented principal/role grant or row-existence test. The page's explicit `require` supplies any narrower page-wide rule. Combine requirements of unconditional dependencies; a nested container with its own `require` keeps its context checks and gate local and is omitted when unavailable. An unconditionally required canonical read invocation, including `data=`, also contributes its existing operation `by` with the bound inputs: consult that owning admission rule without executing the unrelated read body. This is invocation-wide authority, distinct from row-policy filtering; body guards/data success remain ordinary read behavior unless needed by a page guard. Form/action declarations do not invoke their operations during page admission and their `by`/business guards are not added to page admission; their controls and actual calls retain their existing authorization. This preserves a public catalog containing protected actions and an eligible empty private list.

Reuse one derived admission program for discovery and the actual page request. It establishes inherited context and required-read admission prerequisites and evaluates the authored page-level `require` predicates in their source order with the same pure-query authority as rendering. It follows only the dependency closure necessary for those checks. A role-only gate such as `reviewer or finance` reads current canonical auth facts and does not fetch Expense rows. A data-dependent gate may perform its necessary bounded authorized reads; no exact current answer is claimed without those reads. If a guard uses a declared `data=` result, invoke that canonical pure read only as needed to evaluate the guard. Other page-data bodies, body lists, metrics, child-container guards, pickers, form actions and refresh mutations are not executed during discovery; only the owning `by` of an unconditional required read is consulted as above. In particular, neither nonempty results nor success of all contained operations is a condition for a link.

Any guard-needed route/data bindings stay private to that admission. The active renderer reuses them at the same read checkpoint rather than fetching a different result after the gate; bindings not needed for admission are loaded only when that page is rendered. Internal read-operation guards retain their actual order and authority. A data guard is not an excuse to render the entire page or copy the guard into a new authored permission declaration. If required context cannot be established from the declarations, checking diagnoses that source dependency; it does not guess a role, query for sample rows or silently publish the page. Existing page/container `require` is the source place to state a genuine narrower rule.

Discovery evaluates only selected, deduplicated static pages not excluded by `nav=none`. It never enumerates record/token routes or fabricates route parameters. It exposes only allowed descriptors' safe metadata; guard inputs, results, role assignments and private records are not serialized into navigation. A failed page gate is denial and yields no link. A failed dependency read, work-budget overflow or unavailable owner is an unavailable eligibility check, not false permission or permission to reuse a previously allowed link. Keep independently established links and show a generic incomplete-navigation status without exposing the unproven destinations or their count. Work remains bounded by the ordinary read limits plus the shared discovery budget; the descriptor does not promise constant time or zero database work.

The route dispatcher repeats the same admission on direct GET and partial requests, even if a link was just shown. Membership, selected team, data-gate changes and source revision invalidate earlier eligibility; never reuse another caller/team's result. Discovery confers no capability or mutation authority. Every actual query/operation still enforces its ordinary current policies. The request may share equivalent guard reads at a valid checkpoint, but persistent caching cannot outlive its auth/data validity; no cache behavior is required for correctness.

## 9.1. Built-in internationalization

Single-use text stays where it is authored. A JSON source string followed by `@{locale=variant,...}` creates an immutable message descriptor; a string without the suffix remains ordinary literal text. Keys are explicit language tags, not positional columns. Use a simple NAME such as `nl` or a quoted tag such as `"pt-BR"`; variants are JSON strings or `null` for an absent translation. `@{}` explicitly creates a source-only descriptor. Adding a language adds its own key without changing existing variants:

```can
# Track work. @{nl="Volg werk."}
app Tasks
Given
 message add = "Add"@{nl="Toevoegen"}
 Todo {title:text trim,done:bool=false label={values={true="Done"@{nl="Klaar"},false="Open"@{nl="Open"}}}} label="Task"@{nl="Taak"}
When
 crud Todo by=members fields=title,done label={create=add}
Then
 page /tasks title="Tasks"@{nl="Taken",de="Aufgaben"}
  list Todo empty="No tasks yet."@{nl="Nog geen taken."}
   edit
 page /add title=add
  form Todo.create
```

Each logical app or package pins its authored source language to `"en"` unless its own declaration header says `source="other-tag"`. This governs its attached description and owned message values, including metadata on a composed app with no Given body. Composition and imports retain every asset's canonical owner and language; moving a file changes neither. Deployment `context` / `locale default=` controls viewer selection and fallback, never authored source language. Canonicalize/validate BCP 47 tags; reject duplicate canonical variant tags and a variant repeating the owner's source tag. Absence is distinct from an empty translation. The compiler reports missing coverage without generating translations or certifying a variant's actual language.

Use a Given leaf `[export] message name[(typed_parameters)] = "Source"@{...}` only when complete wording is actually shared. Its right side must be a descriptor, including `@{}` when only the source exists. There is no table container or target-binding declaration. Omit parentheses for a static message; typed parameters form a nonempty explicit signature. Names identify reusable meaning, not single-use wording. A zero-parameter message is referenced directly and a parameterized message uses ordinary call syntax. Anonymous inline ICU descriptors use the same postfix call with explicit named arguments, for example `"{n, plural, one {# task} other {# tasks}}"@{nl="{n, plural, one {# taak} other {# taken}}"}(n=count(Todo))`. Every placeholder across every variant must bind explicitly; argument types are inferred from those expressions, with no implicit lexical capture. Named messages retain their declared signatures.

Descriptors retain canonical owner/semantic slot, typed arguments and asset revision. Asset identity is compiler-derived, independent of source offsets and public operation names; single-use text needs no authored key. Descriptors are not stored fields, client-supplied keys, callbacks or MCP tools. Parameters resolve to nonnullable scalar display values: validated string-like values, bool/enum, int/decimal, money and date/datetime. Reused field types retain constraints. Records, files, secrets, JSON, actions, arrays and objects are unsupported inputs. Check every argument's type/disclosure dependencies even if one translation omits it. Ordinary strings/business data remain literal and are never translated automatically.

Shared messages can be exported and imported through `use Owner {word,notice as Alias}` with no deployment binding or lookup wrapper. A message-only group includes referenced pure assets and parameter schemas, not provider models/handlers/pages/context/tools. Mixed production groups retain whole-owner business inclusion; model imports do not become schema-only imports. Extracted interfaces include localization assets referenced by schemas/descriptions without importing provider state. Message dependencies cannot query records or perform effects. A composed app authors its single-use description inline; only actual static-description reuse needs a message-only import after its optional context. `uses` never grants implicit name visibility.

One trailing `label=` attribute supplies declaration captions. Models, contracts, roles, packages, implicit-app owners, user scenarios and preference sections accept a static scalar caption: literal text, an inline descriptor or a shared zero-parameter message. An app caption labels its implicit owning package; a composed app has no such owner/settings section. Preference sections otherwise reuse their owner caption. Schema fields, signature parameters and derived model fields accept either that scalar or the closed object `{text=caption,values={case=caption,...}}`, with at least one member. Omit `text` when the inherited/default caption is unchanged; `values` overrides enum/bool case captions using their exact stable wire values. A CRUD declaration uses the closed map `label={create=caption,update=caption,delete=caption}` for enabled operations only. Unknown slots, foreign targets, duplicate entries and parameterized captions are invalid. Equal complete captions at multiple sites reference one shared message.

## 10. MCP and generated interfaces

Every selected app provides one Streamable HTTP `/mcp` server. Packages contribute namespaced tools, not servers. The compiler emits one operation registry used by UI, MCP, generated routes, and internal calls. Product-selected packages contribute model read/list, publicly permitted enabled CRUD, and user scenarios as business tools; dependency exposure follows §1 rather than publishing every imported package's tools. Registry inclusion for internal execution does not itself imply tool discovery or a public route. With default teams support, owner-authorized `system.team.invite(email,role)`, `.remove(member)`, and `.role(member,role)` are also business tools with the same generated UI rules and mutation envelopes. Their fixed schemas come from the teams primitive. Login, recovery, session management, OAuth consent, source changes, and deployment stay browser/runtime interfaces and are never business tools. Hooks, timers, queues, instrumentation, provider events, and other trusted handlers are never tools.

MCP OAuth consent binds a connection to one app user and one team, or app-only context for a non-team app. Recheck current permissions for discovery and every call; another team requires a separate/re-authorized connection. Tokens have the correct audience and cannot impersonate a source. OAuth/protected-resource discovery follows the [MCP authorization specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization). Browser sessions and MCP grants resolve the same principal model.

Tool names are stable `package.Model.read`, `.list`, `.create`, `.update`, `.delete`, and `package.scenario`. For an implicit package, `package` is its owning app identifier: `TeamTasks.Todo.create` is the same name standalone or within TeamOffice. Composition does not add a selected-app prefix, synthetic `main`, or mount alias. Named-package tools retain their existing names. Distinct canonical owners keep same-named models, roles and operations separate; deduplicated owners contribute a tool only once. The app description becomes initialization `instructions`; attached operation descriptions become tool descriptions. Model/field descriptions enrich generated schemas. In this delivery those descriptions render source-language text only; localized MCP output is deferred (see §9.1). `##` never leaves the source. File moves change no tool name. Names retain the [MCP tool-name conventions](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#tool-names); declaration renames are the explicit identity changes described in §1.

Schemas are closed typed JSON objects. Model reference inputs use `{id}` for reads and `{id,version}` for mutations; money uses integer minor units/currency; datetimes use RFC 3339 UTC strings; files use completed opaque IDs; union values have a discriminator. All int/decimal values use canonical decimal strings at the MCP boundary, including money.minor and record.version; there is no magnitude-dependent wire type. Booleans and collection counts defined by the protocol itself remain JSON booleans/numbers. Mutations have an `operation_id`; identity, roles, and team grants cannot be arguments. Generated CRUD update takes `{record,changes,operation_id}`; scenario business inputs are named alongside `operation_id`. Unknown arguments and undeclared writable fields fail.

New file bytes reach those opaque slots through the shared host/browser upload contract in §8. The generated `fileTransfer` metadata is runtime setup, not a published business tool, and the file schema's format annotation neither authorizes transfer nor validates content. The business operation registry remains the only source of upload target/input binding and final mutation behavior.

An action value serializes as a closed discriminated reference whose target is one of the compiled canonical operations and whose protected binding is runtime-owned. Remote references include an opaque `action_handle`; clients cannot edit its protected contents. Discovery still exposes each canonical target tool once with its owner description/schema. Where ordinary and handle invocation are both exposed, the generated input schema is an explicit closed union: ordinary mode has the normal business inputs and `operation_id` without `action_handle`; handle mode has `action_handle`, `operation_id` and all non-record canonical inputs, omitting every protected record input. Otherwise expose only the available mode. An ordinary remote mode requires its own declared delegated access; an action handle does not authorize that mode. Mixed envelopes, wrong targets, record overrides, principal/team substitution and incompatible revisions fail. This gives a fixed remaining schema per target, without generic `perform(inputs:json)` tools or duplicated owner signatures.

Model list tools accept typed filters/order/cursor/limit constrained by readable fields, and a parent reference for children. Results reuse the UI query and projection rules. Every mutation result has `{status,operation_id,records,deliveries,result}` with applicable members present; its business `result` uses the declared type made nullable for absent, expired or withheld content (§7.1), and changed-record projections obey current access/lifetime. Pure reads return their declared shape. Business errors use structured codes (`validation`, `forbidden`, `not_found`, `conflict`, `rule_failed`, `busy`, `limit`, `delivery_unknown`) and actionable safe details with `isError=true`. Existence-hiding lookups return `not_found`. Protocol errors remain JSON-RPC errors. These choices follow [MCP tools/schema boundaries](https://modelcontextprotocol.io/specification/2025-11-25/server/tools), not an additional app API definition.

## 11. Compiler output and change ownership

Compilation parses and type-checks, resolves names/ownership/permissions/effects, and emits one workerd application, generated interfaces, Cloudflare binding requirements, versioned schema/index migrations, and the inline-example test artifact. These are compiler phases, not app framework layers. Diagnostics identify file/declaration/field and one concrete error; unknown syntax is an error, not an AI interpretation opportunity.

Application source has no executable general-purpose escape hatch. Pure derivations compose expressions; scenarios compose canonical effects; integrations implement declared external contracts. The compiler does not invent business decisions, provider mappings, field names, or functions to make a source file appear complete.

Schema evolution uses the explicit maintenance declarations below. Automatic changes are conditional, not a blanket exemption for optional/defaulted fields or indexes. Never infer a rename from similar spelling or erase data to satisfy a compile. Generated Cloudflare deployment configuration tracks its supported provider version; application data migrations are distinct from Durable Object class lifecycle configuration.

The language version pins builtin signatures, wire schemas, currency scales, timezone data, runtime defaults, and component behavior. App deployments record that version without repeating a version on every declaration. Compiler/runtime versions cannot silently reinterpret a running app. Component download/tree-shaking, SQL planning, password-hash implementation, and bundler choice are implementation work; their absence is not permission to invent alternative source syntax.

### 11.1. Schema evolution boundary and versions

`migration Owner from="snapshot-id"` is a top-level maintenance declaration alongside actual business source. `Owner` references a logical named package or small app's implicit package; it creates no additional owner, package wrapper or namespace. It is outside Given/When/Then and has no `by`, `on`, `export`, business parameters or UI/MCP operation. File placement supplies no execution order. A composed app has no aggregate schema owner: its included local packages contribute their own transitions, including dependency-only packages. Bound providers are never migrated by a consumer.

`from` must identify the exact compiler-produced installed owner snapshot: canonical stored schema, constraints, locks/lifetimes, effective language version, resolved physical bindings/routing and persisted declaration contracts. The deployment also retains release artifacts and inventories the actual contracts of queued work; equal table shapes cannot establish equal handler meaning. Current declarations determine the desired snapshot. Migration bodies are excluded from that snapshot's fingerprint; their canonical content has a separate digest. Diff diagnostics expose the actual predecessor ID and changes requiring explicit disposition. Authors do not repeat old schemas, write version counters or maintain a migration manifest. Missing or mismatched predecessor evidence blocks an upgrade.

The compiler selects transitions relevant to the desired local closure or exact installed local owners being removed. Unrelated declarations remain inert. For `rename owner`, the header names the desired owner and `from` supplies the differently named predecessor. For `drop owner`, the header instead names the removed installed owner, resolved through that exact snapshot and installed inventory despite its absence from current declarations. Each old logical owner is retained, explicitly renamed once, or explicitly dropped; a target consumes at most one predecessor. There may be alternative `from` declarations for different installed snapshots, but at most one exact matching transition for each owner/source is selected. Reject duplicate consumption, merges, collisions and competing mappings. Matching contributions from different owners form one derived deployment plan rather than competing plans. A newly included owner starts empty, without importing another deployment's data.

The generated transition records its predecessor, desired snapshot, body digest and application/progress status. Applied artifacts are immutable: changing their transformation or target is not a replay. Source can replace completed transitions with current upgrade alternatives; generated deployment history retains the applied artifacts. When current declarations change the target of a retained source transition, it is a new candidate artifact requiring validation against that predecessor, never a replacement for the applied artifact. An older deployment requires a matching authored path to the current target, not an inferred jump or a replay retargeted to newer declarations. Fresh installs create the current schema without applying old transitions or requiring their snapshots. They check current syntax/targets and do not claim inactive `before` paths have been typechecked.

| Change | Treatment |
| --- | --- |
| New empty model, nullable/context-free constant field, nonunique query index | Candidate automatic change only if ownership, references, locks/history and the complete stored state remain valid. |
| Actor/clock/random default or historical business snapshot | No inferred backfill. Supply an explicit transition and defensible historical values. |
| Rename/removal, required backfill, narrower enum/type/invariant, new/changed uniqueness, stored-to-derived change or semantic data conversion | Explicit transition; validate the complete desired state, including archived rows and retained key/reference constraints. |
| Creation-default edit | Changes future creation only; does not rewrite existing values. |
| Logical package/implicit-app rename | Explicit one-to-one identity mapping, with physical scope/routing unchanged. |
| Team/parent/physical storage transfer, record split/merge or population of a new model from old rows | Outside this v1 migration subset; block rather than invent a mapping. |

Storage compatibility and UI/MCP, bound-interface, record-version and pending-work compatibility are separate. Automatic candidates must pass both applicable boundaries. In particular, an optional field with a new invariant or a unique index is not automatically safe. Unknown historical membership anchors/intervals cannot be recovered from a current default or mutable plan.

### 11.2. Typed transition directives

Outside a mapper, `before` names the pinned predecessor's declaration namespace; unqualified target names resolve in the header's desired logical owner. Structural directives describe a mapping, not an imperative rename sequence. Establish all mappings before mapper guards or bodies; their written order does not change name resolution. Each old model/field is retained, renamed or dropped once, and each target has at most one mapped source. A drop cannot also map the same source, and competing destinations/sources are errors. Value initialization is a separate phase: one `backfill` per target model may transform retained or renamed fields. Thus model rename plus backfill, or field rename followed by an explicit `set row`, is valid subject to old locks; `before` remains unchanged throughout.

| Directive | Meaning |
| --- | --- |
| `rename owner` | Map the predecessor's canonical package prefix to the header owner; required when those identities differ. |
| `drop owner` | Remove the predecessor's complete logical owner; the header owner must be absent from the desired schema. |
| `rename before.Model to Model` | Preserve rows/IDs through an explicit one-to-one model-name mapping. |
| `rename before.Model.field to Model.field` | Preserve the value through an explicit stored-field mapping; source and destination belong to the corresponding old/desired model. |
| `drop before.Model` or `drop before.Model.field` | Explicitly acknowledge removal of a stored model/field. |
| `backfill Model` | Transform each corresponding old row into its desired stored shape using the body below. |
| `invalidate before.handler` | Dispose eligible undispatched work of an inventoried old asynchronous trusted handler, as specified in §11.3. |

An owner rename preserves physical authority, protected scope/containment, IDs and immutable file objects. Stored model references and schedule namespaces follow the explicit canonical mapping; historical receipt identities remain historical. Carry role grants only to valid surviving mapped roles; removed or incompatible assignments must first be explicitly reconciled, and new roles gain no assignments. The directive supplies no public wire alias, Cloudflare class transfer or remote reauthorization. Bound clients/interfaces need their own compatible installation. Owner/model/field drops remain subject to locks, incoming references, expiry, file accounting and replay rules; `drop owner` is not a namespace-deletion bypass. A transition with no row directives can acknowledge a constraint-only change, but still cannot authorize an undeclared removal or infer a rename.

`backfill Model` binds a read-only `before` old row and a partially initialized desired `row`. After structural mapping, same-representation values may be copied without coercion or normalization; they initialize desired fields only when valid under the desired field definition. Initialize new fields only with proven compatible null/context-free constant defaults. Changed representation types, including incompatible enum/reference types, require explicit assignment; `before.field` retains its old type for conversion. Mapper dataflow must prove a field initialized before reading it or completing the row; if a copied value's validity is not provable, explicitly assign it instead. Leading `require` and one `do` body reuse `let`, `require`, `if`/`else` and `set row {fields}`. Assign every uninitialized stored field on all successful paths. A nullable field is not a license to silently replace incompatible old data with null. Desired derived fields are read-only. Representation-preserving constraint-only transitions may validate unchanged values without a mapper and fail if any violate the desired definition. Final field constraints, invariants, uniqueness, references and lifetimes must hold for the complete target dataset.

The mapper reads frozen stored value components and opaque reference identities of its old row. A reference assignment requires a known retained/renamed target model with the same protected scope/authority. It cannot dereference another record, run collection queries, use actor/clock/random, invoke operations/hooks/providers, or `create`, `delete`, `emit`, `send`, `schedule` or `return`. The runtime supplies complete bounded iteration and checkpoints; ordinary `for ... limit` is not a migration loop. Staged output cannot become another row's input. This is maintenance initialization, not a second user CRUD route.

Old locks are evaluated on original pre-state. Renaming protected data preserves its value; changing/removing still-locked evidence fails. While an old lock protects retained predecessor rows, preserve its mapped predicate and at least its field coverage; this subset permits identifier renames and added protection, not arbitrary lock rewrites or removal. Each originally protected retained row must still satisfy that mapped predicate after backfill, so editing a different predicate input cannot silently unlock it. No general predicate-equivalence prover or historical per-row policy layer is implied. New locked fields can be established during initialization, then their desired locks apply. Include archived rows without unarchiving or changing protected identity/creation metadata. Expired content cannot be read, backfilled or resurrected; affected incompatible physical expiry backlog must finish disposal under its old lifecycle before activation. Retained references and uniqueness still block where applicable. Name-only changes preserve row versions. Actual stored-value initialization/conversion, including default/null materialization, advances each affected row once with trusted migration attribution; pending version bindings must be assessed. File references retain their real object identity; release relationships before retryable collection. Dropping schema does not promise erasure of historical audit/receipt/provider copies beyond the canonical retention contract.

Illustration only: suppose a compiler-recorded predecessor contained `Todo {label:text trim max=200,done:bool=false,legacy:text?}`. The following desired source explicitly renames `label`, initializes a required priority and removes `legacy`. This is not the history of the reference app. Replace the placeholder with its real compiler-issued snapshot ID; an upgrade using the placeholder must fail.

```can
# Track team work.
```

### 11.3. Maintenance application and old work

Compilation produces a reviewable plan and performs no data migration. Authorized deployment closes affected admissions, runtime writers, cleanup and dispatch, fences old runtimes, and freezes the predecessor input. The runtime prepares complete target state in resumable bounded staging, records progress, validates it, then activates it. Preparation failure leaves the installed data/release selected. A logical package may span D1 and several DO authorities: preparation/activation is not a transaction across them. If activation partly succeeds, keep affected access closed and resume; never reopen old code against mixed layouts. DO coverage requires authoritative owner inventory, not the eventual discovery directory. Unsupported coverage or provider capabilities block installation. No zero-downtime or automatic destructive rollback is promised.

Pending work retains its actual release/declaration contract. Incompatible work must drain/reconcile or have an explicit supported disposition before activation. `invalidate before.handler` applies only to inventoried undispatched pending occurrences/intents carrying that pinned predecessor's asynchronous handler contract; matching a handler name from another release is insufficient. Synchronous hooks and user scenarios are not targets. It records a skipped migration outcome and retains replay identity, without undoing committed business effects. In-flight, provider-accepted or uncertain deliveries need reconciliation or a retained compatible contract; they cannot be marked cancelled. Inventory older retained releases too, not just the immediate predecessor. Their work must drain, retain a compatible contract or block; this directive cannot reach it by spelling alone. Missing historical contract/identity evidence blocks the transition. Arbitrary job-payload conversion is outside this subset. Completed receipts preserve old identity/schema and safe outcomes, never re-execute; current retention/read rules still withhold expired or inaccessible content. Changed interface revisions invalidate existing sealed action handles rather than rewriting their protected authority.

Generated SQL/index operations and Cloudflare lifecycle output are implementation artifacts, not an authored second language. [D1 tracks applied SQL migrations](https://developers.cloudflare.com/d1/reference/migrations/), and [D1 batches roll back failed statement sequences](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch); this does not make a multi-batch rollout atomic. [SQLite schema-alteration restrictions](https://www.sqlite.org/lang_altertable.html) inform generation, but the adapter must pin actual provider support. [Durable Object class lifecycle configuration](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/) remains distinct from row evolution and arbitrary authority transfer. Snapshot production, diff/type checking, staging, inventory, installation and migration execution are still unimplemented.

## 13. Desired JavaScript draft target

Uniform translation is a completion requirement for every handwritten target, including the 21 original targets and the nine complex-app additions. The same Can construct must have the same JavaScript representation, import contract, argument order and metadata shape in every app. Differences must follow differences in authored declarations, not the preferences of the worker writing the target. Normalize module section order, naming derived from canonical declaration identities, formatting, guard/effect ordering, query lowering, scalar operations, UI props and fixture/example representation together. A matching metadata shell alone is insufficient. Review representative occurrences of each construct across targets before declaring the corpus consistent; no app-specific convenience wrapper may conceal a second lowering for the same language primitive.

The `.mjs` files are handwritten target examples, not compiler output or executable applications. Imports from `@canlang/stdlib`, `@canlang/ui` and owning-package modules are proposed unimplemented contracts. Can compiles directly to JavaScript; authoring the standard library in TypeScript does not add a Can-to-TypeScript stage. Runtime builtins/web APIs and existing managed Cloudflare bindings are reused; the language does not reimplement encoding or workerd. The Rust toolchain shares one language model across compilation, checking, linting, formatting and editor diagnostics; this draft round implements none of them.

Each target exports an `appDefinition`, one named `canApp()` callable-registry factory and explicit declared page functions. Alternative authored app assemblies use `appDefinition.compositions`, keyed by their declared app identities. The factory is linked once, not reconstructed per request. It returns callable handlers and rule maps only; it does not spread `appDefinition` into that registry. Named pure-function handlers occupy their declared registry names, while their schemas stay in `appDefinition.pure`, avoiding metadata/function collisions. Model metadata uses `readGrants:[{rule,fields?},...]`: each entry refers to a boolean function in the registry's `read` map. Each source policy retains its own field grant; matching grants union, never broaden a limited grant because a different predicate matched. There are no competing `readRule`, `readRules` or `readableFields` model slots. Invariant and lock references are arrays of registry IDs; lock entries are `{fields,when?}`, with absent `when` meaning always locked. Multiple source locks keep separate entries and conditions. Export metadata is `exported`. The one standard import module is `@canlang/stdlib`; UI factories belong to `@canlang/ui`.

Field schemas use a base `type`, with `array:true`, `nullable:true` or `requiredArray:true` only for actual differences. Qualified field-type reuse remains a checked contract with its constraints, not a claim of resolved semantics. Declared results use that same descriptor shape, for example `result:{type:"owner.Record",nullable:true}` or `result:{type:"text",array:true}`; neither string suffixes nor bare identity constants are a second result-schema representation. Void operations omit result. Canonical operation metadata refers to its actual handler and typed input/field allowlists. Disabled operation identities are package-qualified and declared once on appDefinition. Executable guards are functions or references to callable rules, never a runtime interpreter of raw Can strings. An explicitly named source-review note may retain original syntax but is non-executable.

Literal field defaults remain literal `default` values. A nonliteral creation default uses a typed `default(c,{parent})` callable in that same field descriptor; the second argument contains only the resolved parent when containment exists, not arbitrary sibling inputs or an incomplete row. For example, `assignee:{type:"user",default:(c,{parent})=>parent.parent.user}` is the desired lowering of the Step default above. The creation engine invokes it only for omission under §2's authority/fence/replay rules. The existing fixed `server:"actor"`/`server:"now"` metadata remains unchanged; another authored server initializer uses the same callable convention in `server`, always excludes caller input, and retains its creation-context checks. Async functions are used only when the authored expression requires asynchronous pure reads. This is proposed runtime interface metadata, not a second handwritten app helper or implemented default evaluator.

Scalar/effect lowering uses one proposed import name per operation: `addMoney`, `subtractMoney`, `multiplyMoney`, `compareMoney`, `equalMoney`, `negateMoney`, `divideDecimal`, `durationBetween`, `compareInstant`, `compareDate`, `compareDecimal`, `addDuration` and `subtractDuration`. Comparators return -1/0/1; generated relational operators compare that result with zero. Exact integer/duration values and integer-literal schema defaults/bounds use BigInt, checked arithmetic uses `int64`, and source-constant durations need no per-request constructor. Reference identity uses `same`; declared structural equality uses `equalValue(c,canonicalTypeId,a,b)` so arrays/contracts are not compared by JavaScript object identity. Effects use `deleteRecord(c,row,{mode:'archive'|'remove'})`, preserving the authored deletion mode. These contracts are unimplemented. Do not keep alternate `money_*`, `moneySub`, `moneyLTE`, `addInstant`, or app-local comparison/role wrappers in finalized targets. Authored named derives remain named functions; a source operation's `by` lowers directly to `check(hasRole(c,canonicalRole) || ..., 'forbidden')` with its actual boolean expression. A subject predicate `reviewer(person)` lowers to `hasRole(c,"owning_package.reviewer",person)`; omitting the third argument checks the caller. Both forms use the same current-team membership/explicit-assignment and revocation semantics of §4.

Lowercase UI server factories take one props object and `children` arrays. `renderPage(c,descriptor,()=>children)` receives a zero-argument body builder, invoked only after current page admission; the body is not evaluated during navigation discovery. `edit.operation` names the canonical update operation and `edit.record` its protected record; no model-only alternate target is emitted. `form.arguments` binds inputs; `action/actions.boundArgs` binds canonical operations; `card.title` and `details/tab.caption` preserve authored headings. Generated pages express groups, typed queries, record/result scopes and current authority. The library owns daisyUI markup/classes, shell and standard HTMX behavior. App targets contain no `h`, native-element expansion, hydration or browser business-state store. Query, decimal, temporal, file, transport and renderer implementations remain omitted; syntax checks establish neither behavior nor optimal performance.

`appDefinition.pages` contains the sole generated page descriptors in source order: `{owner,path,title,description?,order?,group?,nav?,admit,render}`. `owner` is the canonical declaring package, `path` the normalized existing route pattern, caption slots are the static `message(...)` values already derived from source, and `order` is an exact BigInt when explicitly authored. `group` and `nav:"none"` retain actual exceptions; dynamic routes are intrinsically excluded from discovery. The owning package label remains in its existing package metadata, not copied to every page. No separate exported menu list or app-specific navigation wrapper is introduced.

`admit(c,routeBindings={})` is the compiler-derived shared admission callable. It checks inferred context and page-level guards and returns the typed server-private binding object needed by the renderer (empty when no data/record bindings were needed). A false presentation guard raises the ordinary safe page denial; dependency failures remain failures rather than becoming true/false permission. The canonical dispatcher calls it before `render(c,bindings)`; discovery calls it only for static candidates and discards bindings after using their eligibility. The renderer gets the same admitted bindings at the checkpoint and evaluates any remaining page data lazily. It must not maintain a second copy of the page guard, title or placement. `renderPage(c,descriptor,()=>children)` reads that descriptor's presentation metadata and emits the common shell; it does not dispatch the page or recursively invoke `admit`. Route and partial dispatch, not direct arbitrary module-function calls, is the generated HTTP entry point. Normal record/query/action authorization remains enforced inside rendering and invocation.

For example, the existing Expense review declaration supplies its one role gate and caption:

```can
page /expenses/review title="Expense review"@{nl="Onkostenbeoordeling"}
 require reviewer or finance
 table Expense columns=purpose,amount,status
```

A minimal desired translation uses one descriptor shared by the registry and renderer (ordinary imports/model declarations are omitted here):

```js
const reviewPageDescriptor = {
  owner: "expense",
  path: "/expenses/review",
  title: message("Expense review", { nl: "Onkostenbeoordeling" }),
  admit: async (c) => {
    check(hasRole(c, "expense.reviewer") || hasRole(c, "expense.finance"), "forbidden");
    return {};
  },
  render: reviewPage,
};
// appDefinition.pages includes reviewPageDescriptor once in declaration order.
export async function reviewPage(c, bindings) {
  return renderPage(c, reviewPageDescriptor, () => [
    table({ context: c, model: "expense.Expense", columns: ["purpose", "amount", "status"] }),
  ]);
}
```

Here the explicit role condition already entails the inherited member/team prerequisite, so no redundant check is emitted. Discovery calls only `admit`, never `reviewPage` or the table. The same source/target rule maps CRM's `salesperson` gate and Expense's `members` gate; source-defined descriptions and real body contents remain present in full targets. This is illustrative desired output only, with no implemented descriptor dispatcher or performance claim.

Test-only fixture/example exports may remain visibly marked in handwritten review artifacts. A future compiler extracts their test output and erases fixture-only production imports; no executable erasure marker, test loader or parallel authored contract is introduced by these drafts.


The proposed target's query authority comes from the trusted invocation context `c`, never an app-authored per-query authority string. `records(c,model,{parent?,where?,order?,limit?,archived?})` applies viewer read grants before viewer filters and projection, while policy/invariant/CRUD/mutation contexts use the bounded owner authority specified in §4. Derives inherit the caller. Explicit authority reports retain their source boundary. Limits fail on excess rather than silently reducing business input.

An expression-query `order=expr` lowers to `order:{by:row=>keyExpression,direction:"asc"}`; the default ascending direction may be omitted. A leading ordering minus uses `direction:"desc"` and the unsigned key expression, never arithmetic negation of an int, datetime or text value. `by` inherits the query authority and typed comparison, and the existing stable record identity tie-break applies. The grammar permits one expression ordering key. Presentation `order=` instead remains the declared selector list such as `["-created"]`; it is not a second form of expression-query ordering.

An enabled generated CRUD entry excluded by its owner's `expose` allowlist carries `expose:false`; permitted entries omit the property. UI/MCP/external publishers apply that one property with product selection, while ordinary internal dispatch retains unchanged business admission. The canonical registry is not duplicated into a separate public manifest. No transport error code is added for an interface that is not mounted.

Canonical user-operation exports are their qualified identity constants; the registry holds their implementation. Importing an implementation function must not bypass canonical invocation, input validation or authorization. Exported pure derives remain functions. Trusted handler signatures are `(c,{event})`; a declared-event cohort with an authored child alias receives `(c,{event,child})`, using that exact alias and the admitted current native child. An omitted alias adds no body binding. A source `on=every(duration)` is represented as `on:{every:durationMilliseconds}` with an exact BigInt duration; keyed scheduled events retain their declared event identity. Bound sends use `send(c,'owner.Service.operation',arguments,...)`, with `bindings:{'owner.Service':{capability,from:'deployment.service'}}`; the binding does not copy the capability's operation list. CRUD effects pass the canonical admission function as `create(c,model,input,{when:crudWhen.Model})` or `set(c,record,changes,{when:crudWhen.Model})`. These proposed shared effects normalize the candidate and run admission before staging as specified above; ordinary source effects do not gain invented CRUD guards.

Associated delivery fields use `{type:"delivery",operation:"owner.Service.operation",nullable:true}` (omit nullable when nonnullable), resolving the existing bound operation once. Send returns its protected handle; ordinary set stores it. Every stored property read lowers to the sole proposed observation helper `await delivery(c,{record:row,field:"notification"},["status"])`, using compiler-resolved owning record/field provenance and a static selected-property list. The runtime resolves the current association internally, checks record/team/lifetime and every requested leaf before reading, applies independent content restrictions and returns one immutable selected object or null for an authorized null association. Missing authorization is denied/withheld, not null or a silently missing requested property. There is no handle-only/raw-ID alternate lookup or default all-properties request. Nullable source access therefore reads the checked locator first, then accesses its selected result. Stored `.id` uses the same helper with `["id"]`; it needs no mutable receipt fence, while status/result/error reads enroll the observation revision. A current local send result's immutable ID remains available under that originating effect authority, but mutable observation requires association first. Partial viewer projections cannot become handles or locators. Standard field rendering and pure query predicates use this same checked contract.

Authored capability version metadata uses an exact BigInt literal, consistently with other authored integer metadata; it is not a Number-valued exception to the target contract. External wire serialization follows the declared interface and is not implicit JSON serialization of this registry.

A delivery fixture recipe is `{delivery:canonicalOperation,values:async(c,s)=>({request,status?,result?,error?})}`, mutually exclusive with model/user/file recipe kinds; provisioned scope values are protected isolated handles. Initial recipe attributes use the existing table `selectors` and row `values` descriptors, with §5.1 planning/validation before provisioning; there is no second constructor or mutable receipt helper. Receipt recipe immutable IDs may supply trusted callback fixtures under test-provisioning authority; they are not production directory reads. No operation schemas or helper implementations are copied.

Parameterized inline descriptions/messages lower to `message(source,{locale:translation,...},{name:{type:canonicalType,value:expression},...})`. Static messages omit the third argument. Typed parameters preserve exact numeric and temporal formatting rather than serializing values prematurely. `format(c,descriptor,{locale:null})` uses the existing recipient fallback semantics. This is one target contract, not a second localization key system.

Test output uses one proposed `exampleFixtures({self,other,imported})` factory returning exactly `{fixtures:{recipeName:recipe,...},examples:[...]}`. Fixture recipes never share the top-level namespace with example metadata. Its `exampleImports` metadata lists canonical `{provider,member,alias}` references once; `imported` supplies recipes in the same test context, preserving shared fixture identity. A model recipe is `{model,dependencies:[recipe,...],value:async(c,s)=>fields}`; a user recipe uses `{dependencies:[],user:async(c,s)=>({roles:[roleIdentity,...]})}` (an empty list is the default), with canonical role identities rather than role predicates. The test runner provisions that recipe to a user reference before dependent records/files; an `as` cell returns that reference from `s`. A file recipe uses `file:async(c,s)=>recipeFields` with the same dependency metadata. During initial setup planning, scope `s` resolves validated baseline dependencies and reserved identities; ordinary finalized files retain their real references. Final table overrides are validated before protected receipts are provisioned once. Invocation/observation scopes then resolve real records/files/receipts under §5.1. A recipe is never dereferenced as though it were a stored row.

Each table has common `dependencies` (the deduplicated union of explicit source `seed` recipes and common baseline references) and `inputs:async(c,s)=>inputObject`; each selected row has its own `dependencies`, `values:async(c,s)=>cellArray` and either `expected:async(c,s)=>expectedArray` or an exact error code. Provision only explicit seed, common baseline dependencies, selected-row dependencies and their transitive closure, never the union of all rows or every fixture declaration. Common bindings establish the initial baseline even if the row later replaces an input. Evaluate all cells against that untouched seeded state before applying simultaneous selector overrides, as §5.1 requires. Expected expressions do not seed unrelated records. Selectors remain path metadata; observations are translated `async(c,s)=>expression` functions using fresh post-invocation fixture/input references and `result`. No runtime interpretation of Can strings or recipe proxy properties is implied. These are proposed test-output contracts only; factories, dependency metadata and callbacks do not implement provisioning or an example runner.


The sequence form uses the same test fixture factory with `{operation:enclosingOperationId,dependencies:[recipe,...],sequence:[step,...]}` in the existing flat `examples` metadata. The outer operation identifies the attaching scenario; it does not cause an implicit call. A call step is `{operation:canonicalOperationId,by:async(c,s,b)=>caller,inputs:async(c,s,b)=>inputObject,request?:async(c,s,b)=>envelopeOverrides,bind?:"name",error?:"exact_code"}`. A binding step is `{let:"name",value:async(c,s,b)=>value}`. An assertion step is `{observations:async(c,s,b)=>actualTuple,expected:async(c,s,b)=>expectedTuple,types:[canonicalTypeId,...]}`. Type IDs describe resolved value types: scalar `int`, `file`, nullable `user?`/`text?`, collection suffixes and qualified nominal enum/contract/model identities (for example `expense.Expense.status`). A scalar field reference resolves to its scalar type, not a new field-specific nominal type; preserve nullable/array shape. These distinct required keys discriminate the three step shapes; no Can strings are interpreted. `s` is a freshly reloaded fixture scope per statement; immutable `b` bindings are retained across steps, including captured versions. The runner supplies `c` as bounded read-only test-inspection context for pure callbacks; `by` is resolved to an account and the call obtains its separate genuine production context, so inspection authority cannot become operation authority. Successful declared business results alone enter `b[bind]`; exact-error steps cannot also bind. The runner performs typed assertions and per-call rollback comparison, and resets the current result on rejection. Dependency closure is provisioned once before the first step, not before each call. This is one proposed sequence lowering, not an implemented runner/API; existing table metadata is unchanged.

### 13.1 Judgment lowering

The [single descriptor convention](../../design/complex-apps/inbox.md#accepted-desired-js-lowering) is canonical: `appDefinition.judgments[qualifiedName]` contains the ordered questions with exact BigInt version and localized message descriptors. Its `sourceLanguage` comes from the checked owning declaration's module `source=`, independently of display preferences. A binding uses `{judgment:qualifiedName,from:deploymentPath}`. Generated result schemas, frozen specification and evaluate signature derive from that descriptor. The compiler extracts their canonical definitions into the shared emitted value inventory; authors declare the Judgment once. Source static `Name.specification` lowers to the proposed pure `judgmentSpecification(c,qualifiedName)`. A runtime-choice question adds `runtime:true` to its same descriptor, derives its candidate schemas once, and `Name.specification(options)` lowers to `judgmentSpecification(c,qualifiedName,options)`. The third argument is required exactly for those runtime declarations; fixed NOUL/score/static-choice questions keep their types. Ordinary sends retain the standard `send` lowering. Standard generation/mailbox schemas are canonical `std.*` type references, not app-local copies. Component rendering and the existing transaction, query, authority and example conventions remain unchanged.

The compiler checks and lowers both static and runtime-choice declarations through the [same source fixture](../../compiler/tests/fixtures/static_judgment.can). Static result/enum identities, `evaluate(state:text)` and the specification constant retain their existing shape. Runtime choices derive bounded text aliases, candidate records, required options arrays, `evaluate(state,options)` and the pure specification call with its third helper argument. One checked IR-derived `valueTypes` inventory supplies generated/source/standard contracts, named enums and bounded aliases to the artifact and `appDefinition`; no dynamic enum is fabricated. Reused candidate fields retain count, distinct-ID and authored-ID exclusion constraints, with receiving bounds intersected; nonliteral bounds on these constrained reused fields explicitly refuse. Delivery metadata preserves the declaration version as exact decimal text and reuses its inventory result. Required-array presence survives as `[]!`, independently of a nonempty proof. The extended direct module case passes through production CLI, installed catalog and actual module assembly, including static preservation, runtime metadata coherence and focused missing-options/oversized-ID refusals without modules. Native dispatch, provider normalization, storage/receipt qualification and complete applications remain separately owned and qualified.

### 13.2 Explicit context and pure value selection

An authored file policy lowers once to `appDefinition.context.files`, retaining only explicit deviations: `types` is an array of media-type strings and `max` an exact BigInt byte count. Omitted attributes retain the shared default; do not repeat baseline fields in generated app metadata unless they were authored.

`choose(condition:bool,yes:T,no:T)->T` is a pure standard value function for selecting between two values of one compatible type, with enum literals resolved against that shared expected type. Like other ordinary calls its arguments evaluate eagerly, in order, once. It provides no null narrowing or short-circuit permission check; use existing statement guards/branches before dereferencing optional values. The JavaScript target imports `choose` from `@canlang/stdlib`. This is a small library contract, with ordinary call grammar, rather than an additional conditional-expression syntax. CanSync's field rebase is its concrete witness; branch effects retain ordinary `if` suites.

### 13.3 Image collections

`gallery Query image=image` is the shared image-review collection, with the same typed query, row scope, ordering/filtering and scoped children as `list`. `image` is required and selects exactly one readable `file` field containing an allowed image. The renderer supplies responsive thumbnails, accessible keyboard preview and authorized original access; failures/loading remain ordinary shared states. Every preview/open rechecks current row, field and attachment permission. A thumbnail URL never grants file authority or creates a new published file. No app-authored markup, visual state store or provider fetch is implied. CanCreative and CanGallery are its source witnesses.

Canonical collection factory props are `model` with optional `parent`, `where`, `order` (or `items` plus its `contract` where a typed structural array needs schema metadata) and `renderRow:(row,rowView)=>children`. `gallery` adds `image:"field"` to those same props. Explicit card/details groups use `children` arrays. Do not introduce competing `rows`/row-`children` conventions. The shared factory owns media rendering and daisyUI/HTMX mechanics.

### 13.4 Observable progress and complete invocations

Progress uses the existing `delivery(c,{record,field},selectors)` accessor. Static nested selectors such as `["progress.state"]` return a nested selected object without exposing private sibling content; requesting `["progress"]` requires the complete grant. Mutable progress participates in the receipt revision fence. Observable interface relations live once in the standard catalog, not per-app handler wiring. Handler metadata uses the normal `on:"owner.Service.start.progressed"` form. Model-derived fields and the factory's `derives` rule map supply UI projections.

Complete invocation metadata is `{type:"invocation",operations:[canonicalOperationIds...]}`. Its local constructor is the proposed `invocation(c,canonicalTarget,arguments)` helper; execution is the existing `call(c,value,{})`. Typed provider schema extraction, frozen authorization context and reference validation derive from this metadata and the owning declarations. Generic presentation shows exact arguments and protected versions under current disclosure; it does not execute or imply approval. No per-app decoder or privileged tool executor is added.

### 13.5 Corpus lowering

`appDefinition.corpora[canonicalName]` contains `{model,scope,title,content,from,eligible:(c,row)=>predicate}` once. Generated interfaces and opaque result schemas derive from that descriptor. Effects retain ordinary `send`, receipt reads retain `delivery`, and the component remains `content({context,value})`. The only new pure helper contracts are `corpusStatus(c,canonicalName,record)` and `groundedAvailable(c,value)`. See the owner catalog for complete admission, proof, freshness and fixture behavior; no handwritten source-policy callback tree or raw answer string is emitted per app.
