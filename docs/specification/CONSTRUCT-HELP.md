# Can v1 construct help catalog

**Status:** proposed agent-help contract for the Can development server, recorded before an implementation plan. This is the single authored set of help cards for this design stage. [GRAMMAR](GRAMMAR.md) remains normative for source spelling, [DESIGN](DESIGN.md) for behavior, the [UI component catalog](../../packages/ui/src/catalog.ts) for renderer profiles, and the [Values catalog](../../packages/values/src/catalog.ts) for callable builtin signatures. The dev server does not yet serve these cards.

## Card and link contract

Each row below is one card with a stable `can.v1.*` ID, a compact source signature (or the owning catalog's generic typed signature for builtins), a short meaning, a minimal `.can` source fragment, availability, and a stable self link. Binding and structural options are shown in the signature; component-specific appearance options remain the closed set in the linked UI catalog. The explicit HTML anchor is the link target; future renderers must preserve it even when headings or row order change. A source fragment shows placement **inside the stated owning context** with its referenced models, operations, bindings and resources declared; it is not a standalone app unless it includes `app`, `Given`, `When` and `Then`. Square brackets in signatures mean optional syntax, `...` means a bounded repetition from the linked grammar, and uppercase placeholders such as `NAME`, `TYPE` and `EXPR` are notation, not source tokens. Examples are explanatory source, never an assertion that a whole deployed workflow was run.

Availability has independent dimensions. **Parser** means the current Rust parser has a branch for the shape; it does not certify a resolved name, permission, type, example execution or deployed runtime. **Catalog implemented** means the owning UI or Values factory is marked implemented; a compiler check and target runtime profile are still required. **Profile dependent** means the effect needs a declared binding, actor, provider, deployment/runtime capability or supported host path. **Proposed** means the spelling is specified but the current implementation is not qualified; it must not be ranked as a closest *working* suggestion. An actual `can dev` response may call a card *working* only after the compiler confirms that construct in the current source position and the selected runtime profile supports its required capability. Unknown context, unsupported profile or unresolved authority produces an explicit availability limit rather than a confident recommendation.

The server should first restrict cards by file/section, expression role, expected type and compiler profile. Deterministic spelling or grammar matches can return a card directly; Jev may rank a finite set of eligible IDs when intent is ambiguous, including `none/unclear`. Jev returns IDs and uncertainty, while Can supplies the signature, meaning, example, availability and link from this catalog. An ID or link never implies that the user's intended permission or effect was inferred. Changes to a card's syntax or behavior need an owning source change and a consistency check; incompatible semantics require a new ID or language version. At implementation, move this single authored catalog into a structured compiler-owned registry and generate this page, or generate one registry from the owning sources. Do not hand maintain two independent help texts.

## Coverage and qualification

This design-stage catalog contains one anchored card per listed source construct. It intentionally excludes compiler/runtime helper functions, generated JavaScript, deployment commands and undocumented guessed words. UI cards include all 68 approved authored words; `calendar` and `tabs` each have two context-distinct cards. Callable builtin cards cover the 36 `kind: "builtin"` entries in the Values catalog; `kind: "helper"` entries are not Can calls. Two compiler-registered context types, `Team` and `OperationContext`, are withheld from the authoring-card set until their legal source positions are established. The corpus and some provider/resource examples are syntax illustrations whose full semantic and runtime profiles are still unqualified.

The current completion list is narrower than the grammar and does not provide these five card fields. Some historical prototype caveats in GRAMMAR conflict with current Rust parser branches (`delivery`, `invocation`, sequences, CSV form attributes and page refresh), while the scenario header table omits parser-supported `expose`. Those discrepancies are explicit availability and consistency work for the registry, not grounds to call an unverified card working. All 202 full-looking examples in this draft passed `can check` with the existing local debug compiler and Values catalog; context fragments, source-current compilation and runtime behavior remain unqualified. Before the dev server advertises a card as working, check exact compilation, intended context, permissions and resource profile; unsupported or ambiguous guesses may return `none/unclear`.
