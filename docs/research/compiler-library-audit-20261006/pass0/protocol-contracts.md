## Supported protocol and independent expectations

The present application is an **LSP 3.17 stdio server**, not a generic JSON-RPC service. LSP requires version `2.0`, request IDs of string or signed 32-bit integer, optional structured params, and UTF-8 bodies. Null is permitted in response IDs, not request IDs. Framing counts bytes; CRLF and Content-Length are specified. Unsupported charsets should produce an error. These are specification-derived constraints, not crate defaults. See [official base protocol source](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/specification.md).

Generic JSON-RPC permits string, number or null request IDs, discourages null/fractions, and defines a notification by **absence** of the ID. It requires structured params when present, a matching response ID when readable, and null when identification fails. Its error categories distinguish invalid JSON, invalid request, unavailable method and invalid params. Thus a generic `null` ID request is not an absent-ID notification, but its legality does not override LSP's narrower type. See [JSON-RPC 2.0](https://www.jsonrpc.org/specification).

LSP coordinates are `uinteger`, bounded at `2^31−1`, and use negotiated encoding; Can advertises UTF-16. Existing `parse_coord` instead admits through `u32::MAX`. Preserve UTF-16 behavior while classifying that wider boundary as a correction question, not a standards requirement. [Position definition](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/types/position.md), [base integer definitions](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/specification.md).

## Lifecycle and error mapping

Ready request behavior is established: initialize once; before initialization requests receive `-32002`; unknown methods receive `-32601`; most bad positions/unknown documents receive `-32602`; shutdown returns null, subsequent requests receive `-32600`. `initialized` and cancellation notifications are no-ops. Analysis requests complete synchronously, so no pending cancellable request exists; stale diagnostics are notification work without request ID.

The notification branch lacks lifecycle gating: valid didOpen before initialize produces diagnostics, and sync notifications after shutdown can mutate/publish. Before initialization notifications must be dropped except exit; treat that as an identified correction. [Initialize lifecycle rule](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_specifications/lsp/3.17/general/initialize.md). After shutdown clients must send only exit; define server handling of violating notifications before changing it. [Shutdown](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_includes/messages/3.17/shutdown.md).

Exit after shutdown gives 0, otherwise 1. EOF/torn body flushes and returns stored code (initially 0 even without shutdown). This disconnect behavior is existing Can behavior; exit-notification rules alone do not prescribe EOF status. Framing errors currently continue without response/resynchronization guarantees; write failures return stored lifecycle code; SIGINT uses default OS disposition. Keep separate fixtures for exit, EOF and torn disconnect. [Exit rule](https://raw.githubusercontent.com/microsoft/language-server-protocol/gh-pages/_includes/messages/3.17/exit.md).
