# Flat arithmetic stack review (read-only, 2026-10-07)

## Confirmed evidence and limits

`/private/tmp/can-resume-stages/stages.rs` marks entry to public stages, not individual recursive functions. Its saved `results.json` proves 64 and 512 terms complete parse/resolve/types/effects/examples/IR/JS/drop on the tested observer executable; 1024 aborts after `begin JS`, 2048 after `begin types`, and 3000 after `begin resolve`. These delimit stages, not exact failing frames. The second observer below independently establishes failure during the public expression-lowering path; it still does not identify the first failing internal frame in full `emit_program`.

Saved sources are directly under `docs/research/compiler-library-audit-20261006/responsibility-map/failure-evidence/source-flat-{64,256,512,1024,2048,3000}.can` (there is no `resource-inputs/` subdirectory here). The 64-term case is a read scenario returning unparenthesized `1+1+…`; it has no authored nested grouping. Parser `parse_value_inner` (parser.rs:1486, binary construction around 1567–1574) loops while wrapping the previous left node, so constant parser call depth can create a linear-depth left-associated CST. Existing expression-entry budgeting consequently does not bound this resulting tree depth.

## Confirmed recursion owners

- Resolver `walk_expr` (resolve.rs:4885; Binary arm around 5027) records the parent scope, then recursively walks left followed by right. The 3000 failure stage is consistent with this direct recursion. `has_error` (802) uses the iterative `SyntaxNode::descendants`, so its repeated subtree scans add potential quadratic work but are not themselves recursive-stack owners.
- Types `Typer::expr` (types.rs:9668) dispatches to `type_binary` (11085), whose arithmetic arm (11203 onward) recursively types left then right and applies `type_arithmetic`. `expr` records the completed node afterward. This directly explains a vulnerable path in the confirmed 2048 failure stage; no function-frame trace was obtained here.
- IR `decode_expr` (ir.rs:2137) / `decode_binary` (3068) recursively construct left and right `Box<TypedExpr>` operands. `expr_uses_async` (3379), `collect_s_refs` (8721), and JS preference-use scanner `expr_uses` (js.rs:3401) are further recursive expression consumers.
- JS `lower_expr` (1624) → `lower_binary` (1869) → `lower_arithmetic` (2162) recursively lowers left then right. Integer addition emits `int64(left + right)` at **every binary node**, preserving checked intermediate results. Repeatedly copying the accumulated left string also gives a quadratic allocation/copy path.
- JS item traversals repeatedly call `self.ir.items.clone()` (e.g. `emit_identity_consts` around 3549, called before expression emission at 998; derive functions at 5554 and registry handling at 5594). IR `TypedExpr`/`IrExpr` derive `Clone` and own nested boxes, so ordinary derived cloning recursively traverses the linear expression. Temporary cloned item lists are also recursively dropped. The second observer below rules out whole-item cloning and ordinary destruction as independently failing at 1024 in its tested invocation. These recursive operations remain depth-sensitive closure risks beyond those tested sizes or under a different caller stack; they should no longer be presented as equally supported explanations for the observed 1024 abort.
- Effects `walk_tree_calls` (effects.rs:3863) and examples `check_inline_patterns` (examples.rs:512) recursively traverse CST children. They completed for 512/1024 under this observer but remain future downstream stack risks when earlier stages are repaired.
- CST `SyntaxNode` owns `Vec<SyntaxNode>` and derives `Clone` (cst.rs:201); IR owns boxed recursive expressions and derives `Clone`. Neither has a custom iterative drop implementation in these files. Normal clone/drop, debug formatting, and CST `dump_into` (391) need explicit closure review. Passing `begin drop` at 512 proves only that tested size.

## Bounded-stack alternatives (proposals only)

A focused arithmetic-spine worklist can preserve the exact tree without imposing a new source-admission limit: collect left-spine nodes as borrowed frames, process the bottom operand, then each original right operand and parent in order. Do not reassociate, fold, or balance arithmetic: overflowing intermediate `int64` results, subtraction/division, effectful operands, and diagnostic spans/order can change. A mixed-operator spine needs each frame's original operator, checked type, and span; unrelated nested child shapes still require their own safe traversal.

For resolver use explicit enter frames and push right then left so processing remains preorder left-first; retain each frame's lexical scope/context, `has_error` pruning, `is` type-target handling, and alias-scope creation. For arithmetic typing/IR use enter/finish frames or a borrowed-node postorder worklist, recording exactly after both operands as today. Keep typer comparisons, enum expectations, and boolean narrowing on their existing ordered continuation paths unless separately modeled: a generic unordered child walk would be incorrect.

For emission use explicit enter/finish actions plus a token/rope buffer, or typed rendered-child slots, to emit original nested `int64` wrappers and evaluation order without deep Rust calls or repeated full-prefix copies. Preserve current behavior where an unsupported operation reports its own diagnostic without necessarily descending operands; eager generic child lowering could add diagnostics/imports that current code suppresses. Boolean/coalesce short circuit and money scalar-first helper normalization deserve separate outcome checks.

Removing emitter-wide item clones through immutable borrowing or small metadata snapshots avoids one immediate clone/drop recursion, but does not close public `Clone`, IR cleanup, CST cleanup, scanner traversal, or output runtime behavior. Arena/index-backed expression storage could close clone/drop more systematically but is a broader representation/API change. An iterative custom drop must detach all recursive edges, including nested expressions in statements/items/query/message/default/UI shapes; simply moving a box into a temporary still drops it recursively. Worklists are bounded in call stack, not constant total memory; they use O(tree depth/nodes) heap storage.

## Direct lowering and clone controls (updated evidence)

Independently read `/private/tmp/can-resume-stages/stages2.rs` and `results2.json`. Both modes reconstruct the same parsed/resolved/typed/effects/examples-checked program and build public IR before diverging. At 512, `lower` selects a checked scenario `Return` value and calls a fresh public `Emitter::lower_expr`, produces 6134 bytes, then completes all ordinary drops. At 1024 it aborts after `begin direct lower_expr`, before completion. At both 512 and 1024, `clone` clones the **whole** `ir.items` vector and then drops the clone, IR, checked program, and CST with exit 0. This provides an actual positive clone/drop control, not merely an absence of clone instrumentation.

Observer correctness: it uses the real catalog, asserts parse coverage/no parse diagnostics, checks combined analysis diagnostics and IR diagnostics, and borrows the expression directly without cloning it. The saved flat sources contain exactly one scenario and one return, making the selected value unambiguous. The `lower` marker technically precedes `Emitter::new` and selection, rather than immediately bracketing `lower_expr`. Source review of `Emitter::new` (js.rs:1263) shows only iterative item enumeration/canonical-name cloning and empty collections, with no recursive expression traversal. Therefore the observed failure is securely attributable to the expression-lowering public path for this input; the precise stack frame (`lower_expr`, `lower_binary`, `lower_arithmetic`, formatting, or their call combination) is inferred from source, not directly sampled. A marker after `Emitter::new` would make the executable boundary exact without relying on that source exclusion.

The observer is adequate for failure localization; it is not yet an output-semantic oracle: lower mode does not assert that a return was selected, inspect emitter diagnostics, check the rendered value beyond its byte length, or execute the result. Those checks should be added to any permanent regression. `results2.json` also omits input hashes/build metadata present in the first result file; a durable evidence bundle should link the exact input bytes and executable/build revision. Clone control does not claim every possible consumer clone/drop stack depth is safe, and direct lower failure does not prove full `emit_program` reaches precisely the same first failing helper.

Root reports three independently worded JEV requests advising iterative-first, with confidence 0.49/0.94/0.86 (selection probabilities 0.66/0.96/0.91). Treat that as an advisory preference and retain the large confidence spread as uncertainty. It neither validates an implementation nor closes the full representation/consumer work listed above.
