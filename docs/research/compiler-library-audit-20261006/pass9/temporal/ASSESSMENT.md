## Independent outcomes and comparison

43 owner-derived fixed vectors cover min/max years, 0000/10000, Gregorian 2000/1900/2024/2023 leap distinctions, month-end rejection, fixed width, lowercase t/z, numeric positive/negative offsets including 23:59 and invalid 24:00/00:60, leap seconds, zero/nonzero sub-ms including >9 fractional digits, malformed Unicode in dates/time/zones, trailing newline, required seconds/zone, and min/max **after offset** with adjacent valid cancellation cases. Expected UTC milliseconds are independently fixed for accepted datetime cases. Public constructor acceptance and real compiler diagnostics agree 43/43; all asserted milliseconds agree.

Candidate is exactly `time=0.3.55`, defaults disabled, features `std,parsing` (`std` enables alloc); no macros/local-offset/large-dates/formatting/serde. Primary APIs are `Date::from_calendar_date`, `Month::try_from`, `OffsetDateTime::parse(...,&Rfc3339)`, `unix_timestamp_nanos`. Actual linked transitives: time-core0.1.9, deranged0.5.8, powerfmt0.2.1, num-conv0.2.2; feature tree, lock checksums and local primary-source hashes are saved. The date type normally permits -9999..9999; Can requires 1..9999. The crate requires Rust1.88; host Rust1.99 qualifies. Timezones/local host offset are unused.

Executed raw Rfc3339 differences: accepts space as separator; accepts year0000; normalizes a valid month-end leap second to the prior nanosecond; accepts nonzero sub-ms, and silently loses nonzero digits beyond nanosecond precision; does not enforce the Can UTC min/max after offset. It does accept lowercase t/z and ±23:59. Therefore `timestamp % 1ms == 0` alone cannot preserve the constructor: the >9-digit nonzero fraction already disappeared before that check. Candidate mismatches are not defects in current Can.

The executed adapter checks ASCII fixed spelling/year, rejects seconds60, scans **all** fractional digits and permits only zero after digit3, normalizes only permitted fractional precision, validates zone shape, and checks resulting UTC ms bounds. Date shape/year guards wrap `Date::from_calendar_date`. This adapter matches acceptance and exact ms 43/43. Its errors are demonstration categories or crate messages, **not** existing compiler E3001 prose/precedence; production adoption would still need that adapter and caller diagnostic tests. One allocation for normalization remains. Sharing a small approved calendar primitive could remove the Gregorian arithmetic duplication, but sharing private runtime Value/Failure code is not the present released contract.
