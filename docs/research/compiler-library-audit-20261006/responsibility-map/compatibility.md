## How to read the classifications

| Class | Rows | Meaning at the declared boundary |
| --- | ---: | --- |
| Required semantic behavior | 43 | Language, public contract, accepted owner policy or actual consumer needs the value, schema, order of evaluation, identity or outcome. |
| Required byte property | 7 | A specific identity/hash or current public byte promise applies. It does not freeze all surrounding serialization. |
| Migration guard | 18 | An accepted cutover or characterization retains the detail today; its continuing necessity needs an explicit owning revision. |
| Incidental representation | 3 | The identified mechanism has no demonstrated consumer requirement; enclosing semantics and API support still matter. |
| Repository test-only use | 2 | Observed production callers are absent for the named helper scope. Exported API support is a separate question. |
| Demonstrated invalid behavior | 1 | Known locale-owner mismatches must not become compatibility targets. |
| Unresolved boundary | 9 | Owning policy, conflicting claims or incomplete qualification blocks the dependent choice. |

Some rows have mixed scope. Descriptor and formatter rows, for example, combine semantic requirements with explicit public byte properties. The row's `classification_scope`, authority and current binding take precedence over treating the class count as a count of freely removable obligations.

Accepted migration checks and documented public promises remain binding for their declared releases. This audit does not retroactively waive them. A consumer that parses named JSON fields supports a narrower semantic minimum; it does not erase a separate public promise about key order. Conversely, a test asserting old bytes does not independently establish a permanent language rule. Unpublished Cargo configuration does not prove absence of path/git Rust callers.
