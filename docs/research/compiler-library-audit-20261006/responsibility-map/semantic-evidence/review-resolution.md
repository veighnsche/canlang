## Confirmed nullable array admission defect

DESIGN139 excludes nullable elements from v1. GRAMMAR189/197 forbids their value representation, including qualified reuse. These contracts are independent of the primary lane's notes and of implementation inference. `types.rs::type_array`12346–12430 remembers the first concrete element type, strips nullable wrappers only when comparing later elements, and never widens or rejects a later nullable element. `types_compatible`9742–9825 correctly rejects nullable-to-nonnullable assignment once the actual array carries that nullability; the problem precedes argument comparison.

The two root raw receipts are syntax-qualified (`parse_codes=[]`, coverage/complete true) and use the installed catalog, not a changed producer. For the same `take(xs:text[])` and `g(x:text?)`, `["fixed",x]` is typed `Array<Text>`, reports no diagnostics and emits `take(c,["fixed",x])`; `[x,"fixed"]` is typed `Array<Nullable<Text>>`, reports E3001 at82..93, and blocks emission. The element expression `x` remains nullable in both receipts. This confirms unsupported potentially-null data is admitted into a nonnullable array argument by element ordering.

List order itself has meaningful runtime semantics. The independent invariant here is that both permutations must satisfy the same nonnullable element safety obligation; this is not an assertion that arbitrary reordering preserves business behavior. `count` does not need to crash on null for admission to violate the language subset. These receipts establish type/emission unsoundness, not an executed runtime failure, disclosure or permission bypass. The reversed literal is rejected at its call consumer; this pair does not prove standalone nullable array literals are consistently rejected. Empty/error/opaque/unknown/nested-array cases remain outside the pair.
