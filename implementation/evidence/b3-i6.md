# B3-I6 activation checks evidence

Scope: packet §c (scope-6): wire the four activation gates (installed
compat, requires bridge, installed digest, outstanding-work inventory)
behind one typed verdict, refuse to serve unless active, add
`can-platform activate`. OUT OF SCOPE (untouched): schedule-backend
verification (OPEN-139), L4 `handlerContractFor` mapping (attestation
stays injected), `compiler/src/cli.rs` (`can activate` passthrough is
the coordinator's integration step).

## Design decisions (all loud in code)

- **Gates are injected, not imported.** This package has no runtime
  dependency on `@canlang/state`/`@canlang/work` (and `package.json`
  is out of scope), and their TS sources cannot load under the
  plain-node dist CLI — so `activate` takes `ActivationGates` typed
  against the EXISTING signatures (positional
  `(store, plan, inventory)`; single-object
  `{ outboxItems, handlerContractFor }`). Additive extension stays
  compatible. The plan is the minimal structural view the checker
  reads (`migrationId` + `invalidates`, verified by read); tests
  adapt it to the real `ValidatedMigrationPlan` with a documented
  cast (re-verify if that signature ever extends non-additively).
- **Fail-closed wiring.** `store` runs gate 3; `inventory`+`gates`
  run gate 4; any absent group BLOCKS with `activation-incomplete`
  (never passes, never throws). The CLI passes store-from-bundle
  only, so gate 4 always reports the producer join there; the full
  four-gate pass runs in vitest through the REAL producer functions.
- **Fresh install passes gate 3** (null snapshot: S7 never applies
  transitions without a predecessor, so nothing can disagree).
- **`min_version` pins are NOT verified** (installed registry
  carries no versions; presence only). Wanted version rides the
  reason detail.
- **`probeInstalledRuntime(env, opts)` is declaration-based.**
  Verified by grep: the worker env exposes no capability signals
  today, so the deployment declares and the probe validates
  (unknown ids throw — a deployment bug, never a verdict). `env`
  is threaded+validated for the binding cross-check join.
- **Descriptor-side unknown upgrade is additive post-processing**
  in `activate` (`compat.ts` itself still collapses; owned
  elsewhere).
- **Gate-4 error classification is structural** (`StateError`
  name+code shape → `blocked-work`, else
  `activation-check-failed`); both block, detail preserves the
  message.

## Demo proof (`can-platform activate`, TeamTasks bundle)

Bad bundle (requires `values.decimal`, target lacks it, no store):

```text
activation: refused (2 reason(s))
{"ok":true,"command":"activate","active":false,"reasons":[{"code":"missing-capability","detail":"artifact requires \"values.decimal\" (min_version 1) but the target does not install it"},{"code":"activation-incomplete","detail":"no store: the store-backed digest + outstanding-work inventory gates are unchecked, activation cannot proceed"}]}
exit=0
```

Good bundle (gates 1–3 pass from bundle data; gate 4 names the join):

```text
activation: refused (1 reason(s))
{"ok":true,"command":"activate","active":false,"reasons":[{"code":"activation-incomplete","detail":"outstanding-work inventory gate unchecked (missing inventory, gates (@canlang/state + @canlang/work producer join))"}]}
exit=0
```

`activate` without `--env` is a usage failure (exit 2,
`code: "usage"`). Full four-gate `active: true` (empty outbox +
pinned-undispatched-still-pending) is proven in `activate.test.ts`
with the real `buildWorkInventory` + `checkActivationInventory`.
