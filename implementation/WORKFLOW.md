The human launches each Muse session. Use Muse Spark 1.3 Contributor at MAX when available as requested; never silently downgrade. This document authorizes implementation within the lane and normal GitHub PR/review/merge cycles. It does not instruct Codex to launch sessions. Do not spawn additional orchestrator sessions; use your session's normal subagents inside your one lane worktree.

## File foresight and bounded autonomy

The user identifies file-tree foresight as a Muse weakness. Additional risks here are planning risks, not measured claims about the model: duplicate APIs, shared-file drift, mock-backed completion, context overload and premature stopping.

- Before each slice, list every file you expect to create/change, its owner, entry-point wiring, consumers, tests and generated outputs. Check it against PLAN's tree. An owned module may be refined locally; a cross-lane boundary requires the owner's acknowledgment.
- Keep a short public API section and exact task reservations in your status file. Other leads read committed status/PRs; changing a file does not magically message another session. Poll waiting dependencies only on ordinary task/goal boundaries or supported waits, never tight loops.
- Prefer a complete narrow behavior over many disconnected stubs. Test doubles are explicitly test-only and get replaced at their integration milestone. Unsupported production behavior returns a precise failure; it never quietly succeeds.
- Each assignment gives an agent requirements, exact paths, interface inputs/outputs, acceptance and a stopping condition. Do not dump the whole repository/history into each agent or ask one agent to implement and independently approve everything.
- Start with at most two active implementation subagents per coordinator, plus a short focused review when useful. Increase only after observing available CPU/memory/disk and independent work. Avoid concurrent heavy builds, repeated full installs, copied repositories, private caches and full session dumps. Seven worktrees are the repository isolation, not seven required full build environments.
- Use existing workerd/Web APIs, Cloudflare resources and suitable libraries. Verify the used functions under the actual environment; importability alone is not compatibility. Do not recreate encoding, TLS, cryptography, HTTP parsers, model SDKs or another LSP protocol stack from scratch.
- Difficult design choices follow repository JEV rules: verified facts and balanced alternatives, three fully rewritten equivalent requests, appropriate question types, saved responses/uncertainty. Standing authorization applies; previous automatic approval rejections must not be bypassed. Consultation does not override user requirements.

## Parallel contracts and merge order

Implementers can start independent work immediately. Send a dependency request as a committed status entry and PR description naming producer, exact type/function/behavior, a consuming example and earliest needed milestone. The owning lane ships its minimal contract/implementation increment; the consumer fetches/rebases after merge. Do not copy the missing producer into your lane.

L1 owns Rust Cargo manifests/lock and editor package; L7 owns root Node workspace/lock/shared CI configuration; package owners own their own manifests and source catalogs. Route root lock updates to L7 with exact manifest changes. L7 must process these early instead of accumulating a last-day integration pile. Each contract source file has its producer owner in PLAN. Shared root documentation changes follow the owning contract and require affected consumers' acknowledgment for breaking semantics.

A compatible additive interface PR can merge before all implementations if no incomplete production feature is advertised. Breaking interfaces need a producer-first compatible transition or one coordinated atomic change with released file ownership. Do not create mutually dependent unmerged branches, permanent mocks, a second builtin catalog or a new runtime just to appear independent.

## Commit → PR → own review → merge → repeat

1. Make small coherent commits early on your owned branch, staging exact paths. Keep source, relevant tests, interface docs and status evidence together. Never stage another agent's unfinished work or all files blindly.
2. Rebase onto current `origin/main` before opening/updating a PR. Run focused checks that actually exercise the changed behavior. The baseline may evolve through the existing draft coordinator; refresh affected inputs and reconcile meaning explicitly.
3. Push and open a real PR against main using `gh`. Describe the problem/result, contracts touched, actual checks and residual limits. Use a body file for multiline text. Attach the PR to the current chat if that capability is available; otherwise include its URL in your status/handoff.
4. Review the actual PR diff yourself. For meaningful semantics, use one independent read-only subagent with requirements/raw diff, not your favorable verdict. Pay particular attention to authority, money, file disclosure, retry and migration behavior. Fix material findings and recheck their affected scope. Self-review is not a fabricated independent GitHub approval, and additional review rounds need new evidence/risk.
5. Merge only when the reviewed head is unchanged, conflict-free, applicable checks are green, required contracts are present, substantive findings are resolved and branch protection is satisfied. Use the reviewed head with `gh pr merge --squash --match-head-commit <sha>` or the repository's supported merge queue. Never use admin/bypass flags or disable checks. An unknown/pending check or mere `mergeable=true` is not success.
6. Fetch main after merge. In the SAME owned worktree, create the next slice branch from `origin/main`; do not check out the primary worktree's main or allocate another worktree. Record merged PR/evidence and continue until the lane's entire authorized scope is complete or genuinely blocked. A scaffold, one PR, or exhausted immediate subtasks is not lane completion.

If main changes and invalidates your tested base, rebase and run relevant affected checks again. Do not repeatedly run unrelated broad suites to simulate progress. A blocked dependency does not prevent ready independent tasks. A real unresolved design/credential/resource blocker gets a precise question and preserved work, not an invented replacement.

The user wants sustained substantial Muse work. Use the available effort to finish real implementation, testing, integration and repairs.
