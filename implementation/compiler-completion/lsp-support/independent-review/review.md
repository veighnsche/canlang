## Public builders and fair replacement challenge

I inspected the public module/reexport route in `compiler/src/lib.rs`, `lsp/mod.rs`, and `transport.rs`; the `Json` variants/accessors/render implementation; all three builders; and the separate typed output envelopes. `Json::Obj(Vec<(String, Json)>)` preserves order and duplicate members. `Json::Num(String)` is directly constructible, and `render_into` copies its contents without validation. The builders accept arbitrary `Json` IDs and values, never call `parse_call`, always return `String`, and keep compact envelope/member order. `response_err(None, ...)` emits null, and its signed i64 code spelling is independent of LSP i32 admission.

`output::response` is a different, private contract: it revalidates the rendered admitted ID through `RawValue::from_string` and serializes DTO payloads directly. A general serde value replacement loses duplicate members or raw lexemes. RawValue validation rejects an unchecked malformed hand-built value and cannot preserve the current infallible builder signature by itself. Those replacements do not meet the selected public contract. Current success/error builders are live in server and stdio routes. Public transport notification has only its shape-test caller internally; private typed notification serves diagnostics. Internal nonuse does not establish that a public helper can be removed.

A consolidation preserving public names, signatures, and arbitrary rendering could be supported without removing public API. A shared prefix helper or compatibility wrapper is not excluded merely because retaining the source is easier. But no exact candidate establishes a complete removed mechanism or net result here. Keeping the Json renderer in a wrapper does not retire it; removing names changes support. The original row explicitly permits retention when its qualified replacement does not meet the closure target. Retention is justified at that scope and does not preclude a later counted, byte-qualified consolidation.

## Position, source, and URI ownership

I inspected public `TextPos`/`LspRange`, every `LanguageAnalysis` callback signature, public location/edit fields, `RealAnalysis` input/output conversions, source `LineIndex`, `ide::queries::offset_at_position`, range projection, authored document-map lookups, and URI output wrappers. Five callbacks take TextPos; code actions take LspRange. Both nominal types are still consumed by public return/edit structures and backend implementations. The complete repository implementation set is StubAnalysis, RealAnalysis, KindsAnalysis in server unit tests, **and Observed in `compiler/tests/session_history.rs:34`**. The candidate raw search includes that fourth implementation.

`output::range` copies source-domain values into lsp-types fields. LineIndex owns UTF16 counting, supplementary scalar width, byte-inside-scalar clamping, CRLF handling, and end clamping. Position-to-byte conversion owns missing-line None, excess-column clamp, and surrogate-interior clamp. A protocol position type does not itself implement those source policies. Aliasing may reduce adapter/type declarations and preserve some construction syntax, but changes nominal ownership/identity and introduces library API coupling; the public owner has selected continuity, not that migration. Nominal wrappers preserve ownership while reducing the available retirement credit. No fully qualified alias/consolidation candidate has been submitted.

Authored String URI keys remain document identities. The server looks them up exactly and sends authored URI strings to callbacks and wire outputs; edits preserve first-URI-occurrence grouping. URL admission only derives native display metadata. A library URI normalization that merges `%2f`/`%2F`, rejects malformed/opaque/nonfile identities, or reads through projected paths would change this contract. Such behavior cannot be attributed to retirement of two position carriers.
