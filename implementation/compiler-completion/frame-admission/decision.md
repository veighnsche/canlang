# FAIL-R03 implemented support contract

Owning sources are `compiler/src/lsp/transport.rs` and the `run_stdio` framing-error branch in `compiler/src/lsp/server.rs`. Reader/allocation witnesses live in `compiler/tests/lsp_frame_reader.rs`; bounded actual-process transcripts live in `compiler/tests/lsp_admission.rs`. No language/source admission limit or generic transport framework was introduced.

## Decisions and rationale

- Accept at most 65,536 bytes in the complete header section, counting all wire line endings and the empty separator. One aggregate budget bounds both a long line and many short lines without separate line/count knobs. Exact-boundary headers work. The ordinary inspected VS Code peer and server writer emit one short Content-Length header; 64 KiB provides generous extension room. A 16 KiB alternative has a lower worst-case bound but less compatibility headroom without an evidenced need. Keeping unbounded headers leaves the demonstrated gap. A broader framework requires unrelated policy/compatibility qualification and does not itself establish this contract. The number is a supported local policy, not a normative LSP maximum; previously accepted larger extension sections intentionally become unsupported.
- Retain the existing 67,108,864-byte (64 MiB) body limit. Check every declared length before acquiring payload. Start with an empty Vec; acquire at most 8 KiB at a time from available buffered payload, growing fallibly and geometrically only when needed, with requested capacity no larger than the accepted declaration. The first growth request is at most 16 KiB. No payload means no body storage request. Returned bytes and the following frame boundary are exact, including UTF-8 byte counts. Header and body reservation failure returns an OutOfMemory I/O error. Interrupted reads retry as the prior std readers did.
- Accept repeated Content-Length declarations only if all parsed counts agree (case variants and zero padding remain accepted). Reject conflicts, malformed values and any oversized declaration immediately. Equal duplicates preserve an unambiguous part of prior compatibility. Rejecting all duplicates would remove that compatibility; last-wins would leave two possible body boundaries. Other existing reader extensions, including bare LF, whitespace trimming, numeric parsing and ignored unknown headers, remain.
- Close stdio on framing refusal or other non-EOF input I/O failure, flushing prior output and returning exit 1 without a fabricated JSON-RPC response. This deliberately replaces the unqualified previous continuation in the same server state. Resynchronization requires a separate design: missing/conflicting lengths and budget failure do not establish the next body's boundary, and scanning can reinterpret payload as messages. Clean EOF and torn header/body EOF retain the existing lifecycle exit behavior. Correctly framed complete invalid JSON/UTF-8 still produces one null-ID parse error and continues. Malformed framing remains a transport failure even after a successful shutdown response.

## Verified primary context

Microsoft's [LSP 3.17 specification source](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.17/specification.md#header-part), checked through the web tool, defines required Content-Length in bytes, ASCII header fields, CRLF separators and UTF-8 content. Its [3.18 source](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.18/specification.md#header-part) uses the same framing. These sections do not prescribe numeric resource budgets or a malformed-stream resynchronization recipe. The selected budgets, duplicate normalization and transport-failure exit are local support choices. No claim of full protocol validation is added: Content-Type handling remains the existing ignored-header behavior; alternate encodings are not newly implemented.

Actual peer recipe inspected: `editors/vscode/src/client.ts` spawns `can lsp`, computes UTF-8 body length and writes `Content-Length: ...\r\n\r\n` plus the body. The compiler's writer emits that same framing. The actual-process tests invoke Cargo's real `CARGO_BIN_EXE_can`, with 10-second deadlines, concurrent bounded output capture, three-byte input writes and kill/reap guards. Framing-failure tests hold stdin open until process exit, so EOF cannot explain the closure.

## JEV advice and uncertainty

Three independently worded equivalent choice requests and complete responses are saved as `jev-{a,b,c}.{request,response}.json` (jev-1.13.0). All selected 64 KiB headers plus incremental body storage, and all selected equal-only duplicates. Duplicate confidence varies from 0.37 to 0.83; the result is advice, not a compatibility survey.

Lifecycle advice is split and low confidence: a and b select close_failure (confidence 0.32/0.27), c selects close_lifecycle (0.21). In b the displayed probability for either closure is 0.45; c gives 0.41 to lifecycle closure and 0.40 to failure closure. This is not unanimous evidence for exit 1. Investigation compared the actual server exit path and explicit shutdown/exit tests: existing clean/torn EOF uses lifecycle status, while malformed framing previously had no qualified recovery boundary. Both closure choices prevent further interpretation; exit 1 was chosen to expose a failed transport rather than classify it as successful disconnect, including after shutdown. Complete-body parse recovery and clean/torn EOF are preserved and independently exercised. No external evidence establishes unusual clients that rely on malformed framing or conflicting duplicate lengths; their intentional refusal is a compatibility change.

## Validation and limits

`checks.json` and its four logs record the focused reader/process tests, LSP unit tests, strict focused Clippy and source/test formatting. The reader/process, LSP unit and scoped formatting checks pass. The initial strict focused Clippy run is blocked by four needless_borrow warnings in separately owned `compiler/src/codegen/js.rs` at lines 2047, 2048, 2054 and 2055; it reports no framing/test warning before that library failure. The coordinating agent was notified; this worker did not edit JavaScript lowering. The first allocation test mistakenly included the small heap-allocated io::Error in a header-length-only assertion; its corrected independent threshold stays below the minimum body growth block and passes. No production change was made for that observer correction.

The allocation observer measures maximum requested allocation size on the calling test thread, not RSS, allocator overhead, transient realloc copies or the caller's BufRead buffer. Bounded fixtures test an absent 64 MiB declared payload, one acquired byte and a 65,537-byte prefix, without allocating a 64 MiB probe. Fallible header/body allocation is tested by refusing only small specific requests, not exhausting the host. The full 64 MiB complete-body happy path is not materialized; declaration acceptance and exact smaller body boundaries are verified separately. This finite per-frame admission does not add slow-peer deadlines, whole-process memory limits, JSON materialization/session budgets or signal handling.

Checks ran on the current macOS native Rust toolchain. Linux/Windows installed distributions and a live VS Code launch are not qualified by these focused tests; the peer's source recipe and native real stdio server are qualified here. No remaining blocker was found in the owned framing task.
