## Actual producer, semantics, mapper

`cloudflare/src/runtime/stdlib.ts:261` owns `require(condition:unknown,code='forbidden'):void`. Truthy returns; false throws plain `Error(nonempty string code or 'forbidden')`. `hasRole` at 277 accepts `HandlerContext`, a string role, and optional unknown subject. A defined subject throws exactly `unsupported(hasRole-subject): subject-scoped role tests need the L3 membership directory.` An undefined subject uses canonical `builtinRoles` for `public/authenticated/members/owner` when canonical scope exists, otherwise `c.memberships.includes(role)`. Declared roles always use the membership array. Do not export the runtime's unrelated stub `check(c,...args)` as compiler guard `check`.

Direct probe fixtures confirm only these local function semantics: empty local memberships deny, local declared role allows, canonical built-in role allows, injected built-in membership does not override canonical roles, defined subject rejects, truthy guard returns, false guard throws `Error: forbidden`. They do not establish an authenticated context, admission, revalidation, or a scenario receipt.

The real canonical context join is `cloudflare/src/runtime/invoke.ts:2802–2830,2893,3000`: built-in roles derive from actor identity and active live membership; declared role grants derive from the membership reader; `caller.roles` guard revalidates the snapshot. The seam inserts these grants and scope into `createContext`. Preserve this join rather than equating user-supplied fixture arrays with canonical authorization. Existing canonical evidence must be rerun for the actual newly imported generated handler before completion claims.

Technical mapper qualification: `invokeWith` stringifies handler errors (`invoke.ts:404–412`). The canonical scenario seam at 3016–3034 first restores recorded engine failures by exact message; otherwise plain guard errors become `StateError('rule_failed',message)`. Consequently a local `require(false,'forbidden')` throws message `forbidden`, but that alone does not prove a canonical receipt code `forbidden`; genuine admission may deny before the generated redundant handler guard runs. No mapper changes are proposed in this export lease.

## Public routes and dependency closure

`@canlang/cloudflare/runtime/stdlib` is already a supported package export pointing at `dist/runtime/stdlib.{js,d.ts}`. Cloudflare root barrel does not expose the two guards. Its emitted JS loads state transition; HandlerContext/contracts imports are type-only. A root provider re-export would unnecessarily load a Node-side platform barrel; a filesystem/sibling `dist` import would bypass the supported package contract.

However `stdlib/package.json` currently depends only on values and state, and `cloudflare/package.json` already depends on stdlib (not merely for tests: `deploy/bundle.ts:90` imports its distribution). Adding cloudflare to stdlib makes a package cycle. Turbo `build.dependsOn:["^build","build:prepare"]` then has a cyclic task graph even if that runtime subpath's ESM imports happen to be acyclic. An undeclared cloudflare dependency or ad hoc build order is not a complete join.

Existing `state/src/policy/roles.ts:41` is **not** a substitute: its async `hasRole` takes identity/team/reader context, returns Promise<boolean>, resolves subjects, and owns different semantics. Re-exporting it under the emitted synchronous name could turn Promise truthiness into authorization and changes the API.

## Minimal proposed patch lease (requires owner choice, not accepted)

The smallest DAG-preserving behavior-preserving candidate found is a **dedicated state-owned handler guard producer**, keeping its API distinct from existing async policy roles:

- Add `packages/state/src/runtime/guards.ts`: move the exact current guard bodies, preserving error text and role behavior; use an explicitly named structural `HandlerRoleContext` limited to readonly memberships and optional canonical builtinRoles. No import from cloudflare and no duplicate async authority implementation. The subject unsupported branch can throw the exact existing message locally, without moving unrelated stub helpers.
- Add supported `./runtime/guards` JS/types export in `packages/state/package.json`, avoiding the root barrel's `hasRole` collision/ambiguity.
- Change only guard definitions in `packages/cloudflare/src/runtime/stdlib.ts` to `export {require,hasRole} from '@canlang/state/runtime/guards'`, preserving its current public subpath consumers. Leave invoke.ts/context.ts/deploy bundle ownership with root.
- Add `export {require,hasRole} from '@canlang/state/runtime/guards'` in `packages/stdlib/src/index.ts`. Its existing state dependency suffices. Export the named carrier type if the filed producer request explicitly asks for it; do not auto-assemble all provider exports.
- Update exact facade inventory and binding-identity assertions in `packages/stdlib/test/assembly.test.ts`; add focused guard producer tests and actual unmodified compiler-emitted scenario import/execution receipts through supported installed public packages. Do not change `STDLIB_CONTRACT_VERSION=1` without deciding its compatibility meaning; two additive bindings preserve existing callers, while behavior/mapping remain unchanged.
- File an explicit producer request naming only require/hasRole, signatures, supported route, type surface choice, errors, caller/canonical assumptions, and subject gap. Current stdlib contract assembles filed producer requests verbatim; no verified current filed request for these guards was found in the bounded lane-03/lane-07 status inspection. Record the ownership choice and uncertainty separately from accepted implementation decisions.

Alternative is a new lower-level independent runtime package with equivalent guard ownership and re-exports; that adds manifest, workspace/lock, distribution and release inventory work. Direct cloudflare re-export is superficially smaller but does not close the package graph. Removing cloudflare's stdlib dependency is not a narrow alternative because deployed distribution uses it. If ownership placement is difficult, root should consult JEV with these verified alternatives before granting an implementation lease. This research did not select policy or request JEV.
