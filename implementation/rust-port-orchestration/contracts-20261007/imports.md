## Normalized records and edit result

Proposed adapter path `packages/cloudflare/src/deploy/module-imports.ts`, a host-side pure leaf with a synchronous API. This filename/type is a proposal, not an implemented export. Each record identifies original UTF-16 half-open statement, argument/literal and literal-content spans; numeric lexer kind normalized to evaluation-static, reexport, literal-dynamic, import-meta, computed-dynamic or unsupported-phase; group and raw/decoded identity. UTF-16 means string indexes, including two units for non-BMP prefixes and individual lone-surrogate units. Do not convert to UTF-8 bytes or code-point indexes. Every returned span addresses the **original** JS, never edited output. Preserve the original module key and source text without Unicode or path normalization.

For actual string-literal import records use the lexer's decoded n for exact whitelist and relative resolution, including escaped literals and line continuations. Keep raw spans/spelling alongside n for diagnostics evidence. No truthy-n glob admission. import.meta is informational and has no module edge. Admit evaluation-phase static imports, side-effect imports, named/default/namespace/star reexports, and literal dynamic evaluation imports, including dynamic options and preserved attributes. A no-substitution dynamic template is a newly admitted literal only when the lexer reports a fixed n; interpolated templates/concatenations/variables are computed. Source/defer phases are explicitly classified and rejected in artifact modules pending a distinct compiler/platform profile; old regex recognition of their from-clause does not certify their execution semantics.

Artifact imports admit only exact `@canlang/stdlib`, `@canlang/ui` or relative `.`/`..`/`./`/`../` spellings. ## Complete error/order contract

For each module in artifact array order, lex that module fully; a lexical parse fault in that module wins over that module's import-policy faults. An earlier module's policy fault still wins over a later module's syntax fault. This new precedence is explicit; lexer accepts some invalid JS, so passing it is not full syntax/loadability proof.

Within an ordinary successfully lexed module the stable group order is: (1) import-from/reexport records; (2) literal/computed dynamic import records; (3) side-effect records. Within group use ascending original UTF-16 statement/specifier start. Source-only/defer phases are classified in their corresponding group; import.meta produces no validation fault. Previously recognized real forms retain their group ordering. Newly recognized real forms participate in the same groups. False regex matches in strings/comments/regex/template text no longer produce imports or edits; they must be labeled intentional corrected behavior in the differential report.

Let P be `assembleModules` or `deploy bundle`, M the raw module key and S the decoded specifier. Existing complete messages remain:

- `${P}: module ${JSON.stringify(M)} imports ${JSON.stringify(S)} (resolves to ${JSON.stringify(T)}): no such artifact module`
- `${P}: module ${JSON.stringify(M)} has unresolvable import ${JSON.stringify(S)} (only @canlang/stdlib, @canlang/ui, and relative imports are supported)`
- Late deploy link: `deploy bundle: module ${JSON.stringify(M)} has bare import ${JSON.stringify(S)} (no package resolution in workerd)` or `deploy bundle: module ${JSON.stringify(M)} imports ${JSON.stringify(S)} (resolves to ${JSON.stringify(T)}): no such staged module`

Root-acknowledged new-only exact Error.message schemas, with K one of `source-static`, `source-dynamic`, `defer-static`, `defer-dynamic`; offsets are original UTF-16 integers:

- `${P}: module ${JSON.stringify(M)} has invalid import syntax at offset ${O}` (lexer idx; never expose host temp paths/upstream variable messages)
- `${P}: module ${JSON.stringify(M)} has nonliteral dynamic import at offset ${O} (only literal dynamic imports are supported)`
- `${P}: module ${JSON.stringify(M)} has unsupported import kind ${JSON.stringify(K)} at offset ${O} (only evaluation-phase imports are supported)`

Root acknowledged these schemas on 2026-10-07 without target/adoption acceptance. No public error code is newly added. Existing producer-resolution/native TypeError/fs errors and UI producer error remain their current source oracle; normalized parser errors apply only at the newly introduced lexical boundary. Module key/specifier fields use JSON.stringify, including control/lone-surrogate bytes. Loadability legacy error remains `deploy bundle: module ${JSON.stringify(M)} is not workerd-loadable: ${issues[0]}${extra}`; issue collection groups file-URL, require, module.exports, free exports, with raw UTF-16 offsets and ` (+N more)` exactly. No lexer adoption rewrites that legacy guard or masks new host dependency failures.
