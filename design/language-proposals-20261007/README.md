# Can language proposal evaluation

Finish the accepted execution path before adding a broad workflow language. The best small language candidates are exhaustive finite-case handling and dependent form bindings. Approval, resource accounting, cancellation and recovery should first use ordinary typed operations and reusable packages or concrete source templates. Most remaining ideas need evidence from working applications before becoming grammar.

This is a **proposed roadmap**, requested on October 7, 2026. It evaluates all 21 earlier examples; their illustrative syntax is not adopted. [Implementation plans](implementation-plan.md) give phases, owners, dependencies, release conditions and failure checks. The [orchestration plan](orchestration.md) and [packet graph](orchestration.json) turn those into parallel preparation, defining-owner handoffs, bounded implementation and independent qualification. No production implementation or task dispatch follows from this evaluation.

## Evaluation criteria

Each alternative must preserve the same complete app outcome: canonical operation inputs, current permissions, evaluation order, one-owner atomic commits, durable replay, uncertain external effects, files and retention, and compatible upgrades. Compare the whole authored source, including helper models and policies, rather than counting only a shorter example. Token savings, adoption gains and effort below are estimates, not measurements. Small, medium and large refer to relative cross-owner implementation and qualification effort, not dates.

A missing runtime join does not make an accepted design worthless. It changes sequencing. Existing qualification tasks remain their own tasks; this roadmap neither reopens their accepted slices nor marks their broad parents complete.

## Evidence and alternatives

The committed source baseline is [`4e89b117`](baseline.json). Other coding chats are active; foreign working edits are excluded. [Existing dependency records](existing-task-dependencies.json) retain their original historical acceptance scope. Reconcile newer commits and task evidence before implementation. The source excerpts and hashes make this evaluation inspectable without treating a moving checkout as frozen evidence.

The governing constraints are [requirements](../../docs/specification/REQUIREMENTS.md), [grammar](../../docs/specification/GRAMMAR.md), [design](../../docs/specification/DESIGN.md) and [component ownership](../UI-COMPONENTS.md). Concrete witnesses include [ExpenseFlow](../../examples/ExpenseFlow.can), [Generation](../../examples/Generation.can), [CanApprove](../../draft/CanApprove.can), [CanCreative](../../draft/CanCreative.can), [CanWorkbench](../../draft/CanWorkbench.can), and the [chat/media](../complex-apps/chat-media.md), [workbench](../complex-apps/workbench.md) and [sync recovery](../complex-apps/sync.md) designs. Local `draft/` files are ignored by Git and differ from their archived October 4 counterparts. Their [content hashes](draft-intent-hashes.json) and [inspection excerpts](draft-intent-excerpts.md) identify this separate intent evidence; they are not part of the committed implementation baseline. [Independent review and source challenges](review.md) distinguish both stages. Draft apps demonstrate intended workflows, not installed execution acceptance.

At this pin, the Cloudflare stdlib explicitly refuses selected asynchronous effect and receipt entry points. Separate state/work implementations exist. Therefore the task is to trace and qualify the actual generated producer/consumer joins, rather than infer that all async machinery is absent. Generic form lowering also needs to supply the full owning form contract. These limitations make proposals 15, 19, 20 and 21 immediate prerequisites for many richer examples.

Three independently worded JEV choice consultations covered proposals 1–14. They do not reopen already accepted contracts in 15–21. [Raw requests, responses and uncertainty assessment](jev/assessment.md) preserve advice. Decisions differ for 11 of 14 questions, often with low confidence. The roadmap uses concrete source witnesses and bounded release gates instead of counting votes. In particular, match and dependent forms remain candidates subject to a complete before/after app comparison; they are not grammar acceptance.

Reference designs show the costs that a fuller extension would need to address: durable workflow replay retains execution history and resumes recorded progress ([Temporal](https://docs.temporal.io/workflow-execution)); hierarchical/parallel/history states have additional formal transition semantics ([SCXML](https://www.w3.org/TR/scxml/)); browser event streams have connection and reconnection behavior ([HTML standard](https://html.spec.whatwg.org/multipage/server-sent-events.html)). These are reference semantics, not selected dependencies or evidence that Can should copy their APIs.

## Recommended sequence

1. Qualify one real image-generation journey using proposals 15, 19, 20 and 21: create, queue, progress, outputs, failure, stop, uncertain result, reconciliation, retry, and current-authority UI. Reuse the completed flat-machine and polling slices.
2. In parallel with independent runtime work, prepare the enum-only match comparison and dependent-input binding contract. Release each only when its narrow prerequisites and value gate pass.
3. Pilot approval and accounting as concrete ordinary compositions. Finish reviewed invocations and judgments in the applications that require them. No generic package system is a prerequisite.
4. Reuse qualified cohorts and CSV for bulk work. Add a thin authoring surface only if the existing complete interface leaves meaningful repetition.
5. Introduce wizard presentation, named views, calendar helpers, shared flat machines and push only when their stated triggers occur. Keep general awaits, compensation syntax, generic packages and rich statecharts deferred.

The numbering preserves the earlier examples; it is not implementation order. Owners may work on disjoint preparation and test vectors concurrently. Every shared compiler, descriptor, runtime or decision file needs one writer and a released contract; this planning document assigns responsibilities, not active leases.

For task-level deliverables, dependencies, owner roles and completion checks, use [the detailed 63-step sequence](task-sequence.md). Its [structured graph](task-sequence.json) distinguishes preparation, actual qualification, conditional branches and the repeated review/release cycle.

Recommended worker models and reasoning efforts for all 63 detailed tasks appear in [the allocation table](model-allocation.md) and each [task record](task-sequence.json). This remains proposed dispatch guidance.
