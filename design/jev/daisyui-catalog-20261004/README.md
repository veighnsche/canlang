### Full component vocabulary: consultation assessment

The user requests component names that expose the full daisyUI catalog to Can authors. Three independently worded requests compared direct contextual headers, a checked generic component header, and semantic display selectors plus a residual header. Each option retained full coverage and the same canonical data, form/action, settings, navigation and cursor boundaries. Evidence was checked against current repository source and official upstream documentation before dispatch; no classifier was asked to research. #### Disagreement and interpretation

The selected option agrees, but the evidence is sensitive to wording: direct varies from 0.41000000000000003 to 0.75, while generic ranges from 0.06 to 0.32. Request 1 is a near split, with low returned confidence 0.11. It gives substantial weight to unified dispatch and catalog versioning; this remains a concrete benefit even if the authored syntax uses direct names. The later rewrites retain those benefits and the same drawbacks but produce stronger preference for direct names. No request contains additional compatibility or runtime evidence that establishes the spread as a factual disagreement; it remains unresolved classifier uncertainty.

Direct names match the user's stated request and avoid a repeated component introducer. A shared compiler-owned typed inventory can preserve central dispatch and consistency underneath that surface. Neither this engineering inference nor agreement proves parser determinism, concise complete source, preserved bindings or working interactions. Field-placement, action/submit/navigation binding distinctions, scope/slots and generated-default behavior need concrete specification and validation before adoption. The [proposal](../../UI-COMPONENTS.md) records them explicitly, rather than silently authorizing all components as existing APIs.
