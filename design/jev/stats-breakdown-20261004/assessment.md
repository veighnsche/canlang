# Weighted report boundary assessment

The results disagree: request1 favors app_capability .98/.02 with confidence .97; request2 favors shared_analytics .62/.38 with confidence .24; request3 favors app_capability .86/.14 with confidence .71. Complete returned distributions are preserved in the result files. No voting or approval threshold is used.

The disagreement tracks a real tradeoff: making Cloudflare reads a general language service can reduce repeated report contracts, whereas the actual Stats requirement is one bounded business report. Existing typed capabilities already define asynchronous reads, delegated authority and completions. DESIGN's analytics write registry is finite and does not currently promise arbitrary aggregate reads. Inventing an implicit query interface would hide a missing contract; implementing a new query language is unnecessary to express this report.

The draft therefore states DimensionsV1 and its exact provider mapping explicitly, uses existing send/completion/projection primitives, and exposes sampling/coverage/denominators. This is an application-owned business report contract, not a new per-profile manifest or competing CRUD path. A future shared analytics aggregate API remains a reviewable language expansion, not something the current name implies. The provider query and schema mapping are unimplemented and must be tested before deployment; classifier preference is not proof of them.

Source review also found that rolling thirty-day expiry can make the oldest local calendar day partial. The report now rejects a range starting before its retained instant and excludes future-tolerance events from as-of counts. Invalid/mismatched typed completions become visible failed reports instead of leaving the UI pending forever. These corrections came from source reasoning, not the classifier result.
