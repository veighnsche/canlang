# Historical SaaS intake — 2026-10-04

## Decision and scope

Use canonical operations for legitimate current work, and **ordinary locked historical-evidence records inside the existing business owner** for the old facts that those operations cannot truthfully reproduce. No new archive app, raw-write importer, past-authority constructor, fixture-in-production path or language primitive is required. Preserve a controlled readable external archive for unsupported original files or unresolvable evidence; include its continuing access and cost in the replacement decision.

The proposed [Can witness](historical-intake-20261004/witness.can) and [desired JavaScript excerpt](historical-intake-20261004/witness.mjs) describe this bounded path for Expense. They are isolated extracts of the existing `expense` owner, including its existing finance role for standalone readability; they are not a second installed owner/role. No existing app or shared specification was changed. The JavaScript is desired metadata/handler/example output, not a compiler or working import service.

## Verified starting point

MIGRATION task 12 and evaluation R10/L7 require faithful intake of P's 2,000 historical records and 2,000 receipts and W's 20,000 bookings/5,000 invoices with customer/booking linkage. They do not establish actual source export formats or proven provenance. Accounting, identity, payment and other retained systems remain outside the evaluated replacement scope.

Existing Expense CRUD creates a claimant's current draft, with current employee/work-location permission. `decide` requires the assigned distinct current reviewer, submitted state and current workplace eligibility; it records `actor` and `now` and locks the decision snapshot. Running it today is a new approval, not evidence that an absent person approved in 2021. `reimburse` can record an evidenced past payment date, but only for an already approved claim, exact full amount, current finance eligibility and unique reference. It is useful for legitimate current reconciliation, not a bypass for importing a fabricated approval. Runtime `created`, attribution and version metadata are never source import columns.

The same boundary is visible in W: Invoice `issue` stamps current issued time, emits a settlement, sends a notice and schedules overdue work. Rent's trusted quote acceptance checks a verified ingress occurrence, a future interval, current availability and source uniqueness. Replaying these to retain historical issued invoices or past bookings would run new business actions or reject the data. An old CSV row cannot impersonate those verified events. Existing invoice external-payment recording still requires its actual guards and uncertainty resolution; an old “paid” cell cannot settle a live payment attempt.

DESIGN's installed-schema `backfill` maps corresponding records from an exact installed predecessor under fenced maintenance. It cannot populate a foreign SaaS dataset, replace reserved metadata, call business operations/providers or establish foreign historical authority. Test fixtures are similarly isolated test snapshots, never an intake authority.

## Source contract and current authority

The witness adds `LegacyExpense` and a reusable `LegacyClaim` value schema. `source` is a steward-selected stable source tenant/system namespace; `external_id` is the exact source record identifier. The tuple is unique within the existing team owner, including archived rows. Source namespace trims surrounding input whitespace; source IDs preserve case, punctuation and whitespace byte-for-byte after ordinary text decoding, and whitespace-only IDs fail. Do not use display labels, current emails, amount/date or CSV row position as identity. Do not change the namespace on retry to defeat duplicate detection.

`claim` preserves nullable historical actor/reviewer text, original decision-time text, an optional correctly parsed instant, optional source payment date, claimed source status, purpose, optional exact money and receipt or explicit receipt issue. Missing amount is null, never guessed zero; an original negative/refund amount is preserved as evidence rather than subjected to today's positive-expense invariant. Original status is source text, not `Expense.status`; “Paid” does not create `Reimbursement`, settlement, allowance consumption or approval. Historical names are not `user` accounts and confer no role. Ambiguous local times stay in original text with null parsed instant until the source timezone/offset is established; no current timezone is guessed. Missing date/reviewer/account likewise stays missing.

`source_evidence` is a finalized source artifact, kept under current finance/work-location access. It may contain a batch export, so the claimant grant intentionally excludes it, attestation and import attribution. The claimant-readable `claim.receipt` must contain only the intended individual's evidence; attaching a whole multi-person export there would be an incorrect reviewed mapping, not a right conferred by file finalization. The model's immutable fields are locked through all writes. `imported_by=actor` and `imported_at=now` describe the real current intake; they never replace the preserved source assertions.

Only the existing current finance role with `can_work(actor,location)` can retain evidence. A technical steward needs that explicit current business authorization or assists an authorized finance caller; access to deployment, a CSV file, a model ID or the repository is insufficient. Caller/auth/team/role/file checks re-run on every row. No historical role is restored, no old employee account is manufactured, and no provider callback is accepted from spreadsheet contents.

Current claimant disclosure is a separate nullable `claimant:user?` mapping. Initial intake leaves it null. `link_legacy` requires current finance/work-location authority, a reason and a known Employee account tied to that location; existing inactive/archived Employee records can establish a real historical roster identity without asserting current work eligibility. This account lookup is owner-side admission, not a public HR directory. The steward still verifies the source personnel key against that account; equal names or emails are insufficient automatic matches. A missing account remains null and finance-only. Granting or revoking this mapping changes only current disclosure, storing the reason in `access_reason` and ordinary history; it cannot rewrite locked historical names/dates/outcomes. This avoids permanently exposing evidence through an immutable mistaken mapping.

If an immutable source transcription is later disputed, retain it and flag/reconcile the conflict rather than overwrite it or fabricate a new source ID. A justified correction is a separately authorized append-only correction linked to that exact record, retaining its own source evidence/current recorder; it is not an upsert or permission to revise old facts. The bounded witness intentionally implements intake and current-access correction, not a generalized historical correction workflow. Until an owning correction operation is declared, the conflicting row is blocked and the source evidence remains readable to the steward.

## Exact normalized mapping and files

| External material | Normalized destination | Checks and preservation |
| --- | --- | --- |
| Vendor tenant/system identity | `source` | One approved namespace for the same source across CSV batches/retries; recorded in review. |
| Original record key | `external_id` | Exact decoded source key; unique with source; never a human-name lookup or generated Can ID. |
| Original actor/reviewer labels or IDs | `claim.actor`, `claim.reviewer` | Retain source text; no fictitious `user`, privilege or auth email directory. |
| Original decision timestamp | `claim.decision_time_original`, optional `claim.decided_at` | Preserve original spelling; normalize to UTC only with a known offset/timezone and unambiguous source interpretation. |
| Original payment date/status/amount | nullable `claim.paid`, `claim.status`, `claim.amount` | Exact date/source status/currency and integer minor units; no currency conversion, current payment action or inferred certainty. |
| Original receipt bytes | `claim.receipt` | Finalized same-context file reference, exact immutable bytes, supported content/type/size and destination checks. Never the CSV filename/URL itself. |
| Missing/unusable receipt | null receipt + nonempty `claim.receipt_issue` | Explicit incompleteness; source evidence still required. Do not insert a placeholder image claiming to be the original. |
| Source export/document evidence | `source_evidence` | Finalized authorized artifact, finance-only; retain unsupported originals in the controlled source archive and disclose this dependency. |
| Current location | `location` | Explicit authorized canonical Location reference, not a copied display label; it scopes current steward access rather than rewriting source facts. |
| Verified current claimant | separate `link_legacy` input | Existing permitted account mapped by verified source key; missing/ambiguous remains null; revocable independently of immutable facts. |

For each attachment, retain the source namespace/key plus attachment slot identity in the steward's reviewed mapping to the stable upload intent ID and finalized file reference. Use the existing browser/host intent→bytes→finalize flow; `expense.retain_legacy` targets `/claim/receipt` or `/source_evidence` with available canonical arguments/current team/principal. The host selects actual bytes; the model never submits a path or encodes bytes as business input. Repeating the same valid intent returns the same immutable reference. Same bytes uploaded as a different intent do not automatically establish the same source attachment identity or permission.

The CSV panel's ordinary authorized file control supplies the finalized reference after file selection; CSV cells alone cannot provide authority. Each row's document mapping remains reviewable before submission. An upload failure, malformed/oversized/partial file or foreign unreadable reference yields no usable attachment for that slot. Either fix the transfer, exclude/defer the row, or deliberately retain a visibly incomplete historical row with its nonempty receipt issue and valid source evidence. A missing source-evidence artifact blocks this witness's intake entirely. No guessed error-code test is added for malformed fixture setup.

Original unsupported file formats are not relabeled to pass a MIME check. A separately retained readable rendition may help inspection, but does not replace the original bytes/provenance; keep the original in the controlled external archive or explicitly approve an existing supported file policy before transfer. File retention/download/revocation follows the owning record/field; an ID or checksum alone is not attachment authority. The source export's integrity/completeness is a steward-reviewed fact, not something CSV parsing verifies.

## Duplicate, partial and retry behavior

`legacy_matches` is the ordinary current-permission read used by both manual/MCP review and `form retain_legacy import=csv review=legacy_matches`. It returns readable same-source-key candidates; its required inputs are a subset of intake inputs. No hidden upsert occurs. `retain_legacy` independently checks the key and unique constraint at commit. A repeated source key in a fresh operation fails even if values appear equal; a conflicting amount/file/actor cannot overwrite evidence. A concurrent insertion is rejected by owner uniqueness; preview is not a lock. A hidden conflicting record stays a generic safe rejection, not a leaked candidate.

A retry of the **same** admitted row uses its original operation identity and frozen normalized inputs, giving the existing receipt replay/reconciliation behavior. Do not resubmit an uncertain row under a new ID, a changed source namespace or changed attachment. A fresh intentional invocation after changed input must pass a new explicit review. If replay evidence is no longer available, use source-key review and the retained mapping/operation records to reconcile; do not infer that a missing browser result means the row was never stored.

Each row commits separately. Earlier successes survive later denied rows. Store/report row outcomes as succeeded, failed, pending or unknown through the shared import panel; a batch is not complete while rows/files/links remain excluded, failed or unresolved. File finalization alone is not business success; unreferenced files follow ordinary cleanup. Revoking finance/work eligibility after preview prevents subsequent rows; saved preview does not preserve authority. Linking claimant access is a separate versioned canonical invocation after evidence retention, with exact returned Can identity and fresh expected version.

P's 2,000 records require at least two 1,000-row reviews (more if 10 MiB or practical review bounds require it) and explicit mapping of all 2,000 receipt slots, including reported omissions. There is no new “bulk attachment bypass.” A supporting host can orchestrate the existing per-file bridge and canonical row calls; the draft specifies no automatic filename association or parallel batch atomicity. Completion reconciles source key count, retained row count, receipt slot disposition and exact account/access mappings, not merely the number of successful uploads.

## W's linked booking/invoice scope

Apply the same ordinary evidence pattern in the owning Rent and Invoice packages rather than issuing old invoices or replaying quote acceptance. The source relationship key is `(source,entity_kind,external_id)`, with kind fixed by each typed model. Preserve an invoice's original booking/customer source keys even when no current match exists. The source record remains evidence of the vendor's assertion, not a live payment/booking entitlement.

Use explicit typed archived-evidence relationships, e.g. `LegacyInvoice.booking:LegacyBooking?`, alongside immutable original `booking_source:text?` and `booking_external_id:text?`. A verified link requires the same source tuple and matching original key; a missing booking remains null with a recorded unresolved-link reason, never a new empty Booking. Import/read booking evidence before resolving invoice references, and use returned real IDs through authorized controls. Multiple-invoice/booking relationships require the source's actual cardinality; do not flatten multiple links into an arbitrary first match. A separate ordinary link record can preserve each evidenced edge when many-to-many is required. Do not guess cardinality absent source data.

Current Customer and resource/location mappings similarly use authorized existing owner reads and explicit reviewed references. Preserve original customer/resource identifiers as immutable text; historical customer names are not automatic duplicate Customer creations. A missing current customer remains unresolved/staff-readable until an owning authorized mapping operation records the verified match. Updating a current access/reference mapping must retain the original source keys and audit reason, as in the claimant witness; a mapping must not rewrite billed-party evidence. Customer billing/member permissions and current location staff scope govern any later portal disclosure; historic presence alone grants none.

At least twenty booking reviews and five invoice reviews are needed for the stated 25,000 records at the 1,000-row maximum, before size/exclusions/reference-resolution work. Reconcile every original booking↔invoice edge and source/customer mapping explicitly. An old pending/uncertain payment remains an original claim and a reconciliation task in its actual payment owner/provider; importing it cannot schedule collection, claim paid, replay a settlement or release current capacity. A future outstanding obligation needs a separately justified owning business intake, which this immutable archive does not supply. Do not claim full W subscription exit until those outstanding workflows, required history links, source file access and customer continuity are actually resolved.

## Witness evidence and remaining limits

The Can file supplies three canonical operations with 13 authored table rows: retain evidence (success, missing receipt, duplicate, invalid missing-receipt explanation, unauthorized caller), review (allowed/denied), and current claimant mapping (grant/revoke, unknown account, missing reason, stale version, unauthorized caller). The invalid receipt-explanation case changes an ordinary typed operation input and fails the stored invariant during invocation; it is not an invalid initial fixture. Fixture metadata uses current self/default attribution; the historical 2021 values are explicit stored source assertions. All original files in recipes use the standard finalized test fixture, not arbitrary file literals.

The mapping revoke row is an isolated operation on a stored fixture, not a genuine grant-then-revoke journey or proof of serialized privacy. Runtime acceptance still needs actual same-state linking/revocation, file upload/finalization failure, current field-filtered downloads, 2,000/25,000-row reconciliation, concurrency and interrupted retry tests. The current prototype parser rejects the already-specified CSV form attributes; a temporary projection removing only `import=csv review=legacy_matches` parses. The desired JavaScript passes `node --check`. Neither establishes typechecking, module linkage, executing operations, a working CSV/files UI or preservation of real source data.

The witness deliberately adds no shared syntax/API extension. Exact external schemas/export rights/source evidence, unavailable original files, ambiguous actor/customer matches, source relationship cardinality and outstanding live obligations cannot be established from these repository drafts; they remain explicit dataset/reconciliation inputs, not guessed history. The contract is implementable with existing declared primitives, while actual importer/host/runtime behavior and company effort remain unmeasured. No production files, parser/library/infrastructure, stage or commit were changed.


## Actual Expense application

The accepted pattern now appears in the authoritative [Expense source](../draft/CanExpense.can), [requirements](../draft/CanExpense.md) and [desired target](../draft/CanExpense.mjs). The standalone witness remains an isolated proposal specimen, not a second owner to install or a separately maintained schema authority. The application reuses its own finance role, Employee/location identities, canonical file controls and inline-example machinery.

One deliberate refinement is that actual `legacy_matches` is an authenticated **ordinary viewer** lookup constrained by exact source key/location, reused by intake CSV review and the historical lookup UI. Its returned rows are policy-filtered. This permits a real claimant-call result to establish readable-row presence, and an empty result after revocation, instead of using test-inspection access as evidence of privacy. The finance-only source artifact is excluded from the claimant field grant; serialized omission and download denial remain required unexecuted runtime checks. No privileged read is introduced.

The actual connected sequence uses distinct finance/claimant accounts and finance-owned unattached finalized-file recipes, avoiding illegal attachment setup under another fixture principal. Fourteen canonical calls perform retain, grant/read, stale rejection, revoke/read-empty, corrected grant/read, fresh-operation duplicate rejection, HR eligibility loss and subsequent rejection. Role fixtures stay fixed: the real HR change is not mislabeled as actual team-role revocation. Existing claim/reimbursement/person-choice journeys remain preserved. Fourteen new isolated rows cover valid stored snapshots and ordinary invocation failures. The actual source/target and checks supersede the isolated specimen where they differ; no library, parser, runtime or provider was implemented.

Root correspondence correction: the bounded examples/do contract does not author replay identities. The actual sequence therefore uses one ordinary retain call, reuses a typed historical claim at the later fresh duplicate call, and explicitly narrows all nullable lookups. Receipt replay remains required runtime acceptance, not an unsupported claimed inline witness.
