## Accepted Given forms

| Form | Meaning | Ownership and reuse |
| --- | --- | --- |
| Named trait prompt | Reusable generated behavior attached to a model or field | A named trait definition owns its saved implementation; compatible model/field applications reuse it without AI |
| Inline trait prompt | One-off anonymous generated behavior attached directly to a model or field | The attachment owns an internal source/output association; no authored trait name is required |
| Named custom Given keyword prompt | Defines a new standalone Given declaration with its own target, arguments and implicit semantics, at the same declaration level as built-in policy/unique/invariant/lock | A required semantic name identifies the declaration form; compatible standalone applications reuse the named definition without prompts or AI |
| Inline keyword prompt | Excluded | Do not accept an anonymous keyword definition or a generation prompt on a keyword application |

A trait application on a model/field is not a standalone custom keyword declaration. Naming a trait makes it reusable; it does not turn it into the general keyword mechanism. Named/inline trait forms remain supported independently, including checked contributions; a trait-only example cannot close the novel standalone keyword criterion. The frozen contract specifies a named keyword signature and standalone named-attribute application, compile-time reference kinds and owner-versioned typed producer bindings. Earlier chat examples do not establish independent syntax; use the frozen v1 forms. Future owner kinds/producers need explicit integration rather than self-registration or a trait-only substitute. All supported prompt definitions retain the static `$"..."` marker and common MCP/saved-code lifecycle.

## Retry scope and selected job grouping

The human revokes selective retry and preserving preferred styles during regeneration. Manual retry captures the current source/recipes and regenerates every prompt in the active app/build closure, including successful outputs. It needs no per-prompt names/IDs. Unrelated apps and ordinary authored business code are outside that generation scope; working outputs/direct edits stay active until candidate acceptance, and reset/cancel preserve them. Internal associations remain useful for binding, validation and direct edits, not as required retry selectors.

The former runner design was unit-centered. The frozen v1 contract now gives each frontend job the whole active app's Then context, all style/view prompts and checked contracts, grouped by compatible effective recipe. Given contributions precede frontend consumers. Differing explicit recipes may require several jobs; one job can make many internal model/tool calls. Full retry collects all required outputs into one validated acceptance set and one coordinated run journal; incomplete/failed work preserves all current groups. Do not implement a process per prompt or independent partial retry promotion merely because records are unit-shaped.

## Accepted MCP output boundary

The build-time coding agent must submit generated CSS, JavaScript, contribution code and other admitted outputs through a custom Can generation MCP server. The server supplies checked context and permitted logical output targets; the agent submits content for those targets instead of choosing filesystem paths. The host resolves placement, checks target/role/content, writes isolated candidates and records associations/provenance. Submission does not accept a candidate or change working saved code. A job can submit several outputs; an MCP call does not establish a model-call or per-prompt job boundary, and D6 still owns aggregate grouping/promotion.

Enforce the boundary through each adapter's restricted tools and filesystem permissions: the captured project is read-only to the generator, and current/candidate output roots are writable only by the host. Generic file-write tools or shell access capable of bypassing that boundary must be unavailable. MCP alone is not filesystem isolation. Diagnose unsupported MCP attachment or write restrictions before launching, without a direct-file fallback. Native CLI session/cache housekeeping must be isolated from protected app outputs. This applies to build-time generators; the authoring agent's normal source editing and lease-coordinated direct refinement remain supported. The frozen MCP context/batch-submission interface is private tooling, not new source syntax; each adapter still needs actual supported transport and write-enforcement qualification.

## Ownership and handoffs

- **Rust compiler:** source grammar, structural unit discovery, conservative association evidence, checked contributions/interfaces, saved-input intake, CSS parsing/scoping, emitted wrappers/artifacts and source maps. Existing `NodeKey` is not persisted identity.
- **Existing Node tooling host:** `@canlang/cloudflare` owns local configuration, coding CLI processes, the custom generation MCP server/session, structured generation operations, IDs/records, candidates, write leases, journals and target preparation. `can gen` is a thin Rust CLI delegation through the existing platform host. Host the server in private generation tooling with a bounded run/session lifecycle; no new package or persistent daemon is required.
- **Runtime packages:** Values owns exact representations/codecs; State owns admission, staged effects, commit and replay; Interfaces owns transport/form admission and projection; UI owns semantic markup, canonical controls and browser lifecycle. Cloudflare joins saved modules to these owners and workerd/browser packaging.

Proposed new private modules may live under `compiler/src/generation/`, beside compiler codegen for CSS, and `packages/cloudflare/src/generation/`. These are placement targets, not pre-created files. Keep local filesystem/process code out of worker modules. Existing source-capture helpers cover a limited first profile; they do not already provide the complete source/output closure, leases or promotion protocol.

Required handoffs are concrete data, not completion of another owner's whole lane:

1. Structural declaration descriptors: owner/kind/label, static prompt/profile, source location/revision, normalized non-prompt anchor, target and declared contracts, including separate named/inline model/field trait descriptors, named standalone custom Given keyword definition/application contracts, and named style definition/use ownership and root/part contracts. No descriptor represents an inline keyword prompt. Discovery must work before a keyword implementation/contribution exists, rather than assuming a fixed built-in target list. The frozen signature/target contract defines this producer handoff; do not substitute runtime rows for compile-time references.
2. Associated unit records and a coordinated immutable snapshot of the relevant source/imports/contributions/current code/assets/target inputs.
3. Checked ABI-v1 export, exact-value, effect/control and use descriptors; one canonical schema/registry, without a second authored manifest. The keyword extension contract must admit generated new implicit behavior instead of imposing the existing default/check/model-field role set as its ceiling; D4 owns the concrete typed/lifecycle/read/dependency/effect handoff.
4. A selected candidate plus captured inputs/current bytes/recipe/fence, applicable target-validation result and conditional promotion outcome.
5. A host-bound MCP session for the captured attempt, with checked context, permitted logical output targets and validated content submissions. The server owns physical paths and candidate metadata; runners consume this common output handoff.
