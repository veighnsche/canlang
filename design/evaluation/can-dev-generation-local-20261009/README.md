# Generation local development feasibility — 2026-10-09

**Status:** observed feasibility check, not an accepted first runtime profile. No product implementation was changed.

## App and check boundary

Choose [`examples/Generation.can`](../../../examples/Generation.can) as the single-source probe. It owns one `/` page, one `Job` model with a state machine, member-only reads and mutations, a `job` fixture, and three `queue` example rows (member success, invalid transition, public refusal). Its source says provider delivery remains application work, so this probe needs no external generation provider. TeamTasks has a more realistic task flow but its compiled UI currently has `E6008` failures; compiled Shop has working D1 CRUD but no page or examples; the CanDo example pilot uses a patched source and has no served browser page. These are candidate inventory facts, not equivalent same-app checks.

## Decision for later planning

Keep Generation as the **feasibility witness**, with a narrow current claim: compiled anonymous page and released browser assets work over loopback when a test bridge and `DB` are supplied. Do not promise a complete preview/resource/example loop for this app yet. The missing joins are an HTTP listener in the development command, generated Worker auth/identity, a working compiled-artifact test boot, fixture-aware emitted example closures, per-row `members`/`public` caller execution, and row-isolated local data. Investigate the direct D1 inspection stall if the eventual development server needs that API. Recheck signed-in page state, a canonical mutation, business MCP authorization, and all three isolated rows after those relevant changes.
