# Variant D assumptions and unsupported outcomes

- Company P is one company with departments A/B/C. A current active membership is required for every request/read/export/intake/tool. Membership changes are controlled by the operator, outside staff workflows. Request department is the owner's current department at creation and remains an evidence snapshot on transfer; new intake rows use membership at commit. Owners keep access to their older requests; current department managers see nonprivate requests assigned to their department.
- “Owner-only private request access” is interpreted as an explicit private checkbox. Ordinary nonprivate requests are owner-visible plus current department-manager-readable. Other employees cannot see them. Private defaults false, is prominently described, and suppresses manager access. The brief does not specify whether all requests should default private or whether managers should see every request; this choice requires business confirmation. Managers cannot mutate others' claims. Finance/operation reviewers gain no extra scope. There are no purchasing/approval/provider workflows.
- Open is the only unresolved state. Archived requests cannot reopen/edit; archive preserves the row and prior snapshots with actor/time attribution. Version mismatches yield conflict before state checks. No deletion UI or API. Initial archive has no reason because the later-change request adds that rule separately.
- Title trims and is 1–160 characters; note is optional <=4000 characters. Browser and MCP mutation validate through the same ModelForm-backed service. Owner/department/state are server-owned; submitted escalation fields are rejected by service (browser form omits them).
- CSV intake creates requests only, never updates unrelated records; header is exactly title,note,private, UTF-8, <=1 MB/500 rows. Export is a scoped evidence report including ids/version/state, not an intake round-trip format. Duplicate means exact normalized title/note/private within this owner's existing requests (including archived) or selected rows in this batch. No query against others' hidden data detects duplicates. Excluded prior rows do not block subsequent identical selected rows. Normal interactive create permits duplicates: deduplication is an intake precaution, not a global uniqueness business rule.
- Corrections/exclusions must be saved and previewed before a separate explicit commit. Commit creates selected ready rows and returns created/duplicate/invalid/excluded/failed individually. Versioned server-owned intake prevents double commit; the draft has no idempotency key for separate interactive create calls. Valid rows and outcomes commit together; catastrophic transaction/database failure may roll back the whole intake and is not falsely reported as a row success.
- Application deployment/operator has trusted access to DB and signing secrets; these are outside employee authority. Normal Django user is reused with normalized full email stored in username, max150. No self-service registration or password reset/email provider is introduced; operator can use Django changepassword.
- Authorized MCP means official SDK stdio and a token provisioned by authenticated browser POST. Token is treated as a bearer secret and expires after 8h. It rechecks user/password hash/current membership on each tool. No user id is accepted as a tool principal. Chat-client selection, protected credential-entry UI and subprocess placement are missing information; the necessary documented stdio/environment wiring is supplied, but a turnkey staff chatbot and OAuth connection flow are unsupported. Browser logout does not itself revoke the independent chat grant.
- PostgreSQL is required for production row-lock/version concurrency semantics; no DB provisioning supplied. Ordinary sequential tests use SQLite only. Requests/Evidence/Intake are not exposed in unconstrained Django admin. Current reads re-evaluate scope; concurrent permission edits during an already-running read follow request-start authorization and are not an immediate cancel guarantee.
- Scale is small enough to list 500 records without pagination. Semantic HTML, labels, alert/status outcomes, a keyboard-focusable scroll table and narrow-screen CSS are supplied. Browser rendering, screen reader behavior, SDK runtime, actual tests, deployment, schema generation/migration and concurrent lock behavior remain unverified.
