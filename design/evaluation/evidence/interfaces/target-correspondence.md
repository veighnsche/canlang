## C-I01 — Money constructor/arithmetic drift (significant target defect)

DESIGN:208,220,250 defines exact checked money arithmetic and `money(value:int|decimal,currency)` in **currency units**; :846 requires one canonical helper per operation. CanRent.can:200 has `discount<=subtotal+tax`; :722 and :738 compute snapshot line totals using money multiplication/addition/subtraction; :748 derives subtotal/tax/discount sums as money. The MJS partially uses `addMoney`/`subtractMoney` but also uses raw minor-unit arithmetic/comparison:

- CanRent.mjs:3310 lowers the source **money-valued** `discount<=subtotal+tax` using an unchecked minor-unit sum; :3313 lowers a money comparison to minors. Review these against the required currency/overflow semantics and already-dominating checks.
- Rent.mjs:5605–5611 and :5722–5728 add/subtract minor-unit BigInts into `total`, then call `money(total,resource.currency)`.
- Rent.mjs:5753–5759 accumulates `subtotalMinor`, `taxMinor`, `discountMinor`; :5794–5796 passes these to the same `money(...)` helper used for EUR25 amount-unit literals in Expense.mjs:695.

An undeclared minor-unit overload would make the same helper ambiguous. Static output conflicts with the canonical constructor meaning; raw sums also bypass the specified checked-money operations. This is **not** a claim of an executed 100× error or an observed overflow. There is no running library to resolve or measure it. Root's independent check narrows the scope: source-authored integer projections such as CanExpense.can:19 `row.amount.minor>0` correctly correspond to Expense.mjs:321 `row.amount.minor > 0n`; similar sign tests are not money-lowering defects merely because they access `.minor`. Audit the actual typed source expression rather than banning every minor-unit access.

Smallest remedy: correct the affected desired-target pattern using canonical typed money sum/add/subtract/compare with declared currency/overflow/rounding behavior, then audit equivalent constructs across all 21 targets. A genuinely distinct internal minor constructor would require an explicit typed contract and consistent use; reinterpreting `money` according to variable name is not acceptable. No new Can syntax or broad app rewrite is needed. Benefit: one reviewable scalar meaning and preserved quote/booking/invoice amounts. Tradeoff: slightly more helper calls/target text; optimization belongs behind a verified shared contract. Reevaluate static mapping for EUR25, currency mismatch, zero, quantity rounding, checked intermediate/aggregate overflow and refund bounds against the same source; later runtime property/BDD checks remain future verification.

## Navigation and file-transfer clarification, not a runtime rejection

DESIGN:557–559,585 derives authorized shell links from pages. Expense.mjs:277–281 records `{path,render}`, while title/description/guards are inside page render functions (:450 onward); Mail follows the same pattern. Desired output should clarify how shared shell discovery obtains safe title/order/eligibility without executing unrelated business reads. A compiler-derived descriptor is compatible with the single authored page registry; this is a bounded output clarification, not proof that the future renderer cannot work.

MCP file inputs carry finalized opaque references under the same grants, not arbitrary local file paths (DESIGN §§8,10). A host therefore needs an authorized runtime upload/finalization handoff or an existing browser-uploaded reference for J2. The business operation cannot bypass MIME/size/current download rights. A file parameter alone is not a file-transfer implementation; pure-chat attachment convenience and latency remain unverified. Clarify this host/runtime boundary in generated interface documentation, without exposing deployment or arbitrary upload authority as app business tools.
